# 例外処理の簡素化と停止境界の修復

## 目的と適用範囲

安全に続行できる条件を明示し、条件外の失敗をアプリの終了へ接続する。停止・確定状態・資源寿命に必要な処理を保ち、診断やUIへの詳細輸送だけの複雑性を減らす。アプリ本体、同梱の解析・音声処理、更新プログラムとの連携を対象とする。

採用済みの契約と完了条件の正本は[例外・操作結果・診断](../spec/core/exception-handling.md)とする。本計画はその適合確認と不足の修正を扱い、既存の全機能が移行済みとはしない。文書の整理や機能ごとの修正が済んでも、続行条件と終了までの接続が未確認なら本計画を完了にしない。

## 現状と不足

入力不良の対象内への局所化、確定済み変更の受渡し、任意通知と必須処理の分離、開始済みTaskと資源の寿命管理は、既存実装を起点にする。既に契約を満たす箇所を再実装しない。

一方、操作入口や背景仕事が例外を通知・記録して終わることと、アプリを安全に続行できることは別である。Taskの失敗の観測や上位への再送出だけでは、共通の終了判断へ接続できたことにもならない。これらの接続と、失敗時にも通常終了の保存・更新・再起動を進めてよいかは、適合確認が残る。

以下は未完了の確認・実装項目であり、各箇所に必ず不具合があるという一覧ではない。実入口、捕捉後の結果利用、確定状態、後片付け、終了への経路を読んで判断する。

## 採用する進め方

契約は[仕様の判断単位](../spec/core/exception-handling.md#判断の単位)を使う。例外型だけの共通許可一覧や、未知の失敗から部分復旧する仕組みを新設しない。続行する既存境界について、処理・想定失敗・失敗後の状態から根拠を示す。

現在のツリーを起点に、失敗を受け止めて続行する境界と終了を所有する境界を確認する。過去の実装順を辿り直して診断表現の改善を探す作業にはしない。必要な修正は実装単位へまとめ、診断輸送専用のリスト・包装・転送を利用先とともに減らす。既存の確定結果や実際の停止判断に使う値は削らない。

正常入力の扱いや続行許可について製品仕様だけでは決められない場合は、対象・現行動作・変更後の影響を質問として示す。回答が必要な挙動を推測で変更しない。譜面解析失敗記録の自動再評価は対象外として確定し、既存の版・時間上限等による再評価条件と明示削除を維持する。

## 作業範囲と順序

### 1. 続行条件と終了の所有者を確定する

画面操作と背景仕事の入口から、捕捉・結果の採用・次の操作の許可までを確認する。続行条件、確定済み変更、開始済み処理の所有者、条件外の失敗を届ける終了先を対応付ける。機能が任意、ログ済み、通知済み、Taskが完了したという事実だけでは続行を許可しない。

| 確認する境界 | 主な確認先 | 判断すること |
| --- | --- | --- |
| 入力と対象スキップ | `ChartInfoBuildService`、`BmsonJsonParser`、`BMSTable`、`PlaylistExternalSyncOwner`、IR応答、更新マニフェスト | 既知の入力不良だけを狭い入口で分類し、保存・必要公開・内部故障へ同じ分類を広げない。正常対象との混在を維持する。 |
| 操作入口・任意の背景仕事 | `MainWindow`、設定・補助画面、`StartupBackgroundTaskSchedulerOwner`、URL取得・URL補完 | 通知・記録の後に続行する根拠があるか。条件外の失敗が所有者から終了判断へ届くか。 |
| 保存・確定後の反映 | プレイリスト保存・BMT出力、PlayHistory、設定、ライブラリ変更、DB・LR2 | 保存済み・未反映・未処理を取り違えず、安全な復元・隔離が成立しない場合に続行しないか。 |
| 補償・解放・処理寿命 | 一時入力、音声・先読み、導入、バックアップ、更新、並行走査 | 必要な回収を一件の失敗で放棄せず、重要な回収不能を通常失敗や取消しで隠さないか。 |
| 終了 | `App.ExitAfterUnhandledException`、`ShellShutdownWorkflowOwner`、各終了協調処理 | 受付停止・待機・補償と最終終了を誰が所有し、不確かな状態からの追加保存・更新・再起動をどう止めるか。 |

`catch` の件数や例外型名だけを監査単位にせず、結果を使って続行・停止する呼出元まで追う。全例外を救済するための型一覧は作らない。

### 2. 管理された終了への接続を整える

通常終了の所有者を起点に、致命的な扱いに入った場合の受付停止、所有処理への停止要求、開始済み処理の実終端、必要な補償・解放を接続する。不確かなメモリ状態の保存や更新・再起動の実行は、通常終了から無条件に流用しない。

終了を要求した処理自身を終了側が待って循環しないよう、要求と完了待機の所有関係を確認する。通常利用を再開しないことと、プロセスを即時強制終了することを混同しない。現行の最終例外経路へ投げ直しただけで安全な終端が完成したことにせず、診断・非常用案内に失敗しても終了判断を維持する。

既存の終了契約で管理された終了ができる範囲と、プロセス状態の破損等で最終終了しか行えない範囲を分ける。全復元や強制終了時の全回収を保証する新しい仕組みは追加しない。終了経路の接続を整えずに、全入口の広い捕捉を一括削除しない。

### 3. 境界ごとの不足を修正する

続行条件のない失敗を空結果・解析不能・正常取消し・通知済み成功へ変換する経路を修正する。既知の入力不良は対象内へ閉じ、依存APIの入力由来の失敗を複数層で再分類しない。従来受理した入力を新しい形式検査だけで拒否しない。

必要な参照・索引更新、開始済みTaskの待機、重要な補償・解放は残す。業務状態を変更しない診断・事後案内だけを狭い境界で局所化し、その失敗を上位へまとめ直す処理を減らす。全原因の詳細を保持する代わりに、続行可否を変える事実が確実に届くことを確認する。

### 4. 結果表示・診断・既存テストをそろえる

一般の通知は簡潔にし、保存済み・未保存、成功・未完了、続行・終了を取り違えない。元例外一式をUIへ運ばず、通常のログ環境で代表原因と必要な対象を調査できるようにする。ログ出力や表示が失敗したときの代替保存・再通知・再試行は増やさない。

テストは[仕様の完了条件](../spec/core/exception-handling.md#実装レビュー検証)に対応する実結果を確認する。通知コールバック内の表明が本体に捕捉される構造は、呼出し記録を処理後に検証する形へ直す。診断の細部を追わない方針を理由に、安全性や成功・失敗を確認する表明を弱めない。

| 保証 | 主な確認先と条件 |
| --- | --- |
| 入力と停止範囲の互換性 | 譜面解析・外部表・入力取得の既存テストで、従来受理する入力、不正入力と正常対象の混在、内部故障の差を確認する。旧失敗記録の強制再評価は追加しない。 |
| 条件外の失敗からの終了 | 画面入口・背景仕事・終了所有者のテストで、未知の失敗後の受付停止、開始済み処理の終端、危険な保存・更新・再起動を始めないことを確認する。最終プロセス終了だけを代替し、判断・待機自体は通す。 |
| 確定結果と後片付け | 保存・導入・DB・音声・更新の既存テストで、実ファイル、確定済みDB、所有対象、未完了の後続処理、主処理と重要な回収の重複失敗を観測する。 |
| 診断・通知の非干渉 | 診断・事後通知の境界で、通知先の失敗が元結果や終了を変えない代表例を確認する。各機能で全組合せを重複させない。 |
| 最低限の表示と診断 | 実入口からの保存・未完了・終了の案内と、通常のログ先への代表原因の受渡しを確認する。全原因数・入れ子・全表示文言の完全一致を追加しない。 |

### 5. 完了条件で適合を判定する

[仕様の五つの完了条件](../spec/core/exception-handling.md#実装レビュー検証)を基準とする。指摘には違反する条件、本番の入口と到達経路、誤った続行・停止、状態や処理寿命への影響、または最低限の表示・診断の欠落を示す。

診断の情報量、全原因の保存、文言・スタック・重複の完全性だけを理由に修正必須へ広げない。一方、続行条件や終了の接続が未確認なら、その境界を未完了として残す。必要な修正と確認が済んだ項目は計画から除き、仕様の適用状態と実装・テスト対応を更新する。全条件を満たした時点で本計画と目次の参照を削除する。

## 対象外

全メソッドの汎用Result化、アプリ共通の例外重要度フレームワーク、未知の失敗からの新しい部分復旧状態、全件の事前入力検査、全例外の収集・UI表示、通知済み台帳、診断の永続的な履歴、自動再試行・自動再実行は追加しない。

譜面解析失敗記録の自動救済や一括無効化、一般通知の表示成功、ログ書込み成功、全二次原因の完全保存も対象外とする。診断の改善余地が残ることだけで、安全性の適正化を未完了にはしない。
