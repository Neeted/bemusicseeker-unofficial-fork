# 一覧の描画をDirect2Dへ置き換える計画

## 目的

一覧（`CustomTableView`）の縦横スクロール、つまみのドラッグ、キーボードによる選択移動で、表示が入力に遅れて追従する問題を解消します。通常のスクロールとキー移動に加え、可視行がすべて入れ替わる操作（つまみのドラッグ、ページ送り、並べ替え・絞込みの直後）も対象にします。

現行の契約は[一覧の描画・操作・仮想化](../spec/ui/table-view.md)と[外観](../spec/ui/appearance.md)が正本です。本計画は未実装であり、完了するまで現行仕様を変更しません。

## 現状と不足

`CustomTableSurface` は、スクロール・選択・現在セルの変更のたびに `OnRender` で表示面全体を描き直します。確認した構造上の要因は次のとおりです。

- 文字キャッシュが保持する `FormattedText` は整形済みの行を持たず、描画のたびに行整形と省略処理をやり直します。新しいセルは、高さの取得と描画で二回整形します。
- 横位置をセルの座標に含めるため、横スクロールの一段ごとに全行のセル描画を破棄して作り直します。
- 文字キャッシュのキーに幅・色・配置を含むため、列幅の変更や選択色への切替でも整形からやり直します。
- 縦スクロールのたびに保持範囲の行参照を集め直し、再描画の要求のたびにUI Automationの通知処理へ進みます。
- 選択モデルは添字の集合で、範囲選択の一歩ごとに範囲全体を作り直します。選択の通知は全選択行を列挙して配列にします。
- ホイールは回転量によらず一通知で三行動かします。

### 方式を選んだ根拠

2026-11-15 に、製品コードとは別の使い捨てのプログラムで一回ずつ測った値です。条件は Meiryo UI 11 DIP、GeForce GTX 1080 Ti、3840×2160、表示倍率100%、.NET SDK 10.0.404 です。現在の実装や置換後の性能を保証する値ではなく、方式の比較にだけ使います。

文字列一件あたりの整形の所要時間（マイクロ秒）は次のとおりです。

| 処理 | 平均27文字 | 平均6文字 |
| --- | ---: | ---: |
| 現行の方式で新しいセルを作る | 680 | 91 |
| 現行の方式でキャッシュ済みの文字を描き直す | 326 | 51 |
| WPFの `TextFormatter` で一度だけ整形し、グリフ列を保持する | 72 | 38 |
| DirectWriteのGDI互換のテキストレイアウトを作る | 48 | 27 |

- 整形を八スレッドへ分けても、WPF・DirectWriteとも約2.2倍の短縮に留まりました。
- 文字コード表の字形と送り幅だけで並べる方法は一件1〜2マイクロ秒ですが、通常のレイアウトと幅が一致したのは約半数でした。

WPFで行ごとの `DrawingVisual` を保持し、整形済みのグリフ列だけを描く構成の画面更新は次のとおりです（最大化、4,578セル、毎秒の更新回数）。

| 構成 | 行の位置だけを動かす | 三行だけ入れ替える | 全セルを入れ替える |
| --- | ---: | ---: | ---: |
| セルごとにクリップする | 3.4 | 3.9 | 2.7 |
| クリップしない | 7.8 | 11.4 | 5.3 |
| 行を `BitmapCache` で保持する | 59.7 | 26.7 | 3.2 |

全セルの入替えでも、UIスレッドの所要時間は一回約11ミリ秒でした。残りはWPFの描画スレッドが文字を描く時間で、セル数にほぼ比例します（765セルでは、位置だけを動かす場合で毎秒22回）。WPFのままでは、行のビットマップ保持で通常のスクロールは改善できますが、全行の入替えは描画スレッドが上限を決めます。

## 採用する方針

一覧の表示面をDirect2DとDirectWriteで描き、`D3DImage` でWPFへ合成します。利用者と合意した前提は次のとおりです。

| 事項 | 合意内容 |
| --- | --- |
| GPUが使えない環境 | 同じ描画処理をCPU側のビットマップへ描いて表示する代替経路を用意し、一覧の表示を保つ。 |
| 相互運用 | Vortice.Windows のNuGetパッケージを使う。 |
| 文字の見た目 | 行の高さ・基線・省略・代替フォントの規則は現行仕様を保つ。字形の描かれ方の画素単位の差は許容する。 |
| 行の高さと列境界 | 物理画素へ丸める。表示倍率によって一画素未満の差が出ることを許容する。 |
| ホイールの移動量 | 回転量に比例させる。現在の一通知三行から変わることを許容する。 |

### 構成

- **描画**: Direct3D 11のテクスチャを対象に、Direct2Dで表示面全体を描きます。変更があったフレームだけ描き、停止中に回り続ける描画は設けません。行やセルの描画結果は保持せず、保持するのは行の表示値と文字のレイアウトだけにします。横位置・選択・現在セルの変更は、描き直すだけで反映します。
- **合成**: Direct3D 9Exと共有した面を `D3DImage` へ渡し、WPFは一枚の画像として合成します。専用のウィンドウ（`HwndHost`）は使いません。表の前面に重ねるスクロールバー、セルの編集欄、ドラッグ中の表示が隠れるためです。
- **WPFに残す部分**: スクロールバー、セルの編集欄と候補、ツールチップ、ドラッグ表示、当たり判定、選択、列の幅・順序の操作、UI Automation、行の実体化。座標計算は描画と共通の列配置を参照します。
- **文字**: 通常の文字はDirectWriteのGDI互換の方式（WPFの `TextFormattingMode.Display` に相当）、スコア用の文字は通常の方式で整形します。レイアウトは文字列と書体をキーに保持し、色と位置は描画時に与えます。省略記号が必要なセルだけ、幅を含めたレイアウトを追加で持ちます。字形を独自に並べる簡易な方法は採りません。
- **フォント**: 選択されたフォントを第一候補、既定のフォントを代替候補とする規則と、固定の行の高さ・基線（[表示フォント](../spec/ui/appearance.md#表示フォント)）をDirectWrite側で再現します。Sovjet Box はアプリのリソースから読み込みます。
- **資源の復旧**: デバイスの消失と前面バッファーの利用不可を検出し、描画資源を作り直して表示を復旧します。共有面を作れない環境と復旧できない場合は、CPU側の経路へ切り替えます。
- **入力と状態**: 入力は位置と選択だけを更新し、行の購読範囲の更新・UI Automationの通知・描画は画面更新の単位でまとめます。ホイールは回転量を累積して行数へ換算します。
- **選択**: 選択集合を区間で保持し、通知のために全選択行を実体化・配列化しません。対象行が必要な操作（コピー、ドラッグ、一括操作、UI Automationの照会）の境界で列挙します。

現行の行単位の描画キャッシュ（`CustomTableRowDrawing`）、`FormattedText` のキャッシュ、横位置による描画の全失効は、新しい構成へ置き換えて削除します。旧方式との二重管理は残しません。

### 確認課題

次は未確認です。該当する単位の中で確かめ、結果に応じて方針を見直します。

- Direct2Dで可視範囲の全面を描く所要時間。方式の前提であり、最初の単位で実データに近い条件で確かめます。期待を大きく下回る場合は、利用者へ結果を示して方針を再確認します。
- 全行の入替えでの整形の所要時間。未整形の文字列が多いフレームでは整形が下限になります。繰り返す値のキャッシュと作業スレッドでの整形で短縮する想定ですが、常に画面の更新周期へ収まることは保証しません。
- 小さい文字サイズでの埋め込みビットマップの扱いと、セルの編集欄（WPFの `TextBox`）との文字位置の一致。
- 画面テストの共有ホストで、Direct3Dの資源の生成・解放が他のテストと干渉しないこと。
- Vortice.Windows の追加による配布物の増加量。

## 対象外

- 行データの供給、検索、並べ替え、DB、ライブラリ変更の意味の変更。
- 一覧以外の画面の文字描画の変更。
- 画素単位の滑らかなスクロールやアニメーション。縦方向は行単位のままです。
- 性能の証明だけを目的とする恒久的な計測基盤の追加。

## 作業範囲

主な対象は `BeMusicSeeker/Views/CustomTable` の描画面、行キャッシュ、文字キャッシュ、選択モデル、スクロール入力、UI Automationの通知と、`BeMusicSeeker.csproj` のパッケージ参照です。選択の通知を変えるため、その利用先も含みます。機能の状態や保存の責務を `MainWindow` へ集めません。

描画資源の寿命とDispatcher上の画面更新の順序、可視範囲のキャッシュ方式、描画を検証するテストの置換を変えるため、各単位は[重大変更](../spec/development/agent-workflow.md#重大変更の判定)として扱います。

次の順に進めます。番号は本計画の中だけで使います。

1. **描画面と合成**: Direct2Dの描画器、`D3DImage` による合成、文字のレイアウトの保持、フォントの再現、アイコンの描画を作り、`CustomTableSurface` の描画を置き換えます。確認課題のうち描画の所要時間、文字の位置、埋め込みビットマップをここで確かめます。行キャッシュは表示値と警告だけを持つ形に縮めます。
2. **CPU側の経路と復旧**: 共有面を作れない環境の代替経路、デバイスの消失からの復旧を加えます。描画を検証するテストは、CPU側の描画結果と描画器への入力を調べる形へ置き換えます。
3. **入力と通知の整理**: 画面更新の単位での確定、ホイール量の累積、行の購読範囲の差分更新、UI Automationの通知の分離を行います。
4. **選択モデルの区間化**: 選択集合を区間で保持し、選択の通知から全選択行の配列化を除きます。利用先の契約を確認して置き換えます。

1は2の前提です。3と4は描画方式に依存しないため、1と並行して進められます。各単位で、対応する仕様の節（「スクロール領域」「保持範囲とセル描画の再利用」「選択とキー操作」「表示フォント」）と「実装とテストの対応」を同じ変更で更新します。

## 完了条件

- 一覧の表示・選択・編集・コピー・ドラッグ・列操作・UI Automationが、合意した見た目の差とホイールの移動量を除き、現行仕様の契約を満たす。
- 横スクロール、選択と現在セルの変更、縦スクロールで、文字の整形と表示値の取得を、新しく表示する文字列と行に限って行う。
- GPUが使えない環境とデバイスの消失後も、一覧を表示できる。
- 旧方式の描画キャッシュと失効処理が残っていない。
- 仕様と「実装とテストの対応」が新しい構成を表し、本計画から完了した項目を除いている。採用理由として残す内容は[設計判断](../decisions/README.md)へ移す。
