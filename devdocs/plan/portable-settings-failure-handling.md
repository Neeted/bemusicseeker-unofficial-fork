# Portable settings failure handling

Status: complete; implementation, Functional acceptance and fresh static review passed. This is the historical execution/packet record; the linked spec is authoritative for current behavior. Base: `97af9af4caaa6a8b8bbc29e41702c9112fb548ee`.

## Goal and authority

The user approved the proposed failure policy on 2026-09-05 and authorized implementation and commits when useful. Save failures must be visible, failed settings edits remain retryable/cancellable, and malformed portable XML is preserved before startup resets it. This document records the implementation plan and independent test contract; the durable contract will live in `devdocs/spec/settings-change-impact-and-startup-operations.md`.

## Decisions

1. A successful provider save return means the document was persisted. Read-only, read, serialization, invalid document structure, and write failures must propagate with target path and cause. Provider code does not present UI.
2. Keep same-directory temporary writing and atomic replacement. Failed saves preserve existing target bytes and attempt temporary-file cleanup without masking the primary failure.
3. A missing file is a normal default-settings case. An existing file that cannot be read is not an empty configuration. Missing required configuration/userSettings/application-settings structure is an explicit format failure; missing individual setting keys continue to use defaults. Existing migration compatibility remains.
4. Only XML syntax corruption triggers startup recovery. Before the first Settings getter, move original bytes to a unique `user.config.broken-<timestamp>`-style path without overwriting any existing backup; show a warning identifying the backup and default reset; then create a minimal valid configuration and follow first-run setup. Do not salvage individual XML fragments or fall back to another legacy copy after recovery.
5. Failure to read, quarantine, or create the startup configuration is fatal: show an error and do not compose the main window or read settings afterward. Ordinary save-time corruption is an error and does not trigger recovery.
6. Valid read-only configuration remains readable with existing in-memory compatibility normalization. Failure to persist normalization or a version update is reported and startup may continue using valid loaded values. Do not confuse this with a failed initial read or failed fresh-file creation.
7. Settings Save failure leaves the window open and drafts intact, with no saved-snapshot advancement or post-save application. Preserve the existing audio selection restoration and Cancel snapshot restoration. A later LR2-save failure must not claim that user.config was not saved; no cross-file rollback is added.
8. Other production save paths report failure at their UI boundary. LR2 stop only captures position into existing in-memory settings; normal Settings Save and terminal shutdown persist it. Terminal shutdown captures the last player position before its single final Save, warns on persistence failure, and still completes cleanup/exit. No UI is invoked under player/model locks.
9. Startup file preparation occurs after acquiring the existing single-instance mutex, before settings materialization or main-window composition. Startup warnings before a usable configured language exists use the existing supported OS/default resource behavior.
10. Do not add persistent recovery flags, automatic retry, replay, configuration repair, broad coordinator interfaces, an independent settings-edit buffer, release/version changes, or unrelated cleanup.

User clarification (2026-09-05): if quarantine succeeded but fresh creation failed, the next startup must not import legacy AppData settings merely because the target is absent. When a sibling `user.config.broken-*` backup file exists and the current target is absent, suppress legacy migration and continue fresh configuration creation. Use the already-preserved backup files, not an additional marker/journal. An existing current configuration remains authoritative. Exact user answer: "退避ファイルがあれば旧版設定を自動移行しない（推奨）". Packet delta P04b is frozen below before implementation.

Historical second user clarification (per-stop Save policy superseded by revision 5 below): if ONLY the external LR2 window-position Save fails, stop and cleanup still complete, a warning is shown outside player locks, and requested next-track playback/player replacement continues. Actual process-stop failure remains a failure and must not be treated as successful stop. Exact user answer: "警告して次曲再生・切り替えは続行する（推奨）". Packet delta P08b is frozen below before U2 implementation.

## Production evidence

- Settings Save -> SettingsDialogViewModel.SaveSettingsCore -> SettingsEditSession.Save -> Settings.Save -> PortableSettingsProvider.SetPropertyValues. Provider currently swallows read-only and exceptions; the view model consequently advances to LR2 save, application and snapshots. Existing Apply catch keeps the window open if an exception escapes.
- App initialization -> legacy migration -> ApplicationSettingsLifecycle.Initialize -> normalization -> settings read/version save. Both lifecycle and App currently catch and continue; provider reads additionally treat malformed or unreadable XML as empty. Startup must own the fatal boundary.
- Pause/next track/exit -> LR2body.CloseProcess -> storeWindowPosition -> player settings gateway Save, currently before process stop. A newly propagated save exception would skip stop and cleanup unless the caller is adapted.
- Shell terminal close -> ShellShutdownWorkflowOwner.CompleteTerminalShutdown -> settings session Save. Its existing log-only catch must report failure without aborting cleanup.
- External filesystem edits, read-only attributes and access/sharing failures are reachable inputs at these ingress points. Tests must use these production routes/owners rather than inventing private-only states.
