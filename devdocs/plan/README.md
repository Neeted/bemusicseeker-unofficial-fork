# 作業計画

このディレクトリは、進行中・着手待ち・再開予定の作業について、進捗把握と再開に必要な計画を置く。完了した計画の保管場所にはしない。現在の仕様は [../spec/](../spec/README.md)、情報を残す基準は [現行情報の維持](../README.md#現行情報の維持) を参照する。

## 進行中・着手待ちの関連計画

- [ライブラリ変更操作の性能課題と実装計画](BeMusicSeeker-library-mutation-performance.md): 大規模実測・性能受入など、未完了の調査・調整項目を扱う。現行の変更契約は [ライブラリ変更境界](../spec/library-mutation-boundary.md) を参照する。
- [v3 安全性改善計画](v3-safety-improvements-plan.md): 安全性に関する修正・確認・説明改善と、受付方針の適用範囲を扱う。
- [LR2 startup 手続き化計画](lr2-startup-procedural-orchestration-plan.md): 起動・reloadの直接結果引渡しと操作受付。製品方針は採用済み、runtimeの再構成は未実装。

## 運用

- 冒頭に全体の状態、目的、完了条件を示し、作業項目ごとに現在の状態と短い要約を更新する。完了した項目を蓄積せず、未完了部分の再開に必要な前提は現行仕様への参照に置き換える。
- 進行中は、決定事項、担当範囲、依存順、検証方法など、再開や委譲に必要な情報を保持する。詳細は [エージェント運用契約 section 4](../spec/codex-agent-workflow.md#4-最終計画と記録の使い分け) に従う。
- 段階番号・作業番号・Packet ID / Contract ID は計画と引継ぎ内の一時的な参照名とする。恒久仕様やコード・テストには番号ではなく機能・契約・条件・期待結果を記し、計画の実施順や旧 ID 対応表を転記しない。

進捗は次の形を基本とする。表の一行を、結果を説明できる未完了の作業単位にする。

| 作業項目 | 状態 | 現在の判断・残課題・参照先 |
| --- | --- | --- |
| 意味の分かる作業名 | 未着手／進行中／保留 | 次の作業、再開条件、現行仕様へのリンク |

### 完了時の退役

完了は単に状態を「完了」へ変えることではない。次を同じ変更で閉じる。

1. 現行の挙動・制約・未達要件と実装・テストの対応を `spec/` へ、現在も適用する採用理由を `decisions/` へ統合する。計画をそのまま移動せず、機能・契約を主語に書き直す。
2. 必要な残課題は進行中の計画へ移し、目的・現在の判断・再開条件を示す。親計画が継続する場合も完了部分の履歴は削り、未完了部分だけを残す。
3. 完了した計画と、その作業専用のテスト設計書・配置表・調査メモ・検証証跡を削除する。短い完了記録、アーカイブ、別名の履歴資料は作らない。中止・別計画への統合時も、必要な未解決事項を引き継いで同様に退役する。
4. README、仕様、他の計画、コード・テストのコメントなどの参照元を更新する。必要な参照は現行の正本へ向け直し、履歴だけの参照は削除する。削除したパス・計画名・一時 ID の残存を検索し、リンク切れと仕様・テストの対応漏れがないことを確認する。

承認や実施内容の経緯は Git 履歴で確認する。現在も必要な設計判断・測定根拠は [現行情報の維持](../README.md#現行情報の維持) に従い、完了計画を残す理由にしない。
