# ChartFile 共通化の実装計画

## 目的・現状と不足

BMS と bmson の共通処理が保存行へ戻らずに情報を読み取り、変更を確定できる構造へ整理する。本書はリソース表現と譜面の所有・更新に関する未完了の計画である。

共通化の調査基準は `dev` の `a95840645a34166ea78e2999f3f0bd00aae7b4de`。着手時には現在のコードと仕様を再確認する。親参照の判定条件は [導入先推定](../spec/library/install-estimation.md#入力とリソースキー)を正本とし、後続の構造変更でも維持する。

| 現状 | 不足と対応 |
| --- | --- |
| `ChartResourceSnapshot.Create(ChartFile)` は配列の件数で保存主体へ戻るかを分岐し、BMS では原文の逆引きと遅延ファイル読取りも行う。bmson は文字列集合への変換時に正常参照の原文を失う。 | 確定した解析結果を共通入力にし、未取得と0件を区別する。コミット2で入口から消費先まで移行する。 |
| [`ChartFile`](../../BeMusicSeeker/Models/Chart/ChartFile.cs) は保存主体と `chart_info` 行型を持つ。コピーで保存主体を外しても、原文・非対応理由を表せない。 | 共通の不変な値だけで読み取りと変更要求を表せるようにする。状態所有・表示・DB変換はコミット3で移行する。 |

方向性は、解析結果の情報欠落と保存主体への逆参照を取り除く点で妥当である。リソース表現の統一と所有・更新の移行を分けて進める。ただし、全リソースの常駐、既存の詳細情報管理の二重化、操作対象の拒否条件の厳格化を共通化の要件に加えない。

## 適用する契約と対象外

現行の契約は [共通モデル](../spec/library/chart-model.md)、[ファイル読取り](../spec/library/chart-file-reading.md)、[データと索引](../spec/core/data-and-indexes.md)、[性能](../spec/core/performance-and-scale.md)、[変更セッション](../spec/library/mutations.md)、[ファイルとDBの整合](../spec/library/file-db-consistency.md)を参照する。本書の到達点はこれらを更新する提案であり、現行仕様を書き換え済みとは扱わない。

対象外は、親ディレクトリ参照の新規対応、パス検査の厳格化、新しい警告種別、再生解析の統合、DBスキーマ移行、全件解析の追加、操作の受付条件や失敗時保証の拡張である。形式の解釈と入力の受理範囲を維持し、実装上新たな挙動選択が必要になった場合は [要件の確定手順](../spec/development/agent-workflow.md#要件と到達可能性)に戻る。

## 到達点

BMS と bmson の共通処理は、読取りだけでなく変更要求・確定結果も Chart を単位として扱う。形式別の構文解析と DB の入出力を境界に閉じ込め、共通処理が `BMSFile` / `bmson_song` に戻って情報を取得・更新する経路をなくす。

`ChartFile` は共通の譜面情報を表す不変な値とし、DB 行の継承・参照・変更通知への依存を持たせない。所持譜面の基本情報の現在値は既存の `OwnedChartCollectionState`、保留譜面の現在値と導入状態は `PackageChartEntry` が所有する。詳細情報・スコア等の正本は既存の専用管理主体に置き、表示用の投影へ必要な値を渡す。保存行への逆参照で更新しない。

共通化は、すべてを同一クラスへ詰め込むことではない。構文解析、ファイル読取りスナップショット、再生用 `PlaybackChart`、検索索引、軽量表示行は目的が異なるため残す。ただし、同じ意味のデータを失って別経路から復元する中間表現は残さない。

### 最終的な責務

| 対象 | 責務 | 持たせないもの |
| --- | --- | --- |
| `ChartFile` | 形式共通の識別・基本情報・用途に必要な不変の情報 | `BMSFile` / `bmson_song`、DB 行型、保存先への脱出口 |
| `OwnedChartCollectionState` | 所持 Chart の現在値、配置・ハッシュの索引 | 形式別保存行をもう一つの可変な正本として保持する仕組み |
| `CatalogOwnedCollectionOwner` と既存の専用管理主体 | 集合の排他・版と派生索引、詳細情報・保守・スコアの各管理 | 所持基本情報への全状態の吸収、表示値だけの更新による集合全体の無効化 |
| `PackageChartEntry` | 保留 Chart、導入先・候補・検索状態 | 保存行を変更して Chart を作り直す処理 |
| `ChartFileProjection` と表示行 | 現在の共通情報から用途別の読取り値を作る | getter 内の解析・DB 行参照・状態書戻し |
| 共通リソース解析結果 | 元記述、パス判定、検索キーを一貫して保持する | 下流の分類し直し、元記述を探し直す辞書 |
| `ChartResourceSnapshot` | 確定したリソースから用途別索引を構築する | ファイル読込み、パス解析、警告理由の推定 |
| BMS / bmson の読取り処理 | 形式固有の構文・文字コードを解釈し共通の結果を作る | 保存行をアプリ内の譜面の代用品にすること |
| DB 境界 | 既存テーブルとの変換、列の保持、永続化 | UI 状態・再生状態・解析キャッシュの所有 |

不変性は `IReadOnlyList` の宣言だけで済ませない。生成後に書き換わらない値と集合を使い、投影は確定済みの集合を共有する。譜面ごと・表示行ごとに原文や詳細情報を深く複製しない。

`BMSFile` の最終責務は BMS 保存行の値に限定する。既存の `LR2SongDB.song` だけで表現できるなら、空のラッパーを残さず `BMSFile` 自体を削除する。残す必要がある場合も DB 境界の外へ公開しない。`Ribbit.BMS.BMSFile` は別の再生用解析型であり、同じ名前だけを理由に削除対象にしない。

### 変えない契約

既存 DB のテーブル・列、設定キー、プレイリスト保存形式、譜面ファイルのバイト列を変更しない。BMS と bmson の実際の構文差、LR2 の対応範囲、文字コードの解釈、再生用の解析方式は維持する。名前・namespace の変更だけで境界を作ったことにしない。

所有単位の変更に伴って、同じ MD5 の別配置を一つにまとめない。所持譜面と未所持プレイリスト項目、保留譜面の識別条件を混同しない。用途ごとの既存のハッシュ解決契約を維持し、取得できない情報を契約外のハッシュや保存行の古い値で代用しない。

## コミット構成

| 順序 | コミット案 | このコミットで閉じる境界 |
| --- | --- | --- |
| 2 | `refactor: リソース参照を共通の確定結果に統一する` | リソース抽出から推定・健全性検査まで |
| 3 | `refactor: 譜面の所有と更新をChartへ統一し保存行依存を除去する` | 基本情報・所有・更新・表示・DB 入出力の全経路 |

テストと仕様の更新、旧経路の削除は各コミットに含める。共通型だけを追加する準備コミット、利用側の移行を待つ互換アダプター、最後に削除する予定の旧 API を新設しない。第3コミット内の実装・レビューは領域別に進めても、カタログ側と UI 側を別々の未完了な変更として確定しない。

これは論理的な変更単位である。コミット3の所有者・通知・DB変換を着手前に具体化し、各節の契約を確認してから実装する。独立して完結する境界が見つかれば分割を再検討できるが、新旧の同期経路を残して通す分割にはしない。コミット操作は明示指示に従う。

## コミット2: リソース表現と消費経路を完成させる

### 確定結果の意味

既存の `ChartResourceReference` を中心に、両形式が同じ不変のリソース結果を生成する。`ChartFile.Resources` はその結果をそのまま受け取る。必要な集合の包みは一つにとどめ、形式ごとの共通化用 DTO や旧形式へ戻すアダプターを増やさない。

| 情報 | 意味 |
| --- | --- |
| 種類・用途 | 音声、画像、動画、任意画像など、既存の集計と表示で必要な区分 |
| `RawPath` | 譜面の元記述。検索キーから作り直さない |
| `NormalizedPath` | 既存規則で正規化された拡張子付きの照合パス。拡張子の別名変換を含み得るため、実ファイルの名前とはみなさない |
| `LookupKey` | 拡張子の照合規則を反映した検索用の値。作れない場合もある |
| パスの解析状態 | 実際の解析結果。空キーや拡張子不明から理由を補わない |

元記述・照合用パス・検索キーは用途が違うので、無理に一つの文字列にはしない。同じプロパティ名 `NormalizedPath` を、一方では拡張子付きパス、もう一方では拡張子なしキーという意味で使わない。現行の `.ogg` → `.wav` 等の照合用変換から実在するファイル名を復元しない。実ファイルへの解決は原文と既存の照合規則を使う利用側の責務である。

パスの正規化と検索キーの生成は入口で一度だけ行う。BMS の CP932 デコード判定はバイト列の解釈であり、共通の文字列パス処理へ押し込まない。形式固有の診断は入口で確定し、下流では結果として扱う。

有効なパスでも検索キーが空になる場合があり、`Valid` と索引への採用可否を同一視しない。親参照やCP932診断をキーの有無から生成しない。CP932診断は個別の元パスを取得できない場合もあるため、架空のパスを作らず入力由来の診断として保持する。用途別の件数・診断・警告を決める規則は、共通結果を消費する各機能に残す。

### 入力から利用側までの変更

BMS の WAV/BMP 定義、任意画像、bmson の音声・key/mine channel・BGA・preview・任意画像を同じ結果へ変換する。種類の採用条件など、既存の形式差は変えない。

`ChartFile.AudioResourcePaths` / `VisualResourcePaths` を経由した再構成を廃止する。`BMSFile.WAVfiles` / `BGAfiles` と bmson 側の独立した解析済み文字列集合も、共通処理の別の入力として残さない。既存 DB に対応する値があれば、その表現は DB の読書きにのみ使用する。

`ChartResourceSnapshot` の入力を確定結果だけにする。`Create(BMSFile)` / `Create(bmson_song)`、owner を参照する補完、`BuildRawResourceReferenceLookup`、`ResolveRawReference`、`HasProjectedResourceLists`、`EnsureComponentCollectionsLoaded` をリソース処理から除去する。スナップショット生成時にパスを解析し直したり、ファイルを読んだりしない。

推定、リソース健全性、LR2 リソース互換性、パッケージ集約、再スキャン、コピー用・変更要求用の投影まで同時に切り替える。`ChartFileProjection` の各コピー経路で確定結果を失わないようにし、失った結果を保存行から復元する処理は設けない。

### 未取得・空集合と寿命

`Resources == null` はこの値に解析結果が付属しない状態、空の不変結果は読取りに成功して参照が0件の状態とする。未取得と、利用後に解放した状態を履歴として区別する必要はない。コレクションの件数から状態を推定する追加フラグは設けない。

リソースを必要とする操作が、既存のファイル読取り経路で明示的に取得し、結果付きの Chart を消費先へ渡す。`ChartResourceSnapshot` の生成には取得済み結果を必須とし、未取得を空集合へ変換せず、getter から I/O を起こさない。取得失敗は既存の失敗結果へ伝え、空の成功としてキャッシュしない。取得と公開の間の整合性は、各操作の既存の内容確認・受付契約に従う。外部変更の完全な検出保証を追加しない。

| 利用場面 | 保持・解放 |
| --- | --- |
| 初期化・差分走査・再スキャン | 読み取った同じバイト列から解析し、当該処理の保守・互換性評価へ渡す。現行どおり必要な保存用結果へ畳み込んだ後に参照集合を解放し、所持全件へ常駐させない。 |
| 保留パッケージの推定・再構成 | 操作や項目が必要とする期間だけ共通結果を共有する。パッケージの再構成で元記述や理由を落とさず、譜面バイト列を導入まで長期保持しない。 |
| 所持一覧・検索・並べ替え | 保存済みの基本情報・保守情報から表示し、全件リソース解析を開始しない。未取得を表示のためだけに具体化しない。 |

同じ処理内で既に得た結果は再利用し、解放のために後続の必須処理で即座に再読取りする構造にしない。導入先変更では相対参照の解析結果を共有できても、実在判定・ディレクトリに依存するLR2互換性の結果は新しい配置で再評価する。

### 保持する索引と削除する重複

検索用のハッシュ集合など、消費先があり性能上必要な派生索引は残す。共通化を理由にすべての索引を消して毎回再計算させない。ただし索引を解析結果と独立に書き換えられる正本にはしない。

同じ検索キーを持つ `sound.wav` と `sound.ogg` の索引は既存どおり重複排除し、診断に必要な元記述は保持する。名前の途中のドットを二重に除去しない。任意画像と通常の画像を区別し、健全性の分母も維持する。

### 第2コミット末の境界

基本情報を扱う既存 `BMSFile` と、その既存の解析入口の戻り値はまだ残してよい。ただしリソースについては、確定した同じ不変結果を受け渡すだけにする。旧配列を復元する getter、raw 値の逆引き、`ResourcesV2`、新旧優先順位の切替は残さない。

解析入口の戻り値型そのものと保存行の責務は、第3コミットで所有・更新側と一緒に切り替える。このためだけの一時的な `BmsParseResult` / `BmsonParseResult` は追加しない。

### テストと完了条件

owner を持たない Chart だけで推定・健全性検査・集約を実行できることを確認する。確定済みの Chart を投影・複製・集約しても、元記述、解析理由、キー、件数が変わらないことを検査する。

共通化着手直前の誤警告修正を含む版を比較基準とし、通常譜面の推定候補と健全性が維持されることを確認する。生成元や投影の有無で結果が変わるテストは、同一の確定結果なら結果も同じという契約に置き換える。

リソース処理から保存行参照、隠れた I/O、再正規化、別表現の再構成がなくなった時点を完了とする。

## コミット3: Chart の所有・更新・表示・保存を一括で切り替える

この単位は大きくする。カタログだけを新モデル、UI と変更処理を旧保存主体という状態で確定すると、同期・通知・逆変換が新たに必要になるためである。以下はコミット内の実装順であり、互換経路を残した分割コミットではない。

### 3.1 基本情報の解析結果を保存行から切り離す

`BMSFile.CreateBMSFileFromSnapshot` 等の軽量解析を BMS の読取り処理へ移す。`BmsonSongParser.ParseSnapshot` も DB 行を返す入口ではなく、共通情報を返す入口へ変更する。既存 `ChartFileContentReader` と詳細解析処理を使い、解析済みのバイト列からハッシュを再生成するためにファイルを読み直さない。

可能な範囲で最終的な `ChartFile` の共通情報を直接生成する。解析結果を BMS 行へ変換し、それを再度 Chart に投影する経路は残さない。形式固有の構文木を保持する必要がない場合、形式別の解析結果ラッパーも作らない。

BMS の生の title/subtitle/artist/subartist、LR2 の派生列、bmson の chart_name/mode_hint など、既存の保存・表示で区別される情報を丸めない。ファイル由来の値を適用しても、利用者が設定したタグ・お気に入り・追加日時等を消さない。

bmson の `chart_name` は現状 `subtitle` へ合成されて保存される。元フィールドをDB由来の合成値から逆算せず、新しい列や情報の復元保証を追加しない。ファイル解析時に得た値と、既存DBから得られる値を区別して変換を設計する。

### 3.2 Chart を DB 行型から独立させる

`ChartFile` の `BmsFile` / `BmsonSong` と `GetBmsStorageOwner()` / `GetBmsonStorageOwner()` を削除する。`LR2SongDBExtended.chart_info` も共通モデル・詳細解析の入出力から外し、共通の不変な詳細情報として扱う。DB の `chart_info` 行との変換は DB 境界に置く。表示からだけ型を隠して完了にせず、解析結果・索引・書込み要求・DB窓口までの参照を追う。

健全性・文字コード・スコアは、既存の共通スナップショットを利用・整理する。新しい `ChartState` 群を増やして、既存の状態と二重保持しない。保存行から共通値を作る変換自体は必要だが、その変換を共通モデルの getter に置かない。

`CatalogChartInfoOwner` の情報・失敗の索引と最新性判定を維持する。所持主体がない `chart_info` キャッシュも存続し得るため、詳細情報の寿命を所持カタログへ従属させない。`ChartFile` へは用途に必要な不変値を渡し、情報更新のたびに全件の基本情報を作り直さない。

保守・警告は、所持譜面の確定値と保留項目の一時値を区別する。既存の `BMSFileMaintenanceInfo` 等にDB行の継承・参照がある場合、そのまま共通型へ移さず、不変の保守値と保存変換に分ける。スコアの正本と再読込みは既存のライブラリ側のスコア管理に置き、`BMSFile` が担っているスコア行の購読・解除・変更対象通知をそこへ移す。単に購読を削除して表示を固定しない。

保守の評価・読込みは `CatalogMaintenanceOwner`、健全性の索引は `ResourceHealthIndexOwner` に残す。DBから取得した状態、今回計算した状態、未計算を区別し、未計算を正常な空結果にしない。所持集合のロック・版・派生索引は `CatalogOwnedCollectionOwner` の既存境界を使い、表示値だけの更新で集合全体の版を進めない。

`ChartFile` から削除した保存主体を、新設 `OwnedChart`、`StorageHandle`、`LegacyChartAdapter` や `object` フィールドへ移すことは禁止する。必要な永続化上の対象情報は DB 境界で解決する。

### 3.3 カタログと変更結果を Chart に統一する

`OwnedChartCollectionState` の現在値と索引を共通 Chart に基づくものにする。保存主体から Chart への逆引き、保存主体の参照同一性による可変な現在値の解決を除去する。

`LibraryChartRef` から保存行への参照と Chart・保存主体の相互変換を削除し、共通カタログで対象を解決するための参照にする。`LibraryChartKind` と `ChartFileKind` の重複も解消する。ただし、最終形を「選択時のパス＋期待ハッシュ」だけに先決めしない。

現行の [`LibraryChartRefIndexSnapshot`](../../BeMusicSeeker/Models/BmsLibraryInternal/Catalog/LibraryChartRefIndexSnapshot.cs) は保存主体の同一性を優先し、次に種類とパスで現在の対象を解決する。[`LibraryMutationOwner`](../../BeMusicSeeker/Models/Library/BMSLibrary.LibraryMutationOwner.cs) の削除は、確認前の現行対象への解決と、確認後に固定した対象の整合性検査を分けている。次をコミット3の着手前に具体化する。

- 画面の対象を現在値へ解決する時点と、確認・受付後の実行対象を固定する時点を維持する。選択時の古いハッシュを理由に新しく拒否しない。
- 保存主体の同一性が担う、移転後の現在値への追従と、確認後の対象差替えの検出を、DB行に依存しないカタログ項目の識別・既存の世代と変更通知でどう維持するかを決める。不変値の参照同一性をそのまま主体の同一性にしない。
- 同一 MD5 の別配置を統合せず、ハッシュだけで対象を別配置へ広げない。パスだけの既存参照、未所持項目、保留項目の意味も維持する。

本番の到達と受付条件を [競合対策の判断手順](../spec/core/workflow-concurrency.md#競合対策を決める手順)で確認する。永続 GUID、並行するID台帳、独立した世代管理、操作前の全ファイル再ハッシュを追加しない。既存の項目識別で維持できない挙動が判明した場合は、その経路と選択肢を示して利用者へ確認し、回答に依存する実装・期待結果を確定しない。

既存 `LibraryMutationOwner` と変更セッションを使って、ファイル操作、DB 永続化、カタログ・索引・通知への反映を一つの境界で扱う。DB 永続化の成否が不明な段階で共通 Chart の現在値を書き換えない。失敗・取消し・部分成功は既存の操作結果と補償処理で表し、二つ目のトランザクション管理を作らない。

一つの境界とは既存の論理的な変更セッションを指す。ファイルと複数DBの原子性や操作全体の巻戻しは保証しない。物理成功、永続確定、必須反映、通知・後片付けの失敗を区別する。差分走査のDB確定単位は導入の一操作一セッションとは別であり、共通化のために全件を一括保持しない。

`ChartStorageOwnerMutator` とその周辺の保存主体を変更する API は、共通の変更要求と確定結果の適用に置換して削除する。クラス名を変えたうえで同じ形式別分岐を公開し続けない。

### 3.4 パッケージ、UI、共通操作を同時に移行する

`PackageChartEntry` は現在の Chart と導入状態を持ち、保存行を変更して `CreateCurrentChartFromStorageOwner` で復元する経路を削除する。導入前には所持カタログの保存行が存在しなくても動作する構造にする。

`GetStorageMutationSyncRoot` の保存行依存も除去する。変更の排他は既存セッション・パッケージの変更境界へ合わせ、不変な Chart の差替えでロック対象が変わる実装にしない。

通常一覧、プレイリスト、重複検査、ファイル移動・削除・修復、再スキャン、保留導入、再生パネル、外部操作の呼出しをまとめて更新する。`NormalLibraryRowCache` 等の保存行への購読を、カタログ・項目の既存の変更通知へ統合する。旧 `PropertyChanged` を新通知へ変換する互換 relay は残さない。

パス・ハッシュ・基本情報の更新、詳細情報の索引更新、スコア更新、保守・警告更新で、どの既存通知がどの表示行を無効化するかを実装引継ぎに示す。所持変更の通知だけで別管理主体の更新も届くと仮定しない。局所更新と購読解除を維持し、通常一覧・プレイリスト・導入済み項目に古いスナップショットを残さない。

導入先と候補の所有者は `PackageChartEntry`、再生一時状態は既存の再生担当、スコアは既存のスコア管理とする。表示のためのスナップショットに値を含めることと、その値の正本を別に所有することを区別する。

LR2 IR などの BMS 専用操作は、形式と必要な識別子で可否を決める。owner の有無を形式・所持状態・操作権限の代用品にしない。bmson に偽の BMS 行を作らない。

### 3.5 DB 境界に保存行だけを残す

読込みは既存 DB 行から共通の現在値へ一度変換し、書込みは確定した変更要求から既存の表現へ変換する。`BMSFiles` / `BmsonSongs` は共通処理の正本・更新 API として公開しない。

既存 DB の未変更列を保持し、全列のデフォルト値による再生成で利用者の値を失わないようにする。既存の差分更新・永続化結果の契約を利用する。保存用 DTO に解析済みキャッシュ、警告コレクション、スコア購読、再生状態を持たせない。

`BMSFile` からパーサ、リソース、maintenance の遅延生成、警告管理、スコアの購読、アプリ状態・表示状態を除去する。BMS 行にしか必要ない列・変換を DB 境界に残す。不要になった型や型変換はこのコミットで削除し、別の掃除コミットへ送らない。

### 第3コミットの検証

| 領域 | 必須の確認 |
| --- | --- |
| カタログ | 同一 MD5 の別配置、形式混在、パスの一意性、追加・削除・移転・内容更新後の索引 |
| 操作対象 | 現在値への解決と確認後の検査の区別、移転・内容更新・対象差替えでの現行契約、同一MD5の別配置、パスだけの参照、未所持項目の扱い |
| 永続化 | DB 失敗・取消し・部分成功、未変更列の保持、再起動後の再読込み |
| パッケージ | 単一ファイル、BMS/bmson 混在、入れ子、既所持混在、導入先の入力・明示クリア・候補・警告 |
| UI | 通常一覧・プレイリスト・重複・保守一覧の現在値更新、購読解除、行キャッシュ、検索と並べ替え |
| 形式境界 | BMS 固有の文字コードと LR2 操作、bmson での不正な BMS 行生成がないこと、再生用解析の維持 |
| 性能 | 起動・ソートで全件リソース解析をしないこと、局所変更で全件再投影しないこと、索引・原文の大量複製がないこと |

Windows の標準入口で自動検証する。WPF とDBの保証には既存の自動テストと独立した一時DBを用い、実環境のUI操作や利用者DBの変更を必須にしない。性能比較の基準は共通化着手直前の誤警告修正を含む版に固定し、共通化と無関係な最適化変更を混ぜない。代表規模、入力、ビルド条件、キャッシュ条件、完了地点を合わせ、起動全体・局所更新・再スキャン・推定の完了時間と読取り・解析・再投影の仕事量を比較する。未測定の範囲はそのまま明示する。

## 最終受入条件

1. `ChartFile`、`LibraryChartRef`、共通操作の要求・結果、表示行に保存行への逆参照がない。
2. 共通処理と UI で `GetBmsStorageOwner()` / `GetBmsonStorageOwner()` を使わない。同等の機能を別名へ移しても完了とはしない。
3. 保存行型の使用は DB 入出力の限定された境界に閉じる。共通の詳細情報も DB 行型を直接持たない。
4. リソース判定は経路や owner の有無によらず、確定した同じ結果から同じ答えになる。
5. 新旧コレクションの同期、双方向変換、互換通知、空値で隠す補完が残っていない。
6. 既存 DB のスキーマと譜面形式を移行せずに読取り・通常操作・再読込みができる。明示された操作によるファイル・DB更新は従来どおり行い、取消し・失敗・局所更新の契約を維持する。
7. リソースの短命な保持、詳細情報・スコアの既存所有、画面の局所更新、操作対象の解決と確定時点が維持される。実装開始前の未決事項が解消されている。

完了判定は単なる文字列検索だけにしない。共通型のフィールド・引数・戻り値と呼出し経路を点検する。保存行依存の再導入を防ぐ恒久検査が必要な範囲は独立テスト設計で決め、既存の型・依存関係の検査を優先して振る舞いのテストと併用する。境界の許可対象を無制限に追加して検査を通さない。
