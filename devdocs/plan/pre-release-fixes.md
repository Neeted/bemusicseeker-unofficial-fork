# 3.2.0.0公開前の修正

## 目的と範囲

3.2.0.0の公開前調査で見つかった課題を、任意改善を含めてすべて修正する。課題ごとの成立条件・原因・影響は[課題の詳細](#課題の詳細)に置き、本書の実装単位の契約がそこに書いた案より優先する。性能計測は計画の是非の判断材料に使わない。未リリース分（`dev` だけ）が永続化したデータの移行は扱わず、v3.1.0.0が書いたデータからの互換だけを考える。

進め方は[エージェント運用](../spec/development/agent-workflow.md)に従う。各単位は、計画案 → 必要な設計相談 → 必要な独立テスト設計と承認 → `plan-clarifier` の引継ぎ点検 → 実装 → 整形・ビルド・対象moduleの局所MTP実行 → 凍結 → 新しい `preflight-static-review` → 最終レビュー → `verify` → ブランチ内コミット → `dev` への `--ff-only` 統合の順に進める。予備レビューは指摘のたびに新しい担当で行い、3回目の予備レビューや最終レビューの3回目の再レビューが必要になった単位は、再計画して以後の修正を `issue-resolver` へ渡す。これらの工程は効率化のために省かない。

## 実装単位

区分は[重大変更の判定](../spec/development/agent-workflow.md#重大変更の判定)による。重大は `critical-static-review`、通常は `repo-static-review` で最終レビューする。許可パスは目安であり、単位責任者が調査後に確定して引継ぎへ書く。新しい表示文言は `Resources.resx`、`Resources.cs`、`lang/` の6言語を同じ単位で揃える。リソース辞書は複数単位が追記するため、`dev` への統合時の更新で両方の追加を残して競合を解消する。利用者に見える挙動の変更は[利用者向け文書の編集方針](../README.md#利用者向け文書の編集方針)に従ってマニュアル・リリースノートへ反映する。

### 譜面ビューアのメニュー

- 区分: 通常。対象: [譜面ビューアのメニューの見出しと動作のずれ](#譜面ビューアのメニューの見出しと動作のずれ)。
- 契約: 通常の譜面、未所持のプレイリスト項目、プレイログの3つのメニューで、見出し・表示・可否とクリック時の処理を同じ一つの判定で決める。
  - 1行選択でMD5を持つBMS（所持・未所持を問わない）: 「譜面ビューアで開く」を有効に表示する。ファイルが実在して未登録なら、設定に従って確認してから登録して開き、ファイルがなければMD5で開く。
  - 2行以上の選択で、ファイルが実在する所持BMSを含む: 「譜面ビューアに登録する」を有効に表示する。ファイルが実在する所持BMSだけを登録対象にし、ビューアは開かない。確認の件数は新しく登録する件数とする。
  - それ以外（1行でBMSON・MD5なし、2行以上で上記の所持BMSを含まない）: 項目を表示しない。
  - 複数選択で新しく登録する譜面がなかった場合の情報メッセージは残す。
- 正本: [外部起動](../spec/ui/external-launch.md#譜面ビューアの項目と登録結果の通知)。
- 許可パスの目安: `ViewModels/ChartOperations/ScoreViewerRegistration.cs`、`Views/MainWindow/MainWindowSelectedChartContextMenuTerminals.cs`、`Views/MainWindow/MainWindow.cs` の譜面ビューアのメニュー、`ViewModels/PlayHistory/` のメニュー状態、関連テスト、上記仕様、マニュアル、リリースノート。

## 並列化と統合

作業ワークツリーはメイン以外に同時最大5本とし、メイン作業ツリーは `dev` の統合専用に保つ。着手前に本書と課題の詳細を `dev` へコミットし、各ワークツリーはその版から分岐する。

| 順 | 同時に進める単位 | 備考 |
| --- | --- | --- |
| 第1波 | 保留パッケージの分け方、LR2の局所同期、受付使用中の拒否通知、設定の不備の案内、SQLiteの互換範囲 | 重大な単位を先に進める。 |
| 第2波 | プレイリスト、進捗表示、メイン画面の表示状態、検索、割り切りの明記 | 空いたワークツリーから順に割り当てる。設定画面の操作は設定の不備の案内のワークツリーで続ける。メイン画面の表示状態は受付使用中の拒否通知の統合後に始める。 |
| 第3波 | 統合時に見つかった小修正、譜面ビューアのメニュー | 第1波・第2波の統合中に見つかった課題を扱う。 |

依存のない単位は着手順に縛らず、検証・独立レビュー・コミットが揃ったものから全体ルートが一件ずつ統合する。`verify` は全ワークツリーで同時に一件だけ実行し、全体ルートが順番を調整する。共有するファイル（`MainWindow.cs`、`ViewModels/Install/`、`Models/BmsLibraryInternal/Lr2/`、リソース辞書）は後から統合する側が `git rebase dev` で更新し、影響する検証とレビューを行う。

## 完了条件

各単位が最終レビューの合格と `verify` の成功を得て `dev` へ統合されていること。全単位の統合後の `dev` で `verify` が成功し、正式リリース前に `full` を実行すること。完了した単位は契約・採用理由・検証の対応を仕様へ移し、本書と課題の詳細から除く。すべて完了したら本書を削除し、[計画の一覧](README.md)から外す。

#### 譜面ビューアのメニューの見出しと動作のずれ

見出しと可否は選択件数で決まるが、クリック時の `ScoreViewerRegistrationWorkflowOwner.RunAsync` は譜面ビューアの対象（有効なMD5を持つBMS）だけに絞った件数が1件ならビューアを開く。所持BMSとBMSONの2件選択は「譜面ビューアに登録」と表示して、押すとビューアを開く。未所持の対象1件と対象外1件の選択は、開ける対象があるのに項目が無効になる。最初期の実装は見出し・可否・開く判定のすべてを選択件数で決めており、`050cb8219`（クリック対象をMD5のある行へ絞り、その件数で開く）、`690c0242f`（1行でもファイル実在を要求、BMSON混在で全体無効）、`c534fa741`（対象0件で非表示）、`ef50bc1f6`（絞った件数で開く処理を担当へ集約）の順にずれた。プレイログのメニューはMD5だけの行で項目を出さず、ファイルが消えた所持譜面では無効になる。対象だけの件数で開く挙動は `RunAsync_ChartTargetsProjectsEffectiveSingleTargetAndOpensViewer` が固定している。
