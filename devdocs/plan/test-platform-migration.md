# テスト基盤の残課題

検証区分・期限・所有と回収・結果判定は[テスト検証](../spec/development/testing.md)、module選択と配布物の受渡しは[標準入口](../../tools/BeMusicSeeker.Verify/README.md)を正本とする。

## 現状

テスト基盤の移行と追加の受入シナリオは完了し、Fullの必須IDと実行範囲は正本へ反映済みである。残るのは、追加速度目標の判定と改善、環境不足で未実行の条件、移行中に見つけたテスト側の改善候補だけである。

## 追加速度目標

日常中央値60秒・p95 90秒、Full10分の追加速度目標は、現在の保証と実行構成のままでは達成できない。目標を維持するか、保証・構成の変更と引換えに見直すかは未決である。同じ対象・条件で準備から回収までを比較する。対象削減・skipや運用上限の延長を性能改善と扱わず、各修正で必要な既存の性能回帰検証を維持する。

### 現在の所要時間の構成

12論理CPU（予算B=12、Core 8worker、UI枠3）のWindowsで、Daily全件（Core 7,018件、Windows 2,337件、Scenarios 3件）を成功した `verify` の内訳は次のとおりである。

| 区間 | 所要 | 決める要因 |
| --- | ---: | --- |
| 自動整形 | 変更C#ゼロで0秒、変更C#があれば約60〜90秒 | `dotnet format style` が、変更ファイルの属するprojectの意味解析を全体で行う。Windows.Testsのファイルは1件でも約60秒（読込約8秒・解析約50秒）。診断IDやprojectを絞っても変わらない。 |
| ビルド | 変更なしで約8秒、製品を変更すると約90秒 | 製品のWPFと大きなテストprojectの通常のコンパイル。 |
| テスト段階 | 約280秒 | UIを使う実行の合計約810秒を3枠で分ける下限（約270秒）。Coreは約255秒で律速ではない。 |

UIを使う実行は、1プロセスに一つの共有STA Dispatcherと共有のWindow一覧を使うため、各実行の内部は逐次である。中央値0.1〜0.2秒の多数のケースの実処理（実Window・実DB・実モーダル・言語の往復切替など）に時間が分散している。通常完了を固定時間で待つ処理はなく、実時間を使うのは、製品の保持時間・受付期限そのものを検査するケース（下表）だけである。枠の数Wは `clamp(B/4, 1, 3)` で、Coreとの同時実行によるCPU負荷も各実行を遅らせる。このため、ケースの保証と実行構成を変えずにテスト段階を大きく縮める余地は小さい。

### 残る候補

いずれも未採用である。採否は、保証・契約への影響と、同じ条件の前後比較で判断する。

| 候補 | 見込み | 判断に必要なこと |
| --- | --- | --- |
| 自動整形とビルドの並行 | 変更C#がある `verify` で最大約60〜90秒 | 整形が内容を変えた場合だけ再ビルドする。「前段が失敗したら後段を開始しない」順序の契約変更と、formatterの設計時ビルドとの出力の分離（formatterはDebug、検証はRelease/x64）の確認が要る。 |
| 実行間の配分の見直し | 約10秒 | 最長の実行（現在は `Windows.Remaining`）から、短い実行へケースのカテゴリを移す。所要の偏りは実測で決まり、ケースの追加で変わる。 |
| 一時試聴の保持時間（製品既定2秒）の注入 | Remainingで約12秒、Coreの合計で約60秒 | 製品の構築APIの変更。保持の順序を確認するケースは残す。 |
| 走査・同期パイプラインのブロッキング段をスレッドプール外へ移す | Coreの停滞の根本対策 | 製品の変更。現在はCoreのテストプロセスだけがworker下限を上げて停滞を防いでいる。 |
| `UpdaterProcessGatewayTests` の受付期限 | 約20秒 | 製品既定の10秒期限を短縮せずに実時間で検査する現在の設計を変える判断が要る。 |
| リリーススクリプト試験のgit準備の共有、[PlaylistCatalogViewTestSupport](../../tests/BeMusicSeeker.TestSupport/Components/PlaylistCatalogViewTestSupport.cs) のスコア登録の一括トランザクション | Coreの合計で数十秒 | Coreは律速ではないため、UIの実行を縮めるまで全体時間には効かない。 |

`full` は、配布候補を生成したうえで、Windowsの全実行の後にScenarios全件とDesktopを逐次実行する。このため、Scenarios全件とDesktopの所要は、上の表のテスト段階の下限に加算される。`full` の内訳は、上と同じ条件ではまだ測っていない。

## 未実施条件

権限不足のシンボリックリンク6条件と入力不足の外部encoder 1条件は、合意どおり未実行・未成功として残す。必要な権限・入力が揃った時点で再開し、移行対応済みであることと実行成功を区別する。

## テスト側の改善候補

いずれも現行の検証を止めていない。着手時に現行ソースで到達を確認し、未確認の事象は仮説として扱う。

| 対象 | 内容 |
| --- | --- |
| [SettingsStartupTestFixture](../../tests/BeMusicSeeker.TestSupport/Wpf/SettingsStartupTestFixture.cs) の起動後処理の終端待ち | 起動後グループの集計外で必須の処理（遅延ランキング更新など）が最後に終わると、待機を起こす通知が来ず待ち続けうる。IR有効とスコアDB指定を同時に使う呼出しで到達しうる。現状の呼出しでの到達は未確認である。採用時は終端の判定と通知の順序を揃える。 |
| 初期化完了直後に明示的なライブラリ操作へ進むWPF fixture | 実画面のfixtureは起動後処理の終端を待ってから操作へ進む。`SettingsWindowPresentationTests` の初期化完了直後に設定適用のスキャンへ進む経路は、同じ受付の競合で失敗する候補として未確認である。 |
| `UpdateMarkerReaderSharingTests` の更新ツール解決 | 更新ツールのDLLを `WindowsProcessProbe` のビルド出力内の固定パスから読む。更新ツールの解決をTestSupportへ集約する際に置き換える。 |
| Scenarios/Update の `UpdaterPackageSyncTests.WindowsGatewayCancelsAndPreparesNextUpdate` の間欠失敗 | 13回の実行で1回だけ失敗し、その後のFullでは再発していない。失敗時の症状は記録していない。再発時は期限延長や再試行ではなく原因を特定する。 |
