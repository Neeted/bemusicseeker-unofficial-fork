# テスト基盤の残課題

検証区分・期限・所有と回収・結果判定は[テスト検証](../spec/development/testing.md)、module選択と配布物の受渡しは[標準入口](../../tools/BeMusicSeeker.Verify/README.md)を正本とする。

## 現状

テスト基盤の移行と追加の受入シナリオは完了し、Fullの必須IDと実行範囲は正本へ反映済みである。残るのは、追加速度目標の判定と改善、環境不足で未実行の条件、移行中に見つけたテスト側の改善候補だけである。

## 追加速度目標

日常中央値60秒・p95 90秒、Full10分の追加速度目標は、現在の保証と実行構成のままでは達成できない。目標を維持するか、保証・構成の変更と引換えに見直すかは未決である。同じ対象・条件で準備から回収までを比較する。対象削減・skipや運用上限の延長を性能改善と扱わず、各修正で必要な既存の性能回帰検証を維持する。

### 現在の所要時間の構成

12論理CPU（予算B=12、Core 8worker、UI枠3）のWindowsで、Daily全件（Core 7,023件、Windows 2,337件、Scenarios 3件）を成功した `verify` の内訳は次のとおりである。

| 区間 | 所要 | 決める要因 |
| --- | ---: | --- |
| 自動整形とビルド | 変更C#ゼロならビルドだけ（変更なしで約8秒、製品の変更で約90秒）。変更C#があれば両者を同時に実行し、遅い方（整形は約60〜170秒）で決まる。整形が内容を変えた場合だけ再ビルドが加わる。 | `dotnet format style` は、変更ファイルの属するprojectの意味解析を全体で行う。Windows.Testsのファイルは1件でも約60秒、製品のファイルを含むと約150秒以上かかる。診断IDやprojectを絞っても変わらない。ビルドとCPUを共有するため、製品を含む整形は `format` 段階の期限180秒に近づく。 |
| テスト段階 | 約270秒 | UIを使う実行を3枠で分けた最長の枠。枠の終了は Daily Scenarios（約60秒）とSettings（約210秒）の枠が約271秒、Remainingが約264秒、Shellが約261秒。Coreは約252秒で律速ではない。 |

UIを使う実行は、1プロセスに一つの共有STA Dispatcherと共有のWindow一覧を使うため、各実行の内部は逐次である。中央値0.1〜0.2秒の多数のケースの実処理（実Window・実DB・実モーダル・言語の往復切替など）に時間が分散している。通常完了を固定時間で待つ処理はなく、実時間を使うのは製品の保持時間そのものを検査するケース（下表）だけである。枠の数Wは `clamp(B/4, 1, 3)` で、Coreとの同時実行によるCPU負荷も各実行を遅らせる。3枠の終了の差は約10秒に収まっており、ケースのカテゴリを移す配分の見直しで縮むのは数秒である。このため、ケースの保証と実行構成を変えずにテスト段階を大きく縮める余地は小さい。

### 残る候補

いずれも未採用である。採否は、保証・契約への影響と、同じ条件の前後比較で判断する。

| 候補 | 見込み | 判断に必要なこと |
| --- | --- | --- |
| 一時試聴の保持時間（製品既定2秒）の注入 | Remainingで約12秒、Coreの合計で約60秒 | 製品の構築APIの変更。保持の順序を確認するケースは残す。Remainingだけを縮めても、最長の枠（Scenarios・Settings）が律速のため全体は数秒しか縮まない。 |
| UI枠数の上限（3）の引上げとWindowsの実行の追加分割 | UIの合計約790秒を4枠で分ければ理想で約200秒 | 枠だけを増やしても各Windows実行（約210〜265秒）は縮まないため、Windowsを4実行以上へ分ける必要がある。Coreのworker数の減少、同時実行のCPU負荷、利用者セッションの排他との関係を同じ条件で測る。 |
| リリーススクリプト試験のgit準備の共有、[PlaylistCatalogViewTestSupport](../../tests/BeMusicSeeker.TestSupport/Components/PlaylistCatalogViewTestSupport.cs) のスコア登録の一括トランザクション | Coreの合計で数十秒 | Coreは律速ではないため、UIの実行を縮めるまで全体時間には効かない。 |

`full` は、配布候補を生成したうえで、Windowsの全実行の後にScenarios全件とDesktopを逐次実行する。このため、Scenarios全件とDesktopの所要は、上の表のテスト段階の下限に加算される。`full` の内訳は、上と同じ条件ではまだ測っていない。

## 未実施条件

権限不足のシンボリックリンク6条件と入力不足の外部encoder 1条件は、合意どおり未実行・未成功として残す。必要な権限・入力が揃った時点で再開し、移行対応済みであることと実行成功を区別する。
