# 公開リポジトリへの一本化

## 目的と適用状態

既存の公開リポジトリ `Neeted/bemusicseeker-unofficial-fork` に開発履歴を取り込み、開発と配布を一つのリポジトリで運用します。回帰の混入点を調べ、必要な修正を別の版へ適用できる履歴を残します。

本書は移行前の計画です。履歴整理、ブランチ作成、送信、公開設定、スクリプトの変更は未実施です。現在の実行手順は[リリース仕様](../spec/development/release.md)に従い、実装と同時に正本を更新します。

## 確定した前提

- 元リポジトリのバックアップは利用者が保存済みです。必要最小限の履歴整理によるコミットID変更を許容します。
- `BeMusicSeeker.Tests/TestData/song_snapshot/song.db` は過去の履歴からも除去します。テスト用の実譜面は残します。Git LFSはこの移行のために導入しません。
- 過去の登録情報は整理済みとして扱い、公開の未解決事項に戻しません。
- 公開リポジトリの既存タグ、Release、添付資産とURLは維持します。過去のタグを開発側のコミットへ付け替えません。
- `bms-md5-url-map.tsv` は公開側の内容とルート直下の配置を維持します。
- `version.txt` はv2.1.0.0より前のアプリ向けの互換資源です。旧版は大きい値を観測して通知するだけなので、公開側の `2.1.6.0` を引き継いで固定します。新しい版への追随、現行アプリの読取り、JSONからのフォールバックは行いません。

## 現状と不足

開発側と公開側の履歴には共通祖先がありません。開発履歴には削除済みの約442 MiBのDBが残っており、GitHubへ通常のGitとして送る前に除去が必要です。公開側の `main` はv2.1.6.0の更新情報と、GitHub Pagesの `/docs` を配信しています。

[publish.ps1](../../scripts/publish.ps1) は別リポジトリへの同期を行い、[release.ps1](../../scripts/release.ps1) は開発用・公開用の固定パスを持ちます。両スクリプトに `version.txt` の生成処理があり、[ReleaseScriptVersionSourceTests](../../BeMusicSeeker.Tests/ReleaseScriptVersionSourceTests.cs) もその生成を要求しています。READMEの日英両方には、一部コードだけを公開するという旧運用の説明が残っています。

## 履歴の移行

1. 移行用の複製で、指定されたDBだけを履歴から除去します。コードの履歴を一つにまとめたり、分岐を直線化したりしません。除去で空になったコミットやマージの扱いを事前に固定し、可能な限り元のコミット単位と親子関係を維持します。
2. 履歴整理ツールの旧IDと新IDの対応表を、元履歴のバックアップに付随する移行資料としてリポジトリ外へ保存します。公開ツリーに恒久的な履歴台帳は追加しません。
3. 整理後の開発履歴を `dev` の起点とし、公開側の `main` をもう一方の親とする統合コミットを作ります。開発側を第一親とし、ファイル内容は開発側を基本に、TSV、公開中の `update.json`、固定する `version.txt` を明示的に引き継ぎます。公開用HTMLの生成・追跡範囲も確認します。
4. `dev` を先に公開し、公開 `main` は次回正式リリースまで現在の配信状態を維持します。既定ブランチも `main` のままとします。次回リリースで通常の履歴を保つマージを行い、強制pushは使いません。
5. 移行対象外の退避ブランチや元履歴への参照を一括送信しません。新規cloneと確認が済んだ後、開発の作業先を統一し、二つのリポジトリ間のコピー運用を終了します。

旧公開タグは配布履歴として残します。移行前のコードの回帰調査には、整理後の開発系列のコミットを使います。除去したDBを必要とする過去のテストはそのままでは実行できないため、バックアップからローカルに供給するか、該当コミットを調査上スキップします。欠落による検証不能を成功と扱いません。

## ブランチの契約

| 対象 | 運用 |
| --- | --- |
| `dev` | 次回正式版へ向けた開発の統合先。通常の作業ブランチとPRはここを起点・対象とする。 |
| `main` | 正式公開済みのコードと配信データ。未公開ZIPを指す更新情報を配信しない。 |
| 作業ブランチ | `dev` から作り、完了後に `dev` へ統合する。 |
| 緊急修正 | `main` から分岐し、必要な修正だけで正式版を公開する。公開後に `main` を `dev` にマージする。 |
| TSV・文書だけの修正 | アプリの新バージョンを要求せず `main` へ反映できる。同じ変更を `dev` にもマージする。 |

`dev` と `main` の間ではsquashやrebaseを使わず、祖先関係を保って統合します。正式リリースの境界はマージコミットとタグで示します。作業ブランチも回帰調査に意味のある変更単位を残し、機械的に一つのコミットへまとめません。`main` は最終リリースタグとの常時完全一致を要求しません。

常設の `release` ブランチは設けません。GitHubの既定ブランチが `main` であるため、開発手順にPR先を `dev` と明記します。ブランチと正式版タグの削除・強制更新を防ぐ設定を検討し、リリース用の送信経路を保ちます。線形履歴の必須設定はこのマージ方針と組み合わせません。

## バージョン更新と正式公開

- バージョンの正本は `AssemblyInformationalVersion` とし、画面内の更新履歴と版別リリースノートを同じ変更で揃えます。バージョン更新だけでは送信・公開しません。`AssemblyVersion` は互換上の必要がある場合だけ変更します。
- 公開対象の `dev` のコミットを確定し、最新の公開 `main` からローカルでリリース用の統合を行います。準備中もリモートの `main/update.json` は公開済み版を指したままにします。
- 対象ソースから配布物を生成し、`Full` の検証を行います。生成したZIPから `update.json` と公開用HTMLなどを整え、リリースコミット・タグを確定します。タグのソースとZIPが対応することを確認します。
- タグを送信してRelease下書きを作成し、タグ・コミット・添付資産・更新情報を照合します。Release資産を公開してから、そのコミットを公開 `main` へ送信します。途中で `main` が進んでいた場合は強制更新せず、差分を確認して手順をやり直します。
- 正式公開した `main` を `dev` へマージし、リリース時に加えた生成物や修正を引き継ぎます。
- プレビュー版は `main/update.json` を変更せず、独立したプレビュータグとReleaseで扱います。

## スクリプトと資料の整理範囲

| 対象 | 変更方針 |
| --- | --- |
| `publish.ps1` | 単一リポジトリの対象ソースから配布物を生成する責務へ絞る。別リポジトリ同期、同期専用引数、固定パスを除去する。呼出し元も更新する。 |
| `release.ps1` | 同じリポジトリのタグ・下書き・正式公開を扱う。`version.txt` の生成を削除する。旧コピー運用の「未送信コミットが一つ」という下書き再作成条件やreset処理は引き継がず、通常の開発履歴を壊さない手順へ整理する。 |
| `version.txt` | 移行時に公開側の値を引き継いだ後は固定する。現在の版の正本やリリース前提条件にしない。 |
| `update.json` | 実際に公開するZIPから生成する責務を一か所に定める。公開前の候補と公開中のファイルを混同しない。 |
| READMEの日英両方 | 全ソースを扱う公開リポジトリの説明へ変更する。由来とコンポーネントごとのライセンス区分を保ち、開発参加の入口を揃える。 |
| 開発手順・AGENTS・開発運用の目次 | 作業起点、PR先、緊急修正、TSV更新、リリース後の `dev` への反映を案内する。ブランチ契約の正本はリリース仕様に集約する。 |
| リリース仕様・更新仕様 | バージョン更新と公開操作を区別し、一つのリポジトリでの生成・検証・公開順序と旧版向け固定ファイルを説明する。 |

実装を変える前に、既存テストの更新・削除と不足する振る舞いの検査を[テスト作成](../spec/development/test-authoring.md)に従って設計します。現在の `version.txt` 生成を要求する検査は廃止し、バージョンの正本、既存互換ファイルの不変、公開順序・照合の契約を確認します。運用文書の文言を固定するだけのテストは追加しません。

## 完了条件

- 指定DBが公開対象の全履歴から除かれ、残すコード・実譜面・コミットの対応と親子関係が確認できる。回帰調査に使う代表的な旧版を取り出せる。
- TSVの内容が移行前と一致し、ルートのURLを維持する。旧公開タグの参照先とRelease資産が変わらない。
- 移行だけで `main/update.json` の配信内容を変えない。`version.txt` は `2.1.6.0` を維持する。GitHub Pagesの配信経路を維持する。
- 単一リポジトリの新規cloneから、開発・配布物生成・必要な検証が可能で、旧開発ディレクトリや公開専用cloneへの依存がない。
- リリースに関わる変更は[検証仕様](../spec/development/testing.md)の `Full` で確認し、下書き・送信・公開はその作業で許可された範囲だけを実施する。
- 正本の文書と実装が一致し、必要な契約を移した後に本計画を削除する。
