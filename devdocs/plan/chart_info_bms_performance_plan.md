# chart_info BMS解析時間短縮の実装計画

## 1. 目的と変更範囲

BMSの詳細解析で生成する `chart_info`、譜面文字列、診断の意味を変えずに、1譜面当たりおよび固定コーパス全体の解析時間を短縮する。

対象基準はコミット `19826e89431fc21d763ab40980f5a2ed627c3d3a`。参照会話は `3cc7d059693197a28e79c08f69a0e3773bb12b8c` を調べているが、今回の出力・性能基準には使わない。実装着手時に別のコミットを使う場合は、その版の関連経路・テストを再確認して基準結果を取り直し、途中で比較対象を変更しない。

現時点は計画の確定段階であり、基準出力・解析時間の取得と本番実装は未実施。既存の未コミット作業とは別のワークツリーで進める。

作業は「現行の基準を保存する」「設計を一括置換する」「統合結果を検証して整理する」の三工程とする。基準測定で改修対象を少しずつ選ぶ進め方にはしない。実装中の機能テストは随時実行するが、性能測定のたびに小さな最適化を追加することを作業の基本形にしない。

### 対象

BMSの字句処理、チャンネルデータの展開、タイムライン／LNの探索、確定後の集計、譜面文字列とハッシュの生成を最初の実装単位に含める。BMS経路で扱う `.bms`、`.bme`、`.bml`、`.pms` を形式の識別を保って扱う。

共通の集計・出力処理を変更する場合は、BMSONもその同じ処理を使う。BMSON向けに旧集計・旧出力処理を残す二重実装にはしない。ただし、BMSONのJSON読取り、sound channel処理、タイムライン構築の最適化は対象外とする。

### 対象外

並列度、reader数、ThreadPool、GC設定、キュー容量、DBチャンク数、I/O方式、ファイル差分の軽量パーサー、DBスキーマ、永続キャッシュ、JVMの組込み、外部ライブラリへのパーサー置換は変更しない。汎用のベンチマーク基盤やデータ構造ライブラリも作らない。

目的は解析時間の短縮であり、省メモリや省CPU自体を合格条件にはしない。ただし、新しい索引による割当が解析失敗や著しい時間増大を招く実装は採用しない。

### 現行版で確認した不足

| 経路 | 現状と置換する仕事 |
| --- | --- |
| BMS入力 | `ScanRandomMaxes` と候補ごとの `ParseBmsCandidate` が別々に行文字列を生成し、モード・イベント・ノートがチャンネルペアを再解釈する。小節別バケットと二文字の直接走査は既にあるため、再実装の目的にしない。 |
| BMSタイムライン・LN | 通常は `SortedListTimelineStore`、大入力は `TreapTimelineStore` を使う。完成LNの全件照会と全タイムラインの後方走査が残る。 |
| 共通集計 | モデル確定時の総数、統計の総数・四種類別数・速度用総数、BPM範囲・featureなどを別々に走査する。 |
| 共通出力 | タイムラインごとの `StringBuilder`、全文stringとUTF-8配列、速度要素ごとの配列を生成する。本番の `EvaluateSnapshot` は `ChartString` を利用しない。 |
| 戻り値と保存 | 現行の解析戻り値は不変の `ChartDetails`。DB行への変換は `ChartInfoStorageMapping` とDB窓口が担当する。旧計画の保存行型へ戻さない。 |

これらはソースで確認した処理構造であり、解析時間の配分や改善率を測定済みという意味ではない。

## 2. 互換性の契約

### 2.1 数値変換

`JavaDoubleParserJdk17` と `JavaDoubleToStringJdk21` の数値変換アルゴリズムおよび受理する構文は変更しない。C#標準の `double.Parse`、`TryParse`、`ToString`、`TryFormat` をこれらの代替に使わない。整数の出力に標準APIを使用することと、doubleの互換変換を置き換えることは区別する。

数値引数に文字列が必要なら、その部分の文字列化を許容する。文字列割当をなくすためにJava互換変換を迂回しない。`FormatDouble` のキャプチャ除去など、呼出し側の同値な整理は可能とする。共有書式キャッシュの有無・上限・対象値の調整は、この作業のチューニング項目にしない。

### 2.2 演算と順序

互換対象は最終的な計算式だけではなく、値を生成する順序と各演算の順序を含む。

- 小節開始の累積、小節内位置、BPM／STOPによる時刻計算の括弧・演算順・doubleからlong／intへの変換を維持する。逆数乗算、FMA、decimal、整数tickへの置換をしない。
- タイムラインは従来と同じ要求順で生成する。新しい時刻は、その時点で生成済みの先行タイムラインから計算する。
- 同一座標のイベント優先順、同一種別の入力順、通常ノートとLNの上書き・除去・背景音化を維持する。
- 最終配列の順序は現行実装と一致させる。現在の安定した時刻ソートを、性能改善に便乗して別の並びへ修正しない。
- `mainbpm` のカウント規則、ノート数0のBPMを含む登録順、同点時の選択処理を維持する。
- 空の末尾小節、BGM・BGA・不可視ノートだけの時点を、出力が少ないことを理由に削除しない。演奏長と速度変化の末尾で参照する範囲を混同しない。

### 2.3 構文・RANDOM・診断

通常のBMS decode、位置依存の予約語引数、Unicode整数、BASE 36／62、コロン後の空白、奇数長データ、壊れたチャンネル行による最大小節の更新を維持する。

予約語の `InvariantCulture` による比較と、引数・行データの切出し規則を維持する。空白だけのデータはペア数0として扱い、現在受理するコロンなしのチャンネル行では行全体がデータになる条件も維持する。BASE 62の短いBPMは元の二文字の36進再解釈を保つ。地雷は基準版の `CreateMine(value)` による解釈を固定し、[解析互換性](../spec/library/parser-compatibility.md)の一般記述に合わせるための挙動修正を今回へ混ぜない。

RANDOMの候補順・候補重複排除・分岐選択・再試行条件・タイムアウトの寿命を維持する。字句情報は共有できるが、候補ごとの状態や候補によって変化する数値解釈を共有しない。従来その候補で解釈しなかったコマンドを、前処理の都合で意味評価しない。

診断の内容・順序・回数も比較対象とする。現在のモード判定と本解析で同じ不正ペアが別々に診断される場合、変換を共有してもその観測結果は維持する。診断の重複整理は別変更とする。

タイムアウトの期限はdecode前から結果生成まで候補間で共有する。新しい字句化・展開・座標索引・集計・出力の長いループにも協調checkpointを置く。タイムアウト時の到達phaseと実時間は厳密一致の対象外とし、期限やRANDOMの再試行条件は変えない。

### 2.4 成功・失敗と版

決定的な解析失敗を成功に変えたり、別の値を返したりしない。新処理が失敗した際に旧パーサーや軽量パーサーへ切り替える経路は作らない。

時間超過は値の互換性とは別に扱う。高速化により従来の時間超過入力が同じ上限内で成功することは許容するが、その結果を現行の長時間実行結果または固定参照値で検証する。タイムアウト上限の延長や失敗件数の除外で性能改善を作らない。

保存値の意味を変えないため `parser_version` とDBスキーマは原則据え置く。既存の失敗キャッシュを全件破棄する変更は含めない。性能測定はDBの再利用・失敗省略を経由せず、実際にパーサーを呼ぶ。

この工程が完了するまでは本番パーサーを変更しない。現行バイナリと結果を保存し、改修後にも同じ入力・実行条件で比較できるようにする。

境界資産9件とBMSON527件は、格納済みLFバイト列のハッシュとmanifestの元CRLFの識別子が異なる。残る資産は一致し、差がある全件もLFからCRLFへの変換で元SHA-256と一致することを確認済み。新旧には同じ格納済みバイト列を渡し、その実MD5・SHA-256を入力識別として別に保存する。参照比較とRANDOM seedへ渡すMD5・SHA-256は既存テストと同じmanifest／DBの値を使う。原本ハッシュへ合わせて入力を書き換えたり、識別子・期待値を再生成したりしない。

### 3.2 基準出力の固定

現行の `ParseBytesDetailed` から、譜面単位で次を作業用ファイルへ保存する。

| 項目 | 比較方法 |
| --- | --- |
| `ChartDetails` の解析結果と保存列 | 全プロパティを保存し、整数・文字列・bool・nullを厳密比較する。実行日時である `updated_at` だけは値一致の対象外。DB境界での既存の保存列対応も維持する。 |
| double列 | 文字列表現や許容誤差ではなく、IEEE 754の64ビット列を保存して比較する。nullと±0も区別する。 |
| `ChartString` | 文字列全体およびUTF-8バイト列を比較する。`charthash` だけで済ませない。 |
| 診断 | severity、code、message、順序、回数を保存する。 |
| 失敗 | 入力識別、失敗分類、例外型、意味上のメッセージを保存する。経過時間など変動する値は別項目にする。 |
| 実行条件 | コミット、バイナリ識別、.NET／OS／CPU、構成、カルチャ、コーパス識別、順序、タイムアウトを保存する。 |

doubleはnullableの有無と16桁のビット列表現を保存し、NaN・InfinityもJSON数値へ変換しない。入力識別にはコーパス名、fixture ID、相対パス・拡張子、実バイト列のdigest、解析に渡したdigestとdecode条件を含める。例外時に解析入口が返さない途中診断を保存するための製品APIは追加せず、観測できる診断・例外・本番の失敗結果を比較する。

現行のBMS実譜面テストには、一部の列で参照値との差分件数を許容するものがある。そのテストに合格するだけでは、最適化による新しい差分を検知できない。固定した現行出力との全件厳密比較を追加し、既存参照値との比較も併用する。

既知の差分を直すための期待値更新は行わない。基準側ですでに起きている失敗・参照差分は、譜面と項目を特定して記録する。新旧で同じ差分件数であっても、差分対象が入れ替わっていたら不合格とする。

### 3.3 作業用の性能測定

既存のテストプロジェクトから内部パーサーを呼ぶ小さいハーネスを一時的に作る。新しい恒久プロジェクト、外部計測パッケージ、CIジョブは追加しない。

ファイル読取り、MD5／SHA-256確認、参照DB読取り、期待値比較、結果保存は時間計測の外に置く。バイト列と解析に渡すハッシュを事前に用意し、共通のbytes解析入口の呼出し開始から `ChartDetails`・診断・`charthash` の取得までを計測する。decode、入力準備、全候補の評価、索引構築、集計、出力・ハッシュは全て含める。未使用のChartStringの生成は現行のコストとして含め、改修後の本番モードでは不要な文字列化を行わない。ChartStringを返す診断モードは別プロセスで別項目として計測し、本番モードの初回を先に暖めない。

Release／x64、同じSDK・ランタイム・カルチャ、単一解析ワーカーを固定する。旧版と新版を同一プロセスへ混在させず、それぞれ別プロセスで実行する。テストケース自体の並列実行も止める。本番の並列設定は変更しない。

主指標はBMS主コーパス一巡の実経過時間と件／秒。計測外の結果検査や記録を一巡の内側へ挟まず、個別計時と結果の保持は新旧同じ方式にする。ファイル別の中央値、各巡の1,000入力に対するP95・最大、形式別・低速入力の時間を補助指標とする。5回程度の反復だけから各ファイルの安定したP95は主張しない。ワーカー別時間の合計やテストランナー全体の起動時間を解析時間にしない。

各版5回以上の独立したプロセス試行を基本とする。各プロセスで固定したmanifest順に初回を一巡し、その後の一巡をウォーム実行として別に取得する。旧→新と新→旧の実行順を交互にし、別作業のビルド・検証と同時に測定しない。全試行の値・中央値・範囲を残す。反復で書式キャッシュが温まった結果だけを、全譜面が新規の解析時間と説明しない。既知の低速入力は別枠で全件を記録し、タイムアウトを短い成功として平均へ混ぜない。

性能比較の1譜面の上限は現行本番と同じ60秒に固定する。出力固定の追加予算や既存低速テストの予算は別項目に記録し、この性能値へ混ぜない。タイムアウトを残す入力群では、全入力の経過時間・成功数・失敗数を示し、成功件だけの件／秒を全件処理量として報告しない。

出力の固定用には十分な実行予算を与えた検証と、同じ上限を用いた性能比較を分ける。時間超過で現行結果が取得できないものは、その事実を残し、固定Java参照値による検証対象として明示する。

工程0の成果物は、現行バイナリ、コーパス識別情報、基準出力、性能基準、実行条件、一時ハーネス。これらを取得した後に工程1へ進む。

## 4. 工程1：BMS解析経路を一括で置換する

以下のA～Eを一つの実装単位として完成させる。コードレビューや依存関係のためにコミットを分けることはできるが、途中の局所的な性能改善だけを完成扱いにしない。

### A. 入力を一度字句化し、候補ごとの疎な操作列を作る

`ScanRandomMaxes` と `ParseBmsCandidate` がそれぞれ行文字列を作る構造を置き換える。decode済み文字列を保持し、行・コマンド・引数・チャンネルデータはその範囲で参照する。RANDOMの事前情報もこの読取りから得る。

文字列を保持すべき題名・副題・Java互換数値変換へ渡す引数以外では、必要のない `ReadLine`／`Substring` の連鎖を避ける。予約語は毎候補で同じ比較列を実行せず、一度分類する。ただし位置依存の切出し、前後空白、BOM、比較の意味を変えない。単純な空白splitや一括のASCII限定化には置き換えない。

候補ごとにコマンドを従来順で評価する。添字付きBPMなどの定義時のBASEと、チャンネルデータを展開するときのBASEを混同しない。候補のヘッダー状態が確定してから、2文字ペアを一度変換する。

チャンネルは元のペア数と、有効な非ゼロ要素の元インデックス・値を疎に保持する。位置は元インデックス／元ペア数であり、非ゼロ要素数を分母にしない。BASE 62の再解釈が必要な処理では、元の文字も範囲から参照できるようにする。

モード判定、制御イベント生成、ノート適用はこの展開結果を共有する。不正ペアの位置情報を保持し、診断は変換時に一括出力せず、従来の観測点で再生する。モード判定は入力行順で各行の最初の有効非ゼロペアまでの診断だけを再生し、PMSではモード判定自体を省く。制御イベントは小節開始タイムラインを要求した後に行順・ペア順で収集し、その診断を出してから適用する。ノート・BGM・BGAは行順・ペア順に診断と適用を交互に行う。未知チャンネルなどモード判定だけで読む行の、短絡後の要素を新たに意味評価しない。

この結果から「小節開始、イベント収集時の診断、制御イベント、元の行順のノート／リソース操作」を表すBMS専用の操作列を作る。制御イベントの比較は小節内の `Position`、Scroll→BPM→STOP、入力 `Sequence` の順を維持する。負の小節長で物理座標が逆転する場合や、0長・丸めで座標が重なる場合も物理座標順へ置き換えない。操作列には索引準備に必要な情報を持たせるが、前処理で将来の演算・診断・失敗を実際の適用より先に観測させない。

### B. 座標索引と遅延生成でタイムライン・LN探索を置き換える

#### 採用構成

操作列が要求する小節座標を集め、現行と同じキー比較で整列・重複排除し、整数の位置番号を割り当てる。各操作にはその位置番号を付ける。

タイムラインの本体は位置番号に対応する配列へ置く。生成済みの位置とレーン別の現存ノート位置は、位置番号に対する更新・累積個数・順位選択ができる索引で管理する。実装は配列ベースのFenwick treeを基本とし、解析器内部の小さい補助型に限定する。

BMSの通常／巨大入力を `SortedListTimelineStore` と `TreapTimelineStore` へ分ける仕組みは、この方式に統一する。入力サイズに応じた閾値調整や第三のストアを追加しない。

#### 時刻互換の維持

座標が索引に存在することと、タイムラインが生成済みであることを厳密に分ける。操作列を従来順に再生し、初回要求時だけ生成済み索引から先行位置を求め、従来の式で時刻を生成して有効化する。

将来の座標は先行位置候補にならない。厳密な先行位置がなければ、その時点の生成済み最小座標を使う現行の `LowerEntry` を維持し、基点0への固定参照にしない。キーの同値は `double.CompareTo == 0` とし、±0を別スロットにしない。座標圧縮は順位付けにだけ使い、時刻計算を整数順位や別の座標代表値から行わない。同値とされる座標でも、最初の実際の生成要求で渡されたdoubleをタイムラインへ保持する。

NaN・Infinityを前処理で拒否しない。現行では非有限座標のタイムライン生成時に非有限時刻となり、挿入前の `ToCheckedMicroseconds` で失敗する。同じ遅延生成点で失敗し、要素がなく非有限長が次の要求座標へ影響しない最終小節まで拒否しない。非有限キーでの旧ストア間の後方探索差は、この生成失敗により本番LN探索へ到達しない。

最終配列化では生成済みのタイムラインだけを対象にし、現行と同じ順序を一度確定する。未生成の索引スロットを空タイムラインとして出力しない。

#### LN処理

| 処理 | 新しい探索 |
| --- | --- |
| LNOBJ | 対象レーンで、現在位置より前にある最後の現存ノートを直接取得する。最後のノートが地雷・既対応LNだった場合も、それを飛ばしてさらに昔の通常ノートへ進めない。 |
| LN専用チャンネルの途中ノート除去 | 始点が終点より前なら両端を除く現存ノートを降順に除去し、生成済み始点タイムラインへの到達で対を作る。始点が終点と同じ／後なら終点より前の全現存ノートを除去し、対を作らずpendingを残す。通常ノートの背景音化を同時に反映する。 |
| 既存LN範囲内かの判定 | 完成したLNの区間を位置番号の範囲加算として記録し、照会位置の被覆数を累積和で得る。BMSの両端を含む判定を維持する。 |
| ノートの置換・削除・未閉鎖LN除去 | BMS内の単一の更新口を通し、本体と現存ノート位置索引を同時更新する。 |

完成LNの被覆と、現在見えているノートの有無は別の意味である。現行の完成LNリストに残る区間は、後の上書き・削除で見えなくなっても被覆から勝手に除去しない。逆向きなど従来の包含条件が成立しない区間も、新たに有効な区間へ正規化しない。

始点到達は生成済みタイムラインの `Section == start.Section` で判定する。始点セルが空・別ノートでも到達したものとし、現存ノート索引や参照一致だけで閉鎖可否を決めない。未閉鎖始点や被覆内のpendingの除去は、そのセルの現在値を除去する既存動作を維持し、古いノートの `Owner` を消さない。

レーン別索引は、疎な操作列と候補のLN設定から必要なレーンを事前に判定して作り、該当レーンの最初のノート操作から更新する。LN終端が初めて出現した時点で空の索引を作り、以前の通常ノートを見失う実装にはしない。通常譜面にも将来の拡張用索引を一律に作る設計にはしない。索引は候補解析の寿命内だけの作業データとする。

現存ノート索引が必要なのは、最終LNOBJに一致する通常チャンネル要素か専用LN要素のあるレーン。被覆索引はそのLN生成候補と専用LN／地雷の包含照会があるレーンに限る。通常・LN・地雷のnull境界だけ現存数を更新し、非null同士の置換は数を変えない。不可視ノートは含めない。レーンごとに必要な書込み・照会座標を圧縮し、全レーン×全タイムラインの配列を一律確保しない。BMS専用のノート更新口に索引責務を置き、BMSON共通の `ChartTimeline.SetNote` へ持ち込まない。

### C. ノート確定後の集計を共有する

LN処理と未閉鎖始点の除去が終わる前に、最終統計を確定しない。

第一の走査で `notes / n / ln / s / ls`、タイムライン別のカウント、BPM範囲、feature、BGA有無、演奏長に必要な情報を集める。その結果で難易度推定と既定TOTALを確定する。

第二の走査で分布・レーン別情報を作り、同じ確定済み情報から速度変化と主BPMを生成する。既存の4回の `CountNotes` や、速度集計のためのレーン再走査は削除する。TOTALが確定しないと境界位置を決められないため、無理に一回の走査にまとめない。

総ノート数のLN終端条件と、分布・レーン別情報のLN終端条件を同一視しない。地雷を含む境界カウントや、ノート0のタイムラインも従来どおり扱う。

長いLNの継続数は、秒ごとの逐次加算をやめる。有効な非空区間について始点秒に+1、終点の次の秒に-1を記録し、秒配列の最終走査で累積する。終点の次がバケット末尾なら累積用の終端として扱う。始点秒が終点秒より後の空区間では加算をしないが、ノートごとの既存の減算は維持する。始点・終点での減算、同じ秒で終わるLN、配列外入力の失敗を既存と合わせる。範囲のclampによる救済はしない。

密度・終盤窓・分布文字列の生成では、確定済みの秒データを共有する。整数の計算規則、doubleへ変換する位置、窓の開始／終端条件は変えない。

### D. 出力を一つの実装へ統合する

ChartString相当のUTF-8バイト列を、伸長可能な一つの連続バッファへ書く。各タイムラインの開始位置を記録し、出力不要の行は書込み位置を戻す。行ごとの `StringBuilder`、LNマーカー配列、全文stringを経由するためだけのコピーをなくす。

doubleの出力は必ず `JavaDoubleToStringJdk21` の結果を使う。整数の書式・符号・改行・区切りも現行と合わせ、文字列のASCII決め打ちによる置換や文字欠落を起こさない。譜面文字列の `StringBuilder.Append` の整数書式と、既にInvariantCultureを使う保存文字列を同一視せず、同じカルチャで比較する。LN記号と音声長の整数加算、終端セルの空表現を維持する。出力不要の行で現在BPMを更新するなど、書込み位置を戻しても残る状態更新も現行と揃える。

完成したバイト列を一度でSHA-256へ渡す。ノート単位・行単位でハッシュAPIを呼ぶ逐次方式にはしない。全文バッファを持つこと自体を避けるために解析時間を犠牲にしない。

本番はrow・診断・hashだけを返す。検証で明示的に要求した場合だけ同じバイト列からChartStringを作る。`ParseBytesDetailed` の既存利用者が必要とする文字列取得の動作を維持し、`ChartInfoBuildService.EvaluateSnapshot` などの本番呼出しは文字列保持を要求しない入口へ接続する。旧・新で別の書式処理は持たない。

同じ解析本体へ文字列保持の要求を渡す。既存の詳細入口の既定動作は保持あり、`ParseBytes`／`Parse` と本番の `EvaluateSnapshot` は保持なしとする。保持しない結果の `ChartString` はnullableの契約で表し、空文字列で取得済みと見せない。これ以外の戻り値・診断・timeout・保存の契約は変えない。

`speedchange` の要素ごとの `double[]` と `SelectMany`、レーン情報の不要な中間列挙も、保存する文字列へ直接書く処理へ置き換える。`speedchange` の時刻も、整数に見えることを理由にJavaのdouble書式を省かない。

### E. 接続と旧処理の削除

`Parse`、`ParseBytes`、詳細解析、file diff inline、導入後解析、backfillが同じ新しい解析本体へ到達することを確認する。file diff／backfillの並列・保存構造は変更しない。

不要になった二重行走査、チャンネルの再変換、旧BMSストアと切替閾値・選択用カウント、タイムライン全体のLN後方走査、BMS完成LNリストと全件探索、重複統計計算、行単位出力を削除する。BMSON固有構築が使う `CreateLaneLists`／`IsInsideLongNote` などの共通補助は残すが、旧BMSストアや旧集計・出力の存置理由にはしない。旧パーサーは比較用バイナリ／作業ツリーにだけ残し、製品内の切替・フォールバックとして残さない。

## 8. 記録と整理

一時ハーネス、全件出力スナップショット、性能測定結果は改善作業の判断材料とし、恒久テストへ昇格させない。現行バイナリも製品へ含めない。追加した小さい機能回帰テストは残す。

位置索引を導入する場合は、一つのADRに次の設計理由を記録する。

- 座標の事前索引化と時刻の遅延生成を分ける理由。整列済み座標から一括で時刻を再計算しない理由。
- 現存ノート索引と完成LN被覆を分ける理由。必要な作業中状態であり、将来用途のキャッシュではないこと。
- Javaの数値互換処理を維持する理由。
- UTF-8全文バッファの一括ハッシュを選び、小刻みな逐次ハッシュを採用しない理由。

ADRには一般化できる決定とトレードオフを残す。測定結果を残す場合はコミット・コーパス・環境を限定し、将来版の速度保証にしない。個々の作業履歴や環境依存の絶対パスは残さない。

## 9. 完了形

```text
       既存資産の検証 → 現行出力の厳密スナップショット → 基準時間

工程1：一つのBMS解析経路へ一括置換
       字句範囲の共有・疎な操作列
       → 座標索引・従来順の遅延生成・LN索引
       → ノート確定後の共有集計
       → 共通UTF-8出力・一括ハッシュ
       → 全入口の接続・旧処理削除

工程2：全件互換検証 → 同条件の最終性能比較
       → 作業用資産の整理 → 必要なADRと機能回帰テストのみ残す
```
