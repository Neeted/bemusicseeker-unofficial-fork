## 現行情報の維持

現行ツリーには、現在も適用する仕様・運用・設計判断と、未完了作業に必要な情報だけを置きます。開発の経緯、完了記録、置換済みの仕様は Git 履歴で参照します。完了計画を別の場所へ移す、短い案内だけを残す、検索除外で温存する、といった扱いはしません。

計画や旧資料を退役させる前に、現在も必要な情報を次の正本へ移します。

| 移管先 | 残す情報 |
| --- | --- |
| `spec/` | 現行の入力条件、失敗時の保証・非保証、検証の入力条件・期待結果と既存の実装・テストの対応。 |
| `decisions/` | 現在も適用する採用理由・不採用理由と、その判断の制約。 |
| 未完了の計画 | 具体的な残作業、優先順位、依存関係、利用前に満たす条件。 |

同じ差分のレビューで移管先を確認し、現行の実装・テストに置き換わった古い契約をそのまま復活させません。移管後は、計画・作業専用の設計書・調査メモ・検証記録を削除し、参照元も同じ変更で更新・削除します。履歴台帳や旧番号の対応表は作りません。

設計判断は、過去に作られたという理由では削除しません。現行設計の根拠として有効な背景・代替案を残し、判断が変わったときは本文を更新します。測定資料も、現在の比較用途と測定条件を示せる範囲だけ残します。対象コミットや測定日は適用条件であり、過去の結果を現行実装の実績とは扱いません。通常の成功報告を保存するための移管は行いません。

## 書き方

開発資料の本文は自然な日本語で書きます。製品名、コード識別子、コマンド、外部標準の正式名称は原表記を保ち、コード識別子はバッククォートで囲みます。専門概念は[共通用語集](spec/glossary.md)で定義し、機能固有の用語だけを各文書の冒頭で補います。一般の説明に英単語を混ぜず、同じ概念には同じ日本語名を使います。

仕様は[仕様書の書式](spec/README.md#仕様書の書式)、補助図は[Mermaidの運用](spec/README.md#補助図mermaid)、計画は[計画の運用](plan/README.md#運用)に従います。一つの契約を複数の文書へ複製せず、正本を定めてリンクします。読み順はディレクトリの `README.md` に集約し、単なる目次を目的とする仕様書は作りません。

恒久的なファイル名・見出し・テスト名は、機能、入力条件、期待結果で表します。実装順を表す段階番号や作業専用の識別子を持ち込まず、計画と引継ぎの中だけで使います。外部規格の番号、DBのスキーマ版、製品の正式なバージョンは、この制限の対象ではありません。

ルートREADMEの開発参加など、リポジトリ上でだけ表示する案内は、前後に空行を置いた`<div class="repository-only" markdown="1">`と`</div>`で囲みます。[HTML生成](../scripts/build-doc-html.py)では、その範囲を配布用・公開サイト用HTMLの本文と目次から除外します。利用者向け文書のリンク検証は省略しません。

## 利用者向け文書の編集方針

リリースノート、ユーザーマニュアル、利用者向けREADMEや操作ガイドに適用します。文章の粒度は、[v3.1.0.0のリリースノート](../release%20notes/v3.1.0.0%20リリースノート.md)を参考にします。

### 共通の書き方

- 機能・操作・結果を優先し、「何ができるか」「どう操作するか」「どういう結果になるか」を中心に説明します。
- 設定の選択や操作結果の理解に必要な粒度で書きます。対応形式、設定値、保存先、検索構文など、利用者が使う情報は具体的に示します。内部クラス、スレッド、資源解放、DB内部の更新手順など、操作に不要な実装詳細は開発資料を正本とし、利用者向け文書へ複写しません。
- 正常な操作の説明へ、異常系の振る舞い、細かい注意、非保証の説明を途中で差し込みません。「行わないこと」は、操作結果の誤解を防ぐ場合や利用者の判断に影響する場合に限って短く説明します。
- 必要な注意は通常の説明から独立させます。マニュアル・操作ガイドでは、関連する操作の近くに `> [!CAUTION]` ブロックで書きます。削除・上書き、事前バックアップ、重要な既知の制約など、利用者の行動や設定選択に影響するものに絞り、取り返しのつかない操作では実行手順より前に置きます。不要な説明を注意欄へ移して温存しません。
- 問題が起きた後の対処はFAQ・トラブルシューティングへまとめます。通常の操作説明から案内が必要なら、その節へリンクします。
- 画面上の名称と用語を揃え、自然な文章で書きます。日英の文書では、説明する機能・条件・操作を対応させます。

### ユーザーマニュアル

- 現在の機能と使い方を説明し、目的、必要な準備、操作、結果を中心に、必要な情報だけを書きます。選択肢の比較には表、操作の理解には具体例を使います。
- 別の機能・操作へ移る箇所には、内容が分かる見出しを付けます。複数の機能・操作を段落の区切りだけで並べません。
- 同じ階層の見出しは同じ粒度に揃え、関連する設定や操作をその下へまとめます。一つの機能の説明は見出しの下でつながった文章にし、段落ごとに見出しを増やしません。
- 目次と見出しだけで、使いたい機能・操作へ辿れる構成にします。見出しを変更・追加するときは、目次と参照元も合わせて更新します。

### リリースノート

- 比較起点と記載対象を先に定め、対象版の最終状態で利用者に見える変化を機能別にまとめます。公開済み修正の再掲範囲は依頼に合わせます。
- コミットメッセージを調査の手掛かりにし、必要に応じて実装も確認します。比較起点後に追加され、対象版までに削除された機能、置換済みの実装、途中の変更で生じて解消した不具合を変更点へ計上せず、既存機能を新機能として書きません。比較起点に存在した機能の廃止は、利用者に見える変更として記載します。
- 機能の追加、使い勝手、性能、互換性など、前回版から利用者にとって何が変わるかを簡潔に説明します。内部整理の履歴や細かい失敗経路は列挙しません。
- 更新時の注意は、設定の見直しや操作の判断に必要な変更・制約に絞り、変更点の説明から独立させます。
- 確定版では草案・暫定版の注記を除去し、冒頭に日英のオンラインマニュアル案内と配布ファイルの案内を置きます。配布ファイル名と日英の本文を対象版に揃えます。

### Markdownと生成HTML

マニュアルの編集元は[日本語Markdown](../docs/manual.ja.md)と[英語Markdown](../docs/manual.md)です。生成HTMLは直接編集せず、[PythonのHTML生成スクリプト](../scripts/build-doc-html.py)で再生成します。公開サイト用の生成コマンドと反映手順は[リリース手順](spec/development/release.md#維持する配信資源)を参照します。

本文・画像の変更をHTMLへ反映するときは、生成処理のリンク検証を有効にし、生成後の目次・リンク・画像・Caution表示を確認します。編集方針など開発資料だけの変更では、マニュアルHTMLの再生成は不要です。

## 文書変更の確認

相対リンクと見出しへの参照、目次からの到達、コード・テストの参照先、UTF-8・LF・差分の空白エラーを確認します。移動・削除した文書は、Markdownリンクだけでなく、通知文書などの通常の文章中のパスと、文書を入力として読むコード・テスト・スクリプトからも検索し、参照を同時に更新します。参照更新を理由に、検証する契約や許可対象を広げません。

図を追加・変更した場合は、[補助図の更新と確認](spec/README.md#更新と確認)に従います。
