# 開発資料

このディレクトリは開発者向け資料の置き場です。ユーザー向けの説明は `docs/` に置きます。

## 分類

| 配置 | 役割 |
| --- | --- |
| `spec/` | 現行仕様と採用済みの設計・性能要件。現行挙動と未実装・未検証の要件を区別し、実装とテストへの入口を示す。 |
| `plan/` | 進行中・着手待ち・再開予定の作業の目的・完了条件・進捗と、再開に必要な設計や判断。完了時は必要な内容を正本へ引き継いで削除する。 |
| `decisions/` | 現在も適用する設計判断の採用理由、代替案、背景。採用した契約の本文は `spec/` へ統合する。判断の変更履歴は置かない。 |
| `acceptance/` | 現行の設計・性能判断や比較基準として使う測定・観測根拠。現在の参照用途、対象コミット、データ、環境、条件と結論を揃え、その条件下の結果として読む。 |
| `everything/` | Everything の仕様差や外部挙動の観測。回避策や設計判断の背景として読む。 |

## 現行情報の維持

リポジトリの現行ツリーには、現行仕様・運用、現在も適用する設計判断、未完了の作業に必要な情報だけを置く。古い計画や実装順が `rg` などの通常検索から現行の根拠へ混入しないよう、開発の経緯・完了記録・置換済みの仕様は Git 履歴だけで参照する。別ディレクトリへの移動、短い完了記録や削除済み資料の案内ファイル、検索除外設定で保存を続ける運用にはしない。

設計判断は過去に決めたという理由だけで削除しない。現在の設計を選ぶ理由として有効な背景・代替案・制約を `decisions/` に残し、変更時は現行の判断へ更新する。現在も必要な理由は引き継ぎ、適用しなくなった判断や変更の時系列は残さない。

測定・観測資料も、現在の比較基準や設計根拠として必要な範囲だけを残す。測定日や対象コミットは適用条件を特定する情報であり、過去の測定を現行実装の実績と読み替えない。通常の作業ログやテスト成功報告を履歴保存のために `acceptance/`・`decisions/` などへ移さない。参照用途を失った資料は、参照元と併せて更新・削除する。

既存資料にも関連作業の完了・変更時にこの方針を適用し、恒久契約や未解決事項を失わないことを確認する。退役のための履歴台帳や旧 ID の対応表は新設しない。

## 書き方

本文とコメントは原則日本語で書き、コードの識別子、コマンド、製品名、外部仕様の正式名称は原表記を使う。繰り返し使う専門概念は、文書の冒頭に「日本語名・意味・対応するコード名または原語」を置き、本文では日本語名を使う。共通の概念はその正本の用語表を参照し、機能固有の概念だけを各仕様で補う。

仕様の共通書式は [spec/README.md](spec/README.md#仕様書の書式)、計画の書式は [plan/README.md](plan/README.md#運用) を正本とする。既存文書は変更対象の節からこの書式へ揃える。

## 命名

- `*-plan.md`: 未完了の作業計画。完了後の履歴ファイルにはしない。
- `*-note.md`: 進行中の調査メモや、現在も参照する外部仕様の観測根拠。
- 恒久文書: 機能・契約を表す名前を使い、計画の段階名・実装順の番号をファイル名や見出しへ引き継がない。仕様本文は `spec/`、採用理由は `decisions/` に置く。

## 読み方

現行仕様を確認したい場合は、まず `spec/README.md` から読む。データ規模、処理速度の優先順位、性能退行の判定は [performance-and-scale.md](spec/performance-and-scale.md) を正本とする。未完了の作業は `plan/README.md` と対象計画を読み、過去の経緯が必要な場合だけ `git log`・`git show` で履歴を調べる。過去の計画や判断は、現行仕様の根拠としてそのまま採用しない。
