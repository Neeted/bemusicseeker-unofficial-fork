# ライブラリ変更を操作単位に集約する理由

## 適用する判断

一回の利用者操作に一つの `LibraryMutationSession` を使い、成功した物理変更を集めてDB・索引・関連参照・通知へ反映します。単一対象も同じ経路を使います。操作の契約は[ライブラリ変更](../spec/library/mutations.md)を正本とします。

## 背景と選択理由

対象ごとのファイル処理や、先行対象の成功に依存する導入判定には逐次性があります。しかし、各対象でDB保存と全ての派生反映を完結させる必要はありません。先行成功のハッシュと実際の導入先を操作中の一時状態に加えれば、未実行・拒否・失敗・取消を所持と誤認せず、後続を判断できます。

DBの確定をこの連絡手段にすると、同じ索引・LR2同期・公開を対象数だけ繰り返します。そのため、物理成功の収集と正本への反映を分け、`Commit` が各管理主体を一回呼びます。一時状態は保存せず、公開済みの世代番号やDB確定結果の代わりにはしません。

## 保存と失敗の境界

全DBとファイル操作を一つの物理トランザクションにはしません。各管理主体の書込み範囲は維持し、一体で保存すべき導入行などは同じトランザクションに置きます。SQL引数上限に応じた内部の分割は許可します。

予期しない物理失敗では依存する後続を止め、確認できた成功集合に一回の確定を試みます。DB失敗、確定後の必須反映失敗、後片付け失敗は別々に保持します。確定失敗を理由に全ファイル変更の巻戻し・再実行を追加しません。

上書き元・先の保全に必要な仮置きとバックアップ、局所的な一回の補償は残します。局所結果は `FileDbMutationReceipt`、操作全体は `LibraryMutationSessionReceipt` で扱います。導入元の後片付けは永続確定後に行い、その失敗で正本への反映を繰り返しません。

統合後のリソース保守も同じ操作の必須後処理です。既存の予約解放・再取得は維持しますが、第二の変更セッションや別の成功報告には分割しません。保留だけの追加・削除・設定は、所持カタログを変えない限り `PackageLifecycleOwner` に留めます。

## 採用しない代替案

| 案 | 採用しない理由 |
| --- | --- |
| パッケージごとのDB確定 | 成功依存の表現に、対象数分の反映・公開を要求する。 |
| ファイルと全DBの擬似的な単一トランザクション | 管理範囲を越える巻戻し・再実行と保存状態を増やす。 |
| 操作後の全カタログ・逆引き再構築 | 局所変更には確定した旧新の差分を使える。 |
| 自動リネーム専用のLR2先行捕捉・通知 | 共通の確定結果から同じ局所問い合わせができ、二重実行が不要。 |
| 診断名の文字列による方針分岐 | 診断と挙動が結合する。通知などの方針は型付きの値で渡せる。 |
