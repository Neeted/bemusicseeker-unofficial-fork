# INSTL DST のメタデータ照合方式を選ぶ設計判断

## 目的と適用範囲

推定で選択した導入先候補に適用するメタデータ判定の採用理由を示します。実行契約と実装・テストの対応は[導入先の推定](../spec/library/install-estimation.md)を正本とします。

## 判断

INSTL DSTはリソースの相対キー・逆引き、または既所持ハッシュで候補範囲を得て、通常は作品との関連性を優先して候補を選ぶ。TITLE / ARTISTは分類と表示根拠、自動設定可否に共通の実在ペアを使う。この用途では曲名・副題を言語学的に正確に分けるよりも、**同じフォルダの差分表記を吸収し、リソースで区別できる別フォルダを過度に同一視しないこと**が重要である。

この目的に対して、次を採用する。

- TITLEは先頭から削らず、最後の区切り群から処理し、**右から削る範囲の最も右の `mix` の直後で切る**。部分一致で`remix`、`Himix`、`mixed`も対象とする。区切り文字の開始位置、先頭保護、閉じ忘れの受理は同じ規則で処理する。
- BMSは分離済みの原題・元作者を使う。bmsonは原題と現在の作者を使い、合成作者も同じ正規化へ渡す。形式ごとの入力選択を対象側・所持側で揃え、保存形式や別名義の推定による補完は加えない。
- ARTISTは役割境界で副役割の区間を除き、後続の明示された音楽制作担当から保持を再開する。これにより、客演名が異なっても同じ制作担当へ照合でき、異なるリミックス作者は区別できる。純副役割の複合は除去し、制作担当を含む兼任だけを一括保持する。`SKY.` のような名義の記号や `q/stol` のような名義内スラッシュは残す。保持区間の末尾にある括弧・区切りの整理は全体保持時も共通とし、閉じ括弧の修復や原文の再構成は行わない。認識条件は[導入先の推定](../spec/library/install-estimation.md#比較用の基本情報と導入先の代表ペア)に集約する。
- TITLEの空文字は無効。ARTISTの空文字は有効な比較値であり、空文字と空文字だけが一致する。
- フォルダ代表は独立したTITLE・ARTIST最頻値でなく、**同一譜面に実在する正規化 `(TITLE, ARTIST)` ペアの最頻値**を使う。
- 高いメタデータ一致の条件は、**最頻ペア同士でTITLEの文字2-gram Dice係数0.72以上、かつ正規化ARTISTの完全一致**とする。Strong不成立なら候補側の全実在ペアでTITLEまたはARTISTのDice0.50以上をRelatedとして残す。TITLE完全一致だけを高確信度にする旧分岐は廃止する。

## 比較の考え方

以下の集計はTITLE正規化方式を比較した固定データによるもので、ARTISTは `obj`・`note`・`notes` とスラッシュ以降を除く条件で測定している。現行のARTIST正規化による再測定値ではない。

`path`の直接の親ディレクトリをフォルダとして、`song`と`bmson_song`の合計**214,217譜面・30,783フォルダ**を分析した。空TITLEなどを除いた有効フォルダは30,765、同フォルダを1譜面ずつ除外して代表ペアと照合できた対象は208,969譜面である。

正解ラベルとして同曲・別曲を保証する情報はないため、以下の**二つの代理指標**を使った。

1. **フォルダ内の分裂**：各フォルダ内で正規化TITLEが何種類に分かれるかを数え、全フォルダについて加算する。同じフォルダの差分名の違いで代表値が割れすぎないことを重視する。各譜面を一度除外し、残りの代表ペアへの高一致率も測る。
2. **フォルダ間の衝突**：異なるフォルダの代表ペアについて、TITLE強類似かつARTIST完全一致になる組数を数える。高い衝突数は検討対象だが、別フォルダが別曲である保証はないので「誤判定数」と呼ばない。

この測定に**リソース一致による事前候補絞込みは適用していない**。実運用より広いフォルダ組を比較していることを踏まえて判断する。

## 検討した候補の比較

| TITLE正規化方式 | フォルダ別TITLEグループ総数 | 同フォルダの最頻ペア高一致率 | 別フォルダのペア衝突組数 |
| --- | ---: | ---: | ---: |
| 共通整理だけ | 129,492 | 43.54% | 1,205 |
| 変更前：最初の区切りで切断 | 43,853 | 86.97% | 1,963 |
| 末尾の1組だけ切断 | 45,877 | 84.81% | 1,681 |
| 末尾の区切りを連続除去 | 43,194 | 87.30% | 1,967 |
| 最後の区切り群で切断 | 42,991 | 87.41% | 1,969 |
| 最後の区切り群で切断しMIX範囲を丸ごと保護 | 45,022 | 86.50% | 1,859 |
| **採用方式：MIXの直後で切断** | **44,344** | **86.71%** | **1,862** |

各行は比較対象のTITLE正規化だけを変え、同じ**最頻TITLE/ARTISTペア・強類似TITLE＋完全一致ARTIST**を適用した指標である。「変更前」の行も変更前の製品の高確信度ロジックではなく、新しいペア条件に換算した比較値である。

### 採用理由

**変更前の方式はフォルダ内の差分表記をまとめられるが、最初に現れた区切りで後半を消しすぎる。** 例えば、主題の途中に括弧があるタイトルや複数のMix名を、その前で切り落とす。「最後の1組だけ」の方式では、`VIEW [Portable Disco Mix]`と`VIEW [Portable Disco Mix] [H14]`が別キーになり、変更前から高一致を失う譜面も多かった。最後の区切り群を切る方式で、この不必要な分裂が改善した。

一方、**区切り群だけで判断するとMix名まで削って別版を同一視する**。`夏草の線路`と`夏草の線路 -J-Trance remix-`、`Toki [ANOTHER]`と`Toki (Sound piercer's Timesucker Remix) [SP ANOTHER]`、複数の`Air`のリミックスは区別したい。

「Mixを含む括弧全体は残す」方式は、`Ark (remix/5keys)`と`Ark (remix/10keys)`のように**Mix名と譜面名が同じ囲みに入る場合**に分裂する。そのため、Mix範囲の保護を`mix`直後までに狭めた。結果は、囲み全体を残す方式に比べて**フォルダ別グループが678減少**、同フォルダのペア高一致が**180,768→181,198件（+430）**、別フォルダの衝突が**1,859→1,862組（純増3）**。新規衝突4組・解消1組という内訳も確認している。

この小幅な衝突増と、キーが`Ark (remix`のように括弧途中で終わることは、**照合の仕様として受容する**。代表表示は照合キーの小文字化前の表記とし、TITLE・ARTISTの整理後の値を採用した同一レコードから得る。表示専用の第二の切断規則は作らない。

### ペア判定を一条件にする理由

「TITLEが完全一致ならARTISTが違っても強い根拠」「TITLEが強類似ならARTIST完全一致を要求」「実在ペア完全一致なら強い根拠」といった複数の基準は、TITLEとARTISTの役割が場面で変わる。照合条件を`TITLE強類似 && ARTIST完全一致`に統一すれば、**メタデータがどの理由で自動適用を許したかを一意に説明できる**。独立した最頻値の組合せによる「実際には存在しないペア」の比較もなくなる。

ARTIST空文字を不成立としてしまうと、従来TITLEだけで識別できた譜面に対して条件が過度に厳しくなる。空文字を**通常の値**として扱えば、両側とも欠如している場合にだけ一致する。調査対象では有効TITLE・空ARTISTの621譜面があり、同フォルダ1譜面除外の高一致は339件。空ARTIST同士の別フォルダ衝突は0組だった。この許容を、非空ARTISTとの曖昧一致へ広げない。

## 残る衝突をどう扱うか

採用方式での別フォルダ衝突は**1,862組**（TITLE完全一致1,393、強類似のみ469）。関与するのは1,643フォルダであり、例えば`lamellibrachia` / `guna`のような同名キーが25フォルダにあれば、それだけで300組となる。別配置・差分フォルダを含み、全てが異曲とは限らない。

残る例には、同じ作者の別Mixが強類似0.88以上に入るものもある。MIXを保護しても、`Battlekeys Megamix '18 (LV Mix)` と `Battlekeys Megamix '18 (FR Mix)` は0.90となる。逆に、Mix以外の語を区切り群内に持つ別題を同一視する例もある。これは**別Mixの完全分離までは保証しない**ことを意味する。今回の目的は、リソースによる事前絞り込みと組み合わせて、過度な不一致を避けながら誤確定の危険を減らすことである。

同一フォルダにタイトル改変系の譜面があり得るため、同フォルダ高一致率を100%にする必要はない。同様に、別フォルダが別曲とは限らないため、衝突0組も目標にしない。辞書・例外・第二の判定規則を追加して両方を無理にゼロへ近づけるより、**一貫したキー生成と単一の高一致条件を採用する**。

## 採用しない代替案

| 代替案 | 今回採用しない理由 |
| --- | --- |
| 難易度名・差分名を列挙して削除 | `laner+`、`athlete`、`robo`、`ZOI`など、自由な差分名が存在し、語彙辞書では吸収できない。 |
| TITLEを最初の括弧から無条件に削る | 主題の途中の括弧や版名を過剰に削り、異なるフォルダの識別に必要な部分が失われる。 |
| 最後の括弧を1組だけ削る | 同じMix名と差分名が並ぶと同フォルダ内が割れる。 |
| Mixを含む囲みを丸ごと残す | Mixと譜面区分が一緒に入った括弧を統合できない。 |
| TITLE完全一致だけを高確信度とする | ARTISTの相違を無視する。 |
| TITLE・ARTISTを独立最頻で集計する | 実在しないTITLE/ARTISTの組を作り得る。 |
| 空ARTISTを禁止、または任意文字列へ一致させる | 前者は有効なTITLEだけの譜面を落とし、後者は作者を指定した相手にも不確かな一致を作る。 |
| リソースが弱い場合のTITLE単独救済、旧キーへのフォールバック | 事前の候補判定や自動確定条件の意味が複数に分かれ、失敗を隠す。 |
| 衝突ゼロ・高一致100%を目標に例外を足す | フォルダの同曲／別曲が保証されていない代理評価への過剰適合となる。 |

## 関連性とリソースを分ける理由

連番・普遍的な音源名では、要求音源が揃っても作品を特定できない。全音源同梱では多くの候補が100%になり、追加音源の多い既存作品はJaccardで不利にもなる。通常はStrong→Relatedの関連性を優先し、非関連を除外する。両方改変された差分には一操作の明示保持モードを用意し、リソース優先で確認できるようにする。非Strongを自動設定せず、先頭拒否を下位候補への乗換えで隠さない。

事前実験は214,225譜面・30,782フォルダで、原所属とそれ以外の全6,594,059,725組を比較した。Pythonへ移植した正規化とC++20のUTF-16・重複2-gramモデルによる値であり、現行.NET製品の自動確定正答率ではない。

| 条件 | 原所属保持率 | 別フォルダ一致率 |
| --- | ---: | ---: |
| 最頻TITLE≥0.88かつ作者完全一致 | 88.6409% | 0.000286% |
| 最頻TITLE≥0.72かつ作者完全一致 | 90.2514% | 0.000359% |
| 最頻TITLEまたはARTIST≥0.50 | 97.2207% | 0.147032% |
| 複数ペアのTITLEまたはARTIST≥0.50 | 99.7728% | 0.1610% |

複数ペアの原所属評価だけは対象自身を除いて比較材料が残る209,040譜面が母数で、208,565譜面を保持した。他の原所属評価の母数214,225とは異なる。別フォルダ一致率は全組合せを母数とし、別配置や同作者を含むため誤導入率ではない。

Strong緩和で約3,450譜面を保持できる一方、別フォルダ一致も増える。多作品音源セットでは代表作品と対象の両Diceが0になるため、係数だけでは改善できない。Relatedだけ候補の既存全ペアへ広げ、根拠に選んだ実在ペアを表示する。0.40では保持が73譜面増えるが別フォルダ一致率は0.3846%へ増え、0.60では原所属保持率99.7135%となったため0.50を採用した。未知の表記改変を将来99%以上判別する保証ではない。

同梱充足、候補自身の一致、許可を一つの加重得点にしない。同梱sと不足補完DからU=s+Dを計算し、同梱100%でも候補自身Mで結び付きを比較する。Jaccardは補助順位へ残し、その差だけで高確信度にしない。Precisionは独立した順位情報を持たず削除する。

事前性能モデルは約1,181万音源パスから768万種のキー・1,156万件のフォルダ登録を作り、要求100～1,000・同梱条件別の480合成ケースを5回反復した。500要求・22,116候補では候補ごとの約1,106万回照合に対し、逆引き訪問は296,256登録だった。頻出名96ケースの14件で最初のStrongが11位以降、最深170位にあり、3件・10件の探索打切りを採用しない。全候補を逆引き集計し、プロフィール構築を同じ世代・バッチで共有する。

このモデルはLinux/C++20とPythonで、Relatedの作者曖昧一致・複数ペア・根拠選択、画像・動画・祖先抑制・GC・UI終端を測っていない。計画の時間値を.NET製品の実績や合否時間へ転記しない。最終実装は明示性能検査で初回・再利用、単体・20入力、逐次・有界並列を分けて測る。

メタデータ事前実験の正規化基準は `74e8288946df8136a5bd5ce1ce936451b11b09aa`、逆引き性能モデルの実装構造の基準は `3ef49954427da124f1499004e9c98ee424f99a02` である。これらは実験の適用条件であり、現在の製品版の測定結果を示さない。

## 適用範囲と非保証

- リソース探索80%以上と自動設定90～100%は実験から導出した最適値ではなく製品の許容条件である。既定100%を維持し、確認済み欠損の許容と音源状態を分ける。各譜面へ適用し、集約多数の音源で一譜面の不足を隠さない。
- Strongは最頻同士だけ。Relatedの別ペアに完全一致があってもStrongへ昇格しない。空ARTIST同値を、任意の作者への一致へ広げない。
- ハッシュの解決成否と自動設定成否を分け、リソース探索の最低一致数・80%を直接解決へ追加しない。通常表示の非関連除外は同じで、失敗への偽装や別範囲の再探索は行わない。
- 再導入は非関連を除外したうえで唯一Strongを自動設定できるが、現配置より改善・同梱不使用・各譜面音源条件を要求する。複数Strongは順位差で救済しない。
- 先頭保護・最後の区切り群・MIX途中切断は生TITLEへ一度だけ適用する。括弧修復、旧キーへのフォールバック、別名義辞書は作らない。原題保存、DBスキーマと既存の入力受理範囲を変えない。
- 上の正規化比較表は異なるARTIST条件・0.88の固定評価であり、現在の0.72/Related方式の結果ではない。事前実験の直下所属とDB格納値も、製品の原題入力・子孫を含む実パス取得範囲とは区別する。
