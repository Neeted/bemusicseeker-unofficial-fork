# 一覧をDirect2Dで描く理由

## 適用する判断

一覧（`CustomTableView`）の表示面は、Direct2DとDirectWriteで物理画素の面へ全面を描き、`D3DImage` でWPFへ一枚の画像として合成します。GPUで合成できない環境と表は、同じ描画処理をCPU側のビットマップへ描いて表示します。行やセルの描画結果は保持せず、保持するのは行の表示値と文字のレイアウトだけです。スクロールバー、セルの編集欄、ツールチップ、ドラッグ表示、当たり判定、選択、UI AutomationはWPF側に残します。

実行契約は[一覧の描画・操作・仮想化](../spec/ui/table-view.md)と[外観の表示フォント](../spec/ui/appearance.md#表示フォント)が正本です。

## 比較の根拠

2026-11-15 に、製品コードとは別の使い捨てのプログラムで一回ずつ測った値です。条件は Meiryo UI 11 DIP、GeForce GTX 1080 Ti、3840×2160、表示倍率100%、.NET SDK 10.0.404 です。現在の実装の性能を保証する値ではなく、方式の比較にだけ使います。

WPFで行ごとの `DrawingVisual` を保持し、整形済みのグリフ列だけを描く構成の画面更新は次のとおりでした（最大化、4,578セル、毎秒の更新回数）。

| 構成 | 行の位置だけを動かす | 三行だけ入れ替える | 全セルを入れ替える |
| --- | ---: | ---: | ---: |
| セルごとにクリップする | 3.4 | 3.9 | 2.7 |
| クリップしない | 7.8 | 11.4 | 5.3 |
| 行を `BitmapCache` で保持する | 59.7 | 26.7 | 3.2 |

全セルの入替えでも、UIスレッドの所要時間は一回約11ミリ秒でした。残りはWPFの描画スレッドが文字を描く時間で、セル数にほぼ比例します。WPFのままでは、行のビットマップ保持で通常のスクロールは改善できますが、可視行がすべて入れ替わる操作（つまみのドラッグ、ページ送り、並べ替えの直後）は描画スレッドが上限を決めます。

同じ条件で、整形済みの文字のレイアウトをDirect2Dで全面に描く所要時間は次のとおりでした。

| 表示経路 | 4,578セル | 2,200セル |
| --- | --- | --- |
| `D3DImage` による合成 | 一回約16〜26ミリ秒 | 約8.6ミリ秒 |
| CPU側のビットマップ | 一回約47〜58ミリ秒 | 約17ミリ秒 |

文字列一件あたりの整形の所要時間（マイクロ秒）は次のとおりで、どの方式でも未整形の文字列が多い画面更新では整形が下限になります。

| 処理 | 平均27文字 | 平均6文字 |
| --- | ---: | ---: |
| `FormattedText` を描画のたびに整形する | 326〜680 | 51〜91 |
| WPFの `TextFormatter` で一度だけ整形する | 72 | 38 |
| DirectWriteのGDI互換のテキストレイアウトを作る | 48 | 27 |

## 採らない代替案

- **WPFの保持描画（行ごとの `DrawingVisual`、行の `BitmapCache`）**: 追加の依存がなく通常のスクロールは改善できますが、全行の入替えが描画スレッドで毎秒数回に留まります。
- **専用のウィンドウ（`HwndHost`）とスワップチェーン**: 合成を介さず最も速い一方、表の前面に重ねるスクロールバー、編集欄、ドラッグ表示が隠れ、作り直しが必要になります。
- **文字コード表の字形と送り幅だけで文字を並べる方法**: 整形は一件1〜2マイクロ秒ですが、通常のレイアウトと幅が一致したのは約半数でした。見た目が変わるため採りません。
- **表ごとにデバイスを持ち、非表示で解放する構成**: 再表示のたびにデバイスの生成で約0.1秒（プロセスの初回は約1秒）かかりました。二つの表は表示を切り替えて使うため、デバイスはプロセスで一組を共有し、表ごとに持つのは面だけにしています。
- **描画器への入力を表す中間の表示リスト**: 検証のためだけの層になり、画面更新のたびに中間オブジェクトが増えます。検証は表示面の画素と、整形・値取得の回数で行います。

## 構成上の帰結

- `Vortice.Direct2D1`・`Vortice.Direct3D11`・`Vortice.Direct3D9`（MIT）を配布物に含め、第三者表記へ記載します。
- 行の高さと見出しの高さは物理画素の整数で持ち、描画・当たり判定・編集欄・スクロール範囲・行ドロップ・UI Automationの矩形で共有します。表示倍率によって一画素未満の差が出ます。
- 一覧の文字だけがDirectWriteで描かれます。行の高さ・基線・省略・代替フォントの規則は表示フォントの仕様どおりで、字形の描かれ方の画素単位の差は許容します。
- デバイスの消失からの復旧、GPU合成の選択、二つの表の独立性は、GPUのある環境でだけ判定できます。[環境統合の検証区分](../../tests/BeMusicSeeker.Compatibility.Tests/README.md)の `table-gpu` を明示して実行します。
