# 例外・操作結果・診断の扱い

## 目的と適用範囲

例外を使った処理の停止、操作結果の受渡し、原因調査用の診断を分離する。安全に続行できる条件を明示し、その条件を満たさない失敗ではアプリの終了へ進む。安全性を必須要件とし、全原因の記録やUIへの詳細伝達は保証しない。

本書は採用済みの到達目標であり、新規実装、例外境界の変更、適合確認に適用する。既存実装すべての適合、特に未知の失敗から安全な終了への接続は未確認である。各機能仕様の既存動作や既存テストの成功を、本書への適合済みという意味にしない。未完了の作業は[修復計画](../../plan/exception-handling-simplification-plan.md)で管理する。

## 用語

ここでの「処理済み」は、対象または操作の停止範囲と結果が決まった状態を指す。ログへ書いただけで処理済みとはしない。「通知」は処理後の案内、「確認」は実行前の承認であり、失敗時の扱いを分ける。

「続行可能な失敗」は、発生した処理、想定される失敗条件、失敗後の状態から、安全に次へ進めると判断できる失敗を指す。その操作を中断して既存状態へ戻ることも回復に含む。「致命的な扱い」は、アプリの通常利用を再開せず終了へ進むことを指し、直ちにプロセスを強制終了することとは区別する。

## 仕様

### 判断の単位

続行可能な条件を許可リストとして扱う。例外型だけのアプリ共通一覧ではなく、発生した処理、想定される失敗条件、確定済み変更・共有状態・必要な後片付けの結果を組み合わせる。同じI/O例外でも、入力の読取り失敗と元データの復元失敗では続行条件が異なる。

| 停止範囲 | 続行または終了の条件 | 主な例 |
| --- | --- | --- |
| 対象をスキップして続行 | 対象単位の想定失敗であり、他対象・共有状態へ影響せず、必要な後片付けが済む。 | 譜面の既知の形式不正、外部表の通常の取得失敗。 |
| 操作を中断してアプリは続行 | 操作後の状態を安全に利用できることが契約から分かる。後続処理を止め、開始済み処理と必要な補償・解放を終える。 | 変更前の保存先確認失敗、既存状態への必要な復元が完了した想定失敗。 |
| アプリの終了へ進む | 上の続行条件に該当しない、または安全な状態を確認できない。 | 未分類の内部故障、共有状態の不整合、重要な復元・解放の失敗。 |

アプリ終了の必要性を個別に証明するのではなく、続行を許可する側に根拠を求める。未知の失敗を成功、入力不良、空結果、正常取消しへ読み替えない。未知の失敗が結果的に無害であっても、続行条件を確認できなければ終了するという可用性上の制約を受け入れる。

機能だけを停止して残りを使う扱いは、既に明確な隔離境界があり、その失敗後もアプリを続行できる場合に限る。未知の失敗から部分復旧するためだけに、新しい機能停止状態、回復処理、自動再試行を追加しない。処理が任意であることだけを、内部故障からの続行理由にしない。診断・事後通知の限定された扱いは後述する。

### 捕捉と伝播

回復、停止範囲の判断、資源解放、操作結果への変換が必要な場所で捕捉する。それを行わない中間層は原則として例外を加工せず通す。

処理済みの失敗をUIへ説明するためだけに再送出しない。下位で失敗を処理した後は、上位が次の判断に使う結果だけを返す。全メソッドの戻り値を汎用Result型へ変えることや、例外を全面禁止することは要求しない。

外部入力の解析を囲む狭い境界で、依存APIの既知の入力失敗を一度だけ分類する。上位層はその分類を使い、同じ内部例外を再び調べない。入力不良と判断できる失敗だけを形式エラーへ変換し、内部不具合や資源不足まで入力不良に包まない。

従来受理した入力と、壊れた譜面を対象単位でスキップする互換性を維持する。規格違反だけを理由とする入力検査の厳格化や、既知の入力不良を操作全体・アプリ全体の失敗へ広げる変更は行わない。未分類の内部失敗を、入力由来かもしれないという推測だけで救済しない。

過去の内部故障の救済を目的とする、既存の譜面解析失敗記録の自動再分類・一括削除は行わない。同じ目的での一括再評価や全件再解析も追加せず、既存の版・時間上限等による再評価、解析成功時の失敗記録削除、明示削除の契約を維持する。具体的な条件は[譜面情報](../library/chart-info.md)に従う。

再送出が必要なら、`throw;` など既存の標準手段で原因のスタックを保つ。診断の完全性のための新しい運搬構造は作らない。単に文脈を足すための包装は避け、操作名・対象・段階は診断へ渡す。別の操作契約へ変換するための例外型は、その型を呼出元が実際に使って停止・続行を判断する場合に限る。

### 入れ子のバッチ

対象の失敗と、バッチを中断する失敗を区別する。対象ごとの通常失敗を全件収集してAggregateExceptionに戻す処理を標準としない。

各対象で診断を試み、記録の成功を処理継続の条件にせず、親には失敗件数、失敗対象、未処理、確定済み変更など必要な事実だけを渡す。さらに上位のバッチが同じ例外を再分類する必要を作らない。STATUS表示や再操作対象の選択に必要な簡単な分類・識別子は残してよい。

`Task.WhenAll` 等が既に保持する複数例外は、並列処理を所有する境界でそのまま診断へ渡してよい。全原因の記録成功は要求せず、集合を全階層で複製・再包装してUIまで保持しない。診断に代表例外を使うことと、停止判断を代表例外だけで済ませることは別である。並行する処理の致命的な失敗や危険な残状態を、他の処理の想定失敗・取消しで隠さない。

失敗や取消しを通知した時点で、開始済みの処理を放置しない。詳細な例外を運ばないことは、Taskを待たないことではない。

### 操作結果と確定済み変更

UIに必要なのは、操作が完了したか、何が変更済みか、何が未完了か、次に操作できるか終了するかである。一般の失敗は簡潔な文言でよく、例外型・本文・内部例外の詳細や全原因の組合せを正確に説明することは要求しない。例外ツリーや全スタックを表示用のデータ構造にしない。

「保存済み・出力未完了」「ファイル変更済み・DB反映未完了」は、どちらも全成功や未変更とは異なる。既存の確定情報を保持し、例外削減のために必要な結果まで削らない。例外がないことや通知が表示されたことだけで成功を判定しない。

失敗した対象を、同じhashを持つ別pathなどへ読み替えて操作しない。指定対象で失敗した事実を残す。既存データを保持して更新失敗を示すことは、成功へのすり替えではない。

結果へ項目を追加する前に、その情報で変わる呼出元の判断または利用者の行動を示す。ログ済みフラグ、通知済み台帳、例外履歴、再試行状態を将来の便宜だけで追加しない。

### ログとSTATUS

例外を最終的に扱い、対象と失敗段階が分かる境界で、代表となる元例外と操作名・必要な対象情報を既存のログへ渡す。通常のログ環境で主原因を調査できることを最低限とする。既に保持する原因を安価に記録できる場合は利用するが、全例外・全スタック・全段階の完全保存、重複の完全排除、書込み成功は保証しない。通過する各層で同じ全文を重複記録することを標準にせず、診断専用の状態や運搬基盤を追加しない。

業務状態に影響しない純粋な診断出力は、欠落しても安全性を変えないことを根拠に、失敗を局所化できる。この許可はログの取得・整形・出力の狭い範囲に限り、任意のコールバックやDB更新・参照反映まで含めない。ログ失敗を元の操作結果へ合成せず、別の保存先、再通知、再試行で救済し続けない。記録できなかったことを記録成功とせず、元の業務失敗に必要な終了も取り消さない。

外部表のSTATUSには、404、403、その他HTTPエラー、通信失敗、ヘッダー未検出、ヘッダー形式不正、データ形式不正、URL不正など、利用者が判断に使う分類を残す。原因の詳細はログへ置き、分類だけを根拠に保存・DB・内部公開の失敗まで通常取得失敗へ変換しない。

### 通知と確認

処理後の案内だけを行い、業務状態・操作可否・所有権を変更しない通知は、表示失敗を局所化する。その場所で診断を試み、元の操作結果へ合成せず、別の通知で救済し続けない。表示待機が画面の寿命管理に必要なら、その待機は残す。一般通知の表示成功を保証しないが、表示する場合は保存済み・未保存、成功・未完了、続行・終了を誤認させない。

処理前の確認は別である。削除・上書きなどの承認を得られなければ実行しない。確認画面の表示失敗を承認済み・利用者取消しへ置き換えない。

進捗表示の更新と、次の操作対象になる参照・索引の更新を区別する。後者の失敗を任意通知へ格下げしない。整合した状態を確立できず、既存の隔離境界による続行条件も満たさない場合は、アプリの終了へ進む。

### 取消しと後片付け

操作が所有する取消し要求と、通信の期限切れを区別する。例外名だけで利用者取消しにしない。取消しだけで正常終了にせず、確定済み変更と後片付けの成否を確認する。取消しと致命的な失敗が重なる場合は、取消しで失敗を隠さず終了へ進む。

後片付けは、独立して実行できる必要なものを一つの失敗で放棄しない。必要な後片付けをすべて試みることと、発生した全例外を上位へ渡すことは別の要件である。二次原因はその場所で診断を試み、上位へは続行可否を変える危険な残状態や未完了の事実を渡す。UI向けの全原因収集は行わない。

最初の失敗が通常の入力不良でも、その後に重要な復元・解放が失敗したなら、対象スキップに戻さない。元失敗優先という規則だけで危険な残状態を捨てず、全原因の詳細を保持できなくても終了判断を失わない。一時ファイルの単なる残留と元データの復元不能を同一視せず、残留物を後続処理が誤用しない等の続行条件を確認できる場合だけ局所化する。

`Dispose` や低水準のファイル操作から、対象ごとのエラーダイアログを開かない。後片付けと表示の責務を分け、`finally` の二次失敗で元の致命的な扱いや必要な残状態を失わない。既存の標準手段で主原因を維持し、通知や全原因保存だけのために独自の後片付け結果基盤を追加しない。

### UI入口と最終防壁

`async void` はイベント入口に限定する。画面操作・背景仕事を所有する入口で続行条件を判定し、条件を満たす想定失敗は対象または操作の失敗として終える。それ以外は、通知してイベントや仕事を終えるだけにせず、共通の終了判断へ接続する。下位の全例外を無条件に正常完了へ変換する捕捉は置かない。

Taskの失敗を観測・記録しただけで終了処理へ接続したことにしない。任意の背景仕事も内部故障からの続行条件を必要とし、共通のTask診断拡張を回復判断や開始済みTaskの待機の代わりにしない。投げ直し先から終了までの所有経路を確認する。

管理された終了が可能な範囲では、新規受付と依存する後続処理を止め、所有する開始済み処理へ停止を要求し、必要な完了・補償・解放を経て終了する。既存の終了管理を使い、通常終了の保存・更新・再起動を無条件に流用しない。不確かなメモリ状態を永続化したり、新しい更新・再起動を始めたりしない。致命的な扱いへ移った後は、取消しや通知失敗を理由に通常利用へ戻さない。

プロセス状態そのものの破損などで管理された終了も安全に実行できない場合は、管理された終了とは別の最終終了として扱う。未知の例外すべてを即時強制終了へ直結せず、逆に最終終了で全回収・全復元を保証しない。「安全な停止」は、不確かな状態から追加の操作や書込みを続けないことを中心とする。現在の終了実装の保証と、ここで求める接続の適合確認は別である。

全体例外ハンドラーは、通常の操作結果を表示する経路に使わない。特定の例外型をログなしに無視する条件や、AggregateExceptionに包まれたかどうかで継続可否を変える条件を追加しない。既存の抑止条件は、通常の操作境界を修復する前に機械的に削除しない。

`App` の最終防壁では、診断や非常用案内の失敗で必要な終了を妨げない。現行の通常終了の資源回収・整合性待ちと、致命的な最終終了の保証は[終了](../runtime/shutdown.md#保証の範囲)に従う。これは、本書で求める条件外の失敗から管理された終了への接続が完了したという意味ではない。

### 実装・レビュー・検証

変更前に、捕捉する場所、そこで分かる確定状態、停止範囲、上位が必要とする結果、診断する場所を短く整理する。それを説明できない共通分類器・収集器・転送層は作らない。

必須の完了条件を次に固定する。改善可能な点を列挙することと、適合を妨げる不具合の指摘を分ける。

| 完了条件 | 確認する結果 |
| --- | --- |
| 通常入力と想定失敗の互換性 | 従来の受理入力を維持し、既知の不正入力を適切な対象・操作の範囲へ閉じる。 |
| 続行許可の根拠 | 続行する境界に安全性の根拠があり、条件外の失敗は終了判断へ届く。 |
| 状態と処理寿命の保全 | 確定状態・対象を取り違えず、管理された終了で必要な後片付けと開始済み処理を放置しない。 |
| 診断・通知の非干渉 | 診断・事後通知の失敗で元の結果、必須処理、終了判断を変えず、再帰的な例外輸送をしない。 |
| 最低限の表示と診断 | 保存済み・未保存、成功・未完了、続行・終了を誤認させず、通常のログ環境で主原因を調査できる。 |

修正必須の指摘は、該当する条件、本番の入口と到達経路、誤った続行・停止、データや処理寿命への影響、または最低限の表示・診断の欠落を示す。全原因の保存、細かな文言、スタックや重複の完全性だけの改善は完了条件を増やす理由にしない。既に簡潔に成立する改善を戻す必要もない。

テストは実入力、実ファイル・DB、確定結果、停止範囲、後続処理の有無を優先する。通常の入力不良と正常対象の混在、未知の失敗後の続行禁止、主処理と重要な後片付けの重複失敗を確認する。終了を検証する代替先は最終プロセス終了の境界に置き、受付停止・完了待機・終了判断そのものを成功を返す代替へ置き換えない。

内部例外の個数・入れ子・順序・参照同一性・全診断文言の完全一致を、実際の制御契約がないまま固定しない。診断先の故障への耐性はその境界で代表条件を確認し、各機能で全組合せを繰り返さない。入力の組合せは下位の既存テストへ集約し、WPFでは実入口と終了判断の接続に固有の保証を代表例で確認する。捕捉される通知コールバック内の表明だけに依存せず、処理後に実結果や呼出し記録を検証する。

| 開始済み処理と中断位置 | [譜面ファイル読取り](../library/chart-file-reading.md)、[LR2楽曲DB同期](../integration/lr2-song-db.md)の実装・テスト対応 | 準備・解析・保存の開始済みTaskを終端まで待ち、実確定位置と必須反映の結果を引き継ぐ。 |
| 補償・解放と残状態 | [ファイルとDBの整合性](../library/file-db-consistency.md)、[音声](../runtime/audio.md)、[LR2バックアップ](../integration/lr2-backup.md)、[ポータブル更新](../integration/portable-update.md)の実装・テスト対応 | 元失敗を保ちながら独立した必要回収を試み、未解決の補償や共有資源を任意診断へ格下げしない。 |
| 起動・設定・最終終了 | [起動](../runtime/startup.md)、[設定](../runtime/settings.md)、[終了](../runtime/shutdown.md)の実装・テスト対応 | 必須準備と任意診断を分離し、実操作の終端と必要な終了を通知故障で飛ばさない。 |

### 適合確認が残る要件

| 要件・適用状態 | 確認する実装境界 | 確認する結果 |
| --- | --- | --- |
| 続行条件と内部故障の停止範囲：適合未確認 | `MainWindow` の操作入口、`StartupBackgroundTaskSchedulerOwner`、各機能の結果利用先 | 想定失敗は限定した範囲で終え、未知の失敗は共通の終了判断へ接続する。 |
| 管理された終了と最終終了の分離：接続・適合未確認 | `App.ExitAfterUnhandledException`、`ShellShutdownWorkflowOwner`、各処理の所有者 | 受付停止、開始済み処理の終端、不確かな状態の保存・更新・再起動の抑止、通常利用へ戻らないこと。 |
| 診断・UIの保証範囲：適合未確認 | 既存の診断・事後通知境界、結果表示 | 安全性に関わる結果を保ち、全原因の輸送を完了の要件にしない。 |

未確認の接続を、最終例外ハンドラーや既存の機能テストが存在することだけで実装済みとしない。
