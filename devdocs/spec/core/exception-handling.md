# 例外・操作結果・診断の扱い

## 目的と適用範囲

失敗を、その対象・操作を所有する境界で終え、操作結果と原因調査用の診断を分けます。停止範囲は、処理の境界と失敗後の状態で決めます。例外が既知か未知かだけで、アプリの終了を決めません。

保証するのは、正本・確定結果と通常の資源所有の保全です。全原因の記録や、UIへの詳細な伝達は保証しません。

新規の実装、例外境界の変更、適合確認に適用する共通の契約です。機能固有の入力条件、操作結果、実装とテストは各機能の仕様を正本とします。既存テストの成功だけで停止範囲を推測せず、実際の入口から結果の利用先まで確認します。診断の出力先と保証範囲は[ログ出力](logging.md)を正本とします。

## 用語

[共通用語集](../glossary.md)の診断、終端、後片付け、補償、任意通知、必須反映を使います。

| 用語 | 意味 |
| --- | --- |
| 処理済み | 対象または操作の停止範囲と結果が決まった状態。ログへ書いただけでは処理済みとしない。 |
| 通知 | 処理後の案内。失敗しても処理の結果は変わらない。 |
| 確認 | 実行前の承認。得られなければ実行しない。 |
| 独立した生成 | 既存の正本・共有モデル・必要な索引や参照を変更せず、未完成の成果物を採用しないことで、失敗を閉じられる処理。 |
| 致命的な扱い | 共有状態の具体的な危険、またはプロセス状態の破損により、通常の利用を再開せず終了へ進むこと。OOMの即時終了と、通常の整合性を保つ終了は、保証を分ける。 |

## 仕様

### 判断の単位

失敗した対象・操作を所有する境界で、未採用の成果物、確定済みの変更、共有状態、通常の後片付けを確認して、停止範囲を決めます。同じI/O例外でも、未採用の入力の読取り失敗と、元データの復元失敗では、停止範囲が異なります。原因の網羅的な分類を、続行の前提にしません。

| 停止範囲 | 続行または終了の条件 | 主な例 |
| --- | --- | --- |
| 対象をスキップして続行 | 失敗した未採用の成果物を捨て、他の対象・共有状態へ影響しない。通常の所有資源を解放する。 | 壊れた譜面。独立した取得・解析・表示の原因不明の失敗。 |
| 操作を中断してアプリは続行 | 未変更、または既存のトランザクション・保存手順・補償で整合した状態に閉じる。依存する後続を止め、開始済みの通常の処理を終える。 | 保存前の失敗。未採用の作業領域での導入失敗。 |
| アプリの終了へ進む | 正本・共有状態に具体的な危険が残り、その境界で閉じられない。 | 正本の復元不能、未解決のトランザクション、確定後の必須反映の失敗。 |

独立した取得・解析・表示の原因不明の失敗は、その対象・操作の失敗として終えます。成功、確定した入力不良、正常な空、正常な取消へは読み替えません。終了へ広げるのは、本番で残る正本・共有状態の危険を示せる場合に限ります。依存側の原因や後処理を判別できないという理由だけで、私有の未採用の入力の失敗をアプリの終了へ広げません。

失敗を閉じるために、新しい恒久的な機能停止の状態、回復の台帳、自動の再試行、独自の巻戻しを追加しません。通常の所有・トランザクション・保存手順を使います。「読取り」「任意」という名称だけで独立性を判断せず、採用までの実経路を確認します。

### OOMとプロセス状態

すでに導入した `Environment.FailFast` は、各実装で捕捉したOOMを即時終了へ接続するもので、維持します。一方、今後の実装範囲に、全経路でのOOMの検出と即時終了は要求しません。

- 各メソッド・通知・ログ・後片付けへ、OOM専用の捕捉を広げません。
- 全Taskの待機、全回収、全復元、診断・案内の成功は保証しません。
- 保存済みの内容や元の操作結果を、終了を案内するためだけに再保存・再実行しません。
- OOMを入力不良や正常な成功へ変換するための捕捉はしません。回復する理由のない場所では標準の伝播を使い、既存の操作境界・最終ハンドラーで扱って構いません。

次のものは追加しません。

- 内部例外・`AggregateException` の全枝の探索。
- 全Task・全層から最終ハンドラーへ確実に届ける新しい仕組み。
- 依存ライブラリの内部で吸収されるOOMの監視。

別のTaskや画面が続く可能性を含め、全経路の即時終了は保証の対象外です。通常の失敗・取消に必要な資源の所有と実際の終端は維持します。

### 捕捉と伝播

例外は、回復、停止範囲の判断、資源の解放、操作結果への変換のいずれかが必要な場所で捕捉します。それらを行わない中間層は、原則として例外を加工せずに通します。

- 処理済みの失敗を、UIへ説明するためだけに再送出しません。下位で失敗を処理した後は、上位が次の判断に使う結果だけを返します。
- 全メソッドの戻り値を汎用の結果型へ変えることや、例外の全面禁止は要求しません。
- 原因を分類するのは、STATUS、取消、解析不能の記録など、実際の扱いが変わる場所だけです。上位で同じ内部例外を繰り返し分類しません。
- 外部入力の狭い解析境界で入力不良と判断できる失敗だけを、形式エラーへ変換します。内部の不具合や資源不足を入力不良に包みません。
- 再送出が必要なら、`throw;` など既存の標準手段で原因のスタックを保ちます。診断の完全性のための新しい運搬構造は作りません。
- 文脈を足すだけの包装は避け、操作名・対象・段階は診断へ渡します。別の操作契約へ変換するための例外型は、呼出元がその型で停止・続行を判断する場合に限ります。

#### 入力不良と対象のスキップ

従来受理していた入力と、壊れた譜面を対象単位でスキップする互換性を維持します。規格違反だけを理由とする入力検査の厳格化や、入力不良を操作全体・アプリ全体の失敗へ広げる変更はしません。破損したRARや短いRARも対象のスキップとし、取得済みのアーカイブ・入力元は通常の所有で解放します。コンストラクターの失敗で返らないネイティブ資源など、依存側の限界は別の作業として扱い、この回収の保証に含めません。

独立した未知の譜面の取得・解析の失敗は、その回だけスキップし、恒久的な解析不能の記録へ保存しません。成功した基本情報と正常な対象は保持し、次の通常の解析の機会に再び対象とします。その場の自動の再試行や、新しい再評価の仕組みは追加しません。

既存の譜面の解析失敗の記録に対して、自動の再分類・一括削除、一括の再評価、全件の再解析は追加しません。次は維持します。具体的な条件は[譜面情報](../library/chart-info.md)に従います。

- 既知の入力不良の失敗記録。
- 既存の版・時間上限などによる再評価。
- 解析成功時の失敗記録の削除と、明示的な削除。

### 入れ子のバッチ

対象の失敗と、バッチを中断する失敗を区別します。対象ごとの通常の失敗を全件収集して `AggregateException` に戻す処理は、標準にしません。

各対象で診断を試みますが、記録の成功を処理の継続の条件にしません。親へは、失敗件数、失敗した対象、未処理、確定済みの変更など、必要な事実だけを渡します。上位のバッチが同じ例外を再分類する必要を作りません。STATUSの表示や再操作の対象の選択に必要な、簡単な分類・識別子は残して構いません。

`Task.WhenAll` などが保持する複数の例外は、並列処理を所有する境界でそのまま診断へ渡して構いません。全原因の記録の成功は要求せず、集合を全階層で複製・再包装してUIまで保持しません。診断に代表の例外を使うことと、停止の判断を代表の例外だけで済ませることは別です。並行する処理の致命的な失敗や危険な残状態を、他の処理の想定内の失敗・取消で隠しません。

失敗や取消を通知した時点で、開始済みの処理を放置しません。詳細な例外を運ばないことは、Taskを待たないことではありません。

### 操作結果と確定済みの変更

UIに必要なのは、操作が完了したか、何が変更済みか、何が未完了か、次に操作できるか終了するかです。一般の失敗は簡潔な文言でよく、例外の型・本文・内部例外の詳細や、全原因の組合せの正確な説明は要求しません。例外ツリーや全スタックを、表示用のデータ構造にしません。

「保存済み・出力未完了」「ファイル変更済み・DB反映未完了」は、全成功とも未変更とも異なる結果です。既存の確定情報を保持し、例外を減らすために必要な結果まで削りません。例外がないことや通知が表示されたことだけで、成功と判定しません。

失敗した対象を、同じハッシュを持つ別のパスなどへ読み替えて操作しません。指定した対象で失敗した事実を残します。既存データを保持して更新の失敗を示すことは、成功へのすり替えではありません。

結果へ項目を追加する前に、その情報で変わる呼出元の判断、または利用者の行動を示します。ログ済みのフラグ、通知済みの台帳、例外の履歴、再試行の状態を、将来の便宜だけで追加しません。

### 失敗した成果物と表示

失敗した未完成・無効な成果物を、正常なデータとして保存・置換・導入・成功公開しません。一方、失敗は現在の要求に対する処理結果であり、取得失敗・未取得として画面へ反映します。成果物を成功として採用することと、処理結果を表示することは区別します。

表示の生成が失敗した場合は、結果領域を失敗の表示へ更新し、その結果に依存する操作だけを止めます。

- 旧い行・カード・選択を外したり、表示用の空のコレクションを使ったりして構いません。ただし、正常な0件として成功を確定しません。
- 古い要求の失敗で、新しい要求の表示を上書きしません。
- 失敗した部分と独立した正常な結果と、他の画面は利用できます。

正本・確定済みデータの保全と、過去の画面表示の再利用は別です。旧い表示の保存・条件照合・復元を、一般的な必須の保証にはしません。個別の機能として必要性と挙動を明示した場合だけ継続利用を要求し、自然に残る保存済みの内容まで一律に消去しません。未取得は通常のデータで表し、getterの例外や恒久的な停止状態を増やしません。

失敗を、正常な空・未変更・取得成功へ読み替えません。機能固有の表示・検索上の既定値を明示して維持する場合は、その機能の仕様に記載します。たとえば、通常のスコア一覧で未取得の譜面をNO PLAY相当として投影・検索する扱いは[譜面モデル](../library/chart-model.md#保存成績の再読込みと旧結果)に従います。これは読取りそのものの成功を意味しません。

起動時に正本DBを正常に初期化・読取りできた場合は、新規・既存、空・非空を問わず、走査の失敗を案内して、保存済みの内容で利用を開始します。不完全な走査による追加・削除は反映しません。必須の設定・正本DBの読取り失敗を、空の成功へ変換しません。

### 診断とSTATUS

例外を最終的に扱い、対象と失敗の段階が分かる境界で、代表となる元の例外と、操作名・必要な対象の情報を既存のログへ渡します。通過する各層で同じ全文を重複して記録することを標準にせず、診断専用の状態や運搬基盤を追加しません。診断の保証範囲と、ログ出力の失敗の扱いは[ログ出力](logging.md#診断の保証範囲)に従います。

外部の表のSTATUSには、404、403、その他のHTTPエラー、通信失敗、ヘッダー未検出、ヘッダー形式の不正、データ形式の不正、URLの不正など、利用者が判断に使う分類を残します。原因の詳細はログへ置きます。分類だけを根拠に、保存・DB・内部公開の失敗まで、通常の取得失敗へ変換しません。

### 通知と確認

処理後の案内だけを行い、業務状態・操作可否・所有権を変更しない通知は、表示の失敗をその場で局所化します。

- その場所で診断を試み、元の操作結果へ合成せず、別の通知で救済し続けません。
- 表示の待機が画面の寿命管理に必要なら、その待機は残します。
- 一般の通知は表示の成功を保証しません。表示する場合は、保存済み・未保存、成功・未完了、続行・終了を誤認させません。

この分離は、操作の所有境界と、既存の `using`・`finally`・保存手順で成立させます。起こり得るという一般論だけで、全通知・全ダイアログ・全ログへ個別の救済を追加しません。閉じた画面への呼出しなど、具体的な寿命・スレッド・順序の不備があれば、その原因を修正します。通知・診断・解放の二次故障の組合せを各機能で網羅せず、すでに簡潔に成立している非干渉の処理も作り直しません。

処理前の確認は別の扱いです。削除・上書きなどの承認を得られなければ実行しません。確認画面の表示の失敗を、承認済みや利用者の取消へ置き換えません。

進捗表示の更新と、次の操作対象になる参照・索引の更新は区別します。後者の失敗を任意通知へ格下げしません。整合した状態を確立できず、既存の隔離境界による続行の条件も満たさない場合は、アプリの終了へ進みます。

### 取消と後片付け

操作が所有する取消要求と、通信の期限切れを区別します。例外の型名だけで、利用者の取消とは見なしません。取消だけで正常終了とせず、確定済みの変更と後片付けの成否を確認します。取消と致命的な失敗が重なる場合は、取消で失敗を隠さず、終了へ進みます。

通常の後片付けでは、独立して実行できる必要な処理を、一つの失敗で放棄しません。所有する資源を解放することと、全例外を上位へ渡すことは、別の要件です。二次的な原因はその場所で診断を試み、上位へは実際に必要な残状態・未完了の事実だけを渡します。UI向けに全原因を収集しません。

元データの復元不能や共有資源の不整合が残る場合は、最初の入力不良を理由に、対象のスキップへ戻しません。一方、解放の例外が起きたことだけで、あらゆる資源を致命的に扱いません。私有の一時物やネットワーク資源の回収失敗と、正本・共有状態の危険を区別します。失敗した作業物を後続で誤用せず、残る対象・操作を所有境界で終えます。

`Dispose` や低水準のファイル操作から、対象ごとのエラーダイアログを開きません。後片付けと表示の責務を分け、`finally` の二次失敗で、元の致命的な扱いや必要な残状態を失いません。既存の標準手段で主原因を維持し、通知や全原因の保存のためだけに、独自の後片付けの結果基盤を追加しません。

### UIの入口と最終防壁

`async void` は、イベントの入口に限ります。画面操作・背景処理を所有する境界で、失敗した対象・操作の非採用と停止範囲を決めます。具体的な正本・共有状態の危険は、通知して処理を終えるだけにせず、既存の終了の判断へ接続します。取得・反映・回収が混在する上位で、下位の全失敗を一律に正常完了へ変換する捕捉は置きません。

Taskの失敗を観測・記録しただけで、結果の非採用や必要な終了を済ませたことにはなりません。共通のTaskの診断拡張を、操作結果の判断や、開始済みの通常のTaskの待機の代わりにしません。依存する採用・操作を止める実経路と、具体的な危険からの終了の所有経路を確認します。

管理された終了が可能な範囲では、次の順に終了します。既存の終了管理を使い、通常の終了の保存・更新・再起動を無条件には流用しません。

1. 新規の受付と、依存する後続処理を止める。
2. 所有する開始済みの処理へ停止を要求する。
3. 必要な完了・補償・解放を経て終了する。

不確かなメモリ状態を永続化したり、新しい更新・再起動を始めたりしません。致命的な扱いへ移った後は、取消や通知の失敗を理由に通常の利用へ戻しません。OOMやプロセスの破損は通常の整合性の待機と分け、全回収・全復元を保証しません。現在の終了の実装の保証と、ここで求める接続の適合確認は別です。

全体の例外ハンドラーは、通常の操作結果を表示する経路に使いません。特定の例外型をログなしに無視する条件や、`AggregateException` に包まれたかどうかで継続の可否を変える条件は追加しません。既存の抑止の条件は、通常の操作境界を修復する前に機械的に削除しません。

`App` の最終防壁では、診断や非常用の案内の通常の失敗が、必要な終了を妨げません。通常の終了の資源回収・整合性の待機と、致命的な最終終了の保証は[終了](../runtime/shutdown.md#保証の範囲)に従います。最終防壁があることだけで、各所有境界の非採用・停止の接続が適合しているとは見なしません。

### 実装・レビュー・検証

変更の前に、捕捉する場所、そこで分かる確定状態、停止範囲、上位が必要とする結果、診断する場所を短く整理します。それを説明できない共通の分類器・収集器・転送層は作りません。

必須の完了条件は次のとおりです。改善できる点の列挙と、適合を妨げる不具合の指摘は分けます。

| 完了条件 | 確認する結果 |
| --- | --- |
| 通常の入力と想定した失敗の互換性 | 従来の受理入力を維持し、既知の不正な入力を、適切な対象・操作の範囲へ閉じる。 |
| 停止範囲と非採用 | 独立した失敗は対象・操作で終え、具体的な正本・共有状態の危険は既存の終了の判断へ届く。失敗した成果物を成功として採用しない。 |
| 状態と通常の処理寿命の保全 | 確定状態・対象を取り違えず、通常の失敗・取消で、所有する開始済みの処理と後片付けを放置しない。OOM時の完全な回収は要求しない。 |
| 診断・通知の非干渉 | 診断・事後の通知の失敗で、元の結果、必須処理、終了の判断を変えず、再帰的な例外の輸送をしない。 |
| 最低限の表示と診断 | 保存済み・未保存、成功・未完了、続行・終了を誤認させず、通常のログ環境で主原因を調査できる。 |

追加の必須対策や修正必須の指摘には、次を示します。任意のコールバックをテストで例外にできることだけを新しい保証の根拠にせず、発生頻度の統計調査も必須の工程にしません。全原因の保存、細かな文言、スタックや重複の完全性だけの改善は、完了条件を増やす理由にしません。すでに簡潔に成立している改善を戻す必要もありません。

- 該当する完了条件。
- 本番の入口と、現実的な到達経路。
- 具体的な誤採用・データ損失・誤操作・通常の寿命への影響、または最低限の表示・診断の欠落。

テストは、実際の入力、実際のファイル・DB、確定結果、停止範囲、後続処理の有無を優先し、次を確認します。

- 入力不良と正常な対象が混在する場合の扱い。
- 失敗した結果の非採用。
- 不完全な走査の非反映。
- 保存失敗時の正本の保持。
- 確認が失敗した場合の非実行。

必要な終了を代替する場合も、本番の判断と通常の実際の終端を、成功する代替へ置き換えません。OOMだけを理由とする横断的な監査・故障条件の網羅や、専用のプロセス終了の検証基盤は、完了条件にしません。

内部例外の個数・入れ子・順序・参照の同一性・全診断文言の完全一致を、実際の制御の契約がないまま固定しません。診断先の故障への耐性はその境界で代表の条件を確認し、各機能で全組合せを繰り返しません。入力の組合せは下位の既存テストへ集約し、WPFでは、実際の入口と終了の判断の接続に固有の保証を代表例で確認します。捕捉される通知コールバック内の表明だけに依存せず、処理後に実際の結果や呼出し記録を検証します。
