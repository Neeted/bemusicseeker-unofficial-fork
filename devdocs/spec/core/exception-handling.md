# 例外・操作結果・診断の扱い

## 目的と適用範囲

失敗を対象・操作の所有境界で終え、操作結果と原因調査用の診断を分離する。停止範囲は処理境界と失敗後の状態から決め、例外が既知か未知かだけでアプリ終了を決めない。正本・確定結果と通常の資源所有を保ち、全原因の記録やUIへの詳細伝達は保証しない。

本書は採用済みの到達目標であり、新規実装、例外境界の変更、適合確認に適用する。既存実装すべての適合は未確認である。各機能仕様の既存動作や既存テストの成功を、本書への適合済みという意味にしない。未完了の実装・検証は[修復計画](../../plan/exception-handling-simplification-plan.md)で管理する。

## 用語

ここでの「処理済み」は、対象または操作の停止範囲と結果が決まった状態を指す。ログへ書いただけで処理済みとはしない。「通知」は処理後の案内、「確認」は実行前の承認であり、失敗時の扱いを分ける。

「独立した生成」は、既存の正本・共有モデル・必要な索引や参照を変更せず、未完成の成果物を採用しないことで失敗を閉じられる処理を指す。「致命的な扱い」は、具体的な共有状態の危険またはプロセス状態の破損により、アプリの通常利用を再開せず終了へ進むことを指す。OOMの即時終了と、通常の整合性を保つ終了は保証を分ける。

## 仕様

### 判断の単位

失敗した対象・操作を所有する境界で、未採用の成果物、確定済み変更、共有状態、通常の後片付けを確認する。同じI/O例外でも、未採用入力の読取り失敗と元データの復元失敗では停止範囲が異なる。原因の網羅的な分類を続行の前提にしない。

| 停止範囲 | 続行または終了の条件 | 主な例 |
| --- | --- | --- |
| 対象をスキップして続行 | 失敗した未採用の成果物を捨て、他対象・共有状態へ影響しない。通常の所有資源を解放する。 | 壊れた譜面、独立した取得・解析・表示の原因不明の失敗。 |
| 操作を中断してアプリは続行 | 未変更、または既存のtransaction・保存手順・補償で整合した状態に閉じる。依存する後続を止め、通常の開始済み処理を終える。 | 保存前の失敗、未採用作業領域での導入失敗。 |
| アプリの終了へ進む | 正本・共有状態に具体的な危険が残り、その境界で閉じられない。 | 正本復元不能、未解決取引、確定後の必須反映失敗。 |

独立した取得・解析・表示の原因不明の失敗は、その対象・操作の失敗として終える。成功、確定した入力不良、正常空、正常取消しへ読み替えない。終了へ広げる場合は、本番で残る正本・共有状態の危険を示す。依存側の原因や後処理が判別不能という理由だけで、私有の未採用入力の失敗をアプリ終了へ広げない。

失敗を閉じるために、新しい恒久的な機能停止状態、回復台帳、自動再試行、独自の巻戻しを追加しない。通常の所有・transaction・保存手順を使う。「読取り」「任意」という名称だけで独立性を判断せず、採用までの実経路を確認する。

### OOMとプロセス状態

既に導入した `Environment.FailFast` は、各実装で捕捉したOOMを即時終了へ接続する。これらの実装は保持するが、今後の未実装範囲に全経路でのOOM検出・即時終了を要求しない。各メソッド・通知・ログ・後片付けへの専用捕捉の横展開は行わない。全Task待機、全回収、全復元、診断・案内成功を保証せず、保存済み内容や元の操作結果を、終了を案内するためだけに再保存・再実行しない。

OOMを入力不良や正常成功へ変換することを目的とした捕捉は行わない。回復する理由のない場所では標準の伝播を使い、既存の操作境界・最終ハンドラーで扱ってよい。内部例外・AggregateExceptionの全枝探索や、全Task・全層から最終ハンドラーへ確実に届ける新しい仕組みは追加しない。依存ライブラリ内部で吸収されるOOMを監視しない。別Taskや画面が続く可能性を含め、全経路の即時終了は今回の保証外とする。通常の失敗・取消しに必要な資源所有と実終端は維持する。

### 捕捉と伝播

回復、停止範囲の判断、資源解放、操作結果への変換が必要な場所で捕捉する。それを行わない中間層は原則として例外を加工せず通す。

処理済みの失敗をUIへ説明するためだけに再送出しない。下位で失敗を処理した後は、上位が次の判断に使う結果だけを返す。全メソッドの戻り値を汎用Result型へ変えることや、例外を全面禁止することは要求しない。

STATUS、取消し、解析不能記録など実際の扱いが変わる場所だけで原因を分類する。外部入力の狭い解析境界で入力不良と判断できる失敗だけを形式エラーへ変換し、内部不具合や資源不足まで入力不良に包まない。上位で同じ内部例外を繰返し分類しない。

従来受理した入力と、壊れた譜面を対象単位でスキップする互換性を維持する。規格違反だけを理由とする入力検査の厳格化や、入力不良を操作全体・アプリ全体の失敗へ広げる変更は行わない。破損・短いRARも対象スキップとし、取得済みのarchive・sourceを通常の所有で解放する。コンストラクター失敗で返らないnative資源等の依存の限界は別作業として扱い、今回の全回収保証へ含めない。

独立した未知の譜面取得・解析失敗は今回だけスキップし、恒久的な解析不能記録へ保存しない。成功した基本情報と正常対象を保持し、次の通常の解析機会には再び対象にする。その場の自動再試行や新しい再評価schedulerは追加しない。

既存の譜面解析失敗記録の自動再分類・一括削除、一括再評価や全件再解析は追加しない。既知の入力不良の失敗記録、既存の版・時間上限等による再評価、解析成功時の失敗記録削除、明示削除は維持する。具体的な条件は[譜面情報](../library/chart-info.md)に従う。

再送出が必要なら、`throw;` など既存の標準手段で原因のスタックを保つ。診断の完全性のための新しい運搬構造は作らない。単に文脈を足すための包装は避け、操作名・対象・段階は診断へ渡す。別の操作契約へ変換するための例外型は、その型を呼出元が実際に使って停止・続行を判断する場合に限る。

### 入れ子のバッチ

対象の失敗と、バッチを中断する失敗を区別する。対象ごとの通常失敗を全件収集してAggregateExceptionに戻す処理を標準としない。

各対象で診断を試み、記録の成功を処理継続の条件にせず、親には失敗件数、失敗対象、未処理、確定済み変更など必要な事実だけを渡す。さらに上位のバッチが同じ例外を再分類する必要を作らない。STATUS表示や再操作対象の選択に必要な簡単な分類・識別子は残してよい。

`Task.WhenAll` 等が既に保持する複数例外は、並列処理を所有する境界でそのまま診断へ渡してよい。全原因の記録成功は要求せず、集合を全階層で複製・再包装してUIまで保持しない。診断に代表例外を使うことと、停止判断を代表例外だけで済ませることは別である。並行する処理の致命的な失敗や危険な残状態を、他の処理の想定失敗・取消しで隠さない。

失敗や取消しを通知した時点で、開始済みの処理を放置しない。詳細な例外を運ばないことは、Taskを待たないことではない。

### 操作結果と確定済み変更

UIに必要なのは、操作が完了したか、何が変更済みか、何が未完了か、次に操作できるか終了するかである。一般の失敗は簡潔な文言でよく、例外型・本文・内部例外の詳細や全原因の組合せを正確に説明することは要求しない。例外ツリーや全スタックを表示用のデータ構造にしない。

「保存済み・出力未完了」「ファイル変更済み・DB反映未完了」は、どちらも全成功や未変更とは異なる。既存の確定情報を保持し、例外削減のために必要な結果まで削らない。例外がないことや通知が表示されたことだけで成功を判定しない。

失敗した対象を、同じhashを持つ別pathなどへ読み替えて操作しない。指定対象で失敗した事実を残す。既存データを保持して更新失敗を示すことは、成功へのすり替えではない。

結果へ項目を追加する前に、その情報で変わる呼出元の判断または利用者の行動を示す。ログ済みフラグ、通知済み台帳、例外履歴、再試行状態を将来の便宜だけで追加しない。

### 保存済み内容と未取得

独立した表示生成が失敗した場合は、現在の取得元・選択に有効な旧結果を保持する。有効な旧結果がなければ未取得・更新失敗として、その結果に依存する操作だけを止める。正常空、未プレイ、別の取得元の表示へ代替しない。未取得は通常のデータ表現で扱い、getterの例外や恒久的な機能停止状態を増やさない。

起動時に正本DBを正常に初期化・読み取れた場合は、新規・既存、空・非空を問わず、走査失敗を案内して保存済み内容で利用開始する。不完全走査による追加・削除は反映しない。必須の設定・正本DBの読取り失敗を空の成功へ変換しない。

### ログとSTATUS

例外を最終的に扱い、対象と失敗段階が分かる境界で、代表となる元例外と操作名・必要な対象情報を既存のログへ渡す。通常のログ環境で主原因を調査できることを最低限とする。既に保持する原因を安価に記録できる場合は利用するが、全例外・全スタック・全段階の完全保存、重複の完全排除、書込み成功は保証しない。通過する各層で同じ全文を重複記録することを標準にせず、診断専用の状態や運搬基盤を追加しない。

業務状態に影響しない純粋な診断出力は、欠落しても安全性を変えないことを根拠に、失敗を局所化できる。この許可はログの取得・整形・出力の狭い範囲に限り、任意のコールバックやDB更新・参照反映まで含めない。ログ失敗を元の操作結果へ合成せず、別の保存先、再通知、再試行で救済し続けない。記録できなかったことを記録成功とせず、元の業務失敗に必要な終了も取り消さない。

外部表のSTATUSには、404、403、その他HTTPエラー、通信失敗、ヘッダー未検出、ヘッダー形式不正、データ形式不正、URL不正など、利用者が判断に使う分類を残す。原因の詳細はログへ置き、分類だけを根拠に保存・DB・内部公開の失敗まで通常取得失敗へ変換しない。

### 通知と確認

処理後の案内だけを行い、業務状態・操作可否・所有権を変更しない通知は、表示失敗を局所化する。その場所で診断を試み、元の操作結果へ合成せず、別の通知で救済し続けない。表示待機が画面の寿命管理に必要なら、その待機は残す。一般通知の表示成功を保証しないが、表示する場合は保存済み・未保存、成功・未完了、続行・終了を誤認させない。

この分離は操作の所有境界と既存のusing・finally・保存手順で成立させる。起こり得るという一般論だけで全通知・全ダイアログ・全ログへ個別の救済を追加しない。閉じた画面への呼出しなど、具体的な寿命・スレッド・順序の不備があればその原因を修正する。通知・診断・解放の二次故障の組合せを各機能で網羅せず、既に簡潔に成立する非干渉処理も作り直さない。

処理前の確認は別である。削除・上書きなどの承認を得られなければ実行しない。確認画面の表示失敗を承認済み・利用者取消しへ置き換えない。

進捗表示の更新と、次の操作対象になる参照・索引の更新を区別する。後者の失敗を任意通知へ格下げしない。整合した状態を確立できず、既存の隔離境界による続行条件も満たさない場合は、アプリの終了へ進む。

### 取消しと後片付け

操作が所有する取消し要求と、通信の期限切れを区別する。例外名だけで利用者取消しにしない。取消しだけで正常終了にせず、確定済み変更と後片付けの成否を確認する。取消しと致命的な失敗が重なる場合は、取消しで失敗を隠さず終了へ進む。

通常の後片付けは、独立して実行できる必要なものを一つの失敗で放棄しない。所有する資源を解放することと、全例外を上位へ渡すことは別の要件である。二次原因はその場所で診断を試み、上位へは実際に必要な残状態・未完了の事実だけを渡す。UI向けの全原因収集は行わない。

元データの復元不能や共有資源の不整合が残れば、最初の入力不良を理由に対象スキップへ戻さない。一方、解放例外の発生だけであらゆる資源を致命的に扱わず、私有の一時物やネット資源の回収失敗と、正本・共有状態の危険を区別する。失敗した作業物を後続で誤用せず、残る対象・操作を所有境界で終える。

`Dispose` や低水準のファイル操作から、対象ごとのエラーダイアログを開かない。後片付けと表示の責務を分け、`finally` の二次失敗で元の致命的な扱いや必要な残状態を失わない。既存の標準手段で主原因を維持し、通知や全原因保存だけのために独自の後片付け結果基盤を追加しない。

### UI入口と最終防壁

`async void` はイベント入口に限定する。画面操作・背景仕事を所有する境界で、失敗した対象・操作の非採用と停止範囲を決める。具体的な正本・共有状態の危険は、通知して仕事を終えるだけにせず既存の終了判断へ接続する。取得・反映・回収が混在する上位で、下位の全失敗を一律に正常完了へ変換する捕捉は置かない。

Taskの失敗を観測・記録しただけで、結果の非採用や必要な終了を済ませたことにしない。共通Task診断拡張を、操作結果の判断や通常の開始済みTaskの待機の代わりにしない。依存する採用・操作を止める実経路と、具体的危険からの終了の所有経路を確認する。

管理された終了が可能な範囲では、新規受付と依存する後続処理を止め、所有する開始済み処理へ停止を要求し、必要な完了・補償・解放を経て終了する。既存の終了管理を使い、通常終了の保存・更新・再起動を無条件に流用しない。不確かなメモリ状態を永続化したり、新しい更新・再起動を始めたりしない。致命的な扱いへ移った後は、取消しや通知失敗を理由に通常利用へ戻さない。

OOMやプロセス破損は通常の整合性待ちと分け、全回収・全復元を保証しない。通常の具体的な共有状態の危険では、不確かな状態から追加の操作・保存・更新・再起動を進めない。現在の終了実装の保証と、ここで求める接続の適合確認は別である。

全体例外ハンドラーは、通常の操作結果を表示する経路に使わない。特定の例外型をログなしに無視する条件や、AggregateExceptionに包まれたかどうかで継続可否を変える条件を追加しない。既存の抑止条件は、通常の操作境界を修復する前に機械的に削除しない。

`App` の最終防壁では、診断や非常用案内の通常失敗で必要な終了を妨げない。現行の通常終了の資源回収・整合性待ちと、致命的な最終終了の保証は[終了](../runtime/shutdown.md#保証の範囲)に従う。最終防壁が存在することだけで、各所有境界の非採用・停止の接続を適合済みとはしない。

### 実装・レビュー・検証

変更前に、捕捉する場所、そこで分かる確定状態、停止範囲、上位が必要とする結果、診断する場所を短く整理する。それを説明できない共通分類器・収集器・転送層は作らない。

必須の完了条件を次に固定する。改善可能な点を列挙することと、適合を妨げる不具合の指摘を分ける。

| 完了条件 | 確認する結果 |
| --- | --- |
| 通常入力と想定失敗の互換性 | 従来の受理入力を維持し、既知の不正入力を適切な対象・操作の範囲へ閉じる。 |
| 停止範囲と非採用 | 独立した失敗は対象・操作で終え、具体的な正本・共有状態の危険は既存の終了判断へ届く。失敗した成果物を成功採用しない。 |
| 状態と通常の処理寿命の保全 | 確定状態・対象を取り違えず、通常の失敗・取消しで所有する開始済み処理と後片付けを放置しない。OOM時の完全回収を要求しない。 |
| 診断・通知の非干渉 | 診断・事後通知の失敗で元の結果、必須処理、終了判断を変えず、再帰的な例外輸送をしない。 |
| 最低限の表示と診断 | 保存済み・未保存、成功・未完了、続行・終了を誤認させず、通常のログ環境で主原因を調査できる。 |

追加の必須対策・修正必須の指摘は、該当する条件、本番の入口と現実的な到達経路、具体的な誤採用・データ損失・誤操作・通常寿命への影響、または最低限の表示・診断の欠落を示す。任意callbackをテストでthrowさせられることだけを新しい保証の根拠にせず、発生頻度の統計調査も必須工程にしない。全原因の保存、細かな文言、スタックや重複の完全性だけの改善は完了条件を増やす理由にしない。既に簡潔に成立する改善を戻す必要もない。

テストは実入力、実ファイル・DB、確定結果、停止範囲、後続処理の有無を優先する。入力不良と正常対象の混在、失敗結果の非採用、不完全走査の非反映、保存失敗時の正本保持、確認失敗時の非実行を確認する。必要な終了を代替する場合も、本番の判断・通常の実終端を成功する代替へ置き換えない。OOMだけを理由とする横断監査・故障条件の網羅や専用death-test基盤は完了条件にしない。

内部例外の個数・入れ子・順序・参照同一性・全診断文言の完全一致を、実際の制御契約がないまま固定しない。診断先の故障への耐性はその境界で代表条件を確認し、各機能で全組合せを繰り返さない。入力の組合せは下位の既存テストへ集約し、WPFでは実入口と終了判断の接続に固有の保証を代表例で確認する。捕捉される通知コールバック内の表明だけに依存せず、処理後に実結果や呼出し記録を検証する。

### 適合確認が残る要件

| 要件・適用状態 | 確認する実装境界 | 確認する結果 |
| --- | --- | --- |
| 処理境界と停止範囲：適合未確認 | `MainWindow` の操作入口、`StartupBackgroundTaskSchedulerOwner`、各機能の結果利用先 | 独立した失敗は対象・操作で終え、具体的な共有状態の危険だけ既存の終了判断へ接続する。 |
| OOM：既存FailFastを保持 | 導入済みの捕捉境界 | 全経路の検出・即時終了を追加の適合条件にせず、専用捕捉の横展開・全回収・依存内部監視を追加しない。 |
| 管理された終了と最終終了の分離：接続・適合未確認 | `App.ExitAfterUnhandledException`、`ShellShutdownWorkflowOwner`、各処理の所有者 | 受付停止、開始済み処理の終端、不確かな状態の保存・更新・再起動の抑止、通常利用へ戻らないこと。 |
| 診断・UIの保証範囲：適合未確認 | 既存の診断・事後通知境界、結果表示 | 安全性に関わる結果を保ち、全原因の輸送を完了の要件にしない。 |
