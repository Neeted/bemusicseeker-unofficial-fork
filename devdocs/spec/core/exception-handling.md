# 例外・操作結果・診断の扱い

## 目的と適用範囲

例外を使った処理の停止、操作結果の受渡し、原因調査用の診断を分離する。新規実装、例外境界を変更する実装、レビューに適用する。全機能が既にこの方針へ移行済みという宣言ではない。

## 用語

ここでの「処理済み」は、対象または操作の停止範囲と結果が決まった状態を指す。ログへ書いただけで処理済みとはしない。「通知」は処理後の案内、「確認」は実行前の承認であり、失敗時の扱いを分ける。

## 仕様

### 判断の単位

例外の型や包み方ではなく、その手続きの状態から停止範囲を決める。通信、ファイル、DBなど発生元の種類だけで、対象停止・操作停止・アプリ終了を一律に対応付けない。

| 境界 | 判断と責務 |
| --- | --- |
| 対象内 | 失敗対象を確定し、その対象の処理を止める。独立した他対象へ進めるかは、共有状態と確定済み変更から判断する。 |
| 操作内 | 続行できない後続処理を止め、開始済み処理と必要な後片付けの終端を待つ。確定済み・失敗・未処理を取り違えない。 |
| 機能・アプリ | 安全な状態へ戻せない機能は利用を止める。アプリ全体を終了するのは、より狭い停止では安全に継続できない根拠がある場合に限る。 |

未知の例外を成功に変換しない。同時に、「未知」「AggregateException」「fatalという名前」だけをアプリ終了の理由にしない。入力の解析不能、再生不能、操作不能、プロセスの継続不能は別の範囲である。

### 捕捉と伝播

回復、停止範囲の判断、資源解放、操作結果への変換が必要な場所で捕捉する。それを行わない中間層は原則として例外を加工せず通す。

処理済みの失敗をUIへ説明するためだけに再送出しない。下位で失敗を処理した後は、上位が次の判断に使う結果だけを返す。全メソッドの戻り値を汎用Result型へ変えることや、例外を全面禁止することは要求しない。

外部入力の解析を囲む捕捉では、入力不良と判断できる失敗だけを形式エラーへ変換する。内部不具合や資源不足まで入力不良に包まない。互換のために許容する入力は、その許容を必要とする箇所で処理する。

再送出が必要なら原因のスタックを保つ。単に文脈を足すための包装は避け、操作名・対象・段階は診断へ記録する。別の操作契約へ変換するための例外型は、その型を呼出元が実際に使って判断する場合に限る。

### 入れ子のバッチ

対象の失敗と、バッチを中断する失敗を区別する。対象ごとの通常失敗を全件収集してAggregateExceptionに戻す処理を標準としない。

各対象で診断を記録した後、親には失敗件数、失敗対象、未処理、確定済み変更など、必要な事実だけを渡す。さらに上位のバッチが同じ例外を再分類する必要を作らない。STATUS表示や再操作対象の選択に必要な簡単な分類・識別子は残してよい。

Task.WhenAll等が保持する複数例外は、並列処理を所有する境界で必要な診断を記録するために使える。その集合を全階層で複製・再包装し、UIまで保持する必要はない。awaitが返す代表例外だけで全件診断を済ませたことにしない。

失敗や取消しを通知した時点で、開始済みの処理を放置しない。詳細な例外を運ばないことは、Taskを待たないことではない。

### 操作結果と確定済み変更

UIに必要なのは、操作が完了したか、何が変更済みか、何が未完了か、次に何をしてよいかである。例外ツリーや全スタックを表示用のデータ構造にしない。

「保存済み・出力未完了」「ファイル変更済み・DB反映未完了」は、どちらも全成功や未変更とは異なる。既存の確定情報を保持し、例外削減のために必要な結果まで削らない。例外がないことや通知が表示されたことだけで成功を判定しない。

失敗した対象を、同じhashを持つ別pathなどへ読み替えて操作しない。指定対象で失敗した事実を残す。既存データを保持して更新失敗を示すことは、成功へのすり替えではない。

結果へ項目を追加する前に、その情報で変わる呼出元の判断または利用者の行動を示す。ログ済みフラグ、通知済み台帳、例外履歴、再試行状態を将来の便宜だけで追加しない。

### ログとSTATUS

例外を受け止め、対象と失敗段階が分かる場所で、元例外と操作名・path・URLなど必要な文脈を記録する。通過する各層で同じ全文を重複記録することを標準にしない。診断の相関には既存の操作識別を優先する。

通常のログ出力の失敗を、既に確定した操作結果へ加えない。ログ失敗を記録するための無限の再通知・再試行を作らない。記録の成功を保証できない環境でも、成功したという虚偽の結果を返さない。

外部表のSTATUSには、404、403、その他HTTPエラー、通信失敗、ヘッダー未検出、ヘッダー形式不正、データ形式不正、URL不正など、利用者が判断に使う分類を残す。原因の詳細はログへ置き、分類だけを根拠に保存・DB・内部公開の失敗まで通常取得失敗へ変換しない。

### 通知と確認

処理後の通知失敗は、原則としてその場所で診断し、元の操作結果へ合成しない。「失敗通知の失敗」をさらにUIへ運ぶための例外連鎖を作らない。表示待機が画面の寿命管理に必要なら、その待機は残す。

処理前の確認は別である。削除・上書きなどの承認を得られなければ実行しない。確認画面の表示失敗を承認済み・利用者取消しへ置き換えない。

進捗表示の更新と、次の操作対象になる参照・索引の更新を区別する。後者の失敗を任意通知へ格下げしない。整合した状態を確立できないときは、該当機能の操作を止める。

### 取消しと後片付け

操作が所有する取消し要求と、通信の期限切れを区別する。例外名だけで利用者取消しにしない。取消しと失敗が重なる場合も、確定済みの変更と後片付けの成否から終端を決める。

後片付けは、必要なものを一つの失敗で放棄しない。後片付けの二次例外をUIへ集約するために元例外を包み続けない。ただし、復元不能・共有資源の解放不能など、次の安全性を変える事実は呼出元へ伝える。元失敗優先という規則だけで、危険な残状態を捨てない。

Disposeや低水準のファイル操作から、対象ごとのエラーダイアログを開かない。後片付けと表示の責務を分け、元の失敗をfinallyの別例外で上書きしない。通知だけのために独自の後片付け結果基盤を追加しない。

### UI入口と最終防壁

async voidはイベント入口に限定する。回復可能な操作失敗を入口または既存の操作所有者で処理し、未処理例外によるアプリ終了へ漏らさない。下位の全例外を無条件に正常完了へ変換するcatchは置かない。

全体例外ハンドラーは、通常の操作結果を表示する経路に使わない。特定の例外型をログなしに無視する条件や、AggregateExceptionに包まれたかどうかで継続可否を変える条件を追加しない。既存の抑止条件は、通常の操作境界を修復する前に機械的に削除しない。

### 実装・レビュー・検証

変更前に、捕捉する場所、そこで分かる確定状態、停止範囲、上位が必要とする結果、診断する場所を短く整理する。それを説明できない共通分類器・収集器・転送層は作らない。

確認するのは、正しい対象で停止すること、確定済み変更が残ること、後片付けと開始済みTaskが終わること、STATUSが正しいこと、必要な診断が残ること、通知失敗が元結果を変えないことである。

内部例外の個数・入れ子深さ・参照同一性・過去例外の保持期間を、利用する契約がないまま固定しない。入力の組合せは下位の既存テストへ集約し、WPFは実入口の捕捉漏れなど画面接続に固有の保証を代表例で確認する。

## 実装とテストの対応

| 適用項目 | 実装・確認先 | 保証する内容 |
| --- | --- | --- |
| 外部表の対象失敗とSTATUS | `PlaylistExternalSyncOwner.ReloadPlaylistTargetCoreAsync`、`PlaylistSyncAttemptResult`、`PlaylistWorkspaceViewModel` / `PlaylistExternalFailureBoundaryTests` | 取得境界の通常失敗をSTATUSへ変換する。正常表の確定と旧表の保持を妨げず、部分失敗を全件成功にしない。 |
| 手動再取得の失敗表示と診断の分担 | `BmsPlaylistExternalReloadTests.PlaylistWorkspaceManualResync_UsesActiveTableAndPublishesLifecycle` / `PlaylistExternalFailureBoundaryTests.ExternalLoad_ReportsOriginalFailureWithoutRetainingItInStatus` | 取得境界で元例外・取得元を記録し、WorkspaceはSTATUS・現在参照・保存済み内容・進捗終端を保つ。診断先の失敗は元原因を置き換えない。 |
| 必要な確定状態と取消しの保持 | `BmsPlaylistExternalReloadTests` の出力失敗・部分取消し | 保存後の参照と全体取消しを失わず、開始済み処理の終端まで待つ。 |
| 通知失敗の局所診断 | `FileDbMutationReport.ShowAsync`、`NotifyBestEffort` | 通知の失敗を元の変更結果へ加えない。 |
| その他の領域 | 変更する実入口、結果利用先、既存の機能テスト | 方針への適用は領域ごとに確認する。上の例だけで全機能の実装済み・検証済みを宣言しない。 |
