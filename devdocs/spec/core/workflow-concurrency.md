# ワークフローと並行性

## 目的と適用範囲

操作の受付、実行中の状態、完了、読取り表示を分け、非同期化で責務や状態を増やし過ぎないための共通設計要件です。新規実装と変更対象へ適用します。全入口が既に同じ構成で実装済みという宣言ではありません。起動は親L/P内で必須手続きを直接待ち、今回の型付き結果を次段へ渡します。現行経路は[起動仕様](../runtime/startup.md)を参照します。

## 用語

[共通用語集](../glossary.md)の管理主体、受付、排他権、操作権限、スナップショット、世代番号、公開、終端を使います。UIの応答性、競合する利用者操作の並行実行、一つの受理済み操作内の計算並列度は別の性質です。通常のライブラリ変更は、変更操作中に別の変更操作を呼び出さない前提です。コードから並行に呼べることは、必須の並行実行要件ではありません。UIの非同期化は応答性のために行います。現行操作の分類・競合結果は[操作の競合ポリシー](operation-concurrency-policy.md)に従います。

## 仕様

### 競合対策を決める手順

競合への対処は、設計・実装前に次の順序で決めます。

1. 本番の入口、成立する前提、競合が起きる時系列、利用者への影響を確認します。新機能は合意済みの計画上の入口を使います。UI・コマンドの受付制限、開始済みの処理、別の本番入口を区別し、内部APIを直接並行に呼べることだけを到達の根拠にしません。
2. 依頼・合意済み仕様と通常の利用目的から、並行操作や表示時機の保証の必要性と適用範囲を判断します。現行コードで可能なこと、既存テストの期待、作業中に追加した仕様だけを、維持必須の保証へ格上げしません。長時間処理中の閲覧、同じデータへの変更、明示操作の完了動作を区別し、必要性を確認せず保証を別の操作へ広げません。
3. 必要な保証を満たす方法を比較し、既存の排他、未開始の拒否、明示的な再操作、完了後の一定の動作で目的を満たせるなら、簡潔な仕様を優先します。下表で方針を決め、必要な受付と内部制御だけを選びます。判断した現行の分類・条件を[競合ポリシー](operation-concurrency-policy.md)へ反映し、調査履歴や重複台帳、追加の確認工程は作りません。

| 確認結果 | 方針 |
| --- | --- |
| UI・受付・処理順により競合が防がれている | その前提に合わせた内部契約にし、任意の内部API同時呼出しまで保証を広げない。 |
| 本来禁止する操作が受付や状態遷移の隙間から入る | 原則として隙間を塞ぐ。並行実行を保証する設計より先に、受付と処理順による防止を検討する。 |
| 並行実行が依頼・合意済み仕様で許可されている | 必要な競合制御を設計し、既存の許可条件を維持する。 |
| 操作の必要性・許可条件・保証の適用範囲が不明 | 具体的な操作例、選択肢・影響・推奨案を利用者へ質問し、回答に依存する設計・実装・テストの期待結果を確定しない。 |

モーダルによる背面操作の禁止は、新規操作を防ぐ根拠として扱います。開始済み処理や別入口まで止まるとは仮定しません。隙間が短いことを放置の理由にせず、依頼・合意済み仕様で許可された操作を意図しない隙間と見なして禁止することもしません。データの正しさと開始済み処理の回収は、どの方針でも維持します。未確定事項の扱いは[要件と到達可能性](../development/agent-workflow.md#要件と到達可能性)に従います。

### 受付と完了を一つの責任にする

競合する新しい変更要求は、実行責任を持つ入口で、原則として待たずに `Busy` として拒否します。拒否は未受理であり、後で自動実行する予約や成功として扱いません。拒否前に、副作用を伴う準備・ファイル操作・DB変更を始めません。

受理した操作は必要な処理と取消・失敗時の後片付けまで、論理的な受付の責任を保持します。利用者が待機をやめたことや画面を閉じたことだけで、実処理を追跡対象から外しません。論理的な責任の保持は、物理ロックやDBトランザクションを長時間保持することではありません。

既存の権限を明示的に渡し、同じ操作が別の管理主体で排他権を取り直して循環待ちにならないようにします。ロック・トランザクション内で、UI、確認画面、通知先、別の管理主体を同期的に待ちません。スケジューラーの空きやキャッシュ更新を、単発の必須処理の完了の代用にしません。

具体的な受付領域、並行可否、例外、受理済み継続は[操作の競合ポリシー](operation-concurrency-policy.md#分類と並行可否)を正本とします。機能仕様は入力・保存・出力・失敗の契約を所有し、競合制約を重ねて定義しません。

### 対象と入力を確定する

画面から持ち越したパス・ハッシュ・行位置だけで、現在の変更対象を代用しません。受付後に意図を保ったまま現在の対象へ一度解決し、古い対象は規定どおり拒否・スキップします。別の対象への読替えや無言の再試行はしません。

確認画面のために排他権を解放して再取得する場合は、承認された対象集合と現在の条件を再検証し、対象を勝手に増やしません。確定直前のファイル存在・保存先等の検証は、利用者の意図を再解釈する処理とは分けます。

処理に必要な設定と入力は、既存の操作プロファイルや用途別のスナップショットで捕捉します。`Settings.Default` の共有編集値を、変更不能な入力と見なして使い続けません。外部の走査結果には取得範囲と完全性を持たせ、部分結果から削除や全件完了を推測しません。

### 変更と公開の順序

一回のライブラリ変更は、成功した物理変更を一つのセッションへ集め、各管理主体へ操作単位で反映します。後続判断に必要な先行成功は操作内の差分で伝えます。対象ごとのDB確定を、判定間の通信手段にしません。複数のDB・外部出力を一つの原子的トランザクションに見せる保証も設けません。

処理は、入力準備、永続確定、必要なメモリ・索引反映、必要な公開、任意通知、終端を、機能固有の依存順で明示します。必須反映を任意通知へ格下げせず、任意のキャッシュを全更新するための新しい完了待ちは追加しません。失敗は実際の結果へ保持し、通知の時機だけで成功を推測しません。

一回限りの必須手順は、型付きの要求・結果と明示的な非同期待機で接続します。通知や世代番号の変化から次の段階を推測するより、実際の結果を直接渡します。必要な公開が排他権の解放後なら、その後まで追跡します。

### 世代番号の用途

| 種類 | 識別するもの | 代用できないもの |
| --- | --- | --- |
| UI要求の世代 | 古い表示要求と現在の要求 | 永続確定、受理済み変更の取消。 |
| 操作ID | 一回の操作と診断の対応 | データが最新である証明。 |
| モデルの改訂番号 | 所有状態の更新 | 特定の書込み成功や全入力の完全性。 |
| キャッシュの世代 | 計算に使った入力との一致 | 操作の必須処理完了。 |
| 公開順序 | 通知・表示反映の順序 | 元データの削除・利用者値の保持の証明。 |
| スキーマ版・互換署名 | 保存形式、解析器等の互換条件 | 現在の操作対象・処理の成否。 |

広いモデルの世代を、狭い変更結果の証票として使いません。番号を追加する場合は、種類、管理主体、元データ、更新契機、有効期間、利用先、不一致時の扱い、無関係な変更への反応、診断上の必要性、廃止条件を説明します。説明できない番号は追加せず、既存の結果や依存関係で表します。

### キャッシュと通知の集約

読取り側で結果の破棄が安全な場合だけ、最新の要求を優先して古い表示を捨てます。利用者が確定した変更や受理済み作業を、この規則で破棄しません。再計算待ちの集約は既存の「現在と最新の保留要求」などの小さい境界を使い、終わりのない再試行や無制限の待ち行列にしません。

無関係な更新で高価な全体再計算を起動する場合は、入力依存を狭めます。広い失効を読取りキャッシュの都合で認めても、永続確定の正否はそれで判断しません。診断用の理由文字列で通知・受付・反映方針を切り替えず、型付きの選択値を使います。

画面受付の最新性と、データ自身の通知による一覧構築の失効を区別します。短命な正規受付参照をUIの副作用から一覧採用まで渡し、適用済み画面対象にも対応付けます。依存更新はその適用済み参照を検査し、後発選択を受理してUIへ適用する前の旧表示を新しい選択へ付け替えません。ライブラリ交換では選択を保ち、旧データからの候補を既存の入力識別と構築番号で不採用にします。

新規の重複解析は[操作の競合ポリシー](operation-concurrency-policy.md#ライブラリ保留保守)の共通Lへ非待機で受け付けます。受理済み変更に必要な再準備は親の生存権限を借用し、自己再取得や解放後の予約にしません。

データ準備と表示の終端は、それぞれの所有者が管理します。完成通知は完成事実だけを渡し、現在の有効な選択から表示を始めます。初回解析の後発選択保護と、明示した保守の成功後自動選択は別の操作契約です。明示保守は成功後の捕捉対象を選び、その準備を現在画面によらず親の受付内で回収します。開始したデータ準備は表示の古さだけで取り消さず、表示の失敗は表示所有者が既存の操作失敗通知へ渡します。開始済みの準備・表示・通知は、停止時に実Taskの終端を回収します。重複解析の条件と保証は[重複仕様](../library/duplicate-files.md#初回解析中の画面移動)に従います。

通常一覧の並べ替えは、要求時の整列版と画面受付をUI入力前にも検査します。通常一覧・部分集合・導入一覧の索引、絞込み、順序はUI外で構築し、行交換準備を含む採用全体はUIで実行します。有効な候補の採用、必要配送、ロック外の表示同期まで同じ実Taskで所有し、並べ替え要求もその終端を待ちます。後発選択で失効した保留候補は、構築の取消だけに依存せず待機を終えます。

### 実ロック状態と表示通知

`ReaderWriterLockSlimWrapper` の実 `Enter` / `Exit` と保持数更新は必須です。ライブラリ・プレイリストが操作可否を判断する保持数の値は、表示通知より先に確定します。既存の保持数計上区分は維持し、昇格可能読取りは書込み相当として扱います。3つの保持数の設定処理の `PropertyChanged` は表示への転送であり、その購読者の失敗で実取得・解放を失敗へ変えません。`ObservableObject` 全体の通知契約は変更しません。

表示通知の失敗はラッパーごとに最初の一回だけ任意診断し、通常のロック遷移にはログを追加しません。通知の例外履歴は保管せず、診断自体の失敗を再診断しません。実 `Exit` の失敗は任意通知として抑止しません。

ファイル操作の複数のスナップショットのロック範囲は、取得済みのロックを逆順に全て解放し、最初の実解放失敗を元スタックを保って伝えます。取得途中の失敗でも既に取得した全ロックの解放を試し、二次的な解放失敗は局所診断に留めて元の取得原因を保持します。現在の同期 `using` 所有経路にない所有スレッド外からの操作や二重解放を、通常の利用フローの保証へ追加しません。

### 完了と複雑性の確認

完了は、成功・失敗・スキップ・未処理の対象、必要な保存・反映・公開・解放が揃ったことで判断します。例外がない、世代が進んだ、成功ログが出た、スケジューラーが空いた、という間接情報だけでは判断しません。

新しい状態、世代番号、実行区分、コールバック、再試行、書込み主体、終端、キャッシュには、必要な契約と既存構造で表せない理由を示します。置換した処理は退役し、同じ意味の判定や失敗通知を複数箇所へ残しません。既存の結果・診断で確認できることのために、常設の状態や対象ごとのログを増やしません。
