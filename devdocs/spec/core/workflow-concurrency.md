# ワークフローと並行性

## 目的と適用範囲

操作の受付、実行中の状態、完了、読取り表示を分け、非同期化によって責務や状態を増やし過ぎないための共通の設計要件です。新規の実装と変更する箇所へ適用します。全入口がすでに同じ構成で実装済みという宣言ではありません。

操作ごとの受付領域、並行可否、受理済みの継続は[操作の競合ポリシー](operation-concurrency-policy.md)を正本とします。本書は、それらを決めて実装するときに従う手順と設計上の規則を定めます。

## 用語

[共通用語集](../glossary.md)の管理主体、操作の受付、競合拒否、排他権、操作権限、スナップショット、世代番号、公開、任意通知、必須反映、終端を使います。ライブラリ変更の受付（L）とプレイリスト変更の受付（P）は[操作の競合ポリシー](operation-concurrency-policy.md#用語)の定義に従います。

次の三つは別の性質です。

| 性質 | 意味 |
| --- | --- |
| UIの応答性 | 画面操作・取消などに応答できること。UIの非同期化はこのために行う。 |
| 競合する利用者操作の並行実行 | 競合する変更要求を同時に受理すること。操作の競合ポリシーで操作ごとに定める。 |
| 一つの受理済み操作の中の計算の並列度 | 独立した計算を同時に進めること。受付の規則とは別に各機能が定める。 |

通常のライブラリ変更は、変更操作の最中に別の変更操作を呼び出さない前提です。コードから並行に呼べることは、並行実行を必須とする要件ではありません。

## 仕様

### 競合対策を決める手順

競合への対処は、設計・実装の前に次の順序で決めます。

1. **到達経路の確認**: 本番の入口、成立する前提、競合が起きる時系列、利用者への影響を確認します。新機能は合意済みの計画上の入口を使います。UI・コマンドの受付制限、開始済みの処理、別の本番の入口を区別し、内部APIを直接並行に呼べることだけを到達の根拠にしません。
2. **保証の必要性の判断**: 依頼・合意済みの仕様と通常の利用目的から、並行操作や表示の時機の保証が必要か、どの範囲に適用するかを判断します。現行コードで可能なこと、既存テストの期待、作業中に追加した仕様だけを、維持必須の保証へ格上げしません。長時間処理中の閲覧、同じデータへの変更、明示操作の完了時の動作を区別し、必要性を確認せずに保証を別の操作へ広げません。
3. **方法の選択**: 必要な保証を満たす方法を比較します。既存の排他、未開始での拒否、明示的な再操作、完了後の一定の動作で目的を満たせるなら、簡潔な仕様を優先します。下表で方針を決め、必要な受付と内部制御だけを選びます。判断した分類と条件は[操作の競合ポリシー](operation-concurrency-policy.md)へ反映し、調査履歴や重複する台帳、追加の確認工程は作りません。

| 確認結果 | 方針 |
| --- | --- |
| UI・受付・処理順により競合が防がれている | その前提に合わせた内部契約にし、内部APIの任意の同時呼出しまで保証を広げない。 |
| 本来禁止する操作が、受付や状態遷移の隙間から入る | 原則として隙間を塞ぐ。並行実行を保証する設計より先に、受付と処理順による防止を検討する。 |
| 並行実行が依頼・合意済みの仕様で許可されている | 必要な競合制御を設計し、既存の許可条件を維持する。 |
| 操作の必要性・許可条件・保証の適用範囲が不明 | 具体的な操作例、選択肢・影響・推奨案を利用者へ質問し、回答に依存する設計・実装・テストの期待結果を確定しない。 |

モーダル画面による背面操作の禁止は、新規の操作を防ぐ根拠として扱います。開始済みの処理や別の入口まで止まるとは仮定しません。隙間が短いことを放置の理由にせず、依頼・合意済みの仕様で許可された操作を、意図しない隙間と見なして禁止することもしません。データの正しさと開始済みの処理の回収は、どの方針でも維持します。未確定事項の扱いは[要件と到達可能性](../development/agent-workflow.md#要件と到達可能性)に従います。

### 受付と完了の責任

競合する新しい変更要求は、実行の責任を持つ入口で、原則として待たずに競合拒否（`Busy`）とします。

- 競合拒否は未受理です。後で自動実行する予約とも、成功とも扱いません。
- 拒否の判定より前に、副作用を伴う準備・ファイル操作・DB変更を始めません。

受理した操作の入口は、必要な処理と、取消・失敗時の後片付けまで、論理的な受付の責任を保持します。利用者が待機をやめたことや画面を閉じたことだけで、実処理を追跡の対象から外しません。論理的な責任の保持は、物理ロックやDBトランザクションを長時間保持することではありません。

同じ操作の中で別の管理主体へ処理を渡すときは、既存の権限を明示的に渡します。別の管理主体が排他権を取り直して循環待ちになる構成にしません。ロックやトランザクションを保持したまま、UI、確認画面、通知先、別の管理主体を同期的に待ちません。スケジューラーの空きやキャッシュの更新を、単発の必須処理の完了の代用にしません。

並列の読取りスレッドは窓口を受け取りません。保守の読取りの失敗は、件数と標本を収集先へ集めます。選択の再検査と全体の再検査は、書込み保護と受付を解放した後に、受付を取った呼出し元が表示します。それ以外の保守の経路のうち、導入・導入先の修正・統合・推定先導入は、保守の書込み保護の外で、成功でも例外でも、現行の範囲の通知経路へ渡します。起動後の保守は、受付と書込み保護を解放した後に、成功でも例外でも、集めた失敗を待たない投函で一度だけまとめて渡し、保守の終端と次の受付は表示の完了を待ちません。表示の `await` を受付や書込み保護の内側へ書きません。

機能仕様は入力・保存・出力・失敗の契約を所有し、競合の制約を重ねて定義しません。

### 対象と入力の確定

画面から持ち越したパス・ハッシュ・行位置だけで、現在の変更対象を代用しません。受付後に、利用者の意図を保ったまま現在の対象へ一度解決し、古い対象は規定どおり拒否またはスキップします。別の対象への読替えや、無言の再試行はしません。

確認画面のために排他権を解放して再取得する場合は、承認された対象の集合と現在の条件を再検証し、対象を勝手に増やしません。確定直前のファイルの存在や保存先などの検証は、利用者の意図を再解釈する処理とは分けます。

処理に必要な設定と入力は、既存の操作プロファイルや用途別のスナップショットで捕捉します。共有されている `Settings.Default` の編集値を、変更不能な入力と見なして使い続けません。外部の走査結果には取得範囲と完全性を持たせ、部分的な結果から削除や全件の完了を推測しません。

### 変更と公開の順序

一回のライブラリ変更は、成功した物理変更を一つの変更セッションへ集め、各管理主体へ操作単位で反映します（[変更セッション](../library/mutations.md#操作単位の変更セッション)）。

- 後続の判断に必要な先行の成功は、操作内の成功差分で伝えます。対象ごとのDB確定を、判定の間の通信手段にしません。
- 複数のDBと外部出力を、一つの原子的なトランザクションに見せる保証は設けません。

処理は、入力の準備、永続確定、必要なメモリ・索引への反映、必要な公開、任意通知、終端を、機能固有の依存順で明示します。必須反映を任意通知へ格下げせず、任意のキャッシュを全更新するための新しい完了待ちは追加しません。失敗は実際の結果へ保持し、通知の時機だけで成功を推測しません。

一回限りの必須手順は、型付きの要求・結果と、明示的な非同期の待機で接続します。通知や世代番号の変化から次の段階を推測せず、実際の結果を直接渡します。必要な公開が排他権の解放後に行われる場合は、その公開まで追跡します。

起動もこの規則に従い、親のLとPの中で必須手続きを直接待って、型付きの結果を次の段階へ渡します。現行の経路は[起動](../runtime/startup.md)を参照します。

### 世代番号の用途

| 種類 | 識別するもの | 代用できないもの |
| --- | --- | --- |
| UI要求の世代 | 古い表示要求と現在の要求 | 永続確定、受理済みの変更の取消。 |
| 操作ID | 一回の操作と診断の対応 | データが最新である証明。 |
| モデルの改訂番号 | 所有する状態の更新 | 特定の書込みの成功や、全入力の完全性。 |
| キャッシュの世代 | 計算に使った入力との一致 | 操作の必須処理の完了。 |
| 公開順序 | 通知・表示反映の順序 | 元データの削除や、利用者の値の保持の証明。 |
| スキーマ版・互換署名 | 保存形式、解析器などの互換条件 | 現在の操作対象や処理の成否。 |

広いモデルの世代を、狭い変更結果の証票として使いません。番号を追加する場合は、次を説明します。説明できない番号は追加せず、既存の結果や依存関係で表します。

- 種類、管理主体、元データ、更新の契機、有効期間。
- 利用先と、不一致のときの扱い。
- 無関係な変更への反応。
- 診断上の必要性と、廃止の条件。

### キャッシュと通知の集約

読取り側で結果を捨てても安全な場合だけ、最新の要求を優先して古い表示を捨てます。利用者が確定した変更や受理済みの作業は、この規則で捨てません。再計算待ちの集約には、「現在の要求と最新の保留要求」のような既存の小さい境界を使い、終わりのない再試行や無制限の待ち行列にしません。

無関係な更新で高価な全体の再計算が起動する場合は、入力の依存を狭めます。読取りキャッシュの都合で広い失効を認めても、永続確定の正否をそれで判断しません。通知・受付・反映の方針は型付きの選択値で切り替え、診断用の理由の文字列では切り替えません。

### 表示要求の最新性とデータ準備

画面の受付の最新性と、データ自身の変更通知による一覧構築の失効は、別の判定です。

- 短命な正規の受付参照を、UIの副作用から一覧の採用まで渡し、適用済みの画面対象にも対応付けます。依存する更新はその適用済みの参照を検査します。後発の選択を受理してUIへ適用する前の旧い表示を、新しい選択へ付け替えません。
- ライブラリを交換しても選択は保ちます。旧データからの候補は、既存の入力識別と構築番号で不採用にします。

データの準備と表示の終端は、それぞれの所有者が管理します。

- 完成の通知は完成した事実だけを渡し、表示は現在の有効な選択から始めます。
- 開始したデータ準備は、表示が古くなっただけでは取り消しません。表示の失敗は、表示の所有者が既存の操作失敗の通知へ渡します。
- 開始済みの準備・表示・通知は、停止時に実際のTaskの終端を回収します。

#### 重複解析

新規の重複解析は、共通のLへ待たずに受け付けます（[操作の競合ポリシー](operation-concurrency-policy.md#ライブラリ保留保守)）。受理済みの変更に必要な再準備は、親の生存中の権限を借用し、自己再取得や解放後の予約にしません。

初回解析での後発の選択の保護と、明示した保守の成功後の自動選択は、別の操作契約です。明示した保守は成功後の捕捉対象を選び、その準備を、現在の画面によらず親の受付の中で回収します。条件と保証は[重複ファイル](../library/duplicate-files.md#初回解析中の画面移動)に従います。

#### 通常一覧の並べ替え

通常一覧・部分集合・導入一覧の索引、絞込み、順序はUIの外で構築し、行の交換の準備を含む採用全体はUIで実行します。

- 並べ替えは、要求時の整列版と画面の受付を、UIへの入力の前にも検査します。
- 有効な候補の採用、必要な配送、ロックの外での表示同期までを、同じ実際のTaskで所有します。並べ替えの要求もその終端を待ちます。
- 後発の選択で失効した保留中の候補は、構築の取消だけに依存せず、待機を終えます。

### ロックの実状態と表示通知

`ReaderWriterLockSlimWrapper` の実際の取得・解放と保持数の更新は必須です。ライブラリ・プレイリストが操作の可否を判断する保持数は、表示通知より先に確定します。

- 保持数の既存の計上区分は維持し、昇格可能な読取りは書込み相当として数えます。
- 保持数の変更通知は表示への転送です。購読者の失敗で、実際の取得・解放を失敗へ変えません。実際の解放の失敗は、任意通知として抑止しません。
- 表示通知の失敗の診断は最小限にし、通常のロック遷移にはログを追加しません。通知の例外履歴は保管しません。
- `ObservableObject` 全体の通知契約は変更しません。

複数のロックをまとめて取得する範囲（ファイル操作のスナップショットなど）は、解放時に取得済みのロックをすべて逆順に解放し、最初の実際の解放失敗を元のスタックのまま伝えます。取得の途中で失敗した場合も、取得済みのすべてのロックの解放を試し、二次的な解放失敗は局所診断に留めて、元の取得失敗の原因を保持します。同期的な `using` による所有の経路の外にある、所有スレッド外からの操作や二重解放は、保証の対象に加えません。

### 完了と複雑性の確認

完了は、成功・失敗・スキップ・未処理の対象が確定し、必要な保存・反映・公開・解放が揃ったことで判断します。例外がない、世代が進んだ、成功ログが出た、スケジューラーが空いた、といった間接的な情報だけでは判断しません。

新しい状態、世代番号、実行区分、コールバック、再試行、書込み主体、終端、キャッシュを追加する場合は、必要な契約と、既存の構造で表せない理由を示します。置換した処理は退役させ、同じ意味の判定や失敗通知を複数の箇所へ残しません。既存の結果・診断で確認できることのために、常設の状態や対象ごとのログを増やしません。
