# ワークフローと並行性

## 目的と適用範囲

操作の受付、実行中の状態、完了、読取り表示を分け、非同期化で責務や状態を増やし過ぎないための共通設計要件です。新規実装と変更対象へ適用します。全入口が既に同じ構成で実装済みという宣言ではありません。特に起動の必須処理の一連化は[未完了の計画](../../plan/lr2-startup-procedural-orchestration-plan.md)で扱い、現行経路は[起動仕様](../runtime/startup.md)を参照します。

## 用語

[共通用語集](../glossary.md)の管理主体、受付、排他権、操作権限、スナップショット、世代番号、公開、終端を使います。UIの応答性、競合する利用者操作の並行実行、一つの受理済み操作内の計算並列度は別の性質です。

## 仕様

### 受付と完了を一つの責任にする

競合する新しい変更要求は、実行責任を持つ入口で、原則として待たずに `Busy` として拒否します。拒否は未受理であり、後で自動実行する予約や成功として扱いません。拒否前に、副作用を伴う準備・ファイル操作・DB変更を始めません。

受理した操作は必要な処理と取消・失敗時の後片付けまで、論理的な受付の責任を保持します。利用者が待機をやめたことや画面を閉じたことだけで、実処理を追跡対象から外しません。論理的な責任の保持は、物理ロックやDBトランザクションを長時間保持することではありません。

既存の権限を明示的に渡し、同じ操作が別の管理主体で排他権を取り直して循環待ちにならないようにします。ロック・トランザクション内で、UI、確認画面、通知先、別の管理主体を同期的に待ちません。スケジューラーの空きやキャッシュ更新を、単発の必須処理の完了の代用にしません。

### 維持する受付と例外

共通化のために、現在許されている操作や受理済みの予約を失わせません。異なるDBを使うという理由だけで、新しい並行操作を許可することもしません。

| 対象 | 維持する条件 |
| --- | --- |
| 起動中の操作 | 必須のローカル処理・LR2処理が必要な変更操作を制限し得る。閲覧・設定は維持し、任意の通信・先行読込みは全体の解禁条件にしない。未実装の一連化と現行動作を区別する。 |
| 追加ZIP | 既存の導入待ち行列が受理した追加予約は保持し、順に実行する。これを理由にURL・起動時等の別入口へ受付を広げない。 |
| 保留追加・復元に伴う自動推定 | 受理済みの自動推定は保持する。手動の競合要求は拒否し得る。受理は推定先の発見や導入成功の保証ではない。 |
| 試聴・録音と変更 | 競合する新規要求は拒否する。停止後に実際の後片付けが完了してから変更する既存順序を保ち、自動再実行を足さない。一時コピーや設定変更を伴う試聴を単なる読取りと見なさない。 |
| プレイリストの同期・取得 | 通信中の表編集は機能の受付規則に従う。現在安全に行えるライブラリ操作まで全体一律の拒否へ変更しない。 |
| 設定画面 | 閲覧・編集・取消・許可済みの試行を維持する。保存やスキーマ変更は固有の排他を使う。モーダル表示だけで作業中処理の停止を仮定しない。 |
| 確定済み表示 | 閲覧、検索、並べ替えを許可された読取りモデルで続ける。表示から変更する際は受付後に現在の対象へ解決する。 |

### 対象と入力を確定する

画面から持ち越したパス・ハッシュ・行位置だけで、現在の変更対象を代用しません。受付後に意図を保ったまま現在の対象へ一度解決し、古い対象は規定どおり拒否・スキップします。別の対象への読替えや無言の再試行はしません。

確認画面のために排他権を解放して再取得する場合は、承認された対象集合と現在の条件を再検証し、対象を勝手に増やしません。確定直前のファイル存在・保存先等の検証は、利用者の意図を再解釈する処理とは分けます。

処理に必要な設定と入力は、既存の操作プロファイルや用途別のスナップショットで捕捉します。`Settings.Default` の共有編集値を、変更不能な入力と見なして使い続けません。外部の走査結果には取得範囲と完全性を持たせ、部分結果から削除や全件完了を推測しません。

### 変更と公開の順序

一回のライブラリ変更は、成功した物理変更を一つのセッションへ集め、各管理主体へ操作単位で反映します。後続判断に必要な先行成功は操作内の差分で伝えます。対象ごとのDB確定を、判定間の通信手段にしません。複数のDB・外部出力を一つの原子的トランザクションに見せる保証も設けません。

処理は、入力準備、永続確定、必要なメモリ・索引反映、必要な公開、任意通知、終端を、機能固有の依存順で明示します。必須反映を任意通知へ格下げせず、任意のキャッシュを全更新するための新しい完了待ちは追加しません。失敗は実際の結果へ保持し、通知の時機だけで成功を推測しません。

一回限りの必須手順は、型付きの要求・結果と明示的な非同期待機で接続します。通知や世代番号の変化から次の段階を推測するより、実際の結果を直接渡します。必要な公開が排他権の解放後なら、その後まで追跡します。

### 世代番号の用途

| 種類 | 識別するもの | 代用できないもの |
| --- | --- | --- |
| UI要求の世代 | 古い表示要求と現在の要求 | 永続確定、受理済み変更の取消。 |
| 操作ID | 一回の操作と診断の対応 | データが最新である証明。 |
| モデルの改訂番号 | 所有状態の更新 | 特定の書込み成功や全入力の完全性。 |
| キャッシュの世代 | 計算に使った入力との一致 | 操作の必須処理完了。 |
| 公開順序 | 通知・表示反映の順序 | 元データの削除・利用者値の保持の証明。 |
| スキーマ版・互換署名 | 保存形式、解析器等の互換条件 | 現在の操作対象・処理の成否。 |

広いモデルの世代を、狭い変更結果の証票として使いません。番号を追加する場合は、種類、管理主体、元データ、更新契機、有効期間、利用先、不一致時の扱い、無関係な変更への反応、診断上の必要性、廃止条件を説明します。説明できない番号は追加せず、既存の結果や依存関係で表します。

### キャッシュと通知の集約

読取り側で結果の破棄が安全な場合だけ、最新の要求を優先して古い表示を捨てます。利用者が確定した変更や受理済み作業を、この規則で破棄しません。再計算待ちの集約は既存の「現在と最新の保留要求」などの小さい境界を使い、終わりのない再試行や無制限の待ち行列にしません。

無関係な更新で高価な全体再計算を起動する場合は、入力依存を狭めます。広い失効を読取りキャッシュの都合で認めても、永続確定の正否はそれで判断しません。診断用の理由文字列で通知・受付・反映方針を切り替えず、型付きの選択値を使います。

### 完了と複雑性の確認

完了は、成功・失敗・スキップ・未処理の対象、必要な保存・反映・公開・解放が揃ったことで判断します。例外がない、世代が進んだ、成功ログが出た、スケジューラーが空いた、という間接情報だけでは判断しません。

新しい状態、世代番号、実行区分、コールバック、再試行、書込み主体、終端、キャッシュには、必要な契約と既存構造で表せない理由を示します。置換した処理は退役し、同じ意味の判定や失敗通知を複数箇所へ残しません。既存の結果・診断で確認できることのために、常設の状態や対象ごとのログを増やしません。

## 実装とテストの対応

| 仕様項目・主な条件 | 実装箇所 | テスト箇所・確認内容 |
| --- | --- | --- |
| 変更受付から終端までの責任 | [ライブラリ変更](../library/mutations.md)の各管理主体 | 同仕様の実入口テストで、競合拒否、受理済み処理、部分成功、公開時機を確認する。 |
| 起動・再読込みの区別 | [起動](../runtime/startup.md)、[進捗](../runtime/progress.md) | 各仕様の管理主体テスト。必須処理の一連化は[計画](../../plan/lr2-startup-procedural-orchestration-plan.md)の未完了要件として扱う。 |
| 導入予約と自動推定 | [ドロップ導入](../library/drop-install.md)、[導入先推定](../library/install-estimation.md) | 各仕様の受付・待ち行列・先行成功依存のテスト。 |
| 設定・試聴・終了 | [設定](../runtime/settings.md)、[音声](../runtime/audio.md)、[終了](../runtime/shutdown.md) | 各仕様で、実際の完了と後片付けまでの経路を確認する。 |
| 世代番号と新しい状態の採用 | 対象機能の要求・結果・管理主体 | 自動テストで規定全体を固定せず、設計と差分を点検する。機能テストでは本番の入口からの時系列と結果を確認する。 |
