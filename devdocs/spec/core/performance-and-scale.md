# データ規模と性能

## 目的と適用範囲

カタログ・DB・索引・キャッシュ、導入・削除・走査、一覧、起動の設計と性能受入の正本です。新規実装と変更対象へ適用する要件であり、現行の全経路が代表規模で測定済みという宣言ではありません。未達の既存経路は制約として示し、無関係な全面改修を一律に要求しません。

## 用語

[共通用語集](../glossary.md)の実時間、処理量、差分、計測点を使います。`C` は所持譜面数、`D` は譜面フォルダ数、`K` は逆引きキー数、`E` はフォルダ別リソース登録数、`F` は列挙件数、`L` はプレイリスト項目数、`P` は一操作のパッケージ数、`Δ` は変更対象を表します。

## 仕様

### 優先するもの

同じ仕事を正しく完了するまでの時間短縮と処理量の向上を最優先にします。索引保持、計算結果の再利用、一括処理、独立計算の並列化を認め、CPU使用率や常駐メモリが高いだけでは不合格にしません。メモリ削減のために同じDB取得・ファイル読取り・ハッシュ計算・解析・索引構築を繰り返しません。

並列度の最大化自体も目的ではありません。ロック・I/O競合、GC、ページング、一時コピーが遅延の原因なら、その原因を減らします。固定のRAM・CPU上限やキャッシュ最小化目標は置かず、資源上限が必要な機能では理由と速度への影響を示します。

メモリ不足、停止、破損、不要な旧世代の無期限保持、取消・終了・WPFのスレッド制約違反は許容しません。UI外の計算を並列化することと、UIスレッドで重い同期処理をすることは別です。最初の表示だけ早くし、必要な仕事を後処理・遅延取得・次操作へ移した場合は、その完了と後続操作への影響も測ります。

### 代表規模

[代表ライブラリの測定記録](../../acceptance/performance-reference-2026-09-09.md)を、少なくとも検討・検証する規模として使います。入力上限ではなく、より大きい入力を切り捨てる根拠にはしません。

| 対象 | 規模 | 数え方・制約 |
| --- | --- | --- |
| 所持カタログ `C` | 約21万譜面 | BMS・BMSON混在。同一MD5の複数配置を含み、ハッシュの種類数とは異なる。 |
| 譜面フォルダ `D` | 約3万 | 直下・祖先込み・物理列挙の数は区別する。 |
| 逆引きキー `K` | 約800万台 | 音声・画像・動画のカテゴリ別キーの合計。実ファイル数ではない。 |
| フォルダ別登録 `E` | 約1,200万台 | 譜面フォルダごとのリソース登録。複数フォルダの関係を含む。 |
| 列挙件数 `F` | 約1,200万台 | 列挙した仕事量。異なるキーの数と区別する。 |
| `song` / `bmson_song` | BMS約21万行 / BMSON約1千行 | 同じハッシュが別パスに存在し得る。BMSONをLR2の `song` に入れない。 |
| フォルダ行 | 約3万台 | 通常フォルダ、祖先、独自出力の範囲を区別する。 |
| 譜面情報等 | 各約21万件級 | `chart_digest_map`、`chart_info`、`maintenance`。部分キャッシュ、所持主体のない情報、解析失敗を区別する。 |
| 表・項目 `L` | 約500表 / 約58万項目 | 同じ譜面の複数表所属と未所持項目を含む。 |
| 独自フォルダの出力 | 約31万件 | 物理出力件数。DB行・表数とは別。 |
| スコア・IR | 約2万行級の読込み | 参照記録での観測であり、履歴総数や容量上限ではない。 |

正確な件数・ログ名・チェックサムは測定記録へ集約します。DB容量、索引容量、文字列・BLOB長、逆引き候補数の分布は、この件数だけでは分かりません。必要な比較ではファイル容量、実際の行数・索引・キー分布も記録します。

操作の基準は20 ZIPの一括投入と単一パッケージです。参照操作では20パッケージ・24譜面・20削除フォルダですが、一般に一ZIPが一譜面とは限りません。パッケージは複数譜面と数百のリソースを含み得ます。検証には千件級も含めますが、実分布や最大値が未測定のため上限には使いません。複数譜面が共有するリソース、逆引き変更0件、物理存在確認の回数を区別します。

導入先推定の探索上限は別契約です。[導入先推定](../library/install-estimation.md)では通常10,000ファイル未満を想定し、ディレクトリのパッケージ根ごとに50,000項目で探索を打ち切り、不完全な結果を使わず警告します。この安全境界を、ライブラリ全体の容量上限と混同しません。

### 全件処理と局所処理

局所変更の仕事量は、主として変更対象・関連キー・必要な祖先に依存させます。小さい操作の反復と巨大集合が掛け合わさる `O(P*C)`、`O(P*K)`、`O(ΔD*K)` は退行リスクです。処理をコンストラクター・プロパティ・別管理主体へ移しても仕事量は減りません。

| 経路 | 要件 |
| --- | --- |
| 起動・明示的な全走査 | 必要な全件構築は認めるが、同じ世代の同じ入力を段階ごとに読み直さない。完全性・代替経路の条件を維持する。 |
| 初回の索引取得 | 初回コストを明示し、同じ世代の構築を共有する。パッケージごとに再構築しない。 |
| 少数の導入・移動・削除 | 内側の反復で全カタログ・全逆引き・全プレイリストを走査・複製・整列しない。 |
| フォルダ判定・LR2同期 | 対象パス、関連フォルダ、祖先を既存索引から得る。少数の存在確認だけで全BMS一覧を作らない。 |
| 複数対象の変更 | 一操作の変更セッションで、前処理、DB・索引反映、LR2同期、必要な公開を集約する。 |
| 一覧の絞込み・整列 | 全件が必要な問い合わせと可視行の表示を分け、無関係な更新で全順序を捨てない。 |

全件処理が本当に必要なら、規模、頻度、既存索引で代替できない理由、比較区間と結果を示します。「変更不能だから」「安全側だから」だけで全件複製を選ばず、計算量と定数項・候補数・実測を併せて評価します。

### 再利用と保存

スナップショットは、既存世代、構造共有、差分、影響範囲だけの変更不能な値を利用します。公開済みの可変配列を無保護で共有しません。変更なしの判定前に巨大な辞書を複製して捨てず、対象キー・カテゴリ・候補集合で判定します。逆引きが不変でも、フォルダ対応は変わり得ます。

実変更も操作内で集約し、中間読取りが必要な世代、部分成功、失敗時の旧スナップショットを守ります。結果記録には利用先が必要な事実だけを持たせ、全パスの二重整列や索引の再作成を固定費にしません。失効範囲を入力依存に合わせ、同じ失効への再構築は既存の集約境界を使います。

DBは問い合わせ数だけでなく、読み出す行数・列・索引を確認します。少数パスの処理を全テーブル取得後の絞込みに戻さず、既存窓口でパラメーター化、集合取得・更新、分割処理を使います。パスの識別、同じハッシュの複数所持、動作モード、部分キャッシュの意味を変えません。

同じパッケージの列挙・バイト列・ハッシュ・解析結果は、有効期間の範囲で再利用します。同じ内容でも新しい保存先のリソース存在確認は別です。外部変更、削除結果、解析器・スキーマの版など、再確認が必要な条件は明示します。必要な警告や確認を落とした短縮は認めません。物理処理は件数に加え、容量、同一・別ボリューム、展開済みか、削除方式、失敗・再試行数も記録します。

### 操作単位の反映

競合操作の受付、一操作内の独立計算の並列化、対象の逐次処理は分けます。先行パッケージの実成功が次の分類に必要なら、操作内の成功差分で渡します。逐次判断は対象ごとのDB確定・索引更新・通知の理由にはしません。

一回の確定要求を一つの `LibraryMutationSession` にまとめます。物理処理は対象ごとでよく、成功の旧新事実を追加します。DB、保存行、参照、所持集合、逆引き、関連キャッシュ、LR2、必要な公開は、各管理主体へ原則一回反映します。SQL分割や別DBのトランザクションは認めますが、同じ全体処理を対象数だけ繰り返しません。

事前に判断できるスキップ・衝突・古い対象は通常結果に集約します。予期しない例外は安全でない後続を止め、成功済みと未確認の対象を残します。全対象を元へ戻す擬似トランザクションは要求しません。具体的な保証は[ライブラリ変更](../library/mutations.md)と[整合性](../library/file-db-consistency.md)に従います。

### 計測する完了範囲

主指標は操作の実時間です。CPU時間、割当量、GC、常駐量は原因調査に使います。処理量は譜面/秒、リソース/秒、バイト/秒など単位を示します。

| 操作 | 比較する範囲 |
| --- | --- |
| ZIP投入・保留準備 | 受理から展開・発見・分類・保留登録・必要な推定結果まで。登録と推定の完了は分けてもよい。 |
| 導入 | 確認後の受付から、必要な物理・DB確定、正本と譜面情報の反映、公開・後片付け・終端まで。 |
| 削除・移動・統合 | 受付から対象処理、カタログ・逆引き・LR2、後片付け、終端まで。失敗件数・状態も比較する。 |
| 起動 | 導入準備、操作解禁、必須初期化、後続処理を分ける。スケジューラー外の処理も区別する。 |
| 再読込み・保守・補完解析 | 発見から必要な読取り・計算・保存・反映まで。変更・不変・スキップ・総数を示す。 |
| 一覧・プレイリスト | 受付から正しい検索・整列結果の反映と有用な描画まで。後続集計・先行読込みは別記する。 |

利用者の回答待ちと候補計算、待ち行列・ロック待ち、必須表示、任意の先行読込みを分けます。遅延の区間を外へ移しただけで改善としません。入れ子や並列の累積時間を独立区間として合算せず、計測名と実際の範囲を揃えます。範囲変更時は旧値との比較可否を示し、未計測・欠測を0へ補完しません。

### 変更セッションの集約診断

`LibraryMutationSession.Commit` が返す時点の集約値を、排他権の解放後に `library_mutation_session_apply_done` として一回記録します。作業中の一時集計と変更不能な `LibraryMutationSessionApplyCounts` を使い、永続状態や対象ごとの同期ログを増やしません。

| フィールド | 意味 |
| --- | --- |
| `reason` / `changeCount` | 診断名と、受理した確定変更数。理由文字列で挙動を分岐しない。 |
| `durableCommit` / `requiredFailure` | この時点の永続確定と必須処理失敗。物理変更を取り消す値ではない。 |
| `catalogApplyCount` | カタログ移転・削除の反映試行数。 |
| `installedTargetApplyCount` | 導入先・導入行の反映試行数。カタログ反映とは別系統。 |
| `packageReferenceApplyCount` | カタログ変更に伴うパッケージ参照反映の試行数。導入行書込みや個別物理完了数ではない。 |
| `reverseLookupApplyCount` | 移動・導入・統合・削除フォルダ集合をリソース管理主体へ渡した回数。分割SQL数・フォルダ数ではない。 |
| `lr2SyncCount` | LR2同期主体の呼出数。モード無効やBMS変更なしで内部処理が不要でも、呼出しは数える。 |
| `requiredPublicationCount` | 準備した通常通知グループ数。後の必須失敗で非公開になり得る。通知先の実行・成功数や失敗診断数ではない。 |
| `folderDbTargetRows` | 移転成功の結果記録にある実際の既存フォルダ行数。要求パス数ではなく、対象なし・DB失敗で成功記録なしの場合は0。 |
| `folderDbFullScanCount` | カタログ移転でのフォルダ全件取得数。現在は完全一致の分割問い合わせだけのため0。別目的のLR2全体同期は含めない。 |

呼出し直前に加算し、途中失敗でも到達した段階を残します。未到達は0、変更なしは全0で、失敗後に成功用固定値へ置き換えません。正常な複数対象操作で、同じ反映が対象数に比例する状態は構造上の退行です。

この計測点はセッションの反映範囲であり、操作全体の完了ではありません。統合後の予約再取得を伴う `PostCommitMaintenance` と最終表示は後続します。その失敗は同じ結果の `WithFinalizationFailure` へ保持し、既に数えた反映回数は変えません。

### 比較条件と受入

基本シナリオは、同じ検証用のファイル・DB・設定へ20 ZIPを保留投入し、既所持警告を無視して導入し、新規画面からその追加譜面を削除する操作です。実利用中のライブラリではなく複製を使い、各測定前に状態を復元します。「削除したから元どおり」とは仮定しません。合成入力では、その入力の正しい件数を期待値にします。

変更対象に応じ、固定差分で背景規模を増やす、固定背景で1個と20個を比べる、1・3譜面と100・500・1,000リソースを組み合わせる、逆引き変更なし・空カテゴリ・少数キー・大きい候補集合を使う、複数所持・形式混在・入れ子・部分失敗を通す、初回と再利用を分ける、といったケースを選びます。全組合せの毎回実行は要求しません。

基準版は通常変更直前のコミットです。既知の古い退行を調べる場合も、その版を別の基準として示します。実行物とビルド設定、ハードウェア・OS・ランタイム、DBと入力、設定・表示列、Everything、容量、キャッシュ、並行処理、ログ条件を揃えます。通常は各5回以上を目安に順序を交互にし、全値・中央値・範囲を残します。初回・再利用・起動直後は別群とし、異なる20パッケージを20回の反復とは数えません。少数標本から安定したp95や有意差を主張しません。

受入では、結果・安全性・警告を維持し、操作別の再現する悪化を他操作の短縮で相殺しません。局所変更で全件仕事を増やさず、反映回数と実測を確認し、後処理や次操作への遅延付替えも調べます。未測定・条件不足は制約として示し、機能テスト成功を大規模性能の成功としません。固定の秒数目標や許容退行率は、基準データと反復測定なしには定めません。検証実行の300秒等はアプリの性能予算ではありません。
