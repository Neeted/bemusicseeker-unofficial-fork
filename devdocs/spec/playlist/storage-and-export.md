# プレイリストの保存と更新

## 目的と適用範囲

プレイリストの正本、外部同期の取得と変更判定、手動編集、JSON出力、SQLバックアップと復元を定めます。LR2向けの出力は[LR2カスタムフォルダ出力](lr2-custom-folders.md)、beatoraja向けの出力は[BMT出力](bmt-export.md)で定め、DB保存の成否と区別します。

## 用語

[共通用語集](../glossary.md)に従います。この仕様では次の語も使います。

| 用語 | 意味 |
| --- | --- |
| P | [操作の競合ポリシー](../core/operation-concurrency-policy.md)が定める、プレイリストの正本と必要な管理出力の変更受付。Lはライブラリ側の変更受付。 |
| 項目 | 表に属する一件の譜面の記録（`playlist_entry` の一行と、そのアプリ内の表現）。 |
| 所属 | 項目が属するフォルダと、その中で項目を識別する所属キーの組。 |
| 項目版 | 項目の表示内容の更新を識別する世代番号。所属・解決キーへの依存とは分ける。 |
| 削除履歴 | `is_removed` が1の項目。生存する所属としては数えないが、行として保持する。 |
| 下書き | 保存前の編集内容。新規プレイリストの下書きは、保存するまで正本に含めない。 |
| 確定結果 | DB保存の成功後に、変更前後の値・所属・順序を変更不能な形で記録した結果記録。項目では `PlaylistEntryCommitReceipt`。 |

## 仕様

### 正本と識別

#### 保存する表

永続化の正本は本アプリの `playlist`、`playlist_entry`、`playlist_course` の三表です。共通の `app_schema=1` に含まれ、プレイリスト専用のスキーマ版は持ちません。LR2連携・スタンドアロンの両方で保存します。

| 表 | 主な列と意味 |
| --- | --- |
| `playlist` | `playlist_id`、`name`、`symbol`、`tag`、`page_url`、`header_url`、`data_url`、比較用の `header_sha256` と `data_sha256`、互換フォルダ名の `compat_prefix`、更新日時 `last_update` を保持する。 |
| `playlist` の表示・出力設定 | `output_dir`、`custom_folder_output_base_name`、`is_root_folder`、`ignore_folder_output`、`folder_order`、`folder_sort_key`、`folder_sort_ascending`、`is_external_sync`、`bmt_sort`、`is_bmt_output`。 |
| `playlist_entry` | 所属ID、`md5`、`sha256`、`title`、`artist`、`folder`、`level`、`url`、`url_diff`、`name_diff`、`org_md5` と、ローカル状態の `memo`、`adddate`、`is_removed`。 |
| `playlist_course` | `course_id`、所属ID、元の順序 `course_order`、正規化した `course_json`。 |

アプリ内の現在値・所属・明示順序は、管理主体の `BMSPlaylist`、`PlaylistAggregatePersistenceOwner`、`BMSTable` が所有します。DB保存が成功した後に、同じ項目の参照へ確定値を採用します。

#### 起動時の項目読込み

起動時は[型付きの生値読取り](../core/performance-and-scale.md#全件処理と局所処理)で項目を読み、読取り専用の最終集合を作ります。読込みのために保存値を書き換えません。

| 保存値 | 読込み結果 |
| --- | --- |
| REAL型の `level` | doubleのビット列を保つ。 |
| `adddate` | 1tickまで保つ。旧スキーマの `adddate TEXT` には通常の書込みもticksをTEXTで保存するため、固定形式のTEXT ticksを受理する。ticks以外の日付文字列を地域設定から推測しない。 |
| 所属IDがNULL・範囲外・REAL型・型不適合の行 | 除外する。削除履歴の行は保持する。 |
| 型が合わない `level` | null とする。 |
| 型が合わない真偽値 | false とする。 |
| 型が合わない追加日 | 項目を生成したときの既定日時を保つ。 |

#### 親MD5の遅延解決

親MD5（`org_md5`）の保存生値は、必要になるまで解決せずに保持します。公開の読取り（`Org_md5`）、複製・再読込み用の複製、JSON出力、BMT出力は、同じ一回の遅延解決を通して、同じ親の列と入力順を読みます。

- MD5あり・SHA-256のみの項目、親が0・1・複数件のいずれでも、既存の解析・正規化、空とnullの意味、外部形式を保ちます。
- JSONの `org_md5s` は全親の列、`org_md5` は先頭の親または空文字です。
- 読取りのために元DBを補正せず、起動時に全件を展開しません。

BMTの出力と、旧生成物の通常再生成は[BMTの形式とハッシュ](bmt-export.md#形式とハッシュ)に従います。

#### 項目集合の取込み

JSON解析、内蔵リコメンド・難度推定、DB読込みで完成した項目の集合は、共通の `BMSTable.entries` の設定処理で一度に取り込みます。取込みでは、項目の親、正規化、フォルダの派生状態、読込み状態、項目版を揃えます。

- 公開する所属の列は、構造を共有した読取り専用の列です。未変更の項目の参照と明示順序を保ちます。
- 項目自体は管理主体が更新します。変更不能な入力が必要な読取り側は、読取り区間の中で、必要な値と項目版を同時に捕捉します。
- 少数の追加・削除は対象だけを候補にし、全行の複製・退避・再取込みを行いません。
- MEMO・URL・levelだけの更新では、所持数を再集計しません。

#### 所持譜面の解決と所属キー

項目の所持譜面の解決、所持の集計、参照索引への登録には、MD5があればMD5、ない場合だけSHA-256を使います。所持候補とMD5が一致しない場合に、同じ項目のSHA-256へ探索を広げません。

手動追加では所持譜面から分かる両ハッシュを保存し、外部同期では取得元の値を保存します。手動追加の `org_md5` は、同じディレクトリにある所持BMS・BMSONのMD5の集合です。

表内の所属キーは、表と宛先フォルダごとに、空白だけでないMD5、SHA-256、`lr2_bmsid`、titleの順で最初の値を使い、すべて空なら空キーとします。ハッシュの設定・読込み時の既存の正規化とOrdinal比較を維持します。MD5が同じならSHA-256やtitleが異なっても同じ所属キーで、フォルダが異なれば別の所属です。この所属キーは、所持譜面の解決とは別の規則です。

#### 所持譜面の参照解決索引

所持譜面の参照解決索引はカタログの管理主体が所有し、候補の識別・ハッシュ・配置・候補順に依存します。

- 表示用の譜面の値は保持しません。候補の解決と、選んだ[所持項目の識別](../glossary.md)の現在値・カタログの世代番号を、共通の読取り区間で捕捉します。
- 無関係な内容の変更だけでは候補索引を再構築しません。取消と、ダイジェスト更新範囲の待機を維持します。
- 構築済みの索引へは変更事実を差分で適用し、未構築なら構築を起こしません。同じMD5の別配置と、捕捉済みの旧索引を保持します。

排他の境界は[データと索引](../core/data-and-indexes.md)に従います。

カタログが変わった後も、プレイリスト詳細は有効な項目を保持します。最後に一致していた配置が消えれば未所持にし、別の配置が残れば既存の代表選択で再解決します。サマリーの所持・未所持の集計も更新しますが、表の所属、総項目数の算定規則、同期STATUSは、カタログの変更だけでは変えません。表示の更新だけで、項目のDB値や出力ファイルを変更しません。詳細とサマリーの採用・再利用は[一覧表示](../ui/table-view.md)に従います。

#### ヘッダーの一括保存

ヘッダーの一括保存で現行の対象を要求する場合（`requireCurrentTarget=true`）は、要求した非空の対象に一件でも退役した参照があれば、全件が失効している場合も含めて、DBを変更する前に失敗させます。入力が空なら何もしません。現行の参照の集合は保存要求の中で一度だけ構築し、対象ごとに全件を再走査しません。`false` では、現行の参照だけを保存します。編集の受付での全対象の検証は[プロパティと一括編集](../ui/playlist-properties.md)に従います。

#### コース

コースはヘッダーに由来します。入れ子の配列もコースオブジェクトへ平坦化します。コース専用のハッシュは保存せず、ヘッダーハッシュで更新を判定します。DB内部でのコースの改ざん検出は目的にしません。

#### 数値の所属・順序

JSONの数値の `level_order` / `folder_order` と、データの数値の `level` / `folder` を所属・順序の文字列にするときは、Invariantの書式を使います。受理済みのJSONの基本型の範囲、文字列・装飾名・null、互換接頭辞の扱いは維持し、文字列を一律にJSON表記へ変換しません。数値levelから作るLR2のLEVEL分類は[LR2の出力種類](lr2-custom-folders.md#出力除外と種類)に従います。

#### LR2の出力先を変える保存

LR2の管理出力先を変える保存は、副作用の前に[出力配置条件](lr2-custom-folders.md#出力先と事前検査)を満たす必要があります。配置が変わる表または新規の表が他の表と重なる場合だけ拒否し、他の表同士の保存済みの衝突は問いません。保存済みの衝突に残る表は、出力・移行・出力削除・DB行の整理・ROOT登録の追加と除去を行わず凍結します。正本の保存や出力先の自動修正は行いません。

配置を変えない項目の追加・削除は、DBを先に確定します。保存済みの衝突に残る表の付随するLR2出力は止め、編集済みのDB・モデルを保持して、止めた表を診断ログだけに残します（警告は表の属性の明示保存・明示の再読込み・外部登録・SQL復元に限ります）。出力以外の付随する処理の失敗は、確定後の失敗として通知します。

### 保存済みヘッダーの配送

DB保存の成功と現在値の採用を行う同じ保護区間で、次の値を小さな変更不能なヘッダーとして、既存の確定結果へ捕捉します。

- 表の参照とID
- 名前、記号、互換接頭辞、出力先、更新日時、URL
- 同期・ルート・BMTの各フラグ、順序、出力基点名

件数、STATUS、設定、全項目は載せません。ヘッダーだけの変更では、項目版と更新日時を保ちます。無変更、拒否、DB保存前の失敗では、存在しない変更を登録しません。

既存の単一の配送処理が、保護区間の解放後に配送します。同じまとまりで同じ生存表に複数のヘッダーがあれば、最後のヘッダーを投影します。退役した参照を、同じIDの新しい表へ転用しません。ヘッダーだけの変更では、詳細の再構築や件数の再集計を起動せず、非表示の記録を含む対象行と、その絞込み・整列位置だけを更新します。初回の構築と再表示も同じ投影を使います。

プロパティ、行内編集、一括属性、BMT順、項目の更新、既存表への取込みは、保存済みのヘッダーをこの配送へ集め、必要な出力と実際の表示の終端まで、同じ操作権限で待ちます。一覧の集計を開始した操作に限り、表示の終端は、その集計の採用、取消、または後発の独立した要求に取って代わられた古い要求として採用されずに終わることです。後発の要求に取って代わられた場合の表示は後発の要求が所有し、操作は後発の要求を待ちません。

- DB保存の後に出力が失敗しても表示を試み、元の失敗を保持します。
- 設定による表示名は公開済みの設定を使います。DB保存の後、設定の公開前に失敗しても、その時点の確定値を配送します。
- 前の操作の表示失敗を、次の操作へ持ち越しません。

### プロパティのURL

Page・Header・Dataは、nullによる明示的な解除を受理します。非nullの指定は次の値だけを受理します。

| URL | 受理する非nullの値 |
| --- | --- |
| Page | 有効な絶対URI |
| Header・Data | 有効な絶対URIまたは相対URI |

同期OFFでは、URLの未設定と、Header・Dataの片方だけの指定も許容します。不正な非nullの入力を、未設定や旧値へ置き換えて保存しません。画面での空欄・変換失敗と訂正・取消は[プロパティ画面](../ui/playlist-properties.md#単一プレイリストの編集)に従います。

外部同期のONは、優先取得元 `Page ?? Header` が絶対URIなら受理します。Pageだけ、絶対Headerだけ、絶対Pageと相対Header、ローカルURIも対象です。ONの操作は候補だけを変え、通信と保存はOKまで行いません。

OKで保存するとき、次のいずれかがあれば、既存の取得処理を一回だけ実行します。

- 保存済みのOFFからONへの変更
- 実効取得元の変更
- 保存済みのHeader・Dataを、今回の保存で新たに空欄にしたこと

非空のDataの変更、Pageに隠れた非空のHeaderの変更、同値の保存、取得失敗後の同値の再保存では取得しません。

取得が保存済みの空欄のURIを補完した場合もヘッダーを保存し、現在の表へ採用します。本文・項目が変わらなければ、本文ハッシュ・更新日時・項目の保存を変えません。Dataまで読めた完成した表だけを採用し、途中で失敗した場合は、確定した設定と旧項目を保持します。

### 互換フォルダ名

新規取得と明示的な外部データの初期化では、次の順で互換接頭辞を決めます。レベル値が数字か記号かでは決めません。

1. ヘッダーに `compat_prefix` があれば、空文字やCP932の範囲外の文字を含む場合も、その値を保存します。
2. なければ `tag`、次に `symbol` を候補とし、選んだ値をCP932で厳密に表せる場合だけ採用します。
3. 表せない場合は、文字を削ったり次の候補へ切り替えたりせず `LEVEL ` とします。候補がない場合も同じです。

明示的な接頭辞がないヘッダーの `folder_order` は、読込み済みのフォルダ名と一致する値をそのまま保持し、それ以外を互換レベル名として接頭辞付きへ変換します。保存時は接頭辞をヘッダーへ明記します。通常の外部同期では、取得元の明示値よりDBに保存済みの接頭辞を優先し、推定し直しません。

接頭辞の変更は、各フォルダ名の先頭にある旧接頭辞だけを除いて、新しい接頭辞を付けます。旧接頭辞がなければ元の名前全体へ付けます。既に新しい接頭辞で始まる名前も特別に扱いません。変換途中ではなく最終名の重複を検証し、重複すれば既存の構成を保持して失敗とします。

接頭辞の変更で項目のフォルダ名が変わる場合は、同じ保存単位で保存し、詳細表示の版を進めます。ツリー、FOLDER列、選択中のフォルダキーを同じ対応で更新します。接頭辞だけの変更では外部表を再取得しません。

### 既存DBの正規化

不足する `bmt_sort`、`is_bmt_output`、`custom_folder_output_base_name` は列の追加で補い、専用の表の再構築を行いません。

| 列 | 既存値の正規化 | 新規表の値 |
| --- | --- | --- |
| `custom_folder_output_base_name` | NULLは既定の通常出力先。 | NULL |
| `is_bmt_output` | NULLはtrue。 | true |
| `bmt_sort` | 既存の有効値を優先し、名前・IDで同順位を解消して、1始まりの一意な順序へ揃える。 | 最大の順序+1 |

通常の外部更新では、この3設定を保持します。出力除外ビットの既存値は維持し、新しく増えた種類まで除外するようには拡張しません。

### 外部取得と公開の境界

#### 取得元と相対参照

取得操作で受け付けるURIと、保存済みの表の外部同期元は別の契約です。取得操作は各転送でHTTP(S)だけを許可します。保存済みの外部同期元では、相対・ローカル・ドライブ・`file:`・UNCを維持し、HTTP専用の検証を流用しません。

HTMLは、アプリのHTTP管理主体が取得した本文だけを解析し、パーサーに再取得や外部DTDの取得をさせません。ページ、ヘッダーJSON、データJSONは各一回取得します。相対ヘッダーURLはページ、相対データURLはヘッダーを基準に解決します。

HTTP転送後の相対参照は[外部表の転送と相対参照](downloads.md#外部表の転送と相対参照)に従います。転送があっても、次回の同期元は次のとおり保持し、一時的な転送先へ置き換えません。

| 入力 | 次回の同期元として保持する値 |
| --- | --- |
| HTML | 元の `Page_url`。HTMLにある生の相対ヘッダーを元ページで解決した先が実際のヘッダー要求先と異なる場合だけ、既存の `Header_url` に実際のヘッダー要求先を保存する。 |
| ヘッダーJSONの直接指定 | 元の `Header_url`。 |

完成する表の `GetAbsoluteDataUrl()` が実際の最終データURIと異なる場合だけ、既存の `Data_url` にその実URIを保存してから項目を読み込みます。同じ参照なら、通常の生の相対表現を保持します。

- 返却する表、登録保存、DB再読込みと公開のデータ基準で、項目の本体・差分URLの意味を揃えます。最終URIを永続化する列を追加せず、本文ハッシュにも混ぜません。
- 参照が同じかどうかは `Uri.Equals` で判定します。HTTPのパス・クエリの有意な大小文字を保ち、フラグメントだけの差を変更として扱いません。
- 保存済みの同期元のfile・ドライブ・UNCの解決の意味も維持します。

#### 取得と画面反映の実行境界

取得と解析はUIスレッドの外で行います。表の集合の書込みロックは、重複確認・採番・出力先の算出などの短い状態変更に限り、DB保存はその外で行います。確定後の表示集合への追加・置換はUIスケジューラーへ渡し、その処理の完了を待ってから成功とします。UIの完了を待つ間は、表・集合・UIのロックを保持しません。

置換の受付拒否、取消、中断、例外は再読込みの失敗です。独自の時間切れで成功を推定したり、旧表示のまま成功として扱ったりしません。受付と継続は[競合ポリシー](../core/operation-concurrency-policy.md#プレイリストと必要出力)に従い、必要出力・公開・後片付けの終端を待ちます。

#### URL指定の複数行取込み

URL指定の複数行の取込みは、取得を既存の上限内で並列化し、登録をまとめて行います。既存の名前、または同じ要求の中で先に予約した名前と重複する表は、改名せずに省略し、完了時に件数と名前を通知します。ライブラリ参照、サマリー、URL補完は、登録済みの集合へ一括で反映します。進捗には、取得の後の登録・参照・完了処理も含めます。

#### 出力名が空になる表の登録

通常のURL・JSON取込みの単表・一括登録で、空のLR2出力名を拒否するのは、その操作で捕捉した動作モード（`OperationModeLR2DB`）がLR2連携の場合だけです。

- 取込みの候補準備も、実際のDB窓口から捕捉したモードを使います。LR2連携の混合要求では、出力名が空の対象だけを失敗として除外し、有効な表の登録と必要出力を進めます。
- スタンドアロンでは、`한글` のようなUnicodeの実名とASCIIの `tag` から、CP932向けの `Output_dir` が空になっても、登録・保存・再読込みを許可します。実名・タグ・項目行とJSONの意味値を保持し、翻字・仮のASCII名・強制的な改名は行いません。

重複したURL・名前の扱いと、必要なBMT出力は維持します。LR2連携の出力名・配置の検査は[LR2出力](lr2-custom-folders.md#出力先と事前検査)に従います。

#### 取得失敗とSTATUS

全体同期、手動再取得、起動後の同期では、未採用の外部表の通信、ローカル同期元の読取り、解析の失敗を、取得境界での対象の失敗として扱います。

- 原因の許可リストを続行の条件にしません。未分類の通常の失敗も、既存の「その他のエラー」として残します。
- 詳細はログに記録し、失敗した表の既存データを保持します。取得できた他の表の確定を妨げません。
- 処理済みの取得失敗を、親が操作全体の例外へ再集約・再送出しません。全対象に失敗した場合も、完了通知を全件成功にはしません。

表ヘッダー・データのJSON形式の失敗だけを、対応する解析例外へ変換します。内部故障・資源不足を入力不良へ包装しません。任意の順序・ハッシュ・URL・親ハッシュの項目で従来許容していた不正値の省略は、その入力変換だけを囲む境界に残します。項目集合・フォルダ状態の必要な反映や、購読先の故障は解析失敗へ変換しません。

採用する `last_update` と `adddate` の文法・空値・保存前の停止は[JSON日時の読取り](#json日時の読取り)に従います。通常の新規登録は、読み取った時刻を1tickまでDBへ保持し、再同期では既存項目のローカルの追加日を保持します。既存DBの誤った年を推測して補正しません。

STATUSは404、403、その他のHTTPエラー、通信失敗、ヘッダー未検出、ヘッダー形式不正、データ形式不正、URL不正を区別します。ローカルの読取り失敗は「その他のエラー」を使います。

同期STATUSは、分類・確認日時・取得元・失敗時の診断を事実として保持し、状態名と詳細の文言、整列順、失敗判定は、読取りのたびにその事実から作ります（`PlaylistSyncRuntimeStatus`）。

- 表示言語を変えると、同じ状態のまま、現在の資源（追加辞書を含む）の語に更新されます。詳細の先頭行は現在の状態名で、残りの日時・取得元・診断は変わりません。
- 詳細の日時は、保存値と時刻帯を変えず、Gregorianの `yyyy-MM-dd HH:mm:ss` で表示します。詳細は元例外の全階層を保持しません。
- サマリーの行は、状態の事実と、項目が読込み済みかどうかを保持し、STATUSとツールチップを現在の言語で作ります。項目が未読込みの行は、状態があれば現在の言語の区切り書式で読込み中の案内を付け、状態がなければ案内だけを示します。

この取得失敗の扱いを、DBの読込み・保存、必要な参照公開、出力、内蔵リコメンドの失敗へ流用しません。操作の取消しと、通信の期限切れも区別します。

- 単表のプロパティ保存では、再取得に失敗しても属性の保存と必要出力を進め、保存済みの編集値を採用してから同期の未完了を通知し、ダイアログを開いたままにします。一般の同期操作が処理済みの取得失敗を再送出しないことを、この未完了の結果を消す理由にしません。
- 元例外と取得元URLは取得境界で診断し、通常の取得失敗を再取得の対象境界で重複して記録しません。ワークスペースの診断コールバックが失敗しても、実処理の失敗一覧へ加えません。

#### DB保存と画面反映の完了

DB保存だけでは再読込みの成功になりません。DB接続と短いモデルロックを解放してから、UIスケジューラーによる実際の置換を待ちます。

| 失敗の時点 | 結果 |
| --- | --- |
| 置換前の受付拒否・取消・中断・例外 | 現在の公開状態へ、既存のDB再整合を試みる。その失敗も結果へ残す。 |
| コレクションへの代入後の購読通知の例外 | 実際に採用された新しい参照を維持し、失敗を返す。 |
| 必要なLR2・BMT出力と参照公開 | 保存済みの事実を使って行う。公開の失敗で、実施済みのDBや出力を消さない。 |

外部再取得は、対象ごとの確定参照・変更・失敗と、取消しや一括出力など操作全体の失敗を、同じ結果で返します。

- 対象の保存と必須の参照反映が終わるたびに、最終結果にも含める同じ対象結果を通知します。手動再取得、任意の外部同期、表一覧の再読込みに続く外部同期は、他の表の完了を待たずに、その対象の現在参照・更新日時・STATUSをサマリーへ反映し、選択中の詳細の参照も新しい表へ追従させます。
- 通常の取得失敗では、旧参照・DB・更新日時を保ち、STATUSだけを更新します。
- 重い詳細の再構築は、全件の終端で一度だけ要求します。

対象の確定の通知は、派生出力の完了を意味しません。全件の取得・保存と必要なLR2・BMT出力の終端まで、同じPと受付を保持し、Busyや操作全体の完了を個別の反映で解放しません。通知は、Pを解放した後にまとめて待たずに依頼します（[プレイリスト側の操作通知](../ui/dialogs.md#プレイリスト側の操作通知)）。

- BMTなどの後続の失敗は、対象の成功結果を書き換えず、操作全体の失敗として残します。
- モデルの任意の結果コールバックは、観測者の例外を局所で診断します。ワークスペースの必須の採用失敗は操作内に集め、全件の終了後に、元の対象・出力の失敗と合わせて返します。
- 終端では、個別に採用した参照・STATUS・診断を再採用しません。

呼出し元は確定参照を採用してから失敗を通知し、二表の一方が失敗しても、他方の確定結果を失いません。変更なしの対象は現行の参照を返し、DB保存がないことを参照採用の拒否に読み替えません。プロパティ保存の中では、保存サービスが必要出力を所有し、取得済みの変更から一回実行します。

確定済みの参照やDBは、後段の処理の失敗で戻しません。結果記録と通知は次のように分けます。

- 手動再同期と任意の外部同期の操作結果記録の表示は、共通の境界で元原因と操作経路を局所で診断し、出力・取消の結果や完了事実の成否へ合成しません。
- 結果記録の取得とセッションの寿命、必要な参照・索引・詳細の公開が失敗した場合は、元の出力・取消の原因と、その実際の失敗を返します。
- 進捗表示と、実行周の開始・参照反映・完了を表示先へ知らせるイベントは任意通知です。購読先ごとに失敗を診断し、残りの購読先への通知を続けます。進捗の所有状態と実際の参照反映は、この任意通知から分けて維持します。
- `PlaylistDetailReloadRefreshRequested` は次の操作対象の詳細反映を要求する必須の通知で、任意の結果記録の表示とは区別します。

同期の保存・必要出力の実際の終端まで、受理したTaskとPを保持し、通知はPの解放後に待たずに依頼します。表示の失敗を理由に、同期を自動で再実行しません。次の明示的な要求は、新しい取得内容を通常どおり保存・公開・出力します。

内蔵難度推定表・リコメンドの入力と計算は[専用仕様](local-recommendations.md)に従い、生成結果を同じ登録・再読込みの統合へ渡します。

### 更新検知と更新日時

ヘッダーハッシュは、`compat_prefix` を除き、明示的な接頭辞付きの `folder_order` を比較用に正規化して計算します。`tag`、`course`、`level_order`、`symbol` などは含めます。データハッシュは、取得したデータJSON全体が対象です。

| 変化 | DB保存 | `last_update` |
| --- | --- | --- |
| 既知のヘッダーハッシュから別の値へ変化 | ヘッダーとコース。項目行は保存し直さない。 | 更新する。 |
| ヘッダーハッシュの初期化、または一致する旧形式からの変換 | ヘッダーとコース。 | 更新しない。 |
| 既知のデータハッシュから別の値へ変化 | ヘッダー・コース・項目行。 | 更新する。 |
| データハッシュの初期化 | ヘッダー・コース・項目行。 | 更新しない。 |
| 表示名 `name` または取得元名 `org_name` だけが変化 | ヘッダーとコース。項目行は保存し直さない。 | 更新しない。 |
| 本文ハッシュが同じで、解決済みのデータ参照だけが変化 | ヘッダーとコース。項目が空、または全項目が絶対URLでも保存し、URIの差だけを項目行の保存の原因にしない。 | 更新しない。 |
| 項目行の内容比較だけで差分を検出 | 一致する行のローカル状態を引き継いで、項目行を保存する。 | 更新しない。 |

いずれもBMT再出力の対象です。内容比較は、ハッシュが未初期化・古い状態でも項目の差分を反映するためのもので、更新日時の独立した根拠にはしません。外部表の初回登録では、取得元の日時があればそれを使い、なければ登録時刻を使います。空のローカル表は作成時刻を初期値とし、通常の保存でDBへ反映します。

解決済みのデータ参照が同じなら、生の相対・絶対の表現差や、無関係なページ・ヘッダーの差だけで、保存とBMTの対象を増やしません。データ参照だけの保存は、更新ありとはしない（`Updated=false`）が状態は保存済み（`StatePersisted=true`）の新しい確定表として、既存の確定結果と新旧の参照差で公開します。利用者の同期元、ID、手動の名前・記号、出力設定、ハッシュ、memo・adddateは保持します。相対の項目の解決先が変わる場合の通常のURL値の差は、既存の行内容の比較で、必要な行の保存へ反映します。BMTの入力指紋も実際のデータ参照を含みます。BMTの省略条件は[BMTの管理台帳](bmt-export.md#管理台帳と未変更判定)に従います。

内蔵表の再読込みの名前と実力の更新通知は[内蔵リコメンド](local-recommendations.md#uriui取消と保存)に従います。名前の差だけでも、DB保存と画面の公開を行います。

内蔵の難度推定表・推薦表の生成ヘッダーハッシュには、表示言語のリソースから作る名称（`org_name`）を含めません。推定の種類（ランプ）、推薦の方針の識別子、★の数値（Invariant書式）、`symbol`、並び順など、言語に依存しない値だけで作ります。表示言語を切り替えた最初の再読込みでも、内容が同じなら更新と判定せず、`last_update` を進めずBMTを再生成しません。名称は既存の名称差の処理のとおりヘッダーへ保存して公開します。この規則の導入後の最初の再読込みは、保存済みのハッシュと一度だけ食い違い、その一回に限り日時が進むことを許容します。

内蔵表の再生成では、未修飾の生成ヘッダーハッシュとデータハッシュを確定した後、保存済みの互換接頭辞を、未公開の完成した所属と明示フォルダ順へ、既存の共通変換で一度適用します。リコメンドの内容が変わる再読込みでも保存済みの接頭辞を保ち、旧内容の有効な所属を残したり、接頭辞を生成ハッシュへ混ぜたりしません。同じ入力・設定での次の通常の再読込みでは、不要な保存とBMTの再生成を省略します。BMTでは既存のタグと互換レベルを使い、保存した接頭辞を除いた名前を出力します。

フォルダの作成・改名、項目の追加・削除など構成の手動編集では、更新日時を編集時刻へ更新します。名前、記号、URL、出力先、整列・順序、接頭辞だけの保存では更新しません。接頭辞に伴う表示名の変換も、項目の所属の変更ではありません。

### 手動編集と失敗

#### フォルダ名と所属

正規の「フォルダ名なし」は、空文字の一つの所属です。保存済みの通常のフォルダ名は、前後の空白を含めてOrdinalで比較する所属キーとして扱います。`A` と ` A `、空文字と非空の空白名は別の所属で、表のルートを示すnullとも区別します。

DB読込み、復元、JSON・BMTの取込み、外部同期、出力、並べ替え、再選択、詳細の要求、既存ノードへの追加・移動・コピーは原値を使います。旧版の空白名の一括移行・統合やTrimは行いません。

名前付きの空フォルダかどうかは、削除履歴を除いた有効な所属で判定します。最後の項目の削除・移動後も、既存のダミー表現を残します。読込み、改名、空フォルダ同士の統合も同じ条件に揃えます。空文字は名前なし、受理済みの空白名は名前付きとして区別します。

ツリーの名前なしの案内（リソース `No_folder_name` の語を丸括弧で囲んだ表示）は表示だけの解決です。表示言語の変更に、同じノード・同じ部品のまま追従します。保存名、空白名、特殊ノードの `[NO SONG]` は変えず、保存・再読込み・再検索を起こしません。

#### 改名の入力

新しい手動の改名入力だけは、空欄・空白だけの入力を空文字へ揃えます。

1. 取消、または入力原文と保存キーのOrdinalでの一致を先に判定します。
2. 正規化した後も同じキーなら、保存・所属・順序・選択を変えません。旧版の空白名を無変更で確定・取消した場合は原値を保ちます。
3. 空欄や別の空白列への明示的な変更では、名前なしへ移します。非空白文字を含む入力は前後の空白も保持し、異なる場合だけ、同じ確定名を保存・選択・詳細表示へ渡します。

表示と編集の原値は[見出し編集](../ui/table-view.md#プレイリストツリーのフォルダ名編集)に従います。

名前なしへの改名は、既存の空文字の所属へ統合し、重複する項目には既存の改名統合の規則を使います。

- 名前なしに指定済みの順序があれば尊重し、未指定の場合だけ先頭へ置きます。
- 空の通常フォルダを名前なしへ改名しても、空ノードやダミーは作りません。名前なしの最後の項目を移動・削除した後もノードを残しません。
- 非表示になった名前なしの明示順序の記録は残してよく、再出現時に利用できます。読込みだけで一般の並べ替えや保存順序を書き換えません。
- 明示順が自動整列として読まれる規則は一つです。空の順序と、空文字だけの順序（旧版が名前なしへの所属変更で保存した `[""]`）は自動で、`["", "A"]` のように空文字以外を含む順序は手動です。プロパティ画面の自動判定、フォルダの削除・名前なしへの改名での「明示順が空」の判定、BMT出力の入力指紋の `folderOrder` が、同じ規則に従います。
- 自動整列の表では、フォルダの削除・名前なしへの改名で明示順を作らず、保存済みの空文字だけの順序も書き換えません。手動順の表での名前なしへの改名は、名前なしに指定済みの順序がなければ先頭へ置く既存の挙動を保ちます。
- 並び順・自動指定のフォルダ欄を編集していない保存（プロパティの別項目の保存、概要のセル編集）は、保存済みの明示順を変更対象にしません。手動順の表の表示順を、別項目の保存で明示順として固定しません。

通常の名前への改名は、元の順序を保持します。保存済みの非空の空白名も通常の所属として、明示順序・並べ替え・空フォルダの保持を維持します。空の通常フォルダを空文字へ改名するとき、別の所属である空白名にある項目を、空文字の所属の存在とは数えません。

#### 選択の追従

選択中の通常フォルダを改名した場合は、確定した名前の対応へ選択を移します。接頭辞の変更でも同じ対応を使い、別のフォルダと特殊ノードNO SONGの選択を保ちます。フォルダの削除では、内容の移動先の名前なしフォルダを選び、そのノードが残らない場合は表本体を選びます。

更新後に利用者が新しく明示的に選んだ項目には、旧構成の改名の対応を再適用しません。ツリー、ワークスペース、詳細の集合を一致させ、構造の置換による親の選択を、明示的な選択と混同しません。

#### 構成の公開と編集の確定

フォルダのノード、通常の名前の並び、明示順序は、確定した変更不能な入力として公開します。

- 必要な構成の変更は既存の書込み区間の中で完成させてから公開し、DB確定前の候補で現在の入力を変更しません。
- 読取り、選択の受付、要求の複製で、再構築や列の複製をしません。MEMO・URL・levelなど構成に依存しない編集では、同じ入力を再利用します。
- 必要な通知は保護の解放後に行い、捕捉済みの旧入力は後の構成変更でも書き換えません。

フォルダの作成・改名・削除、項目の削除、ドロップは、それぞれ一つの編集として扱います。

- 対象フォルダの行と、移動先で衝突する候補だけを準備します。DB確定まで、同じ表・項目の参照、所属、フォルダ順、更新日時、項目版を変更しません。
- 少数のフォルダの変更のために、全項目の退避・再取込みやDBの全置換をしません。全表の交換、無条件の再読込み、永続的な取消履歴・再試行は使いません。
- 複数の表の削除は、受理した有限の対象を一回のDB保存へまとめます。
- DB確定後の出力・公開の失敗で、成功済みの事実を戻しません。

DB確定後のLR2・BMT出力の失敗では、保存済みの表や表示を巻き戻しません。対象と元の原因を警告・エラーへ残し、現在の参照と表示は確定した内容へ揃えます。BMTの生成・削除・管理台帳・Table URL反映の失敗も、元の操作の部分失敗として返します。

永続化の成功後だけ、確定差分の表示反映、成功通知、`afterApply` を進めます。

- サマリーの一括変更も同じです。DB保存前の失敗を成功として扱い、索引・検索候補・整列・表示の更新やダイアログの終了を進めることはしません。
- DB保存前には、候補を現在の値へ適用しません。DB保存後の必要出力・通知の失敗では、確定値を維持して、同じ結果を配送します。
- モデルの準備の途中では、プロパティの変更通知を公開しません。
- プロパティ保存では、必要な索引・現行参照の公開と任意通知を区別し、進捗・処理後の通知の失敗を、保存の失敗や次回の未完了出力へ持ち越しません。必要出力の継続には、保存値と未完了の事実だけを保持し、過去の例外を次の明示的な保存へ再合成しません。

受付条件と、既存の下書きの現行性の確認は[競合ポリシー](../core/operation-concurrency-policy.md#プレイリストと必要出力)に従います。購読先を実行する前に集合・表・DBのロックを解放し、必要な出力・公開は同じ処理のTaskとして直接待ちます。

表のプロパティ保存と外部属性の一括初期化も、編集するヘッダー属性を明示した変更不能な `PlaylistHeaderEdit` から、`CommitPlaylistHeaderEdits` を通して同じ候補・確定の経路へ接続します。

- 接頭辞と明示フォルダ順、対象項目のフォルダは、書込み区間の中で現在値から準備し、DB確定の前には現在の値へ反映しません。
- DB確定の後に、同じ項目・ヘッダー・順序・版・確定結果を確定し、保護の解放後に通知します。
- 古い全属性の複製で非編集の値を戻す処理や、現在の値を先に書き換えて全表のスナップショットへ戻す処理は置きません。
- 接頭辞だけの保存では、更新日時を保ち、外部データを再取得しません。

少数の追加・削除は、旧新のキーに影響するDB候補だけを、同じトランザクションの中で取得・差し替えます。DBのNULLと現在値の既存の正規化、対象外の重複候補・削除履歴、空フォルダのダミーを保持し、未変更の行の参照や順序を作り直しません。複数表のまとまりは一つのトランザクションで確定し、二つ目の表の保存が失敗しても、全表の旧所属・日時・版とDBを保持します。

#### 局所候補の照合キー

局所候補の取得は、非一意の候補索引 `playlist_entry_idx_candidate(playlist_id, md5 COLLATE NOCASE, sha256 COLLATE NOCASE, folder, lr2_bmsid, title, is_removed)` を使います。索引は[SQLiteの互換範囲](../core/data-and-indexes.md#sqliteの互換範囲)に従って列と `COLLATE` だけで定義し、次の正規化は局所候補のSQLの側で行います。起動時の読込み、生存項目だけの読込み、局所候補のSQL、LR2カスタムフォルダ生成のSQLは、次の照合と生存判定を揃えます。

| 値 | 照合 |
| --- | --- |
| ハッシュ | NULL・空・Unicodeの空白だけの値は同じ空キー。非空の値は前後を削らず、ASCIIの大小文字だけを同一視する。従来受理している最終LF付きのハッシュは、LFを保持した別のキー。 |
| folder | NULLと空は同値。それ以外は大小文字・前後の空白も区別する完全一致。 |
| title | NULLと空は、既存の項目の識別で同値。通常の読込みがNULLを空として読む場合も、起動時の生値読取りがNULLを保持する場合も、同じ対象を保存・削除する。それ以外は完全一致。 |
| `lr2_bmsid` | NULLと空も区別する完全一致。 |
| `is_removed` | NULLと0は同じ生存候補。1の削除履歴とは分ける。 |

局所候補のSQLは、空キーの各表現（NULL、空、空白文字の範囲ごとの形）を索引で引ける単純なSELECTに分け、`UNION ALL` で結合します。候補索引はこれらの照合に使う列をすべて含み、表の行を読まずに候補を決めます。索引で絞れる範囲は次のとおりです。

- 非空のMD5は、MD5の一点で絞ります。同じ表で同じMD5の行は少数のため、SHA-256と後続の列は絞った行の照合だけで判定します。
- MD5が空キーでSHA-256が非空のときは、MD5の一点の形（NULL、空）ごとにSHA-256の一点で絞ります。同じ表で同じSHA-256の行は少数のため、後続の列は絞った行の照合だけで判定します。
- MD5とSHA-256がどちらも空キーで、どちらも一点の形（NULL、空）のときは、folder・`lr2_bmsid`・title・`is_removed` も索引で絞ります。NULLと空を同値とする folder・title と、NULLと0を同値とする `is_removed` は、NULLの形と値の形に分けて探索します。
- 空白文字で始まる空キーの形は、ハッシュ列の範囲で絞った後、空白だけかどうかと後続の列を照合だけで判定します。空白文字で始まる値は通常の保存では作られないため、この範囲の行は少数を前提とします。

背景の行数が増えても、候補の取得の仕事量は、上記で絞った範囲の行数だけに比例します。上記の前提を外れる行（空白文字で始まるハッシュを持つ多数の行など）は、同じ表の中で照合の対象として読みます。

次の二点は、既知の割り切りとして受け入れた意図した挙動です。不具合・性能課題として扱いません。

- MD5とSHA-256がどちらも空キーの項目の局所候補は、空キーの形とNULL・値の形の組合せごとにSELECTを分けるため、一件の探索が最大62個のSELECTの `UNION ALL` になります。両方のハッシュが空の項目を多数含む表は通常想定しないため、この回数を減らす設計は行いません。
- ハッシュ列の空キーが型BLOBで保存された行は、空キーと同値として拾いません。本アプリの書込み経路はハッシュをBLOBとして保存しないため、この行は生じません。

既存の同名の候補索引の定義が異なる場合は、スキーマの準備で同じ名前の索引に作り直します。以前の開発版が作った式の候補索引も、この処理で置き換えます。定義が一致する索引は作り直しません。全表の保存を伴わない再出力でもNULLの行を含め、LEVEL・ADDDATEの並び順には保存値を使います。保存行のNULLの一括書換えやUNIQUE条件の変更は行いません。

#### 削除履歴と明示的な追加

明示的な追加・移動・コピーでは、宛先の同じ所属キーについて、削除履歴と生存する重複を区別します。

- 削除履歴は今回の入力で置き換え、生存する所属を一件だけ成立させます。
- 生存する重複先がある場合は、その既存値を優先し、同じ所属キーの削除履歴を併存させません。
- 履歴の削除には、入力のtitle・SHA-256ではなく、履歴自身の保存値を使います。同じハッシュの別フォルダ・別ハッシュの無関係な履歴は保持します。フォルダの改名・統合の既存の衝突選択は変更しません。

追加元によって、引き継ぐ値は次のように異なります。

| 追加元 | 値 |
| --- | --- |
| 所持一覧から同じ所属への再追加 | 通常の新規追加の既定MEMOと今回の追加時刻を使う。履歴のMEMO・追加日時を復帰しない。 |
| 現行のプレイリスト詳細からの移動・コピー | 現在の元行のMEMO・コメント・永続URL1/2・`name_diff`・level・追加日時を保持する。 |
| 同じフォルダへの詳細の再ドロップ | 所属・値・追加日時を変更しない。 |

移動元の削除と、宛先の履歴の置換・所属の成立は、既存の一つのトランザクションで確定し、一回の局所変更の配送へ渡します。DB保存前の失敗では、両側のDB・現在参照・値・日時・版・通知を保持します。DB保存後の必要出力・通知の失敗では、確定済みの事実を戻しません。受理したTaskとPは、必要出力・後片付けの終端まで保持し、通知は解放後に待たずに依頼します。

#### 新規プレイリストの初回保存

新規の下書きの初回保存は、登録前に旧出力配置がないことを捕捉し、DBへ一度登録したIDで、必要なLR2の初回出力、ROOTの検索ルートのディスク保存、BMT、表示を完了します。空の名前から求めた共通の基点を、旧出力先として移行しません。

出力や検索ルートの保存の失敗後は、登録済みのIDと未完了の部分を保持し、同じ画面の明示的な再保存で、捕捉済みの配置を使って継続します。既存の配置からの移行では、旧出力先の整理を行います。

#### 操作後の任意表示

共有の操作結果記録を使う次の操作では、操作後の任意表示だけを局所で診断します。フォルダの作成・改名、項目の削除、サマリーの一括変更、外部プロパティの初期化、手動再取得、任意の外部同期、JSON出力、設定の非同期処理とバックアップです。

- 表示先や診断先の故障を、保存・出力の結果へ加えず、例外履歴や次の保存の原因として保持しません。
- 結果記録の取得とセッションの実際の寿命、必要な参照・索引・確認、進捗の所有状態は維持し、表示先の故障とは区別します。
- 受理したTaskと、各入口が所有するセッション・操作権限・受付の既存の解放順を保ち、必要な後片付けを終端まで待ち、通知は受付の解放後に待たずに依頼します。
- 表示役（`PlaylistOperationNoticePresenter`）は結果記録の各要素を、見出しと重要度ごとに一件へまとめて窓口へ依頼し、空の結果記録では依頼しません。

#### 詳細セルの保存

再同期の後の古い詳細行からの保存は、[競合ポリシー](../core/operation-concurrency-policy.md#プレイリストと必要出力)のとおり拒否し、最新の行を選んで再操作するよう通知します。

詳細セルの保存は、正本の現行項目に限ります。

- セル編集は[一覧の共通基準](../ui/table-view.md#行のドラッグと編集)に従い、必要な表示と編集の後片付けまで受付を保持します。既存の単一の配送と実際の適用Taskを使い、確定結果ごとの完了管理や、構築候補の後継への完了の引継ぎは設けません。
- 現在表示の編集列は、正規化・補完後の確定値へ局所的に反映し、後からの参照投影で旧値へ戻しません。参照待ちの元の投影を採用するときは、その対象の現在の項目値を照合して、確定した編集属性を保ちます。全確定結果の完全な投影や、後発の構築の採用を、セル保存の完了条件にしません。
- 所持譜面によるハッシュ補完を含めて同じ項目を一意に保存し、BMSONの両ハッシュ・`Org_md5` を保ちます。levelの変更に必要なLR2出力も、同じ受理操作で反映します。

URLとlevelの入力は次のとおりです。

| 表・欄 | 規則 |
| --- | --- |
| ローカル表の本体・差分URL | 保存時に有効なURLをDBの原値として保存（材料化）し、更新日時を表のヘッダーと一致させる。単一属性の保存は書込み区間の中の最新値を基にし、URL補完後に古い表示行からmemoを保存しても、非編集のURLを戻さない。memoの保存では補完を材料化しない。 |
| ローカル表のURL1/URL2の空欄 | 空文字または空白だけの入力で未設定へ解除し、その欄の実行時の補完も解除する。保存直後や別属性の保存で旧補完を復活させない。他方のURLは有効な補完を材料化し、補完がなければ保存値を保持する。解除後に明示した別のURL補完は通常どおり適用でき、補完を恒久的に禁止する状態は保存しない。 |
| 非空の無効な絶対URI | 画面の受付と保存候補の双方で拒否する。 |
| 外部同期表のURL | 補完URLは派生値のまま保持し、既存のURL編集の制限を維持する。 |
| ローカル表の `ENTRY LEVEL` | 表示・F2の初期値・コピーにInvariantの往復精度の表現を使う。確定は `NumberStyles.Float` 相当の数値全体（固定のドット、小数・符号・指数・前後空白）で有限の値だけを受理し、空文字・空白だけはnull、取消は旧値を保持する。装飾、部分的な数値、カンマ小数・桁区切り、NaN・Infinity・桁あふれによる非有限値は保存前に拒否し、固定の書式を既存の通知から表示する。モデルの確定入口も同じ判定を使い、確定表示へ未保存の文字列を残さない。 |
| 外部JSONの `level` | 別の文法。JSONの数値は値を直接取得し、文字列は既存の一数値の抽出だけをInvariantで読む。`org_level` の優先、明示的なnull、元のfolder・装飾ラベルを保持する。 |

所持行の保存levelがnullの場合に、譜面のlevelを代わりに表示する既存の規則も維持します。

詳細セルは、DB確定から、必要なLR2・BMT出力と結果記録のセッションの終端までを、一つの確定後の境界として扱います。

| 時点・失敗 | 扱い |
| --- | --- |
| DB確定前 | 下書きは、生存する元の表、同じ項目の参照、属性名、入力値として渡す。書込み区間の中の現在値から候補を作り、DB確定まで現在の項目・ヘッダー・版を変更しない。失敗では旧正本を保持する。 |
| DB確定 | 必要な値、更新日時、項目版、変更不能な `PlaylistEntryCommitReceipt` を同じ書込み区間で揃え、配送キューへ登録する。 |
| 確定後の設定捕捉・準備・書込みの失敗、終了によるBMTの取消、結果記録の取得・セッションの実際の寿命の失敗 | 確定後の失敗の分類で、元例外・取消を保持する。登録済みの差分は取り消さない。先行するDB・出力の失敗を、二次的な結果記録・セッションの失敗で置き換えず、二次原因は局所で診断する。 |
| 任意の結果記録の表示とその診断だけの失敗 | 保存の成功を失敗へ変えず、実際の出力失敗や取消へ合成しない。 |

短い書込み保護の解放後に、既存の経路で差分を配送し、現在の表示へ必要な確定値を反映します。表示用の複製同士の手動の同期や、正本の巻戻しは行いません。

受付と後片付けは次のとおりです。

- 受理したTask・受付は、保存と必要出力の実際の終端まで解放せず、編集セッションの後片付けを必ず行います。通知は、受付の解放後に表示を依頼し、表示の完了は待ちません。
- 後片付けとPの解放を含む外側のTaskの終端までは、同じワークスペースの管理主体で、次の詳細編集の開始だけを拒否します。
- 現在の表示元の整列延期の指定を、保存の寿命まで延ばしません。表示元を交換しても、保存中の開始拒否は消しません。
- 開始拒否は全ての終端で解除します。同値の保存、編集の取消、保存先の提供元の同期失敗の後も、次の明示的な編集を受理します。
- 終了では受付の閉鎖を維持し、それ以外の表示失敗の後は、次の明示的な編集を新しい保存値として受け付けます。

`PlaylistEntryCommitReceipt` は、表、元の版・確定版、対象項目の変更不能な旧新の値・所属・順序を持ちます。フォルダの明示順の変更も同じ結果に変更不能な値で含めます。表全体の置換は、旧表の退役と新表の再捕捉で扱います。URLの補完・解除も同じ項目版と差分を発行し、DBと永続化の世代番号は変えません。

設定画面からのLR2・BMT出力の確定と局所保存の単位は[設定変更](../runtime/settings.md)に従います。他のセクションの候補や通常項目の保存を、出力の開始条件にしません。

### 参照プレイリストの索引と表示

`BmsLibraryPlaylistReferenceOwner` は、選択された参照表から派生する索引と、その世代番号（`indexRevision`）を所有します。

- 表・キーごとの件数で多重配置を数え、同じ表の一件を削除しても、残る項目の参照を保持します。
- 項目の確定による旧新のキーだけを反映します。name・symbolの変更は、その表が参加する区分だけを更新します。
- 一件の変更のために、全表の捕捉や全参照キーの表示の再生成を行いません。初回の構築と、実際の参照集合の全置換では、その全体入力を扱います。

表示を構成する表の順序は、BMT SORTの昇順、同順位では正本の表リストの順です。0・負値も数値の順に扱い、欠損だけを末尾へ置きます。項目の編集やスコアの読込みで、表を末尾へ移しません。BMT SORTや正本の表順が変わる場合も、関係する区分だけを並べ直します。

表示の検索は、前後の空白を除いたMD5・SHA-256を、大小文字を区別せずに照合します。MD5の区分が存在すれば、表示文字列が空でもそれを返し、MD5の区分がない場合だけSHA-256へ進みます。この表示の検索を、項目の登録・所持候補の解決のMD5優先の規則と混同しません。

参照の確定結果は、既存の版の前後と、変更キーから変更不能な表示値への差分です。区分の削除はnull、存在する空の表示は非nullとして区別します。

- 同じ参照の管理主体の排他の中で、索引、変更不能な結果、既存の公開先への登録を揃え、その終端で単一の参照版を公開し、排他の解放後に配送を起動します。
- 画面が必要な版だけを読む場合はこの値を使い、索引の排他を待ちません。更新中は最後に公開した版を返します。値との安定した捕捉と、全体の同期の準備は既存のロックを保ちます。
- 結果の構築または登録が失敗しても、変更済みの索引の版は公開し、元の例外を維持します。
- 無変更と、通常のカタログのリセット通知だけでは、参照の版を進めません。

項目の確定結果を消費する第二のキューは置きません。元の操作が返した同じ確定結果の群を、全保護の解放後に参照の管理主体へ渡します。参照の派生状態を必要出力より先に反映し、DB保存後の失敗でも確定値と元原因を保持して、出力・配送の終端を回収します。画面への受渡しと処理済みの位置は[一覧仕様](../ui/table-view.md)を参照します。

### フォルダ単位のドロップ

内部の譜面行を表のルートへドロップした場合は、追加先のノードがないときだけ分類します。

- 実在する通常の子ノードは、空文字・空白だけの所属名でも、その保存キーのまま追加・同じ表での移動・別の表へのコピーを行います。存在確認、元の所属の除去、同じ所属への再ドロップの判定も同じ区別を使い、失効した子ノードを表のルートへ読み替えません。
- 特殊ノード、外部同期がONの表への追加は拒否します。
- 所属名の禁止・Trim・自動改名や、物理ファイルの移動は行いません。

表のルートへのMD5による自動分類では、非空白文字を含む名前の既存フォルダだけを候補にします。名前なしや旧版の空白名だけに一致しても、それらへ自動分類せず、通常の命名規則で新しいフォルダを作ります。新規フォルダのボタンと自動分類の既定名の生成は変更しません。

分類では、入力順を保ったディレクトリ単位の計画を作り、計画中は表示用の表を変更しません。既存のフォルダと先に計画したフォルダ・項目を作業集合に持ち、`GetPlaylistFolderOrgMd5sForCharts` によるパッケージのMD5集合と、フォルダ内のMD5の重なりで分類します。削除履歴しかないフォルダは候補から外しますが、その履歴は保持します。

複数の候補は、実際の一覧と同じフォルダ順・自然順で選びます。名前の衝突は既存の接尾辞の規則で避け、同じタイトルだけ、または空の親MD5集合だけでは統合しません。同じ入力順なら、一括投入と分割投入で、所属と重複除去後の集合が一致します。任意の入力順の同一視や、既存の手動分類の移行は行いません。

入力には、通常の譜面、プレイリスト詳細、解決済みの `PlayHistoryRow.ResolvedChart` を使えます。未解決の履歴行を含む選択は、一部だけを追加しません。

所持詳細の同じ表のルートへの再分類と別の表へのコピーでは、分類用の譜面と元の項目の対応を保持し、通常のフォルダへのドロップと同じ項目の複製を保存候補にします。

- 採用する項目のメモ・コメント・永続URL1/2・`name_diff`・編集済みのlevel・追加日時を保持し、表示用の実行時のURL補完を永続値へ昇格させません。
- 移動先の同じフォルダに生存する重複項目がある場合は、既存の項目の値を優先します。
- 未所持の詳細も元の項目を複製し、ライブラリの行と解決済みの履歴行は、所持譜面から新しく作ります。

### JSON出力・SQLバックアップと復元

#### JSON出力の保存先

JSON出力では、専用のウィンドウでヘッダーとデータの保存先を同時に指定します。

- 未入力、または正規化後のパスが大文字小文字を無視して同じなら、理由を表示し、出力ボタンを無効にします。`.` / `..` の表記差も同一の判定に含め、存在しない先でも同じ条件を使います。同じ名前でも別のディレクトリなら受理します。
- 画面と保存入口は同じ判定を使います。保存入口では、正本の遅延読込み、通知セッション、ファイルの生成に先立って再検査します。
- 取消・拒否では、DB・正本・既存のファイルを変更しません。自動改名、保存先の自動置換、外部リンクの差替えまで含むファイル同一性の保証は設けません。

#### データ参照の出力

必要な正本の入力を読取り境界の中で捕捉します。`Data_url` が空の場合だけ、出力するヘッダーから選んだ実際のデータへ解決できるURI参照を、出力用の値へ入れます。

| 保存先の関係 | 出力するデータ参照 |
| --- | --- |
| 同じドライブ・共有ルート | エスケープ済みの相対参照。別のディレクトリの同名ファイルや、両保存先の空白・日本語・`#`・文字列としての `%23` も区別する。 |
| 異なるドライブ・共有ルート | 明示的な `file:` の絶対URI。 |

この参照が成り立つことは、別の環境へ公開した場合の可搬性を保証しません。既存の非空の `Data_url` は、絶対・相対とも優先し、選んだローカルのデータへ置換・再基準化しません。正本の `Data_url`・`Header_url`・`Page_url` と同期元の参照の意味は変更せず、シリアライズ中も正本を一時的に変更しません。

#### JSON日時の書式

新しく書き出すJSONの日時は、Gregorian・Invariantの壁時計で、時刻と1tickを保持します。新たなオフセットや `DateTimeKind` は付けません。

| 項目 | 書式 |
| --- | --- |
| `output_date` | `yyyy-MM-dd` |
| `last_update`、`adddate` | `yyyy-MM-ddTHH:mm:ss.fffffff` |

#### JSON日時の読取り

JSONの日時は、読取りの操作元によって、厳格（`Strict`）または互換（`Compatible`）の方針で読みます。他の仕様はこの節を正本として参照します。

| 方針 | 操作元 |
| --- | --- |
| `Strict` | モデルの直接の読取りと、ローカルJSONの初回取込み。ローカルJSONからHTTPのデータを読む場合も含む。 |
| `Compatible` | URLからの初回取込み、登録済みのfile・httpの再読込み・同期、外部プロパティの初期化、BMTの読取り。 |

初回か再取得かは、呼出し元が一時的な引数で渡します。初回の元の指定と、既存の本文のJSON分類から、ヘッダーの解析前に一度決めます。設定の継承、既存の表の有無、転送先、ヘッダー・データの参照先では切り替えません。BMTの読取りがこの方針を受け渡す範囲は[Table URL取込み](table-url-import.md#キャッシュからの復元)に従います。

両方針は、Gregorian・Invariantで値全体が一致する次の書式を読みます。

- `yyyy/M/d`、`yyyy/M/d H:m:s`、オフセットが直結した `yyyy/M/d H:m:szzz`
- ISOの日付 `yyyy-MM-dd`
- T区切りの秒までの日時（小数0～7桁、オフセットなし・`Z`・`±HH:mm`）

オフセットなしの値は `Unspecified` の壁時計として、オフセット付きの値は `DateTimeOffset.LocalDateTime` へ変換して、tickを保ちます。オフセットの前の空白は受理しません。

`Compatible` だけは、前後の空白を除いたうえで、次の書式も読みます。

- `yyyy.M.d`
- 8桁のASCII文字列、または8桁の整数トークンの `yyyyMMdd`
- 秒が0の `yyyy/M/d H:m`
- 4桁の年が末尾にあるスラッシュ・ドット区切りの日付。日月順・月日順の有効な候補が同じ一日に定まる場合だけ採用する。
- `yyyy/M/d (曜日)`。曜日は日・月・火・水・木・金・土、またはSun・Mon・Tue・Wed・Thu・Fri・Satで、日付と一致する場合だけ採用する。

曖昧な月日順、2桁の年、10桁の数値、小数・指数のトークン、任意の文章からの抽出、範囲外の値、7桁を超える小数の丸めは受理しません。

検査するのは、実際に採用する `last_update` と、行の `adddate` だけです。空・null・省略は既定値を保ち、入力の `output_date` と採用しない行は検査しません。不適合な値の扱いは方針で異なります。

| 方針 | 不適合な日時の扱い |
| --- | --- |
| `Strict` | 正常な先行行を含む一つの表を、保存前に止める。既存のヘッダー・データの分類と、画面の訂正要求を保つ。 |
| `Compatible` | 日時の代入だけを省略し、採用する全行と他の値を保持する。新規の項目は生成時の現在時刻、既存の項目は統合で旧adddate・memoを保つ。日時を理由とする画面通知、失敗STATUS、失敗の結果記録は作らない。 |

表の更新日時は、既知のヘッダー・データの差だけで進み、ハッシュの初期化・移行・項目の指紋の差だけでは進めません。日時以外の構文・取得・DB・内部故障の停止範囲は変えません。

日時の不適合は、既存の診断窓口から、文書ごとの警告へ集約します。

- 表、操作、元の取得元、実際の文書URI、項目、トークンの型、最初に現れた行の位置・識別値、理由を追えるようにします。
- 文字列はTrim前のデコード済みの値、数値はInvariantの値を記録します。項目・型・値が同じものは最初の出現と件数にまとめ、異なる値を件数の上限で捨てません。`Strict` で拒否した元の値も同じ診断へ残します。
- JSONの字句の完全な再現は保証しません。診断先の故障で、本来の読取り結果を変えません。集計は文書の中だけで保持します。

元のDOMの日時・未知のキーは削除・書換えしません。ヘッダーの生のSHA-256、既存のDOMの再出力による比較用ハッシュ、データ原文全体のハッシュの規則と、同じ原文の未変更の省略を保ちます。未知のキーの新たなDB保存・出力の保証や、既存DBの全件の日時補正は加えません。

#### JSONファイルの書込み

各JSONは、保存先と同じディレクトリの一時ファイルへ、UTF-8・BOMなしで書きます。書込みのバッファ排出と終了、基底ストリームの終了を済ませた後、既存の先は置換、新規の先は移動で公開します。

- 書込み・バッファ排出・公開の失敗では、旧内容を保持します。初回の失敗では、不完全な本番ファイルを作りません。
- 電源断に対する永続性（`Flush(true)`）は保証しません。
- 一時ファイルの削除の失敗は主原因を置き換えず、残ったパスとともに診断へ残します。

選んだヘッダーを先に書き、その正常完了後にデータを書きます。二つのファイルを単一のトランザクションにはしません。

| 失敗 | 結果 |
| --- | --- |
| ヘッダーの書込み | 後続のデータに着手しない。 |
| データの書込み | 新しいヘッダーと旧データ（初回はデータなし）を保持し、部分失敗を通知する。 |

書込みの失敗では、元原因、書込みの段階（ヘッダーまたはデータ）、選んだ保存先を既存の診断先へ渡すことを試みます。診断自体の失敗を分けて、一件のエラーの結果記録で処理を終えます。補償の削除や自動の再試行は行わず、表示や診断の故障でも、この部分状態と `Data_url` を変えません。処理済みの書込み失敗でTaskが正常に終わることは、停止と通知の実際の試行が終わったことを示し、両ファイルの出力の成功を意味しません。

選択画面、必要な項目の読込み、シリアライズ、結果記録の取得・セッションの実際の故障は、書込み失敗として扱いません。次の明示的な出力は、新しい二つの保存先へ通常どおり出力し、以前の書込み・表示・診断の例外を持ち越しません。

#### SQLバックアップ

バックアップは整合読取りを使い、選んだ先と同じディレクトリの一時ファイルへUTF-8・BOMなしで書き、閉じた後に置換または移動で公開します。先に既存の先を消したり、直接の上書きへ切り替えたりしません。

- 後片付けの失敗も診断に残し、成功通知は公開の後だけ行います。
- 書込み・公開の失敗は、ワークスペースで保存先と元原因を診断し、一回の失敗の結果記録へ渡します。
- 結果記録の表示失敗は局所の診断で終え、公開済みのバイト列や元の保存結果を変えず、表示のために失敗を再送出しません。

SQLのリテラルは、SQLiteの保存値と型から作ります。

- 数値に見えるTEXT、空文字、空白、引用符、日本語はTEXTのまま、NULLは空文字と区別して往復します。
- 埋込みのNULや、バックアップの区切りに使う垂直タブを含むTEXTは、引用時の切詰めや区切りとの衝突を避けるため、全バイトから同じTEXTを復元するSQL式へ変換します。
- INTEGERとREALも値・型を保ち、文化圏の数値解釈に依存しません。

旧形式のBMT設定を補正する場合も、`bmt_sort` と `is_bmt_output` の二列だけを更新し、他の列の保存値を保ちます。既存の有効なSQLバックアップも引き続き読み込みます。

#### SQL復元

復元は、ファイルの読込み、DBの復元、表示一覧への反映を分けます。DBの排他、トランザクション、確定後のヘッダーの読込み、接続の解放は、同じワーカーの同期範囲で完結させます。UIへの一覧反映を予約する前にその範囲を抜け、予約の受付だけでなく完了を待ちます。項目行は遅延読込みです。

復元の途中のSQL失敗では旧三表を保ち、`song` や未知の利用者の表は変更しません。SQLの読取りは `SQLITE_ROW` と `SQLITE_DONE` 以外を失敗とし、途中の行をダンプ・復元・表示へ公開しません。読取りの失敗を、解放の失敗より主原因にします。同期の `LoadPlaylistDump` は移行などのDB専用の入口に限り、設定画面は非同期の復元を使います。

既存のカスタムフォルダの出力済み状態は、三表の復元と同じトランザクションで無効にします。同じプレイリストID・ハッシュ・更新日時でも、復元前の項目と同じとは限らないためです。復元後の必須準備で、新しい正本から `.lr2folder` とLR2の `folder` 行を作り直します。復元の確定前の失敗では、出力済み状態も保持します。

LR2連携での旧配置の整理と、スタンドアロンでの扱いは[LR2の管理領域の整理](lr2-custom-folders.md#管理領域の整理)に従います。

受付の分類は[競合ポリシー](../core/operation-concurrency-policy.md#設定全体操作終了)に従います。復元の結果は次のとおりです。

| 時点 | 結果 |
| --- | --- |
| `Busy`・受付拒否 | バックアップを読まず、復元完了の結果を返さない。 |
| 読込み・復元の確定前の失敗 | 旧DBと一覧を保持する。 |
| 確定後のヘッダーの読込み・UI反映の失敗 | 復元済みのDBを保持し、元原因を診断して、終了不可の結果と失敗の結果記録を返す。UIの途中の適用は補償しない。 |
| 必須準備（出力先の同期など）の失敗 | 同じ元例外で準備を終端し、復元処理と、準備を待つ外部取込みの両方へ返して、待機を残さない。準備の開始前の失敗では、既存の準備状態を変えない。成功表示、追加の出力、設定画面の終了、アプリの終了の許可を出さない。 |
| 新しい正本と必須出力の成立後の、旧配置の整理だけの失敗 | 残存の警告を通知し、復元・利用可能性・終了の許可を成功のまま保つ。 |
| 実際の復元と、必要な公開・出力の成功 | 終了を許可する。任意の完了・終了の案内の失敗は、この許可を取り消さない。 |

必須の読込みと出力の修復は、同じ受理操作のTaskとして実際の終端を待ち、表示用の独立した版・対象の識別は維持します。ワークスペースは、必要な公開・出力の完了までLとPを保持し、最終の結果通知より先に解放します。下位の失敗の結果記録があれば、同じ事実を再通知せず、通知の失敗も元の復元結果へ合成しません。必要出力の後の任意のURL補完の予約・診断の失敗は局所で終え、成功済みの復元や必須準備の完了状態を失敗へ戻しません。
