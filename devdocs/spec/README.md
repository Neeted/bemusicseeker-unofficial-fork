# 仕様

現行の挙動と採用済みの設計・性能要件を示します。未実装・未確認の要件はその状態を明記し、現行実装の保証と区別します。作業の経緯は置かず、[未完了の計画](../plan/README.md)と分けます。

## 領域別の入口

最初に[用語集](glossary.md)と[アーキテクチャ](core/architecture.md)を読み、変更対象の領域へ進みます。

| 領域 | 内容 |
| --- | --- |
| [共通基盤](core/README.md) | 責務、データ・索引、パス、性能、並行性、ログ、一時ファイル。 |
| [ライブラリ](library/README.md) | BMS・BMSON、譜面解析、変更セッション、導入先推定、重複・警告。 |
| [プレイリスト](playlist/README.md) | 保存・出力、URL取込み、履歴、ランプ集計。 |
| [画面](ui/README.md) | 一覧、検索支援、外観、ダイアログ、再生表示、外部起動。 |
| [実行時の管理](runtime/README.md) | 起動、進捗、設定、終了、音声。 |

採用理由は[設計判断](../decisions/README.md)、測定条件と比較根拠は[測定・受入資料](../acceptance/README.md)を参照します。

## 仕様書の書式

各仕様は、次の順序で書きます。目次と共通用語集は、それぞれ案内と語義の一覧に専念します。

1. **目的と適用範囲**: 対象の操作・データ・責務と適用状態を示す。
2. **用語**: 共通用語集への参照と、機能固有の定義を示す。
3. **仕様**: 入力条件、処理結果、失敗・取消、保存・通知の境界を意味のある見出しで説明する。
4. **実装とテストの対応**: 仕様項目から実装と確認方法へ辿れるようにする。
5. **関連資料**: 重複記述を避け、他の領域や採用理由へ接続する。

仕様の本文・実装・テストを変更したときは、対応する行も同じ変更で更新します。

| 仕様項目・主な条件 | 実装箇所 | テスト箇所・確認内容 |
| --- | --- | --- |
| 機能・入力・期待結果を示す項目名 | ファイルへのリンクと型・メソッド名 | ファイルへのリンク、クラス・メソッド名、確認する結果 |

複数のテストが分担する場合は役割を示し、データ駆動テストでは条件も添えます。未実装の契約は「未実装」、自動テストで確認していない項目はその範囲と実際の確認方法を記します。運用仕様では、指示ファイル・設定項目・スクリプトと、構文検査や手順点検を対応付けます。対応表を埋めるためだけにテストを増やしません。

本文は[開発資料の書き方](../README.md#書き方)に従います。計画固有の番号・設計書IDを恒久的な対応キーにせず、実際の機能・条件・コード識別子を使います。完了報告や旧仕様を追記して並存させず、本文を現行の契約へ更新します。
