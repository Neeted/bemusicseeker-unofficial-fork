# テストの設計と配置

## 目的と適用範囲

恒久テストを追加・変更・削除するときに、独立した仕様の根拠と、既存テストを生かした最小の検証を選びます。目的はテスト数を増やすことではなく、継続して守る契約を決定的に確認することです。実行条件は[検証仕様](testing.md)、担当の順序と引継ぎは[エージェント運用](agent-workflow.md)を正本とします。

## 用語

[共通用語集](../glossary.md)のテスト設計書、判定基準、テスト群、失敗再現、識別力の確認を使います。本書の「意味変更」は、期待結果・許容差分・判定対象を変える変更です。ファイル移動や名前変更だけでそれらが変わらない場合は、機械的な変更として扱います。

## 仕様

### 変更分類と恒久テストの必要性

ファイル名ではなく目的と影響で分類し、混在する場合は部分ごとに判断します。ルートは継続して守る契約、既存の検証で不足する点、保守負担に見合う効果を数行で示し、「変更なし」「既存更新」「追加」「削除」から必要な扱いを選びます。判断のためだけに台帳や追加の承認手続を作りません。

| 変更の目的 | 判断 |
| --- | --- |
| 不具合修正 | 原則として再発を検出できる検証を確保する。既存テストの活用・更新で足りるなら新設しない。 |
| 新しい利用者仕様・安定契約 | 継続的な保証に価値があり、既存テストが不足する場合に追加・更新する。 |
| 挙動を保つ構成整理、運用、ビルド、検証順序 | 原則として新設しない。既存テストの更新・削除が必要かは別途判断する。 |

新仕様に旧実装が合わないことだけでは、不具合や回帰の証明にはなりません。旧経路の不在も、再導入が具体的な契約違反になる場合だけ固定します。削除のみで代替不要と判断した場合は、その理由と契約への影響を示し、代替テストを必須にしません。

恒久テストが不要でも検証は必要です。既存テスト、実行確認、静的検査から変更に合う方法を選びます。途中でテストの意味変更が必要になった場合は、その部分だけ設計の要否を再評価します。

### 仕様の根拠とテスト設計書

恒久テストの追加・意味変更・置換が必要な場合は、実装前に独立した設計担当が判定基準を作り、ルートが承認します。削除のみで代替不要の場合と、期待結果を変えない機械的変更には、この設計書を要求しません。

根拠にできるのは、対象の挙動を明示したユーザー要件、承認済み課題・再現・受入条件、機能仕様、公開API・通信・スキーマ・ファイル形式、外部標準、明示的に承認した現行挙動の固定範囲です。現在の実装本体・出力・既存期待値・翻訳文言・ソース配置だけを根拠にしません。

実装本体や既存期待値を読む前に、次を揃えます。

| 項目 | 記載内容 |
| --- | --- |
| 根拠 | 要件・仕様の該当箇所と、そこで求める挙動。 |
| 対象と到達経路 | 本番の入口、成立する前提、対象状態、利用者・永続データ・外部データへの影響。 |
| 期待結果 | 必ず維持する条件、結果、失敗、取消、通知、後片付け。 |
| 許容差分 | 変えてよい翻訳、順序、書式、内部構造、時機など。 |
| 誤実装との区別 | 少なくとも一つの現実的な反例と、それを見逃さない観測。 |
| 確認方法 | 本体の挙動を確認する方法。失敗再現や識別力の確認が必要なら、その理由と方法。 |

設計書の作業名・項目名は、進行中の計画と引継ぎだけで使う一時的な参照です。段階番号、`Packet ID`、`Contract ID` を恒久仕様やテストのクラス・メソッド・属性・ケースID・表示名・コメントへ転記しません。機能・条件・期待結果で命名し、根拠は現行仕様へ接続します。外部標準の番号やデータ形式の版は区別します。

本番の入口で成立しない任意状態を、非公開呼出し・リフレクション・代替実装で作っても、到達可能性の証明にはなりません。プロセス専用DB、単一の書込み主体、外部変更の可否、取得時点などの前提を明記します。代替実装は、その前提内の入力と障害を表現するために使います。承認済みの新入口は計画上の経路を根拠にでき、不正入力は入口での拒否を確認します。

### 既存テストの調査と配置

判定基準の確定後に、機能仕様の対応表、本番の入口と識別子、用語、失敗文言から既存テストを絞ります。全テストの台帳を作らず、該当機能と共通補助処理を調べます。既存テストは配置の根拠であり、期待値を書き換える根拠ではありません。

| 設計項目 | 実装の管理主体・識別子 | 既存テスト候補 | 配置 | 共有資源・実行区分 | 完了の待ち方 | 退役するもの |
| --- | --- | --- | --- | --- | --- | --- |
| 機能・条件・期待結果 | 実際の入口と処理主体 | テスト群と関連ケース | 既存への追加・置換・新設 | 資源の所有・分離・復元 | 実際の完了通知と失敗検出期限 | 旧テスト・補助処理・経路 |

同じ管理主体を扱う既存テスト群への追加を優先します。脆い・重複するテストは、同じ契約を守る検証へ置換して削除します。管理主体、共有資源、実行区分、失敗の扱いが混ざる場合だけ新しいテスト群を作り、理由を示します。

### 検証方法の優先順位

利用者に見える結果、永続データ、イベント、失敗・取消・終了・後片付けを、本番の入口から確認します。構造そのものに意味がある場合は、コンパイル後の型・属性・依存関係を確認します。ソース文字列、非公開メソッド、広範なスナップショットは、その詳細自体が契約である理由、管理主体、退役条件が承認されている場合だけ使います。

表示リソースは[全件共通検査と機能テストの分担](#表示リソースの検査)に従います。内部配置や無害な文言変更で壊れるだけのテストは避けます。生成物の整合は実際の生成・利用経路で確認し、自己申告のメタデータと、それを読むテストだけで成功できる形にしません。

現行挙動を一時的に固定するテストは、正しさの証明と分けます。固定対象、現在値を根拠にする承認、利用目的、退役条件を明記します。テスト用の公開API、製品側の計算の複製、非公開の呼出し順を守るためだけの仕組みは増やしません。

### 表示リソースの検査

`Resources.resx`、公開文字列アクセサー、同梱する全言語JSONのキー集合、非空の文字列値、複合書式の成立と引数番号の対応は、`LocalizationResourceParityTests` の全件共通検査で保証します。言語名メタデータは表示リソースのキー集合から除外します。書式引数は番号の集合で比較し、訳文の語順、引数の反復、表記変更を許容します。引数の実際の型に固有の書式や、翻訳の自然さまで保証する検査ではありません。

リソース追加や翻訳修正だけを理由に、特定キーの存在・非空・書式を調べるテスト、機能別のキー一覧、言語ごとの訳文を複写した期待値を増やしません。全件共通検査の不足は全キーに適用する規則として補い、個別のキー表へ移し替えません。

機能テストは、通知の選択、対象・件数・原因の受渡し、表示先、言語切替後の画面・アクセシビリティ名の更新、表示上限、規定の代替表示を検証します。表示を比較する場合は、その役割に対応するリソースと実際の入力から期待値を作り、訳文そのものは固定しません。辞書間で引数が一致しても、呼出側が件数の意味や型を取り違えた誤実装は機能側で区別します。実際の表示挙動を確認する多言語テストは、辞書だけの検査とは区別して維持します。

モデル内の独自例外も、詳細が画面へ渡る場合は表示文言です。文字列の所在ではなく通知経路で判断し、例外型・対象パス・引数名・内部例外・失敗分類を保ってリソースを使います。診断、内部識別子、変換用中間値、解析規則を文字種だけで表示リソースへ移しません。

### 共通補助処理と資源の所有

WPFには `TestUiDispatcherHost` と `TestWindowPresentationScope` を使います。Dispatcher上のTask待機は `TestUiDispatcherHost.AwaitTaskOnDispatcher`、通常のライブラリ準備は既存の `TestBmsFactory` を先に確認します。テストごとの `Application`、STAスレッド、独自のDispatcher待機ループは作りません。直接の `Dispatcher.PushFrame` や `HwndSource` は共通基盤か明示された例外だけに限定します。

実ウィンドウの既定は非アクティブ・画面外表示です。前面操作を許すテスト、表示確認、HWNDの所有・破棄は[検証仕様](testing.md#画面テストの分離)に従います。実OSカーソルの操作・観測は使わず、キー、ルーティングイベント、明示的なヒット判定、型付きの操作入力を使います。

EverythingやOS走査のテストは、取得済みで変更不能な入力集合を明示します。ローカルのサービス、索引の反映時機、テスト作成ファイルの即時発見に依存しません。代替入力の不完全さを、空の成功や別経路で補いません。

外部プロセスの開始・待機・標準出力と標準エラーの読取り・停止・診断・残留確認は、一つの管理主体へ閉じます。起動したPIDと生成時刻・子孫関係を追跡し、名前だけで他の `dotnet` や `testhost` を停止しません。元の失敗を後片付けの失敗で上書きせず、成功時の後片付け失敗も無視しません。

### 非同期処理と不安定なテスト

通常完了は、対象のTask、イベント、状態遷移に直接結び付く通知で待ちます。固定の `Thread.Sleep` や、余裕時間としての `Task.Delay` から成功を推測しません。局所的な制限時間は、外部プロセス、画面表示、解放、ロックが成立しないこと、時間超過契約の失敗検出に限定します。

`DoNotParallelize` は分離不能な共有資源、管理主体、復元方法を説明できる場合だけ使います。不安定さを、制限時間の延長、再試行の増加、実行担当数や分割数の削減だけで隠しません。共有状態、順序依存、待機、資源競合を修正します。

### 失敗再現と識別力の確認

不具合修正で本番の入口から再現できる回帰テストでは、修正前の失敗確認は有用です。ただしコンパイル失敗、テスト準備失敗、無関係な例外は対象不具合の再現ではありません。

変更前の版で実行できないことだけを理由に、一時的な誤実装の実行を必須にしません。失敗再現の代替、またはテストの識別力に具体的な懸念がある場合に限り、必要性と検出すべき誤りを定めて行います。通常の不正入力テストとは目的を分けます。一時的な誤実装は必ず取り除き、その復元を確認します。

### 引継ぎとレビュー

実装担当は期待結果・根拠・許容差分を維持し、テストの準備と表明方法だけを適合させます。技術的な障害は[運用契約](agent-workflow.md#障害解決担当を使う条件)に従い、意味の変更が必要なら `NEEDS_ROOT_INPUT` を返します。成功させるために表明を弱めません。

完了時は機能仕様へ契約と実装・テストの対応を移し、作業専用の設計書・配置表は削除します。レビューでは根拠、到達可能性、誤実装との区別、既存テストとの重複、資源の所有、必要と判断した確認結果を点検します。実施を要件にしていない失敗再現の欠落や、単なる差分量は指摘の根拠にしません。

| 必要性、判定基準、配置 | [テスト配下の指示](../../../BeMusicSeeker.Tests/AGENTS.md)、[設計担当](../../../.codex/agents/test-contract-designer.toml) | 作業の分類、独立した根拠、設計項目と実際の検証内容を点検する。 |
| 表示リソースのキー・非空値・書式引数 | [基準辞書](../../../BeMusicSeeker/Properties/Resources.resx)、[アクセサー](../../../BeMusicSeeker/Properties/Resources.cs)、[全言語](../../../lang) | [`LocalizationResourceParityTests`](../../../BeMusicSeeker.Tests/LocalizationResourceParityTests.cs) の全件共通検査。機能固有の通知・表示の確認は各機能のテストが分担する。 |
| WPFの準備・待機・解放 | [共通テスト基盤](../../../BeMusicSeeker.Tests)、[検証仕様](testing.md#画面テストの分離) | 実際のテスト群と共通補助処理の使用を確認する。機能の保証は各仕様の対応表を参照する。 |
| プロセスの所有と失敗 | [スクリプト指針](../../../scripts/AGENTS.md)、[プロセス検証](testing.md#プロセスの待機と失敗) | 実行側と同じ処理境界、残留確認、失敗の優先順位を点検する。 |
| 一時資料の退役 | [資料運用](../../README.md)、[計画運用](../../plan/README.md) | 移管後のリンク、機能名・テスト名、削除対象を静的に確認する。 |
