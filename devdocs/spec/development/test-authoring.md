# テストの設計と保証の分担

## 目的と適用範囲

恒久テストの追加・変更・削除について、必要な保証、判定基準、検証境界、既存テストとの分担を定めます。必要な保証をテスト群全体で維持したうえで、準備・依存・重複する検証と保守負担を小さくします。テスト数や実処理の通過量だけでは判断しません。

実行区分・環境・待機と失敗の扱いは[検証仕様](testing.md)、担当の独立性・承認・引継ぎの手順は[エージェント運用](agent-workflow.md)を正本とします。本書はテストをどう設計するかを扱い、変更後にどの既存テストを実行するかとは区別します。

## 用語

[共通用語集](../glossary.md)に従います。「意味変更」は期待結果・許容差分・判定対象を変える変更です。移動・改名・整形だけでこれらが変わらない場合は機械的変更とします。検証境界の変更やテストの分解・統合は、名前や最終期待値が同じでも保証の分担を再確認します。

検証境界は、テストが本番処理へ入力する地点と結果を観測する地点です。保証範囲は判定対象の契約、実行範囲は準備や依存を含めて実際に動く処理であり、両者は一致するとは限りません。E2Eは定めたシステムの入口から最終結果までを通す検証を指し、UI・外部サービスを含む範囲は個別に明示します。

## 仕様

### 変更分類と恒久テストの必要性

変更の目的と影響から、継続して守る契約、既存の検証の不足、保守負担に見合う効果を確認し、「変更なし」「既存更新」「追加」「削除」を必要な範囲ごとに選びます。判断は計画か引継ぎに数行で示し、専用の台帳は作りません。

| 変更の目的 | 判断 |
| --- | --- |
| 不具合修正 | 原則として再発を検出する検証を確保する。既存テストの活用・更新で足りれば新設しない。 |
| 新しい利用者仕様・安定契約 | 継続的な保証に価値があり、既存テストが不足する場合に追加・更新する。 |
| 挙動を保つ構成整理・運用変更 | 新しい保証がなければ原則として新設しない。既存テストの更新・削除は別途判断する。実行制御や失敗判定などの契約を変える部分は、前二行に照らして判断する。 |

削除のみで代替不要とする場合は、不要になった契約か、既存の保証で足りる理由を示します。新仕様に旧実装が合わないことは、それだけでは不具合の証明になりません。旧経路の不在も、再導入が具体的な契約違反になる場合だけ固定します。

恒久テストの新設が不要でも、変更に合う既存テスト・実行確認・静的検査は行います。局所的な変更で広いテストを新設しない判断と、既存の統合テストを回帰確認として実行する判断は両立します。

### 仕様の根拠とテスト設計書

追加・意味変更・置換では、独立した判定基準を先に定め、その後に具体的な検証境界と配置を設計します。機械的変更と代替不要の削除には設計書を要求しません。担当への入力、承認、利用不能時の扱いは[テスト設計の要否](agent-workflow.md#テスト設計の要否)に従います。

判定基準の根拠には、対象の挙動を明示したユーザー要件、承認済みの課題・再現・受入条件、機能仕様、公開API・通信・スキーマ・ファイル形式、外部標準、明示的に承認した現行挙動の固定範囲を使います。現在の実装・出力・既存期待値・翻訳文言・ソース配置だけから正解を作りません。入力の受理・拒否や操作の許可条件は[確定した要件](agent-workflow.md#要件と到達可能性)に従い、外部標準だけを理由に従来の受理範囲を狭めません。

実装本体や既存期待値を読む前に、次を揃えます。具体的なAPI名やテスト配置は、その後の調査で確定します。

| 項目 | 記載内容 |
| --- | --- |
| 根拠と対象 | 仕様の該当箇所、保証する責務、対象となる利用者・データ・操作。 |
| 条件と期待結果 | 有効な入力と前提、維持する結果・状態遷移・失敗・取消・通知・後片付け。 |
| 許容差分 | 契約に含めない順序・時機・書式・内部構造など、変わってもよい範囲。 |
| 誤実装との区別 | 現実的な反例と、それを見逃さない観測。 |

判定基準の確定後に、本番の入口・前提・経路を調べ、対象状態への到達可能性を確認します。承認済みの新機能は計画上の経路を使えます。内部APIを直接呼べることや、非公開状態を任意に作れることだけでは到達の根拠になりません。拒否すると定めた入力は、その拒否を担う境界で確認します。

### 検証境界と保証の分担

保証対象を十分な忠実度で観測できる、狭く安定した本番の処理境界を原則として選びます。公開範囲やクラス数だけで境界を決めず、準備・代替実装・診断・保守も含めて比較します。小さい実DBなどを使う方が単純なら、形式的に局所化するためだけに置き換えません。

本番からの到達可能性の確認と、各テストでアプリケーション全体を実行することは別です。実行した処理すべてを保証したことにもなりません。開始地点、実装を動かす範囲、代替する依存、観測する結果を区別します。

| 主な保証対象 | 境界の選び方 |
| --- | --- |
| 一つの責務の条件分岐・境界値・状態遷移 | 有効な要求・通知・結果を受け付ける境界から、判断と出力を担う実装を動かす。条件の組合せは主にここで検証する。 |
| 主体間の接続・データ受渡し・完了順序 | 保証に必要な複数主体と、その実際の接続を動かす。UIのBinding・コマンド接続・描画も、対応する実装で確認する。 |
| 主要な利用者フロー・標準構成の成立 | 代表的な統合テスト・E2Eテストで、定めた開始地点から利用者に約束する結果まで確認する。標準構成を保証するなら、テスト独自の組立てだけで代用しない。 |

これらは保証の分担であり、すべての機能に全種類のテストを新設する指示ではありません。件数や比率は固定せず、既存の保証とリスクから不足する範囲だけを補います。広い境界を選ぶ場合は、局所テストの組合せだけでは不足する保証と、その範囲を動かす理由を示します。局所テストでの検出が原理的に不可能であることまでは求めません。

上位テストは、その接続・フローの保証に必要な条件へ絞り、下位テストの条件網羅を目的に繰り返しません。ただし、代表フローで最終結果を確認するために下位の実装を通すことや、同じ重要な結果を確認することは禁止しません。重複は同じコードを通るかではなく、得られる保証と負担で判断します。

通知の生産、実際の接続、受信側の挙動は分担します。正しい通知を直接入力したテストは受信側を保証しますが、生産側がその通知を作ることや、標準構成で接続されることまでは保証しません。本体の完了、通知、永続化、UI反映の順序や独立性が契約なら、その処理と接続を動かして確認します。例えば、終端通知を手動で入力できても、実処理がUI反映を待たずに完了することを確認したことにはなりません。

### 依存の制御と観測

保証対象の処理は実装を動かし、対象外の依存は既存の境界で固定入力や代替実装にできます。代替は、入力の有効範囲、識別子、失敗、通知順序、寿命など、対象に影響する依存先の契約を保ちます。代替側が期待する最終結果を作り、保証対象の判断を迂回する形にしません。

表示の検証に表示用の入力を与えることと、その入力を生成する処理を検証することは別です。生産側の確認では、識別子の付与や変換を行う本番処理を通します。代替と実依存の不一致は関係する接続の検証で補い、形式的にすべての代替へ専用テストを追加しません。

通常テストでは、テスト所有の入力と資源で結果を再現できるようにします。広い統合テストでも、利用者の実設定・実DB・公開サービスの可用性に依存させる必要はありません。実際の外部環境への接続が保証対象なら、必要条件と未実施時の扱いを[実行区分](testing.md#テスト区分)に従って分けます。入力不足や依存先の失敗を、空の成功・別経路・無条件の再試行で補いません。

境界を狭めるためだけの公開API、テスト専用の本番分岐、製品側の計算の複製は増やしません。既存の境界で単純に検証できない場合は、必要な範囲の実処理を使う方法と、製品の責務整理として有効な変更を比較します。

### 既存テストの調査と配置

判定基準の確定後、機能仕様の対応表、関連する本番経路と識別子から既存テスト・共通補助処理を調べます。全テストの台帳は作らず、同じ責務の既存テストを優先して更新します。調査結果は配置と不足の判断に使い、期待結果を実装へ合わせる根拠にはしません。

設計には、次の対応を必要な範囲で加えます。判定基準と配置を別々の台帳へ複写する必要はありません。

| 項目 | 記載内容 |
| --- | --- |
| 検証境界と観測 | 具体的な入口・処理主体・結果、実装を動かす範囲、代替する依存。広い範囲が必要なら、その追加の保証。 |
| 既存テストとの分担 | 各テストが守る契約、既存で足りる範囲と不足、追加・更新先。 |
| 実行条件 | 資源の所有・分離・復元、実行区分、順序の制御、完了と失敗の観測。 |
| 置換・削除 | 元の保証の移管先、不要になった保証と理由、退役するテスト・補助処理。 |

テストを分解・統合するときは、表明していた結果だけでなく、実接続、通知生成、確定順序、完了・後片付けの保証も移管先で維持できるか確認します。依存の削減だけを理由に削除せず、必要な保証が移った後で重複を取り除きます。反対に、契約として不要な保証には代替を要求しません。

物理配置と共通補助処理の入口は[テスト配下の指針](../../../BeMusicSeeker.Tests/AGENTS.md#配置と共通補助処理)に従います。責務や共有資源・実行区分が混在する場合に分割し、局所・統合・E2Eという分類だけのためにプロジェクトや基盤を増やしません。

### 検証方法の優先順位

利用者に見える結果、永続データ、イベント、失敗・取消・終了・後片付けを、選択した境界から観測します。表明は契約違反を区別でき、許容した内部変更では壊れないものにします。値や文字列の完全一致も、その正確さが契約なら使えます。

構造自体が契約の場合は、コンパイル後の型・属性・依存関係を優先します。ソース文字列、非公開メソッド、広範なスナップショットを使う例外では、その方法が必要な理由、固定範囲、管理主体、退役条件の承認を得ます。生成物は実際の生成・利用経路で確認し、自己申告のメタデータと、それだけを読む検査を同時に変えて成功できる形にしません。

現行挙動の一時的な固定は、仕様上の正しさの証明と区別します。固定範囲、現在値を根拠にする承認、利用目的、退役条件を明記します。

### 表示リソースの検査

辞書の整合と、機能が正しい内容を表示することを分けます。

| 担当する検証 | 保証範囲 |
| --- | --- |
| `LocalizationResourceParityTests` の全件共通検査 | `Resources.resx`、公開文字列アクセサー、同梱する全言語JSONのキー集合・非空値・複合書式・引数番号の対応。言語名メタデータはキー集合から除外し、日本語JSONは `Resources.resx` と全文言を一致させる。他言語との文言一致は求めない。 |
| 各機能のテスト | 通知の選択、対象・件数・原因・型の受渡し、表示先、表示上限、規定の代替表示、言語切替後の画面・アクセシビリティ名の更新。 |

書式引数は番号の集合で比較し、訳文の語順・反復・表記変更を許容します。全件共通検査は、実際の引数の型に固有の書式や翻訳の自然さを保証するものではありません。機能側の誤った引数や表示更新は、対応する機能テストで区別します。

リソース追加だけを理由に、キーの存在・非空・書式を調べる個別テスト、機能別のキー一覧、訳文の複写を増やしません。表示比較には、その役割のリソースと入力に基づく期待値を使います。全件共通検査の不足は共通規則として補い、実際の多言語表示の検証を辞書検査で代用しません。表示文言の適用範囲は[ログと表示文言](../../../AGENTS.md#ログと表示文言)に従います。

### 共通補助処理と資源の所有

準備・実行・観測・解放の所有者を明確にし、既存の補助処理を使います。独立した一時資源を優先し、共有する場合は準備から復元までの競合と再入を確認します。DBの準備と観測を効率化しても、検証対象のスキーマ作成・トランザクション・確定境界は迂回しません。

環境固有の規則は[資源の分離](testing.md#資源の分離と共有)、[画面テスト](testing.md#画面テストの分離)、[外部プロセス](testing.md#プロセスの待機と失敗)に従います。通常テストの入力分離と、実OS・機器との接続確認を区別します。

### 非同期処理と不安定なテスト

順序は要求・通知・明示的な待合せで制御し、固定時間の経過から成功を推測しません。論理的な通知順序だけが対象なら入力順を制御し、スレッド制約・排他・実際の並行動作が対象なら、その制御を担う実装を動かします。本体完了とUI反映など、異なる完了条件を混同しません。

待機・失敗検出・解放と期限は[非同期処理の待機](testing.md#非同期処理の待機)に従います。不安定さは共有状態・順序依存・資源競合・待機の問題として調べ、期限延長、再試行増加、並列度の削減だけで隠しません。

### 失敗再現と識別力の確認

不具合修正では、対象契約を扱う境界から修正前の失敗を確認することが有用です。コンパイル失敗、準備失敗、無関係な例外は対象不具合の再現ではありません。

変更前の版で実行できないことだけを理由に、一時的な誤実装の実行を必須にしません。失敗再現の代替や識別力への具体的な懸念がある場合に、検出すべき誤りと方法を定めます。通常の不正入力検査とは目的を分け、一時的な誤実装は取り除いて復元を確認します。

### 引継ぎとレビュー

実装担当は承認された判定基準と保証の分担を保ち、準備と表明方法を適合させます。意味変更が必要なら判断を戻し、成功させるために判定を弱めません。差し戻しと担当の手順は[エージェント運用](agent-workflow.md)に従います。

レビューでは、根拠と到達可能性、誤実装を区別する観測、実装と代替の境界、既存テストとの分担、置換で失う保証、資源と完了条件を確認します。テストの種類・件数・差分量や、必要としていない失敗再現の欠落だけを指摘の根拠にしません。

完了時は契約と保証の分担を[機能仕様の対応表](../README.md#仕様書の書式)へ反映します。作業専用の設計書・配置表は[文書運用](../../README.md#現行情報の維持)に従って退役させ、機能・条件・期待結果で命名します。一時的な段階番号や作業IDを恒久仕様・テストへ持ち込みません。
