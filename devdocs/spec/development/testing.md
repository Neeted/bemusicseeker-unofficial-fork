# テストの実行と受入検証

## 目的と適用範囲

通常の機能検証、性能測定、大容量データ、外部プロセス、配布・更新の受入検証について、実行範囲・環境・資源・待機・結果判定を定めます。保証対象とテストの追加・変更・削除は[テスト設計](test-authoring.md)、担当の実行責任と引継ぎは[エージェント運用](agent-workflow.md)に従います。

標準入口の対象module・必須ID・段階ごとの制限時間・結果の保存先の一覧は[検証入口の説明](../../../tools/BeMusicSeeker.Verify/README.md)を正本とします。本書は、その一覧を使って検証区分を選び、結果を判定するための契約を扱います。

## 用語

[共通用語集](../glossary.md)を参照します。コードの識別子は原表記を使います。

**テストプロセス**はMTPテストアプリと、その所有するテストホストを指します。**完全修飾名（FQN）**は名前空間・クラス・メソッドまでを含むテスト識別子です。**判定記録**は実行結果を機械的に確認するTRXやJSONです。**必須ID**は、Scenarios・Desktopのテスト名の先頭に置く `SC-01` や `DT-01` などの識別子で、標準入口が選択結果に含まれることを要求するものです。

**実機確認**は、実環境で人またはエージェントが操作・観察する確認です。画面、実OS入力・フォーカス・IME、DPI・実モニター、音声機器、担当の起動・設定適用・入力継承などを含みます。実アプリや外部プロセスを起動して結果を自動判定する既存の検証は、自動検証として扱います。

## 仕様

### 検証方針

開発環境の構築、実装、統合、レビュー、コミット、リリースを通じて、実機確認を必須工程にしません。エージェントは原則として自動テストと静的確認で検証し、表示・配置などの確認に必要なら画面外のWPF描画スクリーンショットを使います。スクリーンショットを全件の必須条件にせず、この方針のためだけに代替基盤やテストを増設しません。

実機確認が有用な場合は、変更に関係する理由、条件、操作、期待結果を利用者へ簡潔に推奨します。結果待ちを必須工程にせず、エージェント自身が実施するのは利用者が明示的に依頼した場合です。実機確認の未実施だけで各工程の完了を妨げません。

自動検証の成功を実機確認済みとは扱わず、未実施・未確認の範囲を報告します。必須の自動検証、失敗の報告と修正、既知不具合への対処は維持します。以下の検証区分・期限・失敗条件と、各機能仕様の自動検証をこの方針で緩和しません。

静的レビューと実行検証は独立した合格条件です。レビューの開始条件と進め方は[レビューの進行](agent-workflow.md#レビューの進行)に従い、`verify`・`full`・性能測定の完了や成功を待ちません。全体テストの未完了・未成功だけを静的な不合格理由にせず、統合・完了時には最終差分に適用できる両方の合格を要求します。レビュー合格で必要なテストを省略せず、失敗・未実行を成功へ読み替えません。

### 実行範囲の選択

検証区分は作業段階で選びます。

| 作業段階 | 使う検証区分 |
| --- | --- |
| 反復中 | 対象moduleの直接MTP実行、または `dev` |
| 通常開発のコミット・`dev` への統合 | `verify` |
| 正式リリース前の公開候補 | `prepare-candidate` で生成した候補に対する `full --distribution-catalog <absolute catalog>` |

必要な実行検証の成功と独立した最終静的レビューの合格を揃えて、通常開発のコミット・`dev` への統合を行えます。文書のみの変更は[文書と検証](../../../AGENTS.md#文書と検証)に従います。

`full` は正式リリース前の公開候補に必須です。公開時には合格summaryと同じZIPを照合し、後で再生成したものへ差し替えません。公開までの順序は[リリース手順](release.md#正式リリースの準備)に従います。

公開候補は、次の条件で再利用を判断します。

- テストだけを変更し、製品・依存関係・配布設定・同梱資料やその内容が変わらない場合は、通常のGit差分を確認して同じ候補を再利用できます。
- それらが変わった場合は、新しい候補を生成して `full` を再実行します。
- `full` の自動整形による変更も、同じ基準で判断します。

配布スクリプトや更新処理を開発中に変更する場合も、通常の最終検証は `verify` とし、変更した契約を確認できる関連テスト・受入検証を絞って追加します。必要なら開発中にも `full` を実行できますが、変更ファイルの種類や将来のリリースだけを理由に、コミット前の `full` を必須にしません。次版のリリースノート作成や、配布物に含まれる実行時設定の変更だけでも同様です。レビューでは作業段階と変更の影響を確認し、変更固有の検証が不足する場合は、その対象と確認すべき契約を示します。

局所テストを追加したことや、広いテストの新設が不要だったことを理由に、選択した段階で必要な既存検証を省略しません。テストの保証範囲と検証区分は別です。統合・E2Eという呼び方だけで `full` へ移したり、すべての変更に全体フローの新設を要求したりしません。必要な環境・資源・規模から[テスト区分](#テスト区分)を選び、どこまで確認したかを報告します。

### 複数ワークツリーの検証

`verify` と `full` は、全ワークツリーを通じて同時に一件だけ実行します。全体ルートが担当間の連絡で開始と終了を調整し、必要な局所検証などの準備が揃った順に実行枠を割り当てます。`full` の通し実行だけが残った場合も同じ順序へ入れ、後から準備が揃った `verify` によって待機が延び続けないようにします。

別ワークツリーの対象moduleの局所MTP実行と、その実行に必要なビルドは並行できます。局所MTP実行は単位責任者が開始・結果・所有プロセスの回収まで管理し、実行のたびに全体ルートの開始許可を求めません。

同一ワークツリーでも静的レビューと実行検証は並行できます。その間は次を守ります。

- レビュー対象と判断に使う共有依存を固定し、それらを書き換える編集・自動整形・生成処理を止めます。必要な自動整形は凍結前に済ませます。標準入口に自動整形が含まれる場合は、その工程をレビューと重ねません。
- ソースを変更しないテストと、レビュー対象外の生成物だけを書くビルドは継続できます。
- 実行中のテストが読むバイナリやデータをビルド等で上書きしません。別ワークツリーを含め、共有出力・設定・DB等の資源衝突を避けます。

実行失敗が判明してもレビュー全体を自動停止・失効させません。新しい証拠を担当へ共有し、判断に影響する箇所を確認します。修正は該当範囲の凍結を解除して行い、修正後に誰を呼ぶかは[レビューの進行](agent-workflow.md#レビューの進行)に従います。

実測負荷や資源問題が出た場合は、その根拠に応じて全体ルートが実行の開始順や並行範囲を調整します。性能測定は他の重い検証と分離し、全体ルートが開始を調整します。版と範囲は既存の担当連絡とGitで引き継ぎ、恒久台帳や自動予約機構は追加しません。

開始済みの処理を別の検証の都合で中断せず、終了と結果回収を待ちます。競合しない別ワークツリーの調査・編集は進められます。ワークツリーの追加・完了・再利用の判断、所有と独立性、移管時の確認結果の引継ぎは[並列作業](agent-workflow.md#並列作業)に従います。

最終検証済みの版をそのまま `dev` へfast-forwardで統合できる場合、統合直後に同じ `verify` を重複して実行しません。検証後にコードや関連する基底が変わった場合は、新しい版に必要な検証を行います。ブランチ更新と影響するレビューは[通常の統合手順](release.md#通常の作業ブランチの統合)に従います。

### 標準入口

WindowsのPowerShell 7からリポジトリルートで実行します。標準入口は [BeMusicSeeker.Verify](../../../tools/BeMusicSeeker.Verify/README.md) です。`global.json` のMSTest.Sdkがテストフレームワーク・アダプター・MTPの版を所有し、ロックファイルに従う復元で依存を固定します。テストの発見・DataRowの展開・filter・TRXは標準MTPへ任せ、独自のFQN列挙や分割実行は作りません。

```powershell
dotnet run --project tools/BeMusicSeeker.Verify -- dev
dotnet run --project tools/BeMusicSeeker.Verify -- verify
$candidate = Join-Path (Get-Location) 'artifacts/candidates/release-1'
dotnet run --project tools/BeMusicSeeker.Verify -- prepare-candidate --output $candidate
dotnet run --project tools/BeMusicSeeker.Verify -- full --distribution-catalog "$candidate/catalog.json"
dotnet run --project tools/BeMusicSeeker.Verify -- compatibility --suite chart-info-bms
dotnet run --project tools/BeMusicSeeker.Verify -- performance --suite scan-commit
```

| profile | 用途 |
| --- | --- |
| `dev` | 自動整形を省いた反復。 |
| `verify` | 変更したC#の自動整形を含む、通常開発のコミット・`dev` への統合の標準。 |
| `full` | 全体の自動整形を含む、明示した公開候補の受入。 |
| `compatibility` | 専用入力・環境を準備して、登録済みsuiteの一つを明示実行する。 |
| `performance` | 全仕事量の計測を他の重い検証と分離して、登録済みsuiteの一つを明示実行する。 |

各profileが選ぶmoduleと必須ID、suiteの一覧は[検証入口の説明](../../../tools/BeMusicSeeker.Verify/README.md)に示します。

#### 結果の判定

標準入口は、選択した全moduleで次をすべて満たした場合だけ成功とします。

- 今回の実行の非空なTRXがあり、全行が `Passed` で、実行単位の結果も成功している。
- テストプロセスが正常終了し、所有するプロセスとパイプがすべて終端している。
- profileが要求する必須IDが、選択結果のテスト名の先頭にすべて現れる。同じmodule内で同じIDの行が複数あることは許可し、その全行に `Passed` を要求する。別moduleへの同じIDの重複は拒否する。

選択ゼロ、一部または全部のskip、TRXの欠落・不正、制限時間超過、回収失敗は成功にしません。`dev`・`verify` の `--filter` はmoduleの集合を減らさず、必須IDが不足すればfilter指定時も失敗します。`full`・`performance` の `--filter`、suiteの指定漏れ・未登録名は準備前に拒否します。環境suiteの未選択は未実施であり、`full` の成功を全環境suiteの成功へ読み替えません。

#### 直接MTP実行

局所的な絞込みは、対象projectを直接実行します。

```powershell
dotnet run --project tests/BeMusicSeeker.Core.Tests -c Debug -p:Platform=x64 -- --filter 'FullyQualifiedName~FractionTests' --report-trx --minimum-expected-tests 1
```

直接MTPの成功は、標準入口の自動整形・ビルド・全moduleと必須IDの結果確認を代替しません。直接実行でも、結果が非空で全行 `Passed` であること、終了コード、所有プロセスの回収を確認します。

Linuxでは[クロスビルドと局所検証](../../setup-linux.md)の実行範囲と未実施のWindows検証を報告し、Windowsの `verify`・`full` の成功に置き換えません。

### 自動整形の対象と実行

`verify` は、未ステージ・ステージ済みの変更ファイルと、Git の除外設定に該当しない未追跡ファイルの和集合から、現在存在する C# ファイルを選びます。対象は作業ツリー上のファイル全体であり、変更行だけには限定しません。`full` は全体を対象とします。いずれも生成先の `artifacts/verification`、`bin`、`obj`、`.tmp` を除きます。変更対象がゼロなら formatter を起動せず、対象指定なしの全体整形に置き換えません。

[共通の整形処理](../../../tests/BeMusicSeeker.TestSupport/Verification/RepositoryFormatter.cs)は、`dotnet format` のスタイル修正を先に行い、続いて空白・改行を揃えます。変更範囲では両方に同じファイル一覧を渡します。整形後に同じ formatter の変更なし検査を重ねません。C# 以外も含む Git 差分の空白検査は、整形後に行います。

標準検証では、対象の取得と両方の formatter が `format` 段階の制限時間を共有します。整形はproject全体の意味解析で長いため、ビルドを整形と同時に開始します。formatterの設計時評価は各プロジェクト既定のDebug構成、検証のビルドはRelease/x64で、中間・出力先は分かれます。整形の書込みとコンパイラの読取りが重なった共有違反は整形の失敗として扱います。Git の取得失敗、formatter の非ゼロ終了・制限時間超過、差分の空白エラーでは、同時のビルドを取り消し、再ビルド・テストへ進みません。整形が対象の内容を変えた場合は、同時のビルドの結果を採らず、整形後の内容で再ビルドした結果で判定します。採らなかったビルドでも、ログ保存と所有プロセスの回収の失敗は非成功です。この段階は復元・ビルド・テストの制限時間に含めません。formatter の警告は診断へ残します。自動整形の成功は、自動修正できないものも含むすべてのスタイル診断がゼロであることを意味しません。

手動で整形だけを行う場合も、同じ処理を使います。

```powershell
pwsh -NoProfile -File .\scripts\format-code.ps1
pwsh -NoProfile -File .\scripts\format-code.ps1 -Scope All
```

手動入口は、ビルド済みのReleaseのVerify実行ファイルへ処理を渡します。未準備なら変更C#がゼロでも失敗し、暗黙のビルド・復元や別構成の探索をしません。準備のコマンドと期限は[手動整形の準備](../../../tools/BeMusicSeeker.Verify/README.md#手動整形の準備)に示します。

手動入口の既定範囲は `Changed` です。整形対象がある場合はロックファイルに従う復元から実行し、復元済みなら `-NoRestore` で省略できます。対象取得・復元・整形は一つの制限時間を共有します。整形規則、SDK、プロジェクト構成を変更した作業では、`-Scope All` で全体を整形します。通常検証が設定変更から対象範囲を推定して自動で広げることはありません。

C# の正規形は [`.editorconfig`](../../../.editorconfig) を正本とし、エラーに設定した規則を formatter の自動修正対象にします。ビルド時のスタイル解析は全モードで有効化せず、スタイルの処理を formatter に集約します。SDK 標準の品質解析は [`global.json`](../../../global.json) の `version` と `rollForward` に従って選択した SDK の既定を維持します。

[`Directory.Build.props`](../../../Directory.Build.props) は本体 `BeMusicSeeker`、更新プログラム `BeMusicSeeker.Updater`、TestSupportと各 `*.Tests` の nullable 診断をビルドエラーとして扱います。nullable 解析の範囲は各プロジェクトとソースの既存設定に従います。補助ツールには nullable 診断のエラー化を追加せず、全警告も一律にエラーへ変更しません。生成コードは SDK の扱いに従い、テストへリンクした補助ツールのコードはテストプロジェクトのコンパイル対象とします。

文書だけの変更の確認は[ルートの指針](../../../AGENTS.md)に従います。Mermaidを追加・変更する場合は[補助図の更新と確認](../README.md#更新と確認)も行い、描画確認と対象アプリの検証を区別します。

### 実行期限と失敗分類

テスト段階の制限時間は、profileごとに一つを全moduleで共有します。現在の値は `dev`・`verify` が600秒、`full` が1380秒です。

- 起動前に取った一つの単調時計の始点をScenarios・Desktopにも渡し、後から起動したmoduleや局所的な待機で延長しません。
- テスト段階には、表示言語ファイルのコピー、テストプロセスの起動、結果判定、summaryの保存、回収を含みます。
- 準備・ビルド・候補の検査と展開は別の段階で、テスト段階の時間に含めません。
- 制限時間は停止を検出するための運用上の上限です。速度の合格基準には使いません。

各時間の記録項目は[時間と証跡](../../../tools/BeMusicSeeker.Verify/README.md#時間と証跡)に示します。

致命的な失敗を検出したときは、検出時刻+10秒と段階の制限時間+10秒の早い方を回収期限として一度だけ確定します。期限後に遅れて正常終了しても成功に戻しません。制限時間内の決定的な失敗は、初回から原因を調べます。

真の時間超過だけは、所有するプロセスツリーの停止・残留確認と診断保存の後、同じコマンド、フィルター、制限時間、版、条件で一回だけ再実行できます。制限時間内に成功し、症状の再発や決定的な診断がなければ一過性の負荷として両方の結果を報告します。それ以外は原因を調べます。局所的な失敗検出タイマーは、この再実行規則の代わりになりません。

`full` の一部で不安定な結果が出た場合は、症状が出た時点で並行していた実行を考慮して原因を調べ、再現や修正の確認はその段階・対象を直接実行して行えます。通しの `full` を繰り返すことを調査の前提にしません。公開候補の受入には、[実行範囲の選択](#実行範囲の選択)のとおり最終版の `full` の成功が必要です。

失敗結果は原因調査の入力です。統合検証の失敗は[不備の差し戻し](agent-workflow.md#不備の差し戻し)で修正担当へ戻します。修正後の新しい版の検証と、失敗した同一版の再実行は区別します。

### テスト時間の短縮

テスト群を整理して実行時間を短縮する場合は、次の方針に従います。短縮は必要な保証を維持したうえでの改善であり、保証の整理と時間の改善は別々に判定します。

#### 比較の方法

同じWindows環境・同じ測定範囲で、変更前の標準 `verify` 一回と最終版の一回を比較することを基本にします。現行版の実行条件が分かる結果があれば基準に使えます。平均や分散を得るためだけの複数回実行は要求しません。反復中は関連する条件を対象moduleの局所MTP実行で確認し、最終版の検証区分と同一版の再実行は[実行範囲の選択](#実行範囲の選択)と[実行期限と失敗分類](#実行期限と失敗分類)に従います。`full` を構成する一部の短縮は、まずその部分（対象module・suite・段階）を直接実行して確認し、最初の手段に `full` の通し実行を使いません。通しの所要や統合した状態を確かめる目的があれば `full` を実行して構いません。`full` の結果を比較に使う場合は、対象・構成が同じ範囲だけを使います。

比較するのはテストプロセスの全体経過時間です。原因の調査では、ホスト別の終了時刻、長いケース、同じ時間帯の待機・共有資源から残る負担を調べます。並列ケースの所要時間を単純合計して全体時間や短縮可能時間と見なさず、スクリプト全体の時間とも区別します。条件が違う結果を同条件の改善実績とは扱いません。

#### 短縮の手段

次の順に検討します。

1. [不要・重複する保証の整理](test-authoring.md#既存テストの採否)
2. 保証に関係しない準備の削減
3. 共有資源に基づく直列化の見直し
4. 通常完了を固定時間で待つ処理の解消

Windowを使わなくしたことだけで `DoNotParallelize` を外さず、設定・文化圏・共有通知等の所有を確認します。通常時に消費しない待機上限を短くすることは、短縮の根拠になりません。残ったホスト間の偏りが実測で分かる場合に分割・配分を検討し、先にホスト数やworker数を増やしません。

次の手段は短縮として扱いません。

- 必要なケースを対象外の検証区分へ移す。
- スキップを増やす。
- 巨大なループへまとめて件数だけを減らす。
- 成功するまで再実行する。
- 制限時間を緩める。

#### 目標時間と報告

目標時間を定める場合は、その短縮作業の計画に置きます。目標は標準入口の制限時間の範囲内で定め、制限時間を延ばして目標を満たしたことにはしません。

報告には、実行件数、スキップとその理由、実測時間、未実施の検証区分を含めます。目標を超えた場合は実測時間と未達を示します。結果は作業用の生成物として使い、時間履歴の恒久台帳や自動配分の保存状態は追加しません。

成功した実行が目標を超えただけでは、追加調査・再実行を始めません。利用者から調査を依頼された場合は、テスト別の所要時間だけでなく最長ホストの遅延区間を確認し、ロックの保持側やDBの確定回数など共通処理まで追います。

### 通常テストの分割と並列実行

標準入口は、次の分割でmoduleを実行します。具体的なworker数の算出と実行順の詳細は[所有と判定](../../../tools/BeMusicSeeker.Verify/README.md#所有と判定)に示します。

- Windows moduleは同じアセンブリを、カテゴリ `Windows.Shell`（MainWindow・Playlist）、両カテゴリ以外、`Windows.Settings` の3実行に分け、各実行を1workerで動かします。カテゴリのないケースは両カテゴリ以外の実行へ入ります。追加のfilterは、分類条件とANDで組み合わせます。
- CoreはWindowsと並行し、複数workerで実行します。走査・同期などの製品パイプラインはブロッキング段を専用スレッドで実行するため、テストプロセスでスレッドプールのworker下限を変更しません。
- `dev`・`verify` のDaily Scenariosは、UIを使う実行の最初の枠で開始します。module全体で利用者セッションの排他を持つため、排他を取得するWindowsのケースとの重なりを段階の冒頭に限ります。`full` では、Windowsの全実行が終端してからScenariosを開始し、Scenariosの後にDesktopを実行します。
- 同じprojectを実行ごとに別々にビルドせず、全実行で一つのビルド結果を共有します。実行ごとにrunsettings・TRX・実行領域・profile・プロセスの所有単位を分けます。

ケースの分配はMTPのメソッド単位の並列化へ任せ、`DoNotParallelize` は標準属性として扱います。

ケースの入力と可変ファイルは、標準入口が用意する実行領域の下に置きます。直接MTP実行でも同じ基底を使います。リポジトリの監視下やOSのシステム一時フォルダーへケース入力を置きません。ケースの `TestWorkspace`・`PreserveArtifacts` は維持し、TRX・ログ・runsettings・配布候補の目録は `artifacts` 側に残します。実行領域の配置は[所有と判定](../../../tools/BeMusicSeeker.Verify/README.md#所有と判定)に示します。

UIの利用者セッションを専有するための排他（session lease）は、moduleごとに次のように取得します。所有する一時領域と入力の分離は[資源の分離と共有](#資源の分離と共有)に従います。

| module | 排他の取得 |
| --- | --- |
| Windows | module全体では取得しない。実Activateを使う `PlaylistLampViewerWindowManagerTests` だけが、UIスレッド外でケース前に取得し、Windowと開始済み処理の回収後に解放する。 |
| Scenarios・Desktop・Compatibility・Performance | module全体で取得する。 |
| Core | 取得しない。実Window・プロセス全体の可変設定を所有しない。 |

### テスト区分

実行集合はmoduleとprofileで決めます。Core・Windowsの通常ケース、ScenariosのDaily・Full、`full` のDesktop、Compatibility・Performanceの明示 `Suite.*` を区別します。`ProcessIntegration` 等の属性がケースに残っていても、標準入口の選択・除外には使いません。明示した導入先が消失した後の再読込・再選択はScenariosのFull、実入力と外部UIAの接続はDesktopで確認します。

環境不足を `Ignore` / `Inconclusive` で飛ばさず失敗にし、未実施を成功として扱いません。[BMS譜面位置の比較ツール](chart-parse-audit.md)は簡易開発用です。変更確認は対象RunnerのReleaseビルドと差分点検に限定し、恒常的なツールのテストは設けません。

Windows moduleの実プロセス境界は、[`ExternalPlayerProcessGatewayTests`](../../../tests/BeMusicSeeker.Windows.Tests/Processes/ExternalPlayerProcessGatewayTests.cs)、[`UpdaterProcessGatewayTests`](../../../tests/BeMusicSeeker.Windows.Tests/Update/UpdaterProcessGatewayTests.cs)、[`UpdaterDeploymentBoundaryTests`](../../../tests/BeMusicSeeker.Windows.Tests/Update/UpdaterDeploymentBoundaryTests.cs) が日常検証で担います。`ProcessIntegration` 属性を持つ更新マーカーのケースも、module全件を選択する標準入口では日常検証に含まれます。これらは共通のWindows probeまたは `OwnedProcess` で子プロセスを所有し、起動前から全終端までの制限時間と、一度だけ確定する独立した回収期限を使います。製品側の元の期限や停止の表明を、回収による停止で代替しません。各ケースの制限時間は[検証入口の説明](../../../tools/BeMusicSeeker.Verify/README.md)に示します。

カテゴリは実行特性を表します。小さい互換性テストや、少数の実部品を接続する検証は通常検証に含められます。`ProcessIntegration` は別プロセス等を扱う区分であり、主体間の接続を確認するすべてのテストを指しません。

### 資源の分離と共有

通常テストは固有の一時ファイル・DB・設定と、再現可能な入力を使い、追跡対象ファイルや利用者のデータを変更しません。公開サービスの可用性、ローカルサービスの索引反映、同じPCでの利用者の操作を合否条件にしません。EverythingやOS走査を利用する機能は、取得範囲と完全性を明示した変更不能な入力集合で検証し、作成直後のファイルが外部索引に現れることを前提にしません。外部環境との接続そのものを確認する場合は、対応する検証区分と条件を明示します。

環境依存を見つけた場合は、保証と必要資源から次の四つへ分類します。準備場所が一時ディレクトリでも、OS全体や利用者セッションへ影響する操作は通常I/Oと区別します。

| 分類 | 適用する条件 |
| --- | --- |
| 日常検証に残す | 所有する一時領域での通常I/O・SQLite・設定、読取り専用属性・共有ロック、明示的に注入した失敗等で保証を再現できる。 |
| 依存をなくす | 保証に不要なドライブ割当や一時フォルダーのパス長への依存を外し、同じ本番処理・観測を所有する一時領域で維持できる。 |
| 専用環境で明示実行する | 実ACL、シンボリックリンク・ジャンクション、ドライブの別名、別ボリューム、HKCUの `Run`・`RunOnce`、外部のネイティブ部品・ツールそのものとの接続が保証対象。`EnvironmentIntegration` を付ける。 |
| 削除する | 必要な保証が既存の担当へ移管済み、または契約上不要。移管先の表明まで確認して旧ケースと不要な補助を除く。 |

専用環境は利用者の通常データ・設定から隔離し、ACL変更・リンク作成・ドライブ別名の割当と解除・HKCU回復登録の作成と回収が可能なWindowsを用意します。`DoNotParallelize` は別利用者や別プロセスとの競合を防がないため、準備した環境でだけ明示実行します。処理・出力の終端後に所有資源を回収し、作業ディレクトリを変更したケースは復元してからドライブ別名を解除します。準備不足・権限不足は失敗です。

クロスボリューム試験は、`BMS_TEST_CROSS_VOLUME_SOURCE_ROOT` と `BMS_TEST_CROSS_VOLUME_DESTINATION_ROOT` に、既存の書込み可能な入力の基点を絶対パスで指定します。両者は異なるローカルドライブのルート配下で、かつ異なる実ボリュームでなければなりません。[GetVolumePathNameW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumepathnamew) で末端のマウントポイントを取得し、[GetVolumeNameForVolumeMountPointW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getvolumenameforvolumemountpointw) のボリュームGUIDで同一実体を拒否します。別名だけを別ボリュームと見なしません。環境の探索や書込みの試行は行わず、指定した基点の下へケース固有の子だけを作成・回収し、基点自体は保持します。

外部依存は対象に応じて用意します。Everythingのネイティブ接続は `BMS_EVERYTHING_PATH_IDENTITY_FIXTURE` に固定SDKとfixture bridgeの基点を指定し、7-Zip接続は既存のProgram Files配置に7-Zip CLIを導入します。Java参照ツールは `JAVA_HOME` またはPATHでJDKを用意し、[`chartstring-dump/run.ps1`](../../../tools/chartstring-dump/run.ps1) の参照リポジトリと固定譜面を準備します。外部エンコーダーは[外部エンコーダー](#解析大規模データ外部エンコーダー)の環境変数を使います。これらの専用保証はCompatibilityの対応suiteで明示実行します。

DBの準備・観測は検証対象の処理と分けます。入力作成だけの複数行投入・スキーマ準備は一つのトランザクションへまとめ、SELECTだけの観測には既存の読取り専用接続を使います。無関係な一時DBの観測がプロセス共通の書込みロックを取り合わないようにします。スキーマ作成・確定境界自体を保証するテストでは、対象の本番処理とトランザクション境界を維持します。

共有設定、リソース辞書、文化圏、テーマ、ウィンドウ一覧などを変更する場合は、準備から復元までの所有を確認します。`DoNotParallelize` は分離不能な共有資源とその復元方法を説明できる範囲に使い、独立した状態だけを扱うテストは並列実行します。この属性は他プロセスや利用者の操作を排他しません。外部入力の分離とテスト間の共有状態は別々に確認します。

通常のテスト群の設定入力には、固定したスナップショット、専用パスの `Settings`、メモリ上の保存先を使い、暗黙の `Settings.Default` や利用者設定の保存先へ戻しません。設定保存の保証には専用パスの実保存処理を使います。日本語リソースの通常の基準は `AssemblyInitialize` で一回だけ準備します。実際の文化圏・テーマの切替と共有通知への購読は、準備から処理の終端・購読解除・復元まで所有します。標準の画面構成はWindowがなくても共有通知を購読するため、その寿命も非並列にします。

### 非同期処理の待機

通常完了は、対象のTask、イベント、状態遷移に直接結び付く通知で待ちます。通知より先に処理が失敗した場合も観測し、来ない通知だけを待ち続けません。テストが閉じた待合せは `finally` で解放し、所有する処理の終結と後片付けを待ちます。

成功通知の到達待ちは、`TestUiDispatcherHost.AwaitNotificationAsync` で通知を生成する実Taskの失敗・取消にも接続します。通知なしで実処理が終わった場合は、その場で未到達として失敗します。生成元が失敗を結果通知へ変換する管理主体では、その管理主体の実際の終端を使います。別に予約されたUI受信は生成側のworkerの完了で代用せず、受信処理自身を所有します。MainWindowの寿命は `CloseCompletion` で終了要求からDispatcherと終端処理まで待ち、通知前の失敗も `Closed`・共有リソースの回収と併せて観測します。

単なる到達・完了確認には局所的な制限時間を追加せず、停止は検証全体の制限時間で検出します。局所的な制限時間は、外部プロセス、ループバックHTTPのfixture、画面表示、解放、ロックが成立しないことの確認、時間超過の契約の失敗検出に限ります。固定の `Thread.Sleep` や余裕時間としての `Task.Delay` から成功を推測しません。短い否定観測は、通常完了を待つ方法や時間保証の証明とは区別します。

ロックが成立しないこと・デッドロックの確認は、probeを専用スレッドで動かし、保持側が判定まで保持したまま「保持中に完了したか」で判定します。判定は `ConcurrencyProbe.AssertCompletesWhileHeld`・`AssertCompletesWhileHeldAsync`・`AssertSignalsWhileHeld` で行います。`AssertCompletesWhileHeld(Async)` では保持側のTaskを `holder` に、`AssertSignalsWhileHeld` では通知の生成元Taskを `producer` に渡し、それらの先行終端をその場で失敗にします。期限にはTestSupportの `ConcurrencyProbe.StallTimeout` だけを使い、正しい実装の合否には使いません。`ManualResetEventSlim` や条件の成立を同期的に待つ到達待ちは `ConcurrencyProbe.WaitForSignal`・`WaitUntil` で、期限なしに通知または生成元の終端まで待ちます。非同期の成功通知は前段の `AwaitNotificationAsync` を使います。製品のcallback内など、その場で投げられない箇所では `WaitCompletedWhileHeld` で完了の有無だけを保持し、保持の解放後にprobeを回収してから表明します。

不安定なテストは共有状態、順序依存、待機、資源競合を調べます。制限時間の延長、再試行の増加、実行担当数や分割数の削減だけで失敗を隠しません。同一版の再実行は[実行期限と失敗分類](#実行期限と失敗分類)に従います。

### HTTP fixtureの待機と回収

ループバックHTTPのfixtureを所有するケースは、操作の待機と後片付けの待機に別々の制限時間を一つずつ使います。現在の通常の上限は操作が30秒、後片付けが10秒です。これらは製品のHTTP期限を仮想時刻で検査する値とは区別します。

#### 操作の待機

開始時に `TestContext.CancellationToken` と連動する操作の取消源を一つ作り、操作全体の監視期限を一度だけ設定します。接続の受付・要求の読取り・応答の書込み・待合せ・各段階とクライアント完了の待機は同じ取消を共有し、段階ごとに期限を延長しません。

- 段階の通知だけを待たず、クライアントの結果とサーバーの実際の終端も監視し、先行した故障や通知なしの終端を失敗にします。
- 実際の生成側の終端を観測した後にも通知を再確認し、同時に終端した通知を失いません。正常終了した補助の生成側は待機の対象から除きます。
- 元のTaskを公開しない管理主体では、対象固有の既存の終了通知を使います。別の処理を保持した全体の終端だけで、HTTPの先行した終了を隠しません。

#### 後片付け

`finally` の開始時に、操作の取消源から独立した後片付けの取消源を一つ作ります。クライアント・全サーバー・切断監視と関連資源の回収は、この取消を共有します。

- クライアントの取消、fixtureの停止通知、リスナーの停止・待合せの解放・受け付けた接続のローカルな切断、実Taskの合流の順に回収します。操作の取消を理由に後片付けを省略しません。
- 複数のサーバーは、一方が失敗しても残りの停止と合流を試みます。
- 待機用のラッパーの取消を製品の取消とは見なさず、元のクライアントTaskの実際の終端と、元のTaskの `await` から得た取消例外を検証します。同期APIを専用スレッドで起動したTaskの `Faulted(OperationCanceledException)` も、元の結果の取消として扱います。
- 保留中の応答に対する相手側の切断（EOF・リセット）は、ローカルの切断や本文の待合せの解放より前に実際に観測します。
- 一次失敗と後片付けの失敗を別に保持し、二次診断または集約例外へ残します。未回収と後片付けの期限超過は非成功とし、実際に所有する処理の終端を確認する前にDB・ディレクトリを解放しません。

#### 非同期の準備と資源の所有

HTTPの準備を非同期に開始する場合は、開始前から呼出し側が元の型付きの準備Taskと、返される資源のディレクトリを所有します。操作の待機だけが取り消された後の遅い成功結果・元の故障も、同じ `finally` と後片付けの期限で観測・回収します。

- メソッドから `TestCleanup` や `using` による解放へ移っても所有を切らず、元のHTTP処理・サーバー・関連workerの同じ実終端条件を使います。
- 外側で後片付けの期限を更新して待ち直しません。未終端なら依存するDB・設定を保持し、明示的に非成功とします。未回収の資源を別のケースへ引き継ぎません。
- HTTP通信の取消・停止と、処理の終端後の通常の `Dispose` は区別します。

HTTPで使う設定は、ケースが所有するディレクトリの `TestSettingsFactory.OpenSettings` へ接続し、元のTaskが未終端のときに `AssemblyCleanup` が設定を削除する全体登録を避けます。既存fixtureの別設定間の値の差と、HTTPを使わない既定経路は維持します。`AssemblyCleanup` を、実処理の未終端時に依存資源を破棄してよい例外にはしません。

#### MainWindowを使うfixture

HTTPを使うMainWindowのfixtureは、HTTPの元のTask・全サーバーの実際の完了・内部で受理したTask・実際の終了処理を、同じ後片付けの取消で合流させます。この一つの実終端確認を、Windowの通常の閉鎖・設定ViewModel・一時DBの通常の解放に共用し、呼出し側とfixtureで別の終端基準を使いません。

失敗・取消で終端した元のTaskも、実際の終端を確認できた場合は資源の回収へ進み、元の失敗と回収の失敗を保持して報告します。終端を確認できなければ資源を保持し、元の失敗と回収の失敗を残してテストを非成功とします。その後の既存 `RunWindowTest` の表示範囲は、失敗時の最終回収としてWindow・HWNDを強制回収します。この最終回収を、実処理の正常終端や通常の終了処理の成功の証明には使いません。

### プロセスの待機と失敗

開始、完了待機、標準出力・標準エラーの読取り、停止、診断保存、残留確認を一つの管理主体が行います。起動したPID、生成時刻、子孫関係を追跡し、名前だけで無関係なプロセスを停止しません。待機と出力読取りは残りの制限時間内に収めます。

標準検証の子プロセスの出力は、[OwnedProcess](../../../tests/BeMusicSeeker.TestSupport/Processes/OwnedProcess.cs) と配布準備の [DistributionPreparer](../../../tests/BeMusicSeeker.TestSupport/Verification/DistributionPreparer.cs) が、所有する境界の中でUTF-8として読み取れるように設定します。保存時にUTF-8へ変換するだけでは、読取り時の誤変換を直せません。親プロセスのコンソール・出力文字コード・カルチャ・環境変数や、この所有境界外のネイティブコマンドの既定の文字コードは変更しません。

失敗時は、実行中または最後に確認したテスト、経過時間、出力、進捗・TRX・停止診断の場所を残します。元の失敗を後片付けの失敗で置換せず、二次的な診断に保持します。元の失敗がなくても後片付けが失敗したら失敗です。開始前の環境変数と作業ディレクトリも復元します。追跡対象ファイルの指紋による外部変更監視は行いません。

### 画面テストの分離

保証の選び方は[画面に関わる保証の分担](test-authoring.md#画面に関わる保証の分担)に従います。以下は、必要と判断した境界での実行・資源管理の規則です。

#### 共有ホスト

WPFは `BeMusicSeeker.TestSupport.Wpf` の `TestUiDispatcherHost` にある一つの `Application` と専用のSTA Dispatcherをプロセス内で共有します。最初の `Dispatcher` / `Invoke` / `ProcessQueuedPresentation` / `RunWindowTest` の利用時に遅延起動し、テストごとに作りません。TestSupportを参照するだけではWPF・設定を初期化せず、画面を使わないmoduleでは起動しません。ウィンドウなしの操作は `Invoke`、実ウィンドウ・Popupは `RunWindowTest` と `TestWindowPresentationScope` を使います。

テストごとの `Application`・STAスレッド・独自のDispatcher待機ループは作りません。直接の `Dispatcher.PushFrame` や `HwndSource` は、共通基盤か明示された例外に限ります。

共有ホストへの要求は、実際のDispatcherOperationと既存のホスト終端通知を観測します。ホストが既に終了していた場合と、要求の受理後に終了した場合は、所有スレッドを合流させて元のホスト例外を返します。Dispatcher停止の二次失敗でも終端通知・合流を失わず、二次失敗を元の例外へ添付します。健全なホスト上のAction自身の失敗は保持し、後続の要求は受理します。

共有ホストのDispatcherで `UnhandledException` に達した例外は、ホストを終端させず継続し、例外本体・順序・発生時のケース（ケースの間なら直前に終了したケース）とともに記録します。ハンドラーは共有ホストにだけ付け、専用STAの検査には付けません。ケースが共有Dispatcherの `UnhandledException` を直接購読して `Handled` を設定することはしません。期間中に未処理例外がないことの表明と、期待する未処理例外の受取りは、次のホストの口を使います。

- 待機・消化API（`AwaitTaskOnDispatcher`・`AwaitPresentationOnDispatcher`・`ProcessQueuedPresentation`・`ProcessQueuedBackground`）の呼出し中に記録された例外があれば、そのAPIは通知を待ち続けず、元の例外で失敗し、記録を消費します（ただし、`ProcessQueuedPresentation` の配置の確定自体が例外を投げた場合を除きます。[表示入力と待機](#表示入力と待機)）。2件目以降は最初の例外の `Data` へ添付します。この失敗で記録は報告済み（消費済み）となり、ケースの終了時に再報告しません。呼出し中に起きたものは、ホスト以外の入れ子フレームで起きたものも対象です。入れ子の待機が先に記録を消費して外側の待機のフレームだけが止まった場合、外側は対象のTaskが未完了なら待機を続けます。
- `AssertNoUnhandledExceptions` は、現在のケースの期間に未処理例外がないことを表明します。記録があれば消費し、各例外の型・メッセージ・スタックを含む `AggregateException`（元の例外を内部例外に保持）で失敗します。
- `TakeUnhandledExceptions` は、現在のケースの期間の記録だけを発生順に受け取って消費します。他ケースの記録とケースの間の記録は見えず、受け取れません。
- 記録の対象は `Dispatcher.UnhandledException` に達した例外です。`BeginInvoke`・`SynchronizationContext.Post`、`Delegate` を受け取る旧形式の `Dispatcher.Invoke(DispatcherPriority, Delegate)` の呼出し先、Win32メッセージから配送される入力・ウィンドウイベントのハンドラーなどが該当します。旧形式の `Invoke` の呼出し先の例外は、`Handled=true` のため呼出し側へ返りません。その `Invoke` を囲む待機・消化APIの呼出し中なら、そのAPIが元の例外で失敗します。それ以外は `AssertNoUnhandledExceptions`・`TakeUnhandledExceptions` か、ケースの終了時に表れます。後から呼んだ待機・消化APIは、呼出し開始時の位置以降の記録だけを使うため、失敗しません。
- `Action`・`Func` を受け取る `Invoke`・`InvokeAsync` の例外は呼出し側（`Task`）へ返り、記録しません。結果を観測しない `InvokeAsync` の失敗は記録されず、`Task` を待つ側で観測します。待機対象のTaskの失敗も呼出し側へ返ります。
- 残る限界：WPFは一度処理した例外を印付けし、同じ例外オブジェクトが再び `Dispatcher` 上で未処理になると、`UnhandledException` を呼ばず、従来どおり `Dispatcher` の外へ送出します（同じ失敗Taskを複数の `async void` で待つ場合など）。`Dispatcher.Run` まで出ればホストが終端し、`InvokeAsync`（`Invoke`・`RunWindowTest` を含む）の中ならTaskの失敗、待機中なら待機の失敗として表れます。印を外す対処はWPFの内部実装に依存するため行いません。また、待機APIは呼出し前に記録された未報告分では失敗しません。待つTaskがその例外で失われた継続に依存する場合は、全体の期限による停止になります。

共有ホストは現在の `AppearanceTheme` を退避し、準備完了前に保存せずLightへ設定します。終了時は同じDispatcherで復元してから `Application` とDispatcherを停止し、通知とスレッドの合流で待ちます。未起動なら何もしません。既存の `Application` との競合、起動失敗、呼出し・終了の失敗は表面化させ、`Application.ResourceAssembly` は変更しません。

#### テストのUIスケジューラー

UIスケジューラー（`IUiScheduler`）を必要とするテスト補助は、呼出し側が窓口を新しく作り特定のDispatcherを必要としない場合、既定の `TestUiScheduler.CreateDefault()` を使います。構築スレッドが共有ホストのDispatcherスレッドならそのDispatcherへ投稿し、それ以外は本番アダプターのDispatcherなしのインライン実行に解決します。

- Dispatcherを返す関数は、メッセージポンプを持つDispatcherかnullに解決します。共有ホストの外のスレッド（MSTestのworker・プールのスレッド・専用スレッド）で `Dispatcher.CurrentDispatcher` を捕捉する関数は使いません。ポンプされないDispatcherへの予約は実行されず、別スレッドからの同期実行が戻らないためです。`Dispatcher.CurrentDispatcher` は共有ホストのスレッド上（`RunWindowTest`・`Invoke` の中など）では共有ホストのDispatcherと同じです。
- 共有ホストのDispatcherを必要とする場合は、`TestUiDispatcherHost.Dispatcher` を返す関数を明示して渡します（例：`new TestUiScheduler(() => TestUiDispatcherHost.Dispatcher)`）。
- Dispatcherがないときの本番アダプターのインライン実行は、呼出し元のスレッドでその場で実行するだけで、UIスレッドへの直列化を保証せず、複数のスレッドから同時に実行されえます。UIスレッドでの直列化を前提とする検査は、共有ホストのDispatcherを使います。

#### ケース境界の検査

UI moduleの `UiModuleLifetime` の `GlobalTestInitialize`・`GlobalTestCleanup` が、共有ホストの未処理例外の記録と、失敗にする観測の記録（[共有ホストの観測記録](#共有ホストの観測記録)）をケースの境界で報告します。ケースの帰属は、Windowsが1 workerで直列に実行されることを前提にします。ホストが起動していない間は、ホスト由来の記録（未処理例外・`B`・`E-a`〜`E-g`）が空で、境界の処理はホスト・`Settings.Default`・`Application` を起動も読取りもしません。未宣言のダイアログ窓口の記録（`D`）はホストの起動と関係なく、呼んだスレッドで記録され、境界はホストを起動せずに出力・判定します。先行ケースがホストを起動した後は、ホストを使わないケースでも、ホスト由来の残留の報告と期間中の記録の帰属を受けます。

- ケースの終了時：そのケースの期間に記録され、ケース内で受け取られなかった例外と、失敗にする観測の記録（項目 `B`、`E-a`〜`E-f`、`D`）および復元の失敗を、そのケースの一つの失敗として報告します。観測と復元は記録の出力より先に、報告は未処理例外の収集（`EndCase`）の後に行い、観測や復元が失敗しても `EndCase` は必ず通します。同じ境界の未処理例外とは一つの失敗にまとめ、元の例外を内部例外として参照のまま持ちます。報告したものは消費し、再報告しません。テスト本体が既に失敗している場合は、本体の失敗を主として残し、境界の記録は `TestContext` の出力へ書いて消費します（この場合、置換は起きません）。クラスの `[TestCleanup]` の失敗は `GlobalTestCleanup` から観測できず、本体が成功していて境界の記録があるとき、TRX上は境界の失敗に置き換わります（失敗の優先順位は本体、表示の観測、後片付け、ケース境界の記録の順ですが、後片付けとの順位はこの限界の範囲で満たされません）。境界の記録を直せば、後片付けの失敗は次の実行で表面化します。境界の失敗のメッセージにも、この置換の可能性を記します。
- ケースの間に起きた例外・未準備のWindowの表示（`B`）・未宣言のダイアログ要求（`D`）：次のケースの開始時に「直前のケースの残留」として、発生元のケース名を付けてその次のケースを失敗させます。無関係な次のケースが失敗しても、帰属を明示して受け入れます。ケースの間に `B` の記録があるときだけ、開始時にもSend優先度の `Invoke` を一回使って終了時と同じ観測と復元を行い、見つけた残留は直前のケースの間へ帰属させます（観測と復元は `BeginCase` より前です）。`B` が無ければ開始時に何も読まず、成功経路の `Invoke` はケースごとに一回のままです。`B` を伴わないケース間の `E` は、従来どおり次のケースの終了時に観測します。
- moduleの終了時：未報告の未処理例外の記録と、ケースの間に残った失敗にする観測の記録（主に `B`）が残っていれば、最後のケースの残留として `UiModuleLifetime.Cleanup` を失敗させます。ホストは終端済みのため、観測も復元もせず、記録だけを判定します。ホストの終了中に追加された記録も対象です。
- ケースの重なり：前のケースの終了処理を経ずに次のケースが始まった場合は、記録がなくても、新しく始まったケースの失敗にします。前のケースの終了処理が呼ばれないこと自体が境界処理の前提崩れで、以後の帰属を信頼できないためです。その時点で消費されていない記録は「帰属不能」として失敗に添えて消費し、誤ったケースへ帰属しません。

- 開始時に失敗したケース：そのケースは本体も終了処理も実行されません。MSTest 4.5.2では、`GlobalTestInitialize` が例外を投げたケースの `GlobalTestCleanup` は呼ばれず、次のケースは通常どおり実行されます（版を上げるときは同じ確認を繰り返します）。そのため境界は、開始に失敗させたケースを記録側でも開始前の状態（ケースの間、直前のケースはそのケース）へ戻し、次のケースの開始で重なりと誤判定しません。開始時に `TestContext` へ書いた行はTRXの標準出力に残り、失敗のメッセージにも記録の行を含めます。

判定は一つの定義に集約し、ケースの開始・終了・moduleの終了の三つの境界が同じ定義を使います。ケース間の帰属・次のケースの開始時の報告・開始時の状態の戻し・観測や本体の失敗時の出力・moduleの終了時の失敗は、ケースの順序や本体の失敗に依存するため恒久テストにせず、制御フローで静的に確認し、局所MTPで一度だけ一時的に確かめます（その確認の改変は取り除きます）。判定の定義（`D` を含む八項目）は `DispatcherHostTests`、復元は `DispatcherHostTests` と `WindowPresentationScopeTests`、未宣言のダイアログ窓口の記録と結果は `UndeclaredUiDialogServiceTests` で確認します。ホストの記録・受取り・待機APIの即時失敗は `DispatcherHostTests` で確認します。

##### 共有ホストの観測記録

未処理例外とは別に、共有ホストの想定外の状態を観測し、記録します。項目 `B`・`E-a`〜`E-f`・`D` は、発生元の修正後はどのケースでも0件であるべきため、ケースの失敗にします（`D` 以外は基準へ戻します）。`E-g`・`E-a-hwnd`・`X-detector` は、正当な残りと区別できない、または検出器自身の欠陥であるため、記録だけです。

- 失敗にする項目と記録だけの項目：失敗にするのは `B`、`E-a`、`E-b`、`E-c`、`E-d`、`E-e`、`E-f`、`D` の完全一致の八項目で、定義は一つです（前方一致にしません。`E-a-hwnd` は昇格しません）。`E-g`（未消化のDispatcher操作）は、後続の通常の処理が正当に積む操作と区別できないため、`E-a-hwnd` は、WPFが遅延生成する内部のHWNDやIMEなど分類しきれない残りを含むため、`X-detector` は検出器の欠陥が全ケースへ波及しないよう、記録だけです。受入の確認では `X-detector` が0件であることを条件にします。
- 失敗の扱い：未処理例外と同じ扱いです。本体が成功していればケースの失敗にし、本体が既に失敗していれば本体の失敗を主として残し、境界の失敗は `TestContext` の出力へ書いて消費します。同じ境界の未処理例外とは一つの失敗にまとめ、元の例外（未処理例外と復元の例外）を内部例外として参照のまま持ちます。失敗のメッセージは、失敗にした各記録の行、帰属、復元できなかった残留、未処理例外の内容と、クラスの `[TestCleanup]` の失敗を置き換えうることを含みます。
- 記録の出力：記録は `[BMS-OBS] <項目> | <帰属> | <内容>` の一行で、全項目を従来どおり、ケースの終了時（`GlobalTestCleanup`）に `TestContext` へ書き、検証1回分のTRXのそのケースの出力から辿れます。ケースの間に記録された分は、次のケースの開始時に「ケース間（直前：ケース名）」の帰属で、そのケースの出力へ書きます。module終了時に残った分は、Consoleと、実行の結果フォルダー（`TestContext.TestRunResultsDirectory`）内の `host-observation-residue-<module名>.txt` へ出力します。結果フォルダーが取得できなければConsoleだけです。出力の失敗は判定を変えません。出力と判定は、境界ごとに同じ記録の一覧を使います。検出器自身の失敗は項目 `X-detector` として同じ経路へ書きます。`TestContext` への書込み自体が失敗した記録は、失敗とともにConsoleへ出力し、失われません。いずれも表示・判定を妨げません。記録の行には、帰属したケース名（ケースの間は直前のケース名）を含めます。例外として、閉鎖の失敗（`close-failed`）の記録は、追加した時点で同じ行を、プロセスの標準エラーの生のストリーム（`Console.OpenStandardError()`、UTF-8の一行を一回の書込みで出して `Flush`、同時の書込みは排他）へ直接出します（MSTestは `Console.Error` をテストごとのメモリ上のバッファへ振り分けるため、`ShowDialog` から戻らず停止してhangdumpで強制終了されると、その行が失われるためです）。出力の失敗は判定を変えず、`X-detector` として扱います。境界・TRXへの出力は従来どおりで、行が二重に見えることは許容します。標準エラーへ直接出る行が強制終了後も残ることは、恒久テストでは確認していません（強制終了する検査を持ちません）。強制終了後に残るという点は、同期の書込みと `Flush`（`HostObservationLog.WriteRawStandardError`）からの推論です。確認できるのは、行が標準エラーへ出ることで、`WindowPresentationScopeTests` の `UnpreparedModalWindow_CancelledClose_IsRecordedAsFailure` を局所MTPで直接実行し、そのプロセスの標準エラーをシェルのリダイレクト（`2>"$env:TEMP\bms-close-failed-stderr.txt"` はPowerShellの例で、出力先はリポジトリの外の一時領域です）でファイルへ取り、`action=close-failed` を含む行があることを一度だけ一時的に確かめます。MSTest.Sdk（現在 `global.json` の4.5.2）またはMTPの版を上げるときは、この確認を繰り返します。
- 項目 `B`（未準備のWindowの表示。失敗にします）：共有ホストのスレッドで表示（初回のレイアウト）されたWindowのうち、どの表示範囲でも `PrepareForOwnedPresentation` を通していないものを、型・Title・モーダル・所有者・HWND・帰属とともに記録します。`Window` の `SizeChanged` へのクラスハンドラーでWindowごとに一度観測し（表示後の最初のレイアウトで観測します）、準備済みのWindow（モーダルを含む）は記録しません。表示されないWindowは通常記録されません。表示したままの非モーダルのWindowは、同じ境界の `E-a` の観測で復元が閉じます。未準備のモーダルは、テスト本体が入れ子のループから戻らず境界へ到達できないため、検出器が閉じます。`ShowDialog` の最初のレイアウトはスレッドがモーダルになる前に起きるため、検出器は表示の観測の直後に `Send` の操作を一つ予約し、その時点で公開APIの `ComponentDispatcher.IsThreadModal`（スレッド全体の状態）が真で、Windowが `Application.Windows` に残っていれば、記録の内容へ `action=close-scheduled` を追記して閉じます（`SizeChanged` の中では閉じず、Dispatcherを進めません）。閉じる入口は復元と同じ一つの関数（`HostResidueRestoration.CloseWindow`、入口の選択は `SelectCloseEntry`）です。閉じたことで記録は消さず、判定は `B` のままケースの失敗です。閉鎖に成功した場合は追加の記録をせず（`ShowDialog` が戻ることで観測します）、閉鎖が取り消された場合と、閉じる入口の呼出しが `WM_CLOSE` を送る前に同期に例外を投げた場合だけ、同じ項目 `B` で `action=close-failed` と理由（`canceled`、または例外の型とメッセージ）・Windowの型・Titleを持つ記録を加えます。同期に受け取った例外はDispatcherの未処理例外へ漏らしません。同期の例外は、上記の未処理例外の残る限界（一度処理した例外の再送出）を除けば、`Close` 自身の前提の検査（閉鎖の途中の再度の `Close` など）に限られます（所有者の終了の入口も `Close` の前に投げる処理を持ちません）。この捕捉は、通常の到達経路のない防御です。表示済みのWindowのClosingの処理（`OnClosing`・`Closing` のハンドラー）の例外は、`Close` が同期に送る `WM_CLOSE` の配送の中で起きてDispatcherの `UnhandledException` に達するため、検出器の呼出しへは返らず、そのケースのDispatcherの未処理例外として記録されます（報告と受取りは上記の未処理例外の規則に従います）。WPFはこの場合もモーダルの枠を終えてWindowを閉じるため、`close-failed` は記録されず、`ShowDialog` は戻ります。`close-failed` の行はプロセスの標準エラーへも直接出ます（上記「記録の出力」）。非モーダルの未準備のWindowは、境界の `E-a` と復元が扱います。表示時の記録の `thread-modal` は最初のレイアウトの時点の値です。ホスト以外のDispatcher（専用STAの検査）は対象外です。
- 項目 `D`（未宣言のダイアログ要求。失敗にします）：画面テストの構成の既定のダイアログ窓口（`UndeclaredUiDialogService`）、および観測の境界が有効なmoduleで、窓口を宣言しないテストが `UndeclaredDialogs.Create()` から受け取る窓口が、記録用の窓口を明示的に注入していない通知・確認・窓口表示・ファイル／フォルダー／保存先の選択・進捗の要求を受けた時点で記録します。製品の通知経路には窓口の例外を捕捉してログだけにする所があるため、例外ではなく記録で失敗にします。内容は `method=<メソッド名> | request=<要求の型名> | title=<題名> | text=<本文の要約> | owner=<要求のOwnerの型名、なければnull>` の一行で、窓口表示だけ `result=<結果の型引数の型名>` を加えます。型名は `FullName` です。題名は通知・確認が `Caption`、ピッカーと進捗が `Title`、本文は通知・確認が `MessageBoxText`、進捗が `Label` で、持たない要求は `-`、値がnullでも `-` です。題名・本文はCRLF・CR・LFをそれぞれ空白一つにし（連続は畳みません）、先頭200文字で切ります（切ったときだけ末尾に `…` を付けます）。200文字目が高位サロゲートなら、ペアを分断せず199文字で切ります。呼出しが戻る前（返したTaskを待つ前）に一件記録し、`B` と同じく呼出し時点のケース（ケースの間なら直前のケース名付き）へ帰属させます。ケースの間の `D` は次のケースの開始時に、直前のケースの残留として失敗にします（ただし開始時の観測と復元は `B` がある場合だけ動き、`D` では動きません）。窓口は状態を変えないため、復元の対象はありません。結果は表示失敗（`Failed`、原因の例外つき）で、`OwnerUnavailable` は返さず、`ShowWindowAsync` のWindow生成と `RunWithProgressAsync` の処理は呼びません（実画面を作りません）。観測の境界を有効にしていないmodule（Core）では記録が消費されず黙って通るため、窓口の生成時に `InvalidOperationException` を投げます。通知を期待するテストは、記録用の窓口を専用の引数へ明示的に渡して表明します。
- 項目 `E-a`〜`E-g`（ケース終了時の残留）：各ケースの終了時に、Send優先度の `Invoke` を一回だけ使って、共有ホストの起動時点を基準に比べます。失敗にする残留を見つけたときだけ、同じ `Invoke` の中で復元します。ホストが未起動・終端済みなら何も起動せず何も読みません。各残留は最初に観測したケースへ一度だけ帰属させ、以後のケースで繰り返しません。値が基準へ戻れば報告済みの印を消し、後で再びずれたら再び報告します。
  - `E-a`：ホストのスレッドの `Application.Windows` に基準の後から残るWindow。基準はホストの起動時点です（表示範囲の開始時点ではありません）。`MainWindow` が残る場合は同じWindowを一つの記録にし、`Application.Windows` に含まれない `MainWindow` だけが `E-b` です。`E-a-hwnd`（記録だけ）は、ホストのスレッドのトップレベルHWNDのうち `Application.Windows` のどれにも（WPFが作るnative ownerを含め）対応しないものです。WPFが遅延生成する内部のHWND（`HwndWrapper[...]` など）も含まれるため、native window classと分類（`kind=`）を記録に添えます。分類は、`wpf-internal`（クラス名が序数比較で `HwndWrapper[` で始まり、`HwndSource` が無く、非表示）、`ime`（クラス名が `IME` または `MSCTFIME UI` に完全一致し、非表示）、それ以外の `other` です。入力は、ホストのスレッドで、観測の時点のHWNDから収集します。限界：Windowの隠し所有者の漏れは `wpf-internal` と同じ特徴を持つため区別できません。
  - `E-c`：`Application.Resources["vm"]`。参照で判定し、別のオブジェクトへ替えるたびにそのオブジェクトごとに一度報告します。観測は、キーが無いことと値がnullであることを区別しません。
  - `E-d`：`Properties.Resources.Culture`（基準は `ja-JP`）。
  - `E-e`：保存値 `Settings.Default.AppearanceTheme`（基準はホストが設定するLight）。`AppThemeService` は適用中のテーマを公開で返さないため、判定するのは保存値だけで、読取りはホストの起動後に限ります。
  - `E-f`：`LogManager.Configuration` の参照の同一性。基準は最初に観測した非nullの構成で、nullから非nullへの変化（`NLogWrapper` の遅延初期化）は基準として採用します。
  - `E-g`：Background以上で未消化のDispatcher操作。公開の `Dispatcher.Hooks`（`OperationPosted`・`OperationCompleted`・`OperationAborted`）で、ホストの起動時点から投稿された操作を追跡し、境界で `Pending` かつ優先度がBackground以上のものを、操作ごとに一度報告します。優先度の変更は購読せず、数える時点の優先度で判定します。ContextIdle以下は数えません。
- 復元：失敗にした残留（その観測で新しく報告した `B`・`E-a`〜`E-f` に対応するもの。以前に報告済みの残留へは手を付けません）を、ホストのスレッドで同期的に基準へ戻します。`Dispatcher` を進めません（`PushFrame`・`ProcessQueued`・`AwaitPresentation` を使いません）。本体が失敗していても復元します。
  - 順序：Window（所有の深い順、同じ深さでは後に作ったものから。表示範囲の後片付けと同じ順序）、`MainWindow`、値（`Resources["vm"]`、文化圏、テーマ、NLog構成）の順です。
  - 閉じる入口：`SettingsWindow`・`PlaylistPropertyDialog`・`PlaylistSummaryBulkEditDialog` は所有者の終了の入口（`CloseForOwnerShutdown`）、それ以外は `Close` です（通常の `Close` はVMを持つこれらの型で閉鎖が取り消され、処理が開始されます）。表示範囲の後片付けの入口は変えません。閉じる前にWindowが `Application.Windows` に含まれなければ閉じた扱いにし、閉じた後は `Application.Windows` から外れたことを確かめます。HWNDの破棄は成功条件に含めません（残れば `E-a-hwnd` の記録に表れます。表示済みの未準備のWindowの `Close` が同じスレッドで同期にHWNDを破棄することは、`WindowPresentationScopeTests.Restore_ClosesShownUnpreparedWindow` が確認します）。`MainWindow`・`ProgressDialog` には特別な入口がなく、閉鎖が取り消されれば復元の失敗です。
  - 復元の対象にしたWindowが `MainWindow` ならば、閉鎖の成否によらず基準（共有ホストでは `null`）へ戻します。復元に成功した項目（閉じたWindowと値）は報告済みの印を消し、同じ値へ再びずれたら再び報告して復元します。`Resources["vm"]` は基準にキーが無ければ `null` を代入せずキーを削除します。
  - 文化圏は `ResourceService.ChangeCulture` の経路で基準（`ja-JP`）へ戻し、`Resources.Culture` と表示の通知（`DisplayCulture`）を戻します。適用されなければ復元の失敗にし、通知の無い直接代入へは後退しません。`ChangeCulture` は `NLogWrapper` を通してログを書き、未初期化なら静的コンストラクターが構成を差し替えるため、NLogの復元を最後にします。
  - テーマは保存値を基準（Light）にし、ホストの起動時と同じ経路で適用します（保存はしません）。成否は保存値で判定します。NLog構成は、復元の時点の基準のオブジェクトを参照のまま `LogManager.Configuration` へ再代入します。基準は最初に観測した非nullの構成のため、テストが置いた構成が基準になりうる限界があります。また、同じ観測で `E-f` が報告されていなくても、文化圏の復元が `NLogWrapper` の初期化で構成を差し替えた場合は、次の境界で `E-f` として表れえます。
  - 項目ごとに捕捉して残りの復元を続け、再試行しません。復元の例外は復元の失敗として元の例外を参照のまま保持します。`Dispatcher` の `UnhandledException` に達した例外は、同じ境界の未処理例外として報告します。復元後に起きる例外は、ケース間の例外として次のケースの開始時に報告します。
  - 復元できなかった残留は、以後のケースへ残りうるため、報告済みの印が残り、同じ残留は再報告しません。基準へ戻れば印が消えます。最初の報告が汚染の起点で、無関係な後続のケースが毎回失敗しないようにするためです。
- 帰属の規則の例外：`E-a`〜`E-g` は発生の時刻を観測しないため、観測したケース（`GlobalTestCleanup` のケース）へ帰属させ、記録に「このケース、またはその直前のケース間で生じた」旨を書きます。`B` と `D` は発生の時点のケース（ケースの間なら直前のケース名付き）へ帰属させます。
- 境界の順序：観測と復元、記録の出力、未処理例外の収集（`EndCase`）、判定の順です。観測処理自体（読取り・比較）が例外を投げた場合は `X-detector` として出力し、判定を変えません。境界が各ケースで明示的に呼ぶ観測で、`UiModuleLifetime` が `AssemblyInitialize` で有効にしたUI moduleだけで動きます。有効にしないmodule（Core）では、共有ホストが起動しても未準備のWindowの検出器・Dispatcher Hooks・基準の読取りを取り付けません。有効化を共有ホストの起動後に呼んだ場合、その起動には取り付けません。
- 対象外・限界：モーダルの閉鎖が取り消された場合と、閉じる入口が `WM_CLOSE` を送る前に同期に例外を投げて閉じられないままの場合は、`ShowDialog` から戻らず境界へ到達できないため、停止が残ります（`close-failed` の記録はプロセスの標準エラーへ直接出るため、強制終了されても実行ログに残ります）。閉鎖の途中の再度の `Close` による同期の例外では、先に始まった閉鎖が後で完了すれば `ShowDialog` は戻ります。表示済みのWindowのClosingの処理の例外では、WPFがWindowを閉じて `ShowDialog` が戻るため停止は残らず、その例外はケースの未処理例外として報告されます。閉鎖の判定はWindowごとに最初のレイアウトの後の一度だけで、最初のレイアウトがモーダルの外で起きた場合（例：`Show`→`Hide`→`ShowDialog`）は閉じず、停止が残ります。スレッドのモーダル状態はスレッド全体の状態のため、準備済みのモーダルが開いている間に表示された未準備の非モーダルWindowも、閉鎖の対象になります（未準備である時点で `B` の失敗の対象です）。Win32のコモンダイアログとネイティブのMessageBox（`EmergencyDialog`）はWPFのWindowではないため `B` の対象外で、ケース終了時にホストのスレッドへ残っていた場合だけ `E-a-hwnd` に現れえます。`UiDialogOwnerResolver` のactive modal・`MainWindowViewModel` のセマフォは、公開の観測点がなくリフレクションを使わないため観測しません。`LogManager.Configuration` の読取りは、NLogが構成の自動読込みを未実施だった場合にその試行を起こしうる限界があります。

観測の比較・失敗の判定・復元は、基準と報告済みの印などの状態を引数に取る関数で、恒久テストは独立の状態（テスト開始時点の現在値を基準）で確認し、境界の記録を作りません。観測の恒久テストと、表示範囲の後片付けの消化の失敗の保持を確かめる恒久テスト（`WindowPresentationScopeTests` の `Cleanup_ContinuesAndKeepsOriginalFailuresWhenProcessQueuedPresentationThrows`）が使う非表示（`WS_VISIBLE` なし）かつ非アクティブ（`WS_EX_NOACTIVATE`）の `HwndSource`（位置の指定は補助で、画面外の保証には使いません。後者は残留HWNDと、その破棄が2回目の消化へ予約を積む契機に使います）、未表示の `new Window`（`D` を作る恒久テストが要求のOwnerに使う未表示のWindowを含みます）、復元の恒久テストが一時的に変える値（`Resources.Culture`、`Resources["vm"]`、保存値 `AppearanceTheme` とそのテーマの適用、`LogManager.Configuration`、`Application.MainWindow`、復元が閉じるWindow）に加え、`B` を作る恒久テストが準備なしで表示するWindow（未準備のモーダルを含む）と、閉鎖を取り消すテスト用Window、閉鎖の処理で例外を投げるテスト用Windowは、この共通基盤自体の検査として明示された例外で、`finally` で元へ戻します。準備なしで表示するWindowには、`TestWindowPresentationScope.PlaceUnpreparedNonActivating` で画面外・タスクバー非表示・`ShowActivated=false`・`WS_EX_NOACTIVATE` を適用しますが、準備扱いにしないため（`B` が記録されます）、前面・矩形の確認と破棄の管理は持たず、モーダルは見張り（`StallTimeout`）で必ず戻します。表明は対象の項目だけに絞り、他の由来で混ざりうる項目（`E-g` など）に依存させません。Windowの表示の記録（`B`）と未宣言のダイアログ要求の記録（`D`）を作る恒久テストは、自分の記録だけを消費し、同じケースの別の由来の `B`・`D` は境界に残して失敗にします。境界が無効なmoduleで `UndeclaredUiDialogService` を生成すると失敗することは、Coreの `UndeclaredUiDialogServiceBoundaryTests` で確認します。ケース終了時の記録・TRXへの出力・module終了時の出力は、制御フローで静的に確認し、TRXへの出力は局所MTPで一度確かめます。

#### UI moduleの寿命

UI moduleの `UiModuleLifetime` は、次の順に初期化します。

1. 実行領域の準備
2. 必要な利用者セッションの排他の取得
3. 実行領域内のmodule専有のprofileによる `ApplicationPathSnapshot.FromLayout` / `ApplicationPathPolicy.Configure`
4. 日本語リソースの基準

配置の確定は `Settings.Default` の最初の読取りより前とし、実行ファイル・Assetsは同じビルド出力を指定します。Windows moduleだけは、ResourceServiceとホストの最初の読取りより前に、同じビルドの表示言語ファイルを専有profileの `lang` へコピーし、その場所を言語ディレクトリとして渡します。他のUI moduleの表示言語ファイルの配置は維持します。必要な素材の欠落を、通常の利用者領域への代替で補いません。素のホストではAppの文化圏一覧を複製しません。初期化と終了処理は既存のmoduleの寿命へ集約します。

各ケースが `OwnedProcess` を回収した後、moduleは次の順に回収します。

1. 開始済みホストのWindow・Dispatcherの終端とスレッドの合流
2. 共有設定fixtureの専有領域
3. 生成済みの管理一時セッションの実Taskの終端
4. 利用者セッションの排他の解放

共有設定はホストの終了を確認できた場合だけ回収し、ホストの終了に失敗したときは保持します。設定の回収が失敗しても管理一時セッションと排他の回収を続け、各失敗を集約します。初期化に失敗したときも取得済みの排他を解放します。未使用の管理一時セッションを後片付けのために生成しません。共通の `WindowsProcessProbe` は排他を取得せず、親ケースの `OwnedProcess` が子プロセスと両方のパイプを終端まで所有します。module全体の子プロセス台帳は持ちません。

#### 表示入力と待機

表示入力の反映には共通の `ProcessQueuedPresentation` を使い、実controlの値・選択・配置を確認します。この補助の契約は、次の(a)〜(e)をこの節の正本とします。

(a) 手順と順序：戻る前に、次を一度ずつ行います。(1) Loaded優先度以上の予約の消化。(2) 共有ホストのスレッドでの配置の直接の確定。ホストが所有する専用の要素の `UpdateLayout` を一度呼び、共有ホストのDispatcherで、PresentationSourceに接続された木の配置を同期に確定します（ホストの要素自体は木に入れないため測定されません）。(3) 配置が積んだLoaded優先度以上の予約の消化。(2)と(3)は繰り返して収束させません。

(b) 保証しないもの：Loadedイベントの発火の時機（配置との前後を含む）と描画の完了は保証しません。Loadedイベントの発火が必要な場合と、Input優先度へ下げた描画の実行が必要な場合は、Background優先度以上（Input優先度へ下げた描画を含む）の積まれている予約を消化する `ProcessQueuedBackground` を使います（Loaded優先度の予約と、Input優先度へ下げた描画の中の発火を含みます。まだ積まれていない予約は対象外です）。描画の完了自体は、実通知と `AwaitPresentationOnDispatcher` で待ちます。機能処理、Background優先度の予約、閉鎖、Dispatcher全体のアイドルも保証しません。

(c) 配置を直接確定する理由：WPFは次の描画を即時に予約するとき、未実行のInput優先度の確認用の予約がなければ積み、それが0.5秒を超えて実行されていないと、次の描画をInput優先度へ下げます。描画の外で積まれた配置の要求は降格済みの描画をRender優先度へ戻すことがありますが、WPFは未処理の配置要求が残っている間は後の要求を同じ要求に合流させるため、後の要求で優先度が戻らない場合があります。描画の最中に積まれた要求も戻さず、既に積まれた描画の優先度も描画の外の経路から書き換えられ得ます。そのため、配置の要求を含む描画が、Input優先度へ下げられたまま残ることがあります（例：描画の最中に積まれた要求。経路の網羅は主張しません）。Loaded優先度までの消化では、Input優先度へ下げた描画に含まれる配置が処理されないため、配置を直接確定します。

(d) 例外の扱い：(2)の配置の確定が例外を投げた場合は、その例外が元のまま伝わり、(3)は行わず、呼出し中に記録された未処理例外は消費されずケースの境界で報告されます（上の待機・消化APIの一般則の例外です）。それ以外の呼出し中に記録された未処理例外は、(3)の後で元の例外で失敗し、記録を消費します。

(e) 確認方法：(2)の効果はWPFの内部の時機に依存して決定的に作れないため恒久テストを持たず、次の二つで確かめます。静的確認として、経路が `Application.MainWindow`・`Application.Windows`・テストのWindowを参照しないこと、`UpdateLayout` の対象がホストの所有する木に入らない要素だけであること、(2)が(1)の消化の後・(3)の前に呼ばれること、(2)の例外が元のまま伝わり、(3)と記録の消費を行わないことを確認します。負荷再現として、Releaseビルドの `BeMusicSeeker.Windows.Tests` の実行ファイルを直接使い、`FullyQualifiedName~SearchEditor_ShortSectionsSizeToContentForSavedValuesAndFields` のfilterを4並列で各5回（計20回）、同時に `Name~SearchEditor` のfilterを2並列で繰り返し、対象ケースが失敗しないことを確かめます。この条件は修正前の実装で失敗を再現した条件です。WPF（.NET）の版を上げるときは、同じ確認を繰り返します。

表示入力の待機では、次を守ります。

- 実処理は、利用側のTaskまたは適用・終端の通知を待ちます。入力側のTaskCompletionSourceの完了だけを利用側の終端としません。
- 未完了の否定観測は到達を止める待合せを保持して行い、`finally` で解放と開始済みTaskの回収を行います。
- 成功後に追加の作用を持たないイベントハンドラーは、コンパイル済みの入口の引数・受理状態と委譲先Taskの回収、委譲後に追加の作用がないことの静的な確認で分担します。
- 実Dispatcherへ配送するcompiledの `async void` ハンドラーの終端は、`MainWindowEventCompletion.CaptureAsyncEventCompletion` で捕捉します。イベントの発生が戻り、捕捉中に現在の文脈を取り込んだ処理の全Post（awaitの継続などを含む）の配送と開始済みの全操作が終端するまで完了せず、同じ発生の中で後から開始したハンドラーを取りこぼしません。ハンドラーが一度も開始しなければ、戻った時点で開始数0（`started=0`）を示す診断で失敗し、無期限には待ちません。Postのcallbackが投げた例外（`async void` の例外を含む）は元の例外のままCompletionを失敗させ、Dispatcherへの送出も維持するため共有ホストの記録と報告が重複します。一次の失敗はCompletion側です。失敗したCompletionを、記録経路の待機の外（すでに完了した後など）で観測するケースは、`TakeUnhandledExceptions` で記録を受け取ります。開始数の累計は `Capture` が返す `StartedCount` で参照し、`OperationStarted` の通知（`async void` のほか `AsyncOperation` なども含む）の累計です。例外時に `AsyncVoidMethodBuilder` が「例外のPost、続いて `OperationCompleted`」の順で呼ぶ公開の呼出し順に依存し、逆転すれば例外のPostの前に完了しうるため、例外を投げるハンドラーの検査が検出します。Completionの完了後に外部のcallbackから開始した操作は対象外です。

注入や表明の前にBackground優先度までの予約を消化する必要がある場合は、`ProcessQueuedBackground` を使います。呼出し前に積まれたBackground以上の予約と、消化中に積まれたBackgroundより高い優先度の予約を、戻る前に実行済みにします。UIスレッド上とテストスレッドの両方から呼べます。ContextIdle・ApplicationIdle・SystemIdleは境界にしません。まだ積まれていないworkerの後続予約や、消化中に積まれたBackgroundの予約は保証せず、それぞれの実通知・Taskで待ちます。その場で空の処理だけを持つ `InvokeAsync` をBackgroundに積んで待つ形は、この補助へ置き換えます。予約した処理がフラグなどの作用を持ち、その実行自体を後で表明する形は、消化ではなくその予約の実行を観測するので置き換えません。

終端の後に別途予約される表示（`ObserveFault` で捨てるTask、`async void` の表示など）が存在しないことを、固定時間の経過で判定しません。注入した窓口に対し、生成元の終端と必要な消化（`ProcessQueuedBackground` など）を確定させた後で表明します。[非同期処理の待機](#非同期処理の待機)の短い否定観測は、この終端と消化を確定した後の補助としてだけ使い、それを不在の根拠にはしません。

Dispatcher上の通常の機能Taskの待機は、局所的な制限時間を加えない `TestUiDispatcherHost.AwaitTaskOnDispatcher` を使います。描画・閉鎖・ネイティブ解放の通知の欠落は、同じDispatcher基盤の `AwaitPresentationOnDispatcher` で、既定15秒の制限時間付きで観測します。明示された通知の制限時間と、通常のTaskの外側の制限時間は別に扱います。

`ShowAndWaitForContentRendered` は表示前に通知を購読し、制限時間付きのDispatcher処理で読込み・描画・非ゼロの配置・HWNDを確認します。任意の `renderNotificationTimeout` はLoaded到達後のContentRendered通知の待機だけに適用し、Loaded・Dispatcher・後片付けの制限時間へ流用しません。モーダル、即時終了、描画通知を制御する場合は、表示直前に `PrepareForOwnedPresentation` を呼びます。ただし、`B` と閉鎖の検査（未準備のモーダルを表示する共通基盤自体の恒久テスト）は準備を通さないことが目的の例外です（[共有ホストの観測記録](#共有ホストの観測記録)）。

表示の観測待機は、実際の描画・配置・ネイティブ条件の成立を完了条件とします。成立後に、無関係な継続処理による一般的な `ApplicationIdle` 待ちを成功条件へ追加しません。描画通知がない場合、即時終了、ネイティブ観測の失敗、期限超過を成功へ置き換えず、表示観測と後片付けの待機を区別します。

#### 表示範囲とWindowの所有

実Window・Popupの表示範囲（`TestWindowPresentationScope`）は共有のWindow・HWND一覧を観測するため、準備から処理の終端・後片付けまで非並列にします。同一テストの親子Windowには同じ表示範囲を渡し、独自の入れ子の表示範囲を作りません。Windowを作らず共有状態を変えない `Invoke` は、この理由では直列化しません。実Dispatcherの終了を保証する専用STAと、共通基盤の意図的な入れ子の表示範囲の検査は、それぞれの保証のために維持します。

どの表示範囲でも `PrepareForOwnedPresentation` を通していないWindowが共有ホストで表示された場合は、型・Title・モーダルなどを記録し、表示したケース（ケースの間なら次のケースの開始時、module終了後ならCleanup）の失敗にします。Windowが残っていれば、非モーダルは境界が同期的に閉じ、未準備のモーダルは検出器が閉じて本体を戻らせます（[共有ホストの観測記録](#共有ホストの観測記録)）。表示範囲の準備を通したWindowはモーダルでも記録しません。

実ダイアログへ届きうる経路には、次のいずれかを接続します。所有者を解決できないこと（`OwnerUnavailable`）や `Application.MainWindow` の有無を、通知を抑止する手段にしません。

- 記録用の窓口：通知の記録だけを確かめる場合に使います。所有者の解決に依存せず窓口ごと差し替える形を主とします（例：`SettingsDialogHarness.RecordingDialogService`）。`SettingsDialogHarness.RecordingDialogService` は通知・確認だけを数え、ウィンドウ・ピッカー・進捗は `UndeclaredDialogs` へ委ねて `D` にします。`ApplicationComposition` の `dialogService` は必須（null は `ArgumentNullException`）で、本番は根の窓口を渡します。テストは、窓口を宣言しないとき `UndeclaredDialogs.Create()` を、通知・確認を宣言するときは記録用の窓口を明示して渡し、構成が暗黙に実の `UiDialogCoordinator` を作る経路を持ちません。この窓口は、構成が作るすべての所有者（再生・導入先・メンテナンス・選択譜面の操作などの子構成を含む）の通知・確認を一つの窓口へ集めて観測する入口です。子構成の担当は専用の引数を持たず、構成の `dialogService` を使います。例外として、フォルダ自動リネームは構成のファイル/DB変更の窓口（`fileDbMutationDialogService`。省略時は `dialogService`）を使います。構成の専用引数（`settingsDialogService`・`fileDbMutationDialogService`・`playlistWorkspaceDialogService`・`restartFailureDialogs`・`libraryDialogService`）を併せて渡した経路は専用の窓口が優先され、共通の窓口へは届きません（[`ApplicationCompositionDialogRoutingTests`](../../../tests/BeMusicSeeker.Windows.Tests/MainWindow/ApplicationCompositionDialogRoutingTests.cs)）。`MainWindowViewModelTestFactory.Create` は、構成の共通の窓口に未宣言の要求を `D` で失敗にする窓口（`UndeclaredUiDialogService`）を渡します。未注入の通知・確認が出るケースは `D` で失敗になるため、通知を期待するケースは、記録用の窓口を `settingsDialogs`・`playlistWorkspaceDialogs`・`fileDbMutationDialogs` へ明示的に渡して表明します。Createの専用引数で差し替えられない経路（ライブラリ、再起動失敗、保守の再検査など構成の共通の窓口を使う経路）で通知を宣言するときは、`ApplicationComposition` を直接構成し、`dialogService` か該当する専用引数（`settingsDialogService` など）で記録用の窓口を渡します。これらの専用引数は従来どおり共通の窓口より優先され、`ApplicationComposition`（ViewModel側）へ届く窓口だけを差し替えます。プロパティ・一括編集・インポート・ランプビューアーなど `MainWindow` 側の経路は、`MainWindow` の `playlistWorkspaceDialogService` 引数で別に渡します。
- `UiDialogCoordinator` の `messagePresenter` だけを差し替える形：`UiDialogCoordinator` は `messagePresenter` の前に所有者を解決し、所有者が null なら `messagePresenter` を呼ばず `OwnerUnavailable` を返します。所有者は、登録中の表示中モーダル、要求の `Owner`、アクティブなWindow、`MainWindow` の順に解決されます。表示範囲の実Windowは非アクティブで表示されるため、アクティブなWindowとしては解決されません。そのため、要求の `Owner` へ表示範囲の実Windowを渡す経路、または `modalScopeFactory` で登録した表示中のモーダルと組み合わせる場合に限り、記録用に使えます。`MainWindow` への自動設定には頼りません。差し替えが効くのはメッセージと確認（`ShowMessageAsync`・`ConfirmAsync`）だけで、`ShowWindowAsync`・ピッカー・進捗表示は実ダイアログのままです。
- 準備を接続した `UiDialogCoordinator`：実ダイアログを表示して確かめる場合に使い、`modalScopeFactory` の中で `TestWindowPresentationScope.PrepareForOwnedPresentation` を呼びます（例：[`PendingPackageRestoreWindowTests`](../../../tests/BeMusicSeeker.Windows.Tests/Dialogs/PendingPackageRestoreWindowTests.cs)）。

`PlaylistWorkspaceViewModel` と `SettingsDialogViewModel` は、ダイアログ窓口（`playlistWorkspaceDialogService`・`schemaDialogs`）を必須の引数とし、null を受け付けません。窓口を宣言しないテストは `UndeclaredDialogs.Create()` の結果を渡します。観測の境界が有効なmoduleでは `UndeclaredUiDialogService` を返し、境界がないCoreでは、記録が消費されず黙って通ることを避けるため、全メンバーで例外を投げる `TestUiDialogService` を返します。共有の生成補助のうち、窓口の引数を省略（null）できるものは、省略されたとき同じ補助の結果へ解決します。窓口の引数を持たない補助（`BmsPlaylistTestSupport`・`RegularChartListOwnerTestSupport`・`PlayHistoryReadModelTestFixture`・`PlaylistWorkspaceFixtureFactory` など）は、常に補助の結果を渡します。`SettingsDialogHarness` は、窓口を渡さないとき既定で `UndeclaredDialogs.Create()` の窓口を使い、未宣言の要求は `D` になります。通知を期待するケースは `SettingsDialogHarness.RecordingDialogService` を明示的に渡します。`composition` を渡した場合は `dialogs` を使わず、構成側の窓口を使います。同じ設定画面へ渡す `ApplicationDataUninstallWorkflowOwner` と `schemaDialogs` には同じ窓口を渡します。Coreの `TestUiDialogService` は記録ではなく例外を投げるため、製品に窓口の例外を捕捉する経路があるとCoreでは到達が隠れうります。到達を表明したいケースは、記録用の窓口を明示的に注入します。

新しく書くテストで引数なしの `new UiDialogCoordinator()` を使いません。例外は、`UiDialogCoordinator` 自体や、所有者を解決できない経路そのものを検査する場合です。この例外は上の `OwnerUnavailable` の規則にも適用します。

MainWindowの生成前から、終了処理・`Closed`・設定購読の解除・`Resources["vm"]` の復元までは `MainWindowTestLifetime` が所有します。機能の入力と実処理の終端の観測は機能側へ残します。コンパイル済みの内容だけを描画する場合も共通の表示範囲の実Windowを使い、Binding・値・選択・配置の表明を維持します。

コンストラクターだけを使うテスト用ハーネスは、`PrepareConstructorOnlyShell` で既存のシェル起動境界へ完了済みの初期化を渡し、表示だけのfixtureから本番の起動を開始しません。実際の起動・起動取消・終了の接続は、`MainWindowViewHostTests` とPlaylistの `ActualMainWindowFixture` が本番の起動経路で検証します。

#### 非アクティブ表示と外部入力

共通基盤は非アクティブ表示専用です。表示直前に手動配置、タスクバー非表示、非アクティブ表示を適用し、全モニターの外へ置きます。HWND生成時には既存の拡張スタイルを保って `WS_EX_NOACTIVATE` を設定・再読取りします。前面でないことと矩形も確認し、Popupにも開く境界で同じ規則を適用します。ネイティブAPIの失敗や表示観測の失敗は、テスト本体とは独立して保持します。

通常テストに前面操作の例外は設けません。次を合否条件にしません。

- 実OSカーソルの取得・移動や `Mouse.GetPosition` による物理位置
- 実フォーカスの取得成功、物理修飾キー、入力キャプチャ
- Popupが外部入力で閉じないこと

イベントを明示しても呼出し先がOSの状態を参照する場合は分離できていないため、本番の処理へ明示入力を渡す境界で検証します。Popupの内容と接続は、開閉イベント・操作入力、閉じたテンプレートのBinding、明示配置などで確認します。

非公開のWPFメソッドによるフォーカスの偽装、テスト専用の本番分岐、外部入力を無視する製品仕様の変更は行いません。実際のフォーカス移動・IME等のOS接続は[実機確認](#利用者に推奨する実機確認)と分担します。共有Dispatcherの待機中には別テストが再入し得るため、Dispatcherの利用だけで排他できると考えず、[資源の分離と共有](#資源の分離と共有)に従います。

#### 後片付けと失敗の優先順位

開始時の共有スレッドのウィンドウ・HWNDを基準に、追跡したPopup、深い所有関係から順にウィンドウ、購読、Dispatcherに残った描画処理、残留HWNDを片付けます。

- 開始時に存在し、明示的に追跡していない別の所有者のWindowは、後からHWNDを持っても、その表示範囲の残留破棄に含めません。そのWindowに属する実際のネイティブの所有者も、訪問済みのハンドルで停止する所有チェーンから導出して保護します。
- 閉鎖前に `Closed` を購読し、実際の閉鎖を待ってから購読を解除します。未表示・閉鎖済みの対象は区別し、閉鎖の取消やWindow・HWNDの残留を成功にしません。
- 機能処理の開始済みTaskは呼出し側が回収します。設定画面には `CloseForOwnerShutdown` を使います。
- 後片付けの2回の消化（`ProcessQueuedPresentation`。購読の解除の後と、残留HWNDの破棄の後）が例外を投げても、その例外を元のオブジェクトのまま、それ以前の失敗に続けて発生順に後片付けの失敗へ保持し、残留HWND・Windowの検査と登録済みの失敗の報告を続けます。失敗を成功にせず、消化が消費した記録は後片付けの失敗としてだけ報告します。確認は `WindowPresentationScopeTests` の `Cleanup_ContinuesAndKeepsOriginalFailuresWhenProcessQueuedPresentationThrows` です（配置の確定の例外は、後片付けが発生元で絞らないため同じ契約で扱い、静的に確認します）。

失敗の優先順位はテスト本体、表示観測、後片付けの順です。

#### 外部UIAによる操作

外部のUI Automation（UIA）クライアントからの操作は、Desktopで確認します。局所的なWPF検証のプロバイダー呼出しの成功だけで、外部クライアントからの操作、通知の受信、本番構成の保存・正常終了・再起動を確認済みにはしません。

- 専有データで起動した本番の実行ファイルへ接続し、実入力、表のパターン、実際の編集欄、ドラッグ、確認画面を操作します。
- 操作対象は、所有するプロセスと親要素の範囲、既存の意味を持つキー（`AutomationId` 等）で一意に選びます。同名要素の先頭一致で代用しません。
- 編集などの非同期操作は、入力前に対象を限定して観測を登録し、登録の応答を確認してから入力します。成功は、既存の実Taskの終端と、独立して読み取った保存値で確認します。UIA呼出しの復帰や通知の到着だけでは保存成功と判定しません。

機能固有の観測条件は対象機能の仕様（例: [一覧表示](../ui/table-view.md)）に従います。

### Fullの処理順と期限

`full` は次の順に進みます。

1. `prepare-candidate` が、公開可能なHTML付きのCurrent、固定のLegacy、試験用のNextと、それらを記録する配布候補の目録を先に生成する。
2. `full` は全体の自動整形・Releaseビルドの後、絶対パスで指定した配布候補の目録を検査し、候補を展開・接続する。製品のpublishやZIPの再生成は行わない。
3. Core・Scenarios・Desktopを各一回、Windowsを重複のない3分類で実行する。環境・性能の明示suiteは含めない。

ScenariosとDesktopの必須ID、各段階とケースの制限時間、候補の展開と受渡しは[検証入口の説明](../../../tools/BeMusicSeeker.Verify/README.md)を正本とします。期限と選択は [VerificationPlan](../../../tests/BeMusicSeeker.TestSupport/Verification/VerificationPlan.cs) と [VerificationRunner](../../../tests/BeMusicSeeker.TestSupport/Verification/VerificationRunner.cs) が所有します。

候補の受渡しでは次を守ります。

- 通常起動の実行ファイル・assets・表示言語ファイル・ネイティブ部品は、検査済みのCurrentを展開した同じ配置へ揃え、profileはケース専有のままにします。更新・故障のfixtureが明示する配置は維持します。
- 候補の指定が片方だけの場合は、日常のビルドへ代替せず失敗します。
- 利用側は配布候補の目録と追跡された旧版の識別情報を照合し、必要なケースでは所有する `TestWorkspace` へ展開します。再publish、別配布候補の目録の探索、欠落した入力の自動代替は行いません。

ケース固有の制限時間は、テスト段階で共有する制限時間を延長しません。Desktopは既存の利用者セッションの排他と単一workerで実入力を専有し、Scenariosの後に実行します。各ケースは、共有の制限時間とケース固有の上限の早い方を外側の期限とし、所有する入力と資源の回収に10秒を先取りした操作期限を使います。

- 残り時間が回収の余裕以下なら、新しい入力を開始しません。
- 実入力後に失敗した場合は、最初の検出時刻+10秒と外側の期限の早い方を一度だけ確定し、所有する入力の解除、入力元のSTA、返却済みのアプリのセッション、fixtureの回収へ渡します。
- 通常の回収は操作期限内で行い、遅い完了や回収の失敗を成功へ変えません。起動接続を返す前の失敗では、既存のドライバーの回収を維持します。

復旧の実製品プロセスの代表ケースは、[`RecoveryScenarioTests`](../../../tests/BeMusicSeeker.Scenarios.Tests/Recovery/RecoveryScenarioTests.cs) の `SC-13` と `SC-14` を `full` で実行し、Dailyには追加しません。専有の `TestWorkspace`、`OwnedProcess`、UI moduleの利用者セッションの排他を共有し、各ケースの同じ期限で確認の到達・操作Task・応答・実際の退出を待ちます。自然な退出は入力前に期待として登録し、未知の切断や未応答を成功として許可しません。

### 公開旧版からの移行とリリース判定

[固定配布物の指定](../../acceptance/v216-first-hop/artifact.json)が示す公開v2.1.6.0のZIPだけを使用します。取得元のHTTPS URL、メタデータ、サイズ、SHA-256はこの指定を正本とし、いずれかが一致しなければ失敗です。キャッシュがない場合だけ同じディレクトリの一時ファイルへ制限時間付きで取得し、検証後に原子的に公開します。既存の不正なキャッシュの自動修復、再取得による隠蔽、別版やソースからの代替ビルドはしません。

旧版からの適用は `ReleaseAcceptance` カテゴリのテスト（`[TestCategory("ReleaseAcceptance")]`）で、固定ZIP内の実際のprotocol-1更新プログラムを直接起動します。現行の実配布ZIPを入力とし、次を確認します。

- 制限時間内の正常終了と出力の回収。
- 全管理ファイルの相対位置と内容。新版から除かれた旧管理ファイルが正規の配置から除去されていること。
- 更新プログラムが再生成する管理一覧は、記載されたパスの集合を比較する。改行・列挙順のバイト一致は要求しない。
- `data/`・`config/` と利用者が追加したファイルは、更新プログラムの起動前に採取したパスの集合・バイト内容と比較する。退避・作業領域を含めた全ツリーの一致は要求しない。

旧更新プログラムは入力ZIPを消費するため、指定された候補を変更せず、同じ内容の検証用コピーを渡します。

旧アプリの画面起動、起動ログ待ち、更新通知や所有モーダルの有無、旧アプリの通常終了、旧版の終了待ちと管理ファイルのロック時の特性は、この受入から除きます。別枠の旧GUI受入も設けません。旧更新プログラムが子プロセスを作る場合は所有・回収しますが、画面内容を合格条件にはしません。現行の更新プログラムの失敗・復元・終了待ちの検査は維持し、現行配布物の起動とDB・設定の意味上の移行は、既存データ起動および現行更新の受入で検証します。

この旧版専用のケースは、.NET Framework 4.7.2から.NET 10への配布構成の移行を確認する一時的な互換性検査です。移行版の受入を終え、旧配布構成からの直接更新を必須の検査対象から外すと判断した時点で、ケース、固定旧ZIPの指定と専用のキャッシュ処理、専用の必須判定、関連資料をまとめて退役させます。旧版番号ごとの検査を恒久的に増やしません。

既存データ起動と更新の受入は、初期設定・ライブラリ構築済みの利用者を表す設定と既存DBを入力にします。設定の生成は共通処理を使い、`AssemblyVersion` を実際の保存形式の `SerializableVersion` XML、その他の単一値の設定を文字列として保存します。更新後の最初の起動は、初期設定からの新規利用ではなく、移行した設定とDBを読み取れるかの確認です。

既存データ起動では、`startup_ready_operable` と `startup_post_initialization_maintenance_complete` の両方を同じ制限時間内で待ってから終了します。必須のローカル処理と必要なLR2同期は画面が操作可能になる前に終端し、その後の任意の外部同期・保守も完了を確認します。終了後に既存の意味の保持と同期結果を検査し、処理が終わったことだけで同期成功とは扱いません。

現行配布物の画面起動の受入では、予期しない所有ダイアログが可視・有効なら失敗とし、自動で閉じて成功にしません。初回構築の通知も自動操作せず、利用済み入力の不備や起動の問題として扱います。初期設定自体の検証を更新の受入へ混ぜません。この判定を、画面を起動しない旧更新プログラムのファイル適用の検査には適用しません。

### 解析・大規模データ・外部エンコーダー

通常の解析確認は小さい合成譜面を使います。解析器・復号・譜面情報の保存形式を変える場合は、対象に合う追加検証を明示します。

#### 互換検査

固定入力と実ツールを使う検査は、Compatibility moduleの `Suite.*` 属性で選択します。suiteの明示選択が実行の条件であり、環境変数による事前の有効化は使いません。通常のCore・Windows検証へ固定入力の全件を混ぜません。

固定入力はリポジトリの `BeMusicSeeker.Tests/TestData` を読取り専用で参照し、ビルド出力へ複製しません。入力・参照DB・外部ツール・Java準備JSONの欠如や不正は失敗です。

正式入口は登録済みのsuiteから一つを選び、Release・1workerで実行します。suiteごとの制限時間は、起動・前提検査・本体・通常の回収・実際の終了で共有し、失敗時の回収は共通の10秒を一度だけ確定します。この制限時間は固定入力全体の完了時間の保証ではなく、内側の解析器・ツールの期限でも延長しません。直接moduleの成功を正式入口の成功へ読み替えません。suiteの一覧・入力・準備・制限時間・直接実行の方法は[互換検査の案内](../../../tests/BeMusicSeeker.Compatibility.Tests/README.md)を正本とします。

環境条件のsuite（DriveRoot、DirectorySymbolicLink、CrossVolume、Junction）も、実能力の不足をskipや代用の入力へ変えません。Compatibilityの全体は既存の `UiModuleLifetime` で利用者セッションの排他・専有profile・日本語辞書を準備し、実ホストは必要なケースで遅延生成します。

#### suiteの共有期限

正式runnerは、suiteの制限時間の始点と長さを `BMS_TEST_SUITE_DEADLINE` で子プロセスだけへ渡します。

- 子プロセス側の排他の待機・更新プログラム・probe・ジャンクション・外部ツールの局所的な上限は、この共有期限を延長しないよう、早い方に制限します。
- 未指定の直接MTP実行だけ、有限の局所的な既定値を使います。明示された値が空・不正・期限切れなら失敗です。
- Compatibility・Performance・Scenarios・Desktop以外のmoduleと準備用のプロセスには、この変数を明示的に除いて渡し、親プロセスの環境は変更しません。
- 親の失敗時の回収は、`min(suiteの期限 + 10秒, 失敗検出時刻 + 10秒)` を維持します。

期限の再読取り・不正値の拒否・実際の子プロセスへの引渡しとrunnerとの接続は、Core・Verificationの契約テストで分担します。

#### ACL・固定ネイティブ・外部音声

ACL、固定Everythingの実ネイティブ処理、BASSencの実WSH子プロセスの終了値、実外部エンコーダーは、それぞれ専用のsuiteで明示実行します。

- ACLの検査は、専有領域の実操作の終端後に両方のDACLを復旧してからworkspaceを回収し、外部のルートのACLは変更しません。
- 固定Everythingのネイティブ検査は、必須の `BMS_EVERYTHING_PATH_IDENTITY_FIXTURE` の固定SDK・fixtureを読み、可変のDLLコピーを `TestWorkspace` に置きます。準備の生成とsuiteの実行は別の制限時間です。
- 未指定・不足・能力の不成立をskip・成功にしません。
- 固定ネイティブの検査は実IPC・索引の `SC-07` の、WSH子プロセスの検査は実外部エンコーダーの代替ではありません。
- デコーダーの既存の待機は、親suiteの残り時間との早い方に制限します。ルート・両方のパイプ・プロセスの所有単位の終端を確認し、未回収の媒体と未解放のエンコーダー・セッションを保全して、主失敗と後片付けの失敗を残します。

入力環境は既存の子プロセス環境の継承を使い、親プロセスの環境を書き換えません。準備例と各suiteの入力は[互換検査の説明](../../../tests/BeMusicSeeker.Compatibility.Tests/README.md#acl固定native外部音声)にまとめます。

外部エンコーダーは、Compatibilityの `ExternalAudioEncoderSmokeTests` を正式の `compatibility --suite audio-encoders` で明示実行します。`EnvironmentIntegration` として専用環境で実行し、`BMS_TEST_AUDIO_ENCODERS=1` を必須とします。指定がなければ失敗です。

- 実行ファイルは `BMS_TEST_AUDIO_ENCODER_DIR`、アプリの基準位置、`libs\x64`、`x64` の順に検索します。
- `BMS_TEST_AUDIO_ENCODER_TYPES` は `MP3_LAME,AAC_NERO,OPUS,FLAC,OGG_VORBIS` の部分集合です。指定した部分集合に未知の名前・カンマ区切りの空要素・重複・実行ファイルの不足があれば失敗です。
- 種類を指定しない場合（未指定・空文字・空白のみ）は、見つかったものだけを実行します。一つも見つからなければ失敗です。

生成した短いステレオPCM・WAVを本番の `BassAudioWriter` とエンコード・停止・後片付けへ通し、ファイルの形式識別と採番を確認します。実行ファイル、ライセンス、生成音声をリポジトリの固定入力へ追加しません。

#### 性能検査

性能検査は `dotnet run --project tools/BeMusicSeeker.Verify -- performance --suite NAME` を使います。登録名・固定仕事量・監視上限は[正式入口](../../../tools/BeMusicSeeker.Verify/README.md#明示性能suite)に示します。Release・単一worker・利用者セッションの排他で実行し、全規模・全経路・全反復を固定します。正式入口のfilter、未登録・未指定のsuiteは準備前に拒否し、部分的な調査は直接MTP実行へ分担します。日常の診断出力の契約や小さな機能保証を、実負荷の成功の代用にはしません。

suiteの起動・前提・本体・通常の回収・実際の終了は一つの制限時間を共有し、親の失敗時の回収10秒も一回だけです。監視上限は実行を監視する運用値であり、速度目標ではありません。性能suiteは既存の保証を移したもので、新しい業務上の期待や仕事量を追加しません。スキャン・LR2同期・フォルダ変更・コピー・BMSONの検査は、準備・表明・回収と分けて対象操作を計時し、既存の時計を維持します。800万規模の逆引きや実DB・20 ZIP導入全体の代わりとは扱いません。条件、完了範囲、反復値、結果の同等性は[性能仕様](../core/performance-and-scale.md)に従います。

### 画面確認

利用者の明示依頼によりエージェントが実機で画面確認を行う場合は、[検証方針](#検証方針)に加えて、次の起動・操作・終了手順に従います。

実アプリを確認するときは、作成したリポジトリ内の `BeMusicSeeker.exe` の正確なパスを指定します。作業ディレクトリと利用データも確認し、インストール版を名前検索で起動しません。起動したPIDと生成時刻を控え、確認後は通常終了を要求して終了を待ち、操作セッションも終了します。無関係な同名プロセスを停止しません。

利用者の操作で画面操作が一時中断された場合は、現在の画面と対象プロセスを確認し、最後の安全な地点から操作を再取得して再開します。一度の中断だけで作業全体を終了しません。利用者が要件を変更した場合は新しい指示を優先します。中止指示や作業の異常終了で確認を終える場合は、一時的な操作権の喪失とは区別し、所有するプロセスと操作セッションを終了します。

画面の表示、入力、完了状態は区別して確認します。単にウィンドウが現れたことやログが静かになったことを、対象操作の成功条件にしません。

### 利用者に推奨する実機確認

入力・フォーカス経路、表示、機器対応、担当設定などを変更し、実環境との接続を確かめることが有用な場合に、次の観点から関係する確認を推奨します。必須工程やレビューの合格条件にはしません。通常の局所MTP実行・`verify`・`full` の成功だけで、この範囲を確認済みとはしません。専用CI、操作禁止のPC、入力遮断を通常テストの前提にせず、エージェントへの明示依頼がある場合の起動と後片付けは[画面確認](#画面確認)に従います。

具体的な操作と期待結果は変更対象の機能仕様から選び、条件・対象操作・観測結果を短く示します。次の表は確認観点であり、全項目を毎回実施する一覧ではありません。

| 確認観点 | 操作と観測 |
| --- | --- |
| OS入力・フォーカス・IME | 入力欄、候補、行内ボタン、表、メニュー等の変更した経路で、規定のキー・修飾キー・マウス操作と移動先を確認する。IME確定と機能の操作を混同せず、対象外の入力・保存状態を変えない。具体的な挙動は[検索支援](../ui/keyword-search.md)、[外観](../ui/appearance.md)、[一覧](../ui/table-view.md)等の対象仕様に従う。 |
| 表示・DPI・実モニター | 変更した画面を対象に、仕様の範囲でDPI・モニター移動による描画・配置・入力位置の対応と操作継続を確認する。 |
| 音声機器 | 利用可能な機器・出力方式で、変更に関係する再生・音量・終了・切断・再接続を確認する。条件と期待結果は[音声仕様](../runtime/audio.md#診断と実機確認)に従う。 |
| 担当の起動・設定適用・入力継承 | 変更した担当を起動し、指定の役割・モデル・権限と、引継ぎ・履歴の受渡しを確認する。設定と引継ぎの静的な整合確認とは区別する。 |

確認時の外部操作による中断は製品不具合と区別します。未確認は未確認として報告し、通常テストのスキップや成功扱いに置き換えません。未実施の扱いは[検証方針](#検証方針)に従います。対象機能の廃止、または同じ接続を外部入力から独立して検証できるようになった場合は該当手順を退役します。
