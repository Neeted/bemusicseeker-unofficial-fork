# BMS/BMSON File Read Benchmark

## 概要

このスクリプトは、BMS / BMSON 譜面ファイル群を解析する前段階として、ファイルをメモリへ読み込むだけの速度を測定するための簡易ベンチマークです。

`file_list.txt` に記載された譜面ファイルのフルパスを1行ずつ読み取り、各ファイルをバイナリモードで先頭から末尾まで読み込みます。読み込んだ内容は保持せず、そのまま破棄します。

これにより、解析処理・パース処理・DB登録処理などを除いた、純粋なファイル読み取り処理に近い時間を測定できます。

---

## 背景

BMS / BMSON 譜面ファイルを大量に解析するプログラムでは、処理時間の内訳として以下のような要素が考えられます。

- ファイルリストの読み込み
- 各譜面ファイルの open / close
- ファイル内容の読み取り
- 文字コード判定
- BMS / BMSON のパース
- ハッシュ計算
- メタデータ抽出
- DB への登録・更新

このうち、ファイル内容を読み取る速度にはストレージ I/O の上限があります。

そのため、解析プログラムの高速化を考える際には、まず

> 解析処理を一切行わず、全ファイルをメモリに読むだけなら何秒かかるのか

を測定しておくと、プログラム側の高速化余地を判断しやすくなります。

例えば、全体で 13GB / 21万ファイル程度ある場合、単純な容量だけでなく、ファイル数の多さによる open / close やファイルシステムアクセスのオーバーヘッドも無視できません。

このスクリプトは、そのような大量の小〜中サイズファイル群に対して、読み取り処理だけの実測値を得ることを目的としています。

---

## 測定対象

`file_list.txt` には、読み取り対象となる BMS / BMSON ファイルのフルパスを1行ずつ記載します。

例:

```text
C:\BMS\package1\song1\chart1.bms
C:\BMS\package1\song1\chart2.bms
C:\BMS\package2\song2\chart1.bmson
```

---

## 実行方法

PowerShell またはコマンドプロンプトで実行します。

```powershell
python read_benchmark.py
```

---

## 設定項目

### `LIST_PATH`

読み取り対象ファイルの一覧が書かれたテキストファイルです。

```python
LIST_PATH = r"C:\file_list.txt"
```

---

### `BUFFER_SIZE`

各ファイルを読み込む際のバッファサイズです。

```python
BUFFER_SIZE = 4 * 1024 * 1024
```

初期値は `4MiB` です。

比較する場合は、以下のように変更して複数回測定します。

```python
BUFFER_SIZE = 256 * 1024
BUFFER_SIZE = 1 * 1024 * 1024
BUFFER_SIZE = 4 * 1024 * 1024
BUFFER_SIZE = 16 * 1024 * 1024
```

大量の小〜中サイズファイルを読む場合、バッファサイズを大きくしても必ずしも高速化するとは限りません。

まずは `1MiB` または `4MiB` 程度で十分です。

---

### `LIST_ENCODING`

`file_list.txt` の文字コードです。

UTF-8 の場合:

```python
LIST_ENCODING = "utf-8-sig"
```

Windows の `cmd.exe` で以下のように作成したリストの場合:

```cmd
dir /s /b *.bms > file_list.txt
```

環境によっては CP932 系になるため、次の設定に変更します。

```python
LIST_ENCODING = "mbcs"
```

## 結果の見方

### `files`

正常に読み取り完了したファイル数です。

### `errors`

読み取りに失敗したファイル数です。

ファイルが存在しない、アクセス権がない、パスの文字コードが合っていない、別プロセスによりアクセス制限されている、などの場合に増えます。

### `bytes`

実際に読み込んだ合計バイト数です。

### `elapsed`

全ファイルを読み終えるまでの経過秒数です。

### `throughput`

読み取りスループットです。

```text
MiB/s
GiB/s
```

の2種類で表示します。

---

## 注意点

### 1回目と2回目で結果が変わる

Windows では、一度読んだファイルが OS のファイルキャッシュに載ることがあります。

そのため、同じスクリプトを連続実行すると、2回目以降の方が大幅に速くなることがあります。

```text
1回目: ストレージから読む速度に近い
2回目: OSキャッシュから読む速度に近い
```

どちらも意味があります。

---

## cold read と warm read

### cold read

OS キャッシュにあまり載っていない状態での読み取りです。

実運用で初回スキャンする場合の性能に近くなります。

### warm read

一度読み込んだ後、OS キャッシュが効いている状態での読み取りです。

解析処理そのものがどれだけ重いかを比較する際の参考になります。

例えば、読み取りだけで 10 秒、実際の解析が 60 秒かかるなら、解析・パース・DB 処理側にかなり高速化余地があると考えられます。

逆に、読み取りだけで 50 秒、解析込みで 60 秒なら、すでに I/O にかなり近いところまで来ている可能性があります。

---

## このベンチマークで測っているもの

このスクリプトは、単に

```text
13GBの巨大な1ファイルを読む速度
```

を測っているわけではありません。

実際には、

```text
21万個のファイルを順番に開く
各ファイルを全読みする
各ファイルを閉じる
```

という処理を測っています。

そのため、測定結果には以下のコストも含まれます。

- ファイルを開くコスト
- ファイルを閉じるコスト
- ファイルシステム上でパスを解決するコスト
- 大量の小さいファイルを扱うオーバーヘッド
- セキュリティソフトや Windows Defender による影響
- HDD / SSD / NVMe などストレージ種別の影響
- OS ファイルキャッシュの影響

BMS / BMSON のように多数の譜面ファイルを扱う用途では、巨大な1ファイルの読み取り速度よりも、この測定の方が実際の下限に近いです。

---

## 解析プログラムとの比較方法

このスクリプトの結果を、実際の解析プログラムの処理時間と比較します。

例:

```text
読み取りだけ: 20秒
解析込み    : 120秒
```

この場合、I/O 以外に 100秒程度かかっているため、以下の処理に高速化余地がある可能性があります。

- BMS / BMSON パース
- 文字コード判定
- ハッシュ計算
- 正規表現処理
- オブジェクト生成
- DB 書き込み
- 重複判定
- ログ出力

一方で、

```text
読み取りだけ: 55秒
解析込み    : 65秒
```

のような場合は、すでに I/O に近い速度で動作している可能性があります。

その場合、解析ロジックを多少最適化しても、全体の短縮幅は限定的です。

---

## 測定時のおすすめ手順

1. `BUFFER_SIZE = 1MiB` で実行
2. 同じ条件でもう一度実行
3. `BUFFER_SIZE = 4MiB` に変更して実行
4. 同じ条件でもう一度実行
5. 実際の解析プログラムの処理時間と比較する

例:

```text
1MiB  1回目
1MiB  2回目
4MiB  1回目
4MiB  2回目
```

1回目と2回目の差が大きい場合は、OS キャッシュの影響が大きいと考えられます。

---

## 制限事項

このスクリプトは、あくまでファイル読み取り速度の目安を測るためのものです。

以下の処理は行いません。

- BMS / BMSON のパース
- 文字コード判定
- SHA-256 / MD5 などのハッシュ計算
- メタデータ抽出
- DB 登録
- 並列読み込み
- ファイルサイズ別の統計
- 拡張子別の集計

必要であれば、別途これらの処理を追加して、どの段階で時間が増えるかを段階的に測定するとよいです。

---

## まとめ

このスクリプトは、大量の BMS / BMSON 譜面ファイルを処理するプログラムにおいて、読み取り I/O の下限時間を確認するためのベンチマークです。

解析処理を最適化する前に、まず読み取りだけの速度を測定しておくことで、

```text
I/O が支配的なのか
解析処理が支配的なのか
DB 処理が支配的なのか
```

を判断しやすくなります。
