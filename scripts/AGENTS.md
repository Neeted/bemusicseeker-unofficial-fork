# スクリプト作業の指針

[ルートの指針](../AGENTS.md)と[検証仕様](../devdocs/spec/development/testing.md)に従います。テストを変更する場合は[テスト作成](../devdocs/spec/development/test-authoring.md)、配布を変える場合は[更新仕様](../devdocs/spec/integration/portable-update.md)も確認します。

## 実行経路と判定

実行順・対象・期限・生成物・失敗判定の要件を確認し、実際の実行側が使う計画・補助処理・マニフェストと観測結果を照合します。現行実装だけを正解の根拠にせず、自己申告のメタデータと、それだけを読むテストを同時に変えて成功できる構造にはしません。

条件の組合せは対応する判断の境界で、起動・受渡し・失敗回収は必要な実行経路で検証します。代表的なプロセス統合・配布受入を、局所テストがあることだけを理由に削除しません。実行条件を変える場合は、観測できる挙動の差と、維持する保証を示します。

## プロセス・期限・失敗

プロセスの開始から待機・出力読取り・停止・診断・残留確認までの所有と、失敗の優先順位は[プロセスの待機と失敗](../devdocs/spec/development/testing.md#プロセスの待機と失敗)に従います。未完了の読取りTaskを `.Result` などで無期限に待たず、名前だけで無関係なプロセスを停止しません。

通常検証は[実行期限と失敗分類](../devdocs/spec/development/testing.md#実行期限と失敗分類)、配布受入は[Fullの処理順と期限](../devdocs/spec/development/testing.md#fullの処理順と期限)に従います。区間ごとの期限更新や、後片付け時間内の終了による成功への変更は行いません。

ホスト構成・並列度・文字コード・予算・診断先・再試行条件を、症状の回避だけを目的に変更しません。変更した実行経路で時間・診断・所有プロセスの回収を確認し、局所確認と全体検証の結果を分けて統合担当へ引き継ぎます。
